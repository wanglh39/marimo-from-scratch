# .py 即 notebook：格式设计哲学

传统 notebook 把文档存成 `.ipynb`——一个巨大的 JSON 文件，里面塞满了 `source`、`outputs`、`execution_count` 等字段。marimo 反其道而行：**notebook 就是一个普通的 `.py` 文件**。你用 `python notebook.py` 就能直接运行它，用任何编辑器都能打开它，用 `git diff` 就能看清改了什么。

这个决定不是审美偏好，而是对 notebook 本质的重新思考。notebook 的核心是"一组带依赖关系的代码"，而 Python 语言本身就有表达"依赖关系"的原生机制——函数的参数与返回值。既然如此，何不直接用 Python 文件来存 notebook，让文件格式与语言语义对齐？这一章我们拆解这个设计哲学。

## 核心思想：合法 Python 优先

marimo 文件的第一原则是：**它必须是合法的 Python 代码**。不是"看起来像 Python 的文本"，而是能被 `python` 解释器直接执行的真代码。这意味着：

- 不需要专门的运行器，`python notebook.py` 即可执行整个 notebook；
- 任何 IDE、linter、formatter 都能直接处理它；
- 可以被其他 Python 模块 `import`，cell 里定义的函数、类都能复用；
- 不存在"JSON 里的代码字符串"这种二度编码问题。

"合法 Python 优先"是一条强约束，它逼着格式设计往特定方向走。比如想存 cell 之间的依赖关系，不能随便发明一个 `# depends_on: cell_3` 注释语法——因为那只是注释，Python 解释器看不见，linter 也无法校验。必须用 Python 能理解的语法：函数参数。于是"依赖即参数"的设计几乎是被迫推出的。

再看"二度编码"问题。`.ipynb` 把代码塞进 JSON 的 `"source"` 字段，代码变成了字符串。于是你面对两层编码：外层 JSON，内层 Python。任何工具想分析代码，都得先剥掉 JSON 外壳，再解析 Python 字符串。linter 报错时给的是字符串里的行号，对应不到 JSON 行号；formatter 改了字符串，JSON 又得重新序列化。而 `.py` 文件只有一层编码，工具链直接对接。

## 一个 cell 就是一个函数

文件里每个 cell 被表示为一个被 `@app.cell` 装饰的函数。下面是一个完整的 marimo notebook 文件，三个 cell 串成一条计算链：

```python
from backend.app import App

app = App()


@app.cell
def _(mo):
    x = 5
    return (x,)


@app.cell
def _(x, mo):
    y = x + 1
    return (y,)


@app.cell
def _(y,):
    print(y)
    return


if __name__ == "__main__":
    app.run()
```

函数名 `_` 是占位符（教学版用单下划线，生产版 marimo 用双下划线 `__` 表示"不关心名字"），参数列表编码这个 cell 依赖的上游变量（refs），`return` 元组编码它产出的变量（defs），函数体就是 cell 的代码。这套编码天然表达了依赖关系，无需任何额外元数据。

`@app.cell` 装饰器的实现极其轻量，它只做一件事——把函数收集起来：

```python
class App:
    def __init__(self) -> None:
        self._funcs: list = []

    def cell(self, func):
        self._funcs.append(func)
        return func
```

装饰器不解析、不执行，只是把函数对象塞进列表。真正的解析发生在 `app.run()` 被调用时：`run` 用 `inspect.getsource` 取回每个函数的源码，再用 `ast.parse` 提取 refs/defs/code，构建依赖图并执行。这种"收集时惰性、运行时解析"的设计，让文件在被 `import` 时不会产生副作用，只有显式 `app.run()` 才真正执行。

## 直接运行：python notebook.py

文件末尾的 `if __name__ == "__main__": app.run()` 是可执行性的关键。在命令行里：

```bash
$ python notebook.py
============================================================

[✓] cell cell_0
    code: 'x = 5'

[✓] cell cell_1
    code: 'y = x + 1'

[✓] cell cell_2
    code: 'print(y)'
    stdout: 6
============================================================
```

`app.run()` 内部按拓扑顺序执行所有 cell，并打印每个 cell 的状态、代码、stdout 和输出。`✓` 表示成功，`✗` 表示出错，`○` 表示因上游失败而被标记为 stale。这段输出逻辑来自 `App._print_results`，它读 `Cell.status` 字段决定图标，让命令行运行也能看到 notebook 的执行全貌。

可执行性带来的好处是实实在在的：notebook 可以塞进 CI 跑测试（`python notebook.py && echo pass`），可以被 cron 定时执行，可以被其他脚本 `import` 后调用 `app.run()`。而 `.ipynb` 做这些都需要 `jupyter nbconvert --to script` 或 `jupyter execute`，多一层工具依赖。

## 对比 .ipynb 的 JSON

一个最简单的 `.ipynb` 文件长这样：

```json
{
  "cells": [
    {
      "cell_type": "code",
      "source": ["x = 5\n"],
      "outputs": [],
      "execution_count": 1,
      "metadata": {}
    }
  ],
  "metadata": {},
  "nbformat": 4,
  "nbformat_minor": 5
}
```

逐字段看：`cell_type` 区分 code/markdown/raw；`source` 是字符串列表，每行一个元素（也允许单个字符串，这是规范歧义之一）；`outputs` 是输出对象数组，每个输出又有 `output_type`（stream/execute_result/display_data）、`text`/`data`、`execution_count` 等子字段；`metadata` 可以塞任意东西，cell 级和文档级各一份；`nbformat`/`nbformat_minor` 是版本号。一个 10 行代码的 cell，JSON 可能占 30 行。

代码被拆成字符串列表，嵌套在多层 JSON 对象里。改一行代码，diff 里看到的是 JSON 行号变动；挪一个 cell，可能引发几十行 JSON 重排。而 marimo 的 `.py` 文件 diff 就是普通 Python 代码 diff——改哪行、加哪个函数，一目了然。

更微妙的是 `source` 字段的歧义：它既可以是 `["x = 5\n"]`（列表），也可以是 `"x = 5\n"`（字符串），不同工具生成的格式不同。解析器得两种都处理，往返测试时容易丢信息。`.py` 文件没有这种歧义——Python 语法由语言规范确定，`ast.parse` 是确定性的。

## 可执行性的代价与收益

把 outputs 排除在文件之外（marimo 默认不存输出），换来的是纯代码文件。代价是重新打开 notebook 需要重算；收益是文件永远干净、可复现、可版本控制。这正契合 reactive notebook 的理念：**输出是代码的函数，存函数就够了，不必存函数值**。

考虑这个场景：你有一个画图的 cell，依赖某个数据加载 cell。在 Jupyter 里，改了数据加载后，画图 cell 不会自动重算，你得手动重跑——容易忘，忘了就看到过期图。而 marimo 是 reactive 的：改数据 cell，框架自动算出画图 cell 是其后代，自动重算画图。既然重算是自动的，存输出就纯属冗余——它随时可以被重新生成。

代价确实存在：重开一个有大量计算的 notebook，要等重算。但 reactive notebook 本来就会按需重算（只重算受影响的 cell，不是全量），且可以缓存中间结果。相比之下，Jupyter 的"存了输出但代码可能已过期"问题更隐蔽——你看着图，却不知道它对应的是哪版代码。marimo 用"重算"换"一致性"，这笔交易划算。

## 可读性与可维护性

`.py` 文件的可读性来自它的平面结构。打开文件，从上到下就是 Python 代码，没有 JSON 的花括号和字段名干扰。每个 cell 是一个函数，函数体就是代码，读 notebook 和读普通 Python 模块没有认知切换。

可维护性则来自工具链的复用。想加类型检查？`mypy notebook.py` 直接跑。想格式化？`black notebook.py`。想找定义？任何 IDE 的"Go to Definition"都能用。想重构重命名？IDE 的 rename 功能直接改。这些在 `.ipynb` 上要么不支持，要么需要专门的 notebook 插件，且经常出 bug——因为工具得先理解 JSON 结构，再理解里面的 Python 字符串，两层映射容易错。

这种"代码即文档"的哲学，让 marimo 的文件格式天然具备可读性、可执行性和可 diff 性三重优势，而实现这一切只需要一个约定：cell 是函数，依赖是参数，产出是返回值。没有新语法、没有新工具、没有新心智模型——只是把 Python 已有的语义用到极致。
