# .py 即 notebook：格式设计哲学

传统 notebook 把文档存成 `.ipynb`——一个巨大的 JSON 文件，里面塞满了 `source`、`outputs`、`execution_count` 等字段。marimo 反其道而行：**notebook 就是一个普通的 `.py` 文件**。你用 `python notebook.py` 就能直接运行它，用任何编辑器都能打开它，用 `git diff` 就能看清改了什么。

## 核心思想：合法 Python 优先

marimo 文件的第一原则是：**它必须是合法的 Python 代码**。不是"看起来像 Python 的文本"，而是能被 `python` 解释器直接执行的真代码。这意味着：

- 不需要专门的运行器，`python notebook.py` 即可执行整个 notebook；
- 任何 IDE、linter、formatter 都能直接处理它；
- 可以被其他 Python 模块 `import`，cell 里定义的函数、类都能复用；
- 不存在"JSON 里的代码字符串"这种二度编码问题。

## 一个 cell 就是一个函数

文件里每个 cell 被表示为一个被 `@app.cell` 装饰的函数：

```python
import marimo

__generated_with = "0.1.0"
app = marimo.App()

@app.cell
def __(mo):
    x = 5
    return (x,)

@app.cell
def __(x, mo):
    y = x + 1
    return (y,)

if __name__ == "__main__":
    app.run()
```

函数名 `__` 是占位符（双下划线表示"不关心名字"），参数列表编码这个 cell 依赖的上游变量（refs），`return` 元组编码它产出的变量（defs），函数体就是 cell 的代码。这套编码天然表达了依赖关系，无需任何额外元数据。

## 对比 .ipynb 的 JSON

一个最简单的 `.ipynb` 文件长这样：

```json
{
  "cells": [
    {
      "cell_type": "code",
      "source": ["x = 5\n"],
      "outputs": [],
      "execution_count": 1,
      "metadata": {}
    }
  ],
  "metadata": {},
  "nbformat": 4,
  "nbformat_minor": 5
}
```

代码被拆成字符串列表，嵌套在多层 JSON 对象里。改一行代码，diff 里看到的是 JSON 行号变动；挪一个 cell，可能引发几十行 JSON 重排。而 marimo 的 `.py` 文件 diff 就是普通 Python 代码 diff——改哪行、加哪个函数，一目了然。

## 可执行性的代价与收益

把 outputs 排除在文件之外（marimo 默认不存输出），换来的是纯代码文件。代价是重新打开 notebook 需要重算；收益是文件永远干净、可复现、可版本控制。这正契合 reactive notebook 的理念：**输出是代码的函数，存函数就够了，不必存函数值**。

这种"代码即文档"的哲学，让 marimo 的文件格式天然具备可读性、可执行性和可 diff 性三重优势，而实现这一切只需要一个约定：cell 是函数，依赖是参数，产出是返回值。
