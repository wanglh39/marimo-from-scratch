# parser 实现：从 .py 到依赖图

`backend/storage/parser.py` 里的 `py_to_graph` 负责把一个 `.py` 文件解析回 CellGraph。它纯粹用 Python 标准库的 `ast` 模块，不依赖任何第三方解析器。这一章逐步拆解它的五个步骤，并用一个完整文件演示解析全过程。

## 第一步：ast.parse 找装饰函数

```python
def py_to_graph(source: str) -> CellGraph:
    try:
        tree = ast.parse(source)
    except SyntaxError as e:
        raise ParseError(f"语法错误: {e.msg} (行 {e.lineno})") from e

    graph = CellGraph()
    cell_index = 0

    for stmt in tree.body:
        if not isinstance(stmt, ast.FunctionDef):
            continue
        if not _has_cell_decorator(stmt):
            continue

        refs = {arg.arg for arg in stmt.args.args}
        defs = _extract_return_defs(stmt)
        code = _extract_body_code(stmt)

        cell_id = f"cell_{cell_index}"
        cell = Cell(cell_id=cell_id, code=code, defs=defs, refs=refs)
        graph.add_cell(cell)
        cell_index += 1

    return graph
```

`ast.parse` 把源代码解析成 AST，若源码有语法错误就抛 `SyntaxError`，被捕获后包装成 `ParseError`（附带错误信息和行号）向上抛——调用方拿到的是"文件解析失败"而非"Python 语法错误"，语义更清晰。

遍历用 `tree.body` 而不是 `ast.walk(tree)`。区别在于：`tree.body` 只看顶层语句，`ast.walk` 递归遍历所有节点。cell 函数一定在文件顶层（不会被嵌套定义），用 `tree.body` 既正确又高效，还避免误把嵌套函数当 cell。判断是不是 cell 函数，看装饰器列表里有没有 `ast.Attribute` 且属性名是 `"cell"`——这匹配 `@app.cell` 这种形式。教学版不要求 `value` 是 `app`，所以 `@anything.cell` 都会匹配；生产版会更严格。

## 第二步：从参数提取 refs

```python
refs = {arg.arg for arg in stmt.args.args}
```

`stmt.args.args` 是位置参数列表，每个 `arg` 的 `.arg` 属性是参数名。装进 set 就得到 refs。我们只取位置参数，不处理 `*args`、`**kwargs`、默认值——cell 不该有这些复杂签名。参数名就是上游变量名，直接进 refs。

用 set 而非 list，因为 refs 是集合语义（一个变量依赖一次和依赖十次没区别），且后续图构建用 set 做成员查找更快。代价是丢了参数顺序——但依赖图不关心顺序，只关心"谁依赖谁"，所以无妨。

## 第三步：从 return 提取 defs

```python
def _extract_return_defs(func: ast.FunctionDef) -> set[str]:
    for stmt in reversed(func.body):
        if isinstance(stmt, ast.Return):
            if stmt.value is None:
                return set()
            return _names_from_return_value(stmt.value)
    return set()
```

注意这里读的是 `func.body` 里的 Return 语句，不是 `func.returns`。`func.returns` 是函数签名里的返回类型注解（`def f() -> int` 的 `int`），跟 return 语句无关——这是个容易混淆的 AST 字段。

`reversed(func.body)` 从后往前找第一个 Return。cell 的 return 应在函数体末尾，从后找更快。`stmt.value is None` 对应裸 `return`，返回空集。值是 `ast.Name`（`return y`）取 `.id`；是 `ast.Tuple`（`return (y, z)`）遍历元素取名字。非 Name 元素（如 `return (f(),)`）被忽略——只认变量名，不认表达式，因为只有变量名能作为依赖图的节点。

## 第四步：提取函数体

cell 的代码是函数体去掉 return 语句后的部分：

```python
def _extract_body_code(func: ast.FunctionDef) -> str:
    code_stmts = [s for s in func.body if not isinstance(s, ast.Return)]
    if not code_stmts:
        return ""
    return "\n".join(ast.unparse(stmt) for stmt in code_stmts)
```

过滤掉 Return 语句，剩下的逐个用 `ast.unparse` 转回代码字符串，用换行符拼接。`ast.unparse` 是 Python 3.9+ 的功能，能把 AST 反向生成代码字符串。代价是它会丢失原始格式（空行、注释、特定缩进风格）——`ast.unparse` 总是用 4 空格缩进、不保留空行、不保留注释。所以生产版 marimo 会保留原始源码片段而非 reparse 后的版本，但教学版用 unparse 跳过这个优化。

注意是逐语句 unparse 再 join，而不是把整个 body 包成 Module 一次性 unparse。逐语句输出更扁平，便于在序列化时重新缩进。

## 第五步：构建图

每个 cell 分配一个 ID（用位置序号 `cell_{index}`），连同 refs、defs、code 一起塞进 CellGraph。graph 内部的 `add_cell` 会触发 `_rebuild`，根据 refs/defs 自动连边。`_rebuild` 做两件事：建"变量 → 定义 cell"映射（检测重复定义），再扫 refs 连边。如果文件里两个 cell 都 return 同一变量，`_rebuild` 抛 `DuplicateDefinitionError`；如果有循环依赖，要等到 `topological_order` 被调用时才检测出来——parser 阶段只建图，不排序，所以循环依赖在 parser 里不会报错，在执行或序列化时才暴露。

## 逐步解析演示

拿这个文件逐步走一遍：

```python
from backend.app import App

app = App()


@app.cell
def _(mo):
    x = 5
    return (x,)


@app.cell
def _(x, mo):
    y = x + 1
    return (y,)
```

**第一步**：`ast.parse` 得到 AST，`tree.body` 有 4 个顶层语句——`ImportFrom`、`Assign`（app = App()）、两个 `FunctionDef`。前两个不是 FunctionDef 跳过，后两个有 `@app.cell` 装饰器，收集。

**第二步**：第一个函数参数是 `mo`，refs = {"mo"}；第二个函数参数是 `x, mo`，refs = {"x", "mo"}。

**第三步**：第一个函数 return `(x,)`，是 Tuple，元素 `x` 是 Name，defs = {"x"}；第二个同理 defs = {"y"}。

**第四步**：第一个函数体过滤掉 Return，剩 `x = 5`，code = "x = 5"；第二个 code = "y = x + 1"。

**第五步**：建两个 Cell，ID 分别是 "cell_0"、"cell_1"，塞进 graph。`_rebuild` 建 `var_to_cell = {"x": "cell_0", "y": "cell_1"}`，扫 refs：cell_1 的 ref "x" 找到定义者 cell_0，连边 cell_0 → cell_1；ref "mo" 找不到定义者，跳过。

最终 graph 有两个 cell，一条边 cell_0 → cell_1，拓扑序 [cell_0, cell_1]。

## 与 App._build_graph 的对比

`App` 类在运行时也建图，但走的是另一条路——用 `inspect.getsource` 取回函数源码再 parse，而非从文件读。`inspect.getsource` 从内存里的函数对象取回源码（依赖源文件存在），`textwrap.dedent` 去掉缩进，`ast.parse` 解析。提取 refs/defs/code 的逻辑与 `py_to_graph` 完全相同——两套入口共享同一套提取规则，只是源码来源不同：parser 从文件文本读，App 从内存函数取。这保证了"文件解析"和"直接运行"看到的依赖图一致。

整个 parser 不执行任何用户代码，纯静态分析——这是 marimo 能在不运行 notebook 的情况下构建依赖图、检测循环、做拓扑排序的根本原因。静态分析意味着安全（恶意 notebook 不会被执行）、快速（不用启动执行环境）、可离线（不依赖任何运行时依赖）。
