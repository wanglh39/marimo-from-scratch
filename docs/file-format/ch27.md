# 与 .ipynb 对比：JSON vs Python

`.ipynb` 是 Jupyter 的事实标准，本质是一个 JSON 文档。marimo 的 `.py` 格式是对它的反思。这一章把两者放在一张桌上对比，看清各自取舍。

## 结构对比

**.ipynb** 是嵌套 JSON：

```json
{
  "cells": [
    {"cell_type": "code", "source": ["x = 5\n"], "outputs": [...], "execution_count": 1, "metadata": {}},
    {"cell_type": "markdown", "source": ["# Title\n"], "metadata": {}}
  ],
  "metadata": {"kernelspec": {"name": "python3", "display_name": "Python 3"}},
  "nbformat": 4, "nbformat_minor": 5
}
```

逐层看：顶层有 `cells`（数组）、`metadata`（文档级元数据，含内核信息）、`nbformat`/`nbformat_minor`（版本号）。每个 cell 有 `cell_type`（code/markdown/raw）、`source`（字符串列表或单个字符串）、`metadata`。code cell 额外有 `outputs`（输出对象数组）、`execution_count`。每个 output 又有 `output_type`（stream/execute_result/display_data/error），各自带不同子字段。代码是 `source` 字段里的**字符串列表**（每行一个元素），一个 10 行代码的 cell，JSON 可能占 30 行。

**.py** 是平面 Python：

```python
@app.cell
def _(mo):
    x = 5
    return (x,)
```

代码就是代码，没有字符串编码层。4 行就是 4 行。没有 `cell_type`（全是 code cell）、没有 `execution_count`（不存输出）、没有 `outputs`、没有 `metadata`（依赖关系在签名里）。整个文件的"额外开销"只有装饰器、函数签名、return 语句——而这些恰恰是表达依赖所必需的，不是冗余。

## diff 友好性

这是 marimo 格式最大的卖点。改一行代码：

**.ipynb** 改动 `"source": ["x = 5\n"]` 为 `"source": ["x = 6\n"]`，diff 显示这行 JSON 变了。但若改动导致 JSON 重新格式化（很多工具会重新序列化），diff 可能爆炸成几十行——所有键的顺序变了、缩进变了、字符串列表和单字符串切换了，明明只改了一行代码，diff 却像重写了整个文件。

**.py** 改动 `x = 5` 为 `x = 6`，diff 就一行：
```diff
-    x = 5
+    x = 6
```
干净、可读、可 review。

挪 cell 顺序：`.ipynb` 里 JSON 数组重排，diff 显示一大片删除 + 一大片新增，reviewer 得仔细对比才知道是挪动而非重写。`.py` 里函数顺序变了，但每个 cell 是独立函数，`@app.cell` + `def _(x):` 明确标记 cell 开头，reviewer 一眼看出是挪动了一个完整函数。

## 可执行性

- **.ipynb**：不能直接 `python notebook.ipynb`，必须 `jupyter nbconvert --to script` 或 `jupyter execute`。要装 Jupyter（jupyter、nbclient、nbformat 等一串依赖）。
- **.py**：`python notebook.py` 直接跑。任何有 Python 的机器都行，零额外依赖。

这让 marimo notebook 能直接当脚本用、当模块 import、塞进 CI 跑测试：

```yaml
# CI 配置片段
- name: Run notebook
  run: python notebooks/analysis.py
```

当模块 import 也很直接：用 `importlib` 加载文件，拿到 `app` 对象后调用 `app.run()`，cell 里定义的函数、类都能复用。这让 notebook 既能作为交互式探索工具，又能作为可复用的计算模块，甚至可以被其他 Python 服务在运行时动态加载执行，实现"探索即开发"的无缝工作流——这是 JSON 格式永远无法做到的事情。

而 `.ipynb` 做这些都需要额外工具链：CI 里得装 jupyter，import 得用 nbformat 解析再执行，测试得用 nbmake 或 pytest-ipynb。每个环节都是额外的依赖和故障点。

## 输出存储

- **.ipynb**：输出（stdout、图表 base64、HTML）全存进文件，导致文件巨大且频繁变动——重跑一次所有输出都变，git 里全是噪声。一张 matplotlib 图存成 base64 可能占几 KB，一个 notebook 几十张图就是几百 KB 的二进制噪声塞在 JSON 里。
- **.py**：默认不存输出，文件只含代码。输出是运行时产物，不进版本控制。

考虑这个场景：你画了一张图，调了调颜色，重跑 cell。`.ipynb` 里，图的 base64 数据变了，git diff 显示几百行 base64 字符变更——完全不可读，且让 commit 历史充满噪声。`.py` 里，只有 `color='red'` 变 `color='blue'` 一行 diff，清晰明了。

代价是重开 notebook 要重算；但 reactive notebook 本来就会按需重算（只重算受影响的 cell，不是全量），且可以缓存中间结果。相比之下，Jupyter 的"存了输出但代码可能已过期"问题更隐蔽——你看着图，却不知道它对应的是哪版代码。marimo 用"重算"换"一致性"，这笔交易划算。

## 往返测试

marimo 的往返测试验证 `py_to_graph(graph_to_py(g)) == g`：序列化成文件、读回、解析、比较图。`.ipynb` 的往返则复杂得多：JSON 解析回来要处理 `source` 是字符串还是列表（规范允许两种）、`outputs` 的各种 mime 类型、`execution_count` 是否保留、`metadata` 里内核信息是否一致……格式规范本身就有歧义，不同工具生成的 `.ipynb` 互不兼容是常态。

而 `.py` 的往返只依赖 Python 语法——语法无歧义，`ast.parse` 是确定性的。同一个 `.py` 文件，无论用谁的解析器，得到的 AST 都一样。这种"靠语言规范而非文档规范来保证一致性"的思路，让往返测试变得几乎平凡。

## 协作场景

两人同时改一个 notebook，合并时：`.ipynb` 两人都改了 JSON，git merge 大概率冲突。冲突标记夹在 JSON 对象中间，手动解决冲突得同时理解 JSON 结构和 Python 代码，极易出错。很多团队干脆禁止直接合并 `.ipynb`，改用 nbdime 等专门工具。`.py` 两人都改了 Python 文件，git merge 按普通代码合并，冲突发生在代码行级别，开发者用熟悉的合并工具就能解决，无需专门工具。

## 总结

| 维度 | .ipynb | .py |
|------|--------|-----|
| 格式 | JSON | Python |
| 代码存储 | 字符串列表 | 原生代码 |
| 可执行 | 需 jupyter 工具链 | 直接 `python` |
| 改一行 diff | 1 行 JSON（可能爆炸） | 1 行代码 |
| 挪 cell diff | 大片删除+新增 | 函数移动 |
| 输出 | 内嵌（含 base64 图） | 不存 |
| git 噪声 | 高 | 低 |
| 往返 | 复杂（规范歧义） | 简单（语法确定） |
| 合并冲突 | 难（JSON 结构） | 易（代码级） |
| 依赖表达 | 隐式（执行顺序） | 显式（函数签名） |

marimo 选 `.py` 不是为了标新立异，而是因为 notebook 的本质是"带依赖关系的代码集合"，而 Python 函数 + 装饰器天然能表达这个结构，何必再套一层 JSON。`.ipynb` 的 JSON 设计源于"notebook 是富文档"的定位（要存 markdown、输出、富媒体），而 marimo 的定位是"notebook 是可执行的可复现计算"——定位不同，格式自然不同。对于重视版本控制、可复现性、工具链复用的场景，`.py` 是更合适的选择。
