# serializer 实现：从依赖图到 .py

`backend/storage/serializer.py` 里的 `graph_to_py` 是 parser 的逆运算：把 CellGraph 序列化成一个可执行的 `.py` 文件。关键在于**按拓扑序输出** cell，保证每个 cell 的 refs 在上游 cell 的 defs 里都已定义。这一章拆解序列化的每个环节，并演示完整过程。

## 拓扑排序

```python
def graph_to_py(graph: CellGraph) -> str:
    lines: list[str] = [_HEADER]

    for cell_id in graph.topological_order():
        cell = graph.get_cell(cell_id)
        refs_str = ", ".join(sorted(cell.refs))
        defs_list = sorted(cell.defs)

        lines.append("@app.cell")
        lines.append(f"def _({refs_str}):")

        if cell.code.strip():
            for code_line in cell.code.splitlines():
                lines.append(f"    {code_line}")

        if defs_list:
            defs_str = ", ".join(defs_list)
            if len(defs_list) == 1:
                lines.append(f"    return ({defs_str},)")
            else:
                lines.append(f"    return ({defs_str})")
        else:
            lines.append("    return")

        lines.append("")

    lines.append('if __name__ == "__main__":')
    lines.append("    app.run()")
    lines.append("")

    return "\n".join(lines)
```

`graph.topological_order()` 返回 cell ID 列表，顺序满足：若 cell A 的 refs 包含 cell B 的 defs，则 B 排在 A 前面。这样生成的文件从上到下执行时，每个变量先被定义再被使用，天然合法。

拓扑排序用 Kahn 算法（BFS + 入度）：入度为 0 的 cell（没有上游依赖）先入队，每次出队一个就把它的下游入度减一，减到 0 就入队。`sorted` 保证输出稳定——同一拓扑序里，cell ID 字母序小的先出，序列化结果确定。如果最后排出的 cell 数不等于总 cell 数，说明有环——环里的 cell 入度永远减不到 0，进不了队列，抛 `CyclicDependencyError`。循环依赖在序列化阶段就被拦住，不会生成无法执行的文件。

## 序列化单个 cell

每个 cell 的序列化是四段拼装：装饰器 `@app.cell`、函数签名 `def _(refs):`、函数体、return 语句。refs 用 `sorted` 排序后逗号拼接，保证同一 cell 的参数顺序稳定（否则 set 迭代顺序随机，每次序列化结果不同，破坏幂等性）。函数体逐行加 4 空格缩进——`cell.code.splitlines()` 切行，每行前缀 `"    "`。空 code（cell 没有代码）跳过缩进，避免生成只有空格的行。

return 语句分三种：空 defs 写 `return`；单 def 写 `return (x,)`（注意逗号）；多 defs 写 `return (x, y)`。单元素的逗号是 Python 语法要求——`(x)` 是带括号表达式不是元组，`(x,)` 才是元组。serializer 必须处理这个细节，否则生成的文件语法错误。

## 文件头与尾

```python
_HEADER = """\
from backend.app import App

app = App()
"""
```

头部导入 `App` 类、创建 `app` 对象。教学版从 `backend.app` 导入，生产版 marimo 导入 `marimo` 并记录 `__generated_with` 版本号。`app = App()` 必须在 cell 函数定义之前，因为装饰器 `@app.cell` 在函数定义时就要执行——它引用 `app` 对象。如果顺序反了，Python 会 `NameError: name 'app' is not defined`。

尾部加 `if __name__ == "__main__": app.run()`。`if __name__` 守卫确保文件被 import 时不执行 `app.run()`，只有直接 `python notebook.py` 时才跑。`app.run()` 会按依赖图顺序执行所有 cell，打印每个 cell 的状态和输出。这个守卫是 Python 模块的惯用法，让 notebook 既能当脚本跑，又能当模块 import——import 时只定义 cell 函数，不执行。

## 逐步序列化演示

假设有这样一个图：cell_0 defs={x} refs={} code="x = 5"，cell_1 defs={y} refs={x} code="y = x + 1"，cell_2 defs={} refs={y} code="print(y)"。边：cell_0 → cell_1 → cell_2。

**第一步**：`topological_order()` 返回 [cell_0, cell_1, cell_2]（已经是拓扑序）。

**第二步**：输出 header `from backend.app import App` + `app = App()`。

**第三步**：序列化 cell_0。refs 为空，`def _():`；code "x = 5" 缩进成 `    x = 5`；defs={x} 单元素，`    return (x,)`。

**第四步**：序列化 cell_1。refs={x}，`def _(x):`；code "y = x + 1" 缩进；defs={y} 单元素，`    return (y,)`。

**第五步**：序列化 cell_2。refs={y}，`def _(y):`；code "print(y)" 缩进；defs 为空，`    return`。

**第六步**：输出 footer `if __name__ == "__main__": app.run()`。

最终文件就是这些片段用 `\n` 拼接。从上到下读：导入 App、创建 app、三个 cell 函数、运行入口。每个 cell 的参数只引用前面 cell 已 return 的变量，文件按书写顺序执行就能正确跑通。

## 保持幂等性

好的 serializer 应满足 `py_to_graph(graph_to_py(g)) == g`——序列化再解析回来，图不变。这要求：

- refs/defs 顺序稳定：serializer 用 `sorted` 排序，parser 用 set 收集再比较，顺序不影响集合相等；
- 函数体不丢信息：教学版用 `ast.unparse` 会丢注释和空行，所以严格幂等性不成立——序列化后的 code 与原 code 在文本上可能不同，但在 AST 上等价。生产版会保留原始 source 片段，实现文本级幂等；
- cell ID 生成规则一致：serializer 不显式写 ID（ID 是 parser 按位置序号生成的），所以往返后 ID 是 `cell_0, cell_1, ...` 按文件里的函数顺序。只要拓扑序稳定，ID 就稳定。

往返测试验证 `py_to_graph(graph_to_py(g)) == g`：序列化成文件、读回、解析、比较图的 code/defs/refs。教学版这个测试能过，因为 unparse 后的 code 与原 code 在 AST 层面等价，再 unparse 出来一致。

## 为什么不直接存 AST

有人问：既然有 AST，为什么不 `pickle` 或 `json` 存 AST？因为目标是**人类可读、git 友好、可直接执行**的文件。AST pickle 满足往返需求，但完全不可读——一串二进制，git diff 全是乱码；JSON 介于两者之间但不可执行，且 JSON 里的 AST 结构同样冗长（每个节点一堆字段）。只有生成真 Python 代码，才能同时满足三个目标：人能读、git 能 diff、python 能跑。

这也是 marimo 选择"代码生成"而非"结构序列化"的根本理由。代码生成本质上是把内存里的依赖图"打印"成 Python 语法树的一个线性化文本，而拓扑序保证了这个文本不仅是合法 Python，还能按书写顺序正确执行——无需运行时重新排序，`python notebook.py` 从上到下就是正确的执行顺序。这种"文件顺序即执行顺序"的特性，让生成的文件作为普通 Python 脚本也完全自洽。
