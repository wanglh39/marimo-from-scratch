# serializer 实现：从依赖图到 .py

`backend/storage/serializer.py` 里的 `graph_to_py` 是 parser 的逆运算：把 CellGraph 序列化成一个可执行的 `.py` 文件。关键在于**按拓扑序输出** cell，保证每个 cell 的 refs 在上游 cell 的 defs 里都已定义。

## 拓扑排序

```python
def graph_to_py(graph: CellGraph) -> str:
    order = graph.topo_sort()
    lines = [_header(graph)]
    for cid in order:
        lines.append(_serialize_cell(graph.cells[cid]))
    lines.append(_footer())
    return "\n\n".join(lines)
```

`graph.topo_sort()` 返回 cell ID 列表，顺序满足：若 cell A 的 refs 包含 cell B 的 defs，则 B 排在 A 前面。这样生成的文件从上到下执行时，每个变量先被定义再被使用，天然合法。

如果图里有环，`topo_sort` 抛异常——循环依赖在序列化阶段就被拦住，不会生成无法执行的文件。

## 序列化单个 cell

```python
def _serialize_cell(cell: Cell) -> str:
    params = ", ".join(cell.refs)
    defs = ", ".join(cell.defs)
    return_stmt = f"    return ({defs},)" if cell.defs else "    return"
    body = _indent(cell.code, "    ")
    return (
        f"@app.cell\n"
        f"def __({params}):\n"
        f"{body}\n"
        f"{return_stmt}"
    )
```

三段拼装：装饰器 `@app.cell`、函数签名 `def __(refs):`、函数体、return 语句。refs 用逗号拼成参数列表，defs 用逗号拼成 return 元组。函数体统一缩进 4 空格。空 defs 时只写 `return`，避免生成 `return (,)` 这种语法错误。

## 文件头与尾

```python
def _header(graph: CellGraph) -> str:
    return (
        "import marimo\n\n"
        f'__generated_with = "{graph.version}"\n'
        "app = marimo.App()"
    )

def _footer() -> str:
    return (
        'if __name__ == "__main__":\n'
        "    app.run()"
    )
```

头部导入 marimo、记录生成器版本、创建 `app` 对象。尾部加 `if __name__ == "__main__": app.run()`，让文件能直接 `python notebook.py` 执行。`app.run()` 会按依赖图顺序执行所有 cell。

## 保持幂等性

好的 serializer 应满足 `py_to_graph(graph_to_py(g)) == g`——序列化再解析回来，图不变。这要求：

- refs/defs 顺序稳定（按字母序或定义序）；
- 函数体不丢信息（教学版用 `ast.unparse` 会丢注释，生产版会保留原始 source 片段）；
- cell ID 生成规则一致。

## 为什么不直接存 AST

有人问：既然有 AST，为什么不 `pickle` 或 `json` 存 AST？因为目标是**人类可读、git 友好、可直接执行**的文件。AST pickle 满足往返需求，但完全不可读；JSON 介于两者之间但不可执行。只有生成真 Python 代码，才能同时满足三个目标。这也是 marimo 选择"代码生成"而非"结构序列化"的根本理由。

serializer 的代码生成本质上是把内存里的依赖图"打印"成 Python 语法树的一个线性化文本，而拓扑序保证了这个文本不仅是合法 Python，还能按书写顺序正确执行。
