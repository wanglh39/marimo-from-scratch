# 函数签名编码依赖：参数=refs，return=defs

marimo 文件格式最精妙的设计，在于用 Python 函数签名天然地编码 cell 之间的依赖关系。不需要任何旁路元数据，不需要在注释里写 `# depends on: cell_3`，依赖图就藏在函数签名里。

## 参数即 refs（上游依赖）

看这个 cell：

```python
@app.cell
def __(x, mo):
    y = x + 1
    return (y,)
```

函数参数 `x, mo` 告诉 marimo：这个 cell 需要变量 `x` 和 `mo`。marimo 据此在依赖图里找哪个 cell 定义了 `x`，建立一条边。`mo` 是 marimo 内置对象，由框架自动注入。

为什么用参数而不是别的？因为参数是 Python 原生的"我需要这些东西"表达方式。函数声明 `def f(x):` 语义上就是"我依赖 x"，这与 cell 依赖上游变量的含义完美对应。而且 Python 会在调用时检查参数是否都传齐了——这是一种免费的合法性校验。

## return 即 defs（产出变量）

`return (y,)` 告诉 marimo：这个 cell 产出了变量 `y`。下游任何 cell 把 `y` 写进参数列表，就自动建立了依赖边。

用 return 而不是"扫描函数体里所有赋值"有几个好处：

1. **显式优于隐式**：作者明确声明哪些变量是对外暴露的，临时变量不会泄漏到全局命名空间；
2. **静态可分析**：不用执行代码就能知道 defs，构建依赖图不需要运行时；
3. **避免误判**：`x = 5` 里 x 是 def，但 `df.col = 5` 里的 `df` 不是新定义——扫描赋值会出错，而 return 列表永远准确。

## 为什么是元组

`return (y,)` 用单元素元组（注意逗号），多个产出写成 `return (y, z, w)`。用元组而非列表，因为元组不可变、语义上更贴近"固定产出契约"。空产出则写 `return` 或干脆不写 return。

## 闭环检查

这套编码让循环依赖无所遁形。如果 cell A 的参数里有 `y`，而 cell B 的 return 里有 `y`，同时 cell B 的参数里有 `x`、cell A 的 return 里有 `x`——那就是 A 依赖 B、B 依赖 A 的循环。marimo 只需对"参数→return"关系做拓扑排序就能检测出来，而传统 notebook 根本没有依赖概念，只能靠执行顺序隐式处理，改一个 cell 不知道该重算谁。

## 命名空间隔离

每个 cell 是独立函数作用域，cell 内的变量不会意外污染其他 cell。想让变量被别人用，就必须显式 return。这比传统 notebook 的"一个大全局命名空间"安全得多——在 Jupyter 里重定义变量会悄悄影响所有后续 cell，而 marimo 里你必须显式声明依赖，漏了就报错，绝不会静默出错。

函数签名编码依赖，是 marimo 用 Python 原生语义解决 notebook 依赖管理的神来之笔：零额外语法、静态可分析、显式且安全。
