# 函数签名编码依赖：参数=refs，return=defs

marimo 文件格式最精妙的设计，在于用 Python 函数签名天然地编码 cell 之间的依赖关系。不需要任何旁路元数据，不需要在注释里写 `# depends on: cell_3`，依赖图就藏在函数签名里。这一章逐层拆解这套编码：参数怎么当 refs 用，return 怎么当 defs 用，以及它为什么比传统方案更安全。

## 参数即 refs（上游依赖）

看这个 cell：

```python
@app.cell
def __(x, mo):
    y = x + 1
    return (y,)
```

函数参数 `x, mo` 告诉 marimo：这个 cell 需要变量 `x` 和 `mo`。marimo 据此在依赖图里找哪个 cell 定义了 `x`，建立一条边。`mo` 是 marimo 内置对象，由框架自动注入。

参数提取的实现极其直接——遍历 AST 的参数列表取名字：

```python
refs = {arg.arg for arg in stmt.args.args}
```

`stmt.args.args` 是位置参数列表，每个 `arg` 的 `.arg` 属性是参数名字符串。装进 set 就得到 refs。不处理 `*args`、`**kwargs`、默认值——cell 不该有这些复杂签名。

为什么用参数而不是别的？因为参数是 Python 原生的"我需要这些东西"表达方式。函数声明 `def f(x):` 语义上就是"我依赖 x"，这与 cell 依赖上游变量的含义完美对应。而且 Python 会在调用时检查参数是否都传齐了——这是一种免费的合法性校验。如果用注释 `# needs: x`，Python 解释器看不见，写错了也没人提醒；用参数，写错了运行时立刻 `TypeError`。

更深一层，参数让依赖关系成为"可被工具理解"的一等公民。IDE 的"查找参数来源"能跳转到上游 cell，linter 能检查"参数是否在已知 defs 里"，refactor 工具能追踪变量流。这些都是白来的，因为参数是 Python 语义的一部分，工具链早已支持。

## return 即 defs（产出变量）

`return (y,)` 告诉 marimo：这个 cell 产出了变量 `y`。下游任何 cell 把 `y` 写进参数列表，就自动建立了依赖边。

return 提取从函数体末尾找 Return 语句，读它的值表达式：`stmt.value is None` 对应裸 `return`，返回空集；值是 `ast.Name`（`return y`）取 `.id`；是 `ast.Tuple`（`return (y, z)`）遍历元素取名字。非 Name 元素（如 `return (f(),)`）被忽略——只认变量名，不认表达式，因为只有变量名能作为依赖图的节点。

用 return 而不是"扫描函数体里所有赋值"有几个好处：

1. **显式优于隐式**：作者明确声明哪些变量是对外暴露的，临时变量不会泄漏到全局命名空间；
2. **静态可分析**：不用执行代码就能知道 defs，构建依赖图不需要运行时；
3. **避免误判**：`x = 5` 里 x 是 def，但 `df.col = 5` 里的 `df` 不是新定义——扫描赋值会出错，而 return 列表永远准确。

第三点值得展开。假设 cell 里有 `result = compute()` 和 `temp = result / 2`，如果扫描所有赋值，会认为 defs = {result, temp}。但作者可能只想对外暴露 `result`，`temp` 只是中间量。用 return，作者写 `return (result,)`，defs 就只有 result，temp 被隔离在 cell 内部。这种"显式选择对外接口"的能力，是扫描赋值给不了的。

## 为什么是元组

`return (y,)` 用单元素元组（注意逗号），多个产出写成 `return (y, z, w)`。用元组而非列表，因为元组不可变、语义上更贴近"固定产出契约"。空产出则写 `return` 或干脆不写 return。

单元素元组的逗号是 Python 的经典坑：`(y)` 只是带括号的表达式，等于 `y`；`(y,)` 才是单元素元组。serializer 在生成代码时专门处理了这种情况——单元素时强制加逗号，多元素时正常拼接。这种细节看似琐碎，却是"生成合法 Python"这条硬约束的必然要求——少一个逗号，文件就语法错误，整个可执行性卖点就崩了。

## 依赖图怎么连边

有了每个 cell 的 refs 和 defs，连边逻辑很直接：对每个 cell 的每个 ref 变量，找定义该变量的 cell，连一条"定义者 → 使用者"的边。graph.py 的 `_rebuild` 实现了这个映射：

```python
var_to_cell: dict[str, str] = {}
for cell_id, cell in self._cells.items():
    for var in cell.defs:
        if var in var_to_cell:
            raise DuplicateDefinitionError(
                f"变量 '{var}' 同时定义于 cell "
                f"'{var_to_cell[var]}' 和 '{cell_id}'"
            )
        var_to_cell[var] = cell_id

for cell_id, cell in self._cells.items():
    for var in cell.refs:
        upstream_id = var_to_cell.get(var)
        if upstream_id is not None and upstream_id != cell_id:
            self._downstream[upstream_id].add(cell_id)
            self._upstream[cell_id].add(upstream_id)
```

第一遍扫所有 defs 建"变量 → 定义它的 cell"映射。如果同一变量被两个 cell 定义，立刻抛 `DuplicateDefinitionError`——marimo 不允许变量被重复定义，这避免了"哪个 cell 才是权威"的歧义。第二遍扫所有 refs，查映射找到上游 cell，连边。ref 找不到定义者（如 `mo` 这种内置对象）就跳过，不报错。

## 闭环检查

这套编码让循环依赖无所遁形。如果 cell A 的参数里有 `y`，而 cell B 的 return 里有 `y`，同时 cell B 的参数里有 `x`、cell A 的 return 里有 `x`——那就是 A 依赖 B、B 依赖 A 的循环。marimo 只需对"参数→return"关系做拓扑排序就能检测出来。

拓扑排序用 Kahn 算法（BFS + 入度）：入度为 0 的 cell 先入队，每次出队一个就把它的下游入度减一，减到 0 就入队。如果最后排出的 cell 数不等于总 cell 数，说明有环——环里的 cell 入度永远减不到 0，进不了队列，抛 `CyclicDependencyError`，异常信息里直接列出涉环的 cell ID 方便定位。传统 notebook 根本没有依赖概念，只能靠执行顺序隐式处理，改一个 cell 不知道该重算谁。

## 命名空间隔离

每个 cell 是独立函数作用域，cell 内的变量不会意外污染其他 cell。想让变量被别人用，就必须显式 return。这比传统 notebook 的"一个大全局命名空间"安全得多——在 Jupyter 里重定义变量会悄悄影响所有后续 cell，而 marimo 里你必须显式声明依赖，漏了就报错，绝不会静默出错。

考虑 Jupyter 的经典坑：cell 1 定义 `x = 5`，cell 2 用 `x`，cell 3 又定义 `x = 10`。如果你重跑 cell 1，cell 2 看到的是 5；但 cell 3 里的 `x` 已经被改成 10，重跑 cell 3 后 cell 2 再跑又看到 10。变量值取决于"最后一次执行了哪个 cell"，而不是代码顺序。这种隐式状态是 Jupyter bug 的主要来源。

marimo 里同样的场景：cell 1 `return (x,)` 定义 x=5，cell 3 `return (x,)` 定义 x=10——直接 `DuplicateDefinitionError`，编译期就拦住。每个变量只有一个权威定义，下游 cell 想用就写进参数，不存在"被悄悄改了"的可能。

函数签名编码依赖，是 marimo 用 Python 原生语义解决 notebook 依赖管理的神来之笔：零额外语法、静态可分析、显式且安全。参数表是依赖声明，return 是接口声明，装饰器是 cell 标记——三样都是 Python 已有的东西，组合起来却精确表达了 reactive notebook 的依赖结构。
