# 断线重连：WebSocket 断开处理

WebSocket 连接不是永远不断——网络抖动、后端重启、浏览器休眠都可能断开。notebook 要可用，就得处理重连。教学版做最简方案，生产版 marimo 做得更完整，这一章讲清两者。

## 断开的触发场景

先理清什么情况下连接会断，不同场景对重连策略要求不同：

- **网络抖动**：WiFi 切换、瞬断，通常几百毫秒到几秒恢复；
- **后端重启**：开发时改后端代码、`uvicorn --reload` 自动重载，连接必断，几秒后服务恢复；
- **浏览器休眠**：笔记本合盖、切后台标签页，浏览器为省电暂停 WebSocket，恢复后连接已死；
- **服务端崩溃**：执行了 `os.exit` 或 OOM，进程消失，连接断开且不会自动恢复；
- **半开连接**：TCP 连接还在但对端已死（比如笔记本休眠后路由器丢了 NAT 映射），不主动探测就发现不了，发了消息才知道断了。

断开后前端 `WebSocket.onclose` 触发，此时若不处理，用户再点 Run 会发现没反应——消息发不出去，`ws.send` 静默失败或抛异常。

## 教学版的后端断开处理

看 `webapp.py` 真实代码，后端处理断开就一行：

```python
@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket) -> None:
    await websocket.accept()
    session = NotebookSession()
    try:
        while True:
            msg = await websocket.receive_json()
            responses = session.handle_message(msg)
            for resp in responses:
                await websocket.send_json(resp)
    except WebSocketDisconnect:
        pass
```

`WebSocketDisconnect` 抛出时循环退出，函数返回，`session` 局部变量失去引用，Python GC 回收它和它持有的 `CellGraph`、`Executor`——所有 cell 的变量值、执行状态、依赖图全部销毁。没有持久化，没有延迟清理，干净利落。

这意味着：后端重启后，前端重连进来，`NotebookSession` 重新构造，是个空 notebook。前端要靠 `get_state` 重新同步——但后端是空的，所以前端得把自己记着的 cell 代码逐个 `update_cell` 发过去重建。或者更简单：前端重连后直接刷新页面，从 `.py` 文件重新加载。

## 教学版策略：重连 + 全量同步

最简单有效的方案——前端负责重连和状态恢复：

```typescript
useEffect(() => {
  let ws: WebSocket;
  let retry: number;

  function connect() {
    ws = new WebSocket("ws://localhost:8000/ws");
    ws.onopen = () => {
      setConnected(true);
      ws.send(JSON.stringify({type: "get_state"}));
    };
    ws.onclose = () => {
      setConnected(false);
      retry = window.setTimeout(connect, 1000);
    };
    ws.onmessage = (e) => { /* dispatch */ };
  }
  connect();
  return () => { clearTimeout(retry); ws.close(); };
}, []);
```

断开后 1 秒重试，重连成功立即发 `get_state` 拉全量状态。后端 `NotebookSession` 在新连接进来时重建（教学版不持久化 session，所以重连后 notebook 回到上次保存到磁盘的状态，未保存的改动丢失）。

这是"无状态重连"——简单但代价是丢运行时状态（变量值、输出）。对教学演示够用，因为演示时改动都会即时保存到 `.py` 文件。

## 重连时序图

把教学版重连的完整时序画出来：

```
前端                            后端
  │                              │
  │══ 正常通信中 ════════════════│
  │                              │
  │── (后端 --reload 重启) ──────│  进程退出
  │   onclose 触发              │
  │   setConnected(false)       │
  │                              │
  │   等待 1000ms               │  后端重新启动
  │                              │
  │── new WebSocket(/ws) ──────→│  新 NotebookSession
  │←── 101 升级成功 ─────────────│
  │   onopen 触发               │
  │   setConnected(true)        │
  │                              │
  │── {type:get_state} ────────→│  后端返回空状态
  │←── {type:state, cells:[]} ──│
  │                              │
  │   前端发现后端空             │
  │   逐个 update_cell 同步代码  │
  │── {type:update_cell, ...} ─→│
  │── {type:run_all} ──────────→│  重新执行
  │←── {type:cell_result, ...} ─│
```

重连后的状态恢复分两步：先 `get_state` 看后端有什么，再把前端记着但后端没有的 cell 同步过去。教学版可以简化成直接刷新页面，让前端从 `.py` 文件重新加载，省去增量同步逻辑。

## 生产版的增强

生产 marimo 做几件事让重连更顺：

1. **session 持久化**：后端不随连接断开销毁 session，而是保留一段时间（比如 30 秒），同 notebook 的新连接复用旧 session，变量值都在。这要求 session 有唯一标识（notebook 文件路径或 session ID），且后端能按标识找回 session；
2. **增量同步**：重连后不只发全量 state，还发"你断开期间发生的 cell_result 队列"，前端 replay，恢复到断开时一致的状态。这要求后端给每条消息编号或带时间戳，前端重连时带上"我最后收到的是第 N 条"，后端从 N+1 开始补发；
3. **指数退避**：重试间隔 1s → 2s → 4s → ...，封顶比如 30s，避免后端挂了时前端疯狂重连浪费资源；
4. **心跳**：定期 ping/pong，及时检测半开连接（TCP 连接还在但对端已死）。WebSocket 协议自带 ping/pong 帧但应用层要主动发，浏览器 API 不直接暴露 ping，通常用应用层自定义 `{type:ping}` 消息模拟。

## 前端 UX 提示

断线期间要给用户明确反馈，不能静默失败：

- 顶部显示红色"已断开，重连中…"指示器；
- 编辑器仍可编辑（代码存前端 state），重连后批量 `update_cell` 同步过去；
- Run 按钮置灰或点击时提示"未连接"；
- 重连成功变绿色"已连接"，自动触发 `get_state`。

教学版 `App.tsx` 顶部一个 `connected ? "🟢" : "🔴"` 指示器即可。更完善一点可以显示重试次数和下次重连倒计时，让用户知道"还在努力，别急"。

## 为什么教学版不做持久化 session

持久化 session 要解决：session 标识（哪个连接属于哪个 notebook）、过期清理、内存中 Python 命名空间保活（不能 GC 变量）、并发安全（同一 notebook 多个连接同时改）。这些是工程量，与"理解 notebook 通信"的教学目标无关。教学版让重连 = 重新加载文件，把复杂度留给生产版。

具体来说，保活 Python 命名空间最难：变量值可能是 numpy 数组、pandas DataFrame、打开的文件句柄、数据库连接——这些不能简单序列化存盘再恢复，必须在 Python 进程里一直活着。所以生产版持久化 session 是"内存里留 30 秒"而非"存盘再读"，30 秒内重连能找回，超时才真销毁。这又引出内存管理问题：多个 notebook 的 session 都留 30 秒，内存占用可能很大，要限制并发 session 数。

断线重连是 notebook 可用性的底线——不处理就是"改一下后端前端就废了"，处理了开发体验顺滑很多。教学版用最简方案演示核心思路，理解了再去看生产版增强就不难。
