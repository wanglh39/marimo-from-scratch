# cell 状态机：IDLE → PENDING → RUNNING → DONE/ERROR/STALE

每个 cell 在执行过程中有状态，前端要据此显示图标、后端要据此调度。marimo 给 cell 定义了一个小状态机，状态转换由执行事件驱动。状态定义在 `backend/core/cell.py` 的 `CellStatus` 枚举里。

## 六个状态

```python
class CellStatus(Enum):
    IDLE = "idle"
    PENDING = "pending"
    RUNNING = "running"
    DONE = "done"
    ERROR = "error"
    STALE = "stale"
```

逐个解释：

- **IDLE**：初始或已就绪，未执行过或运行时状态已被重置；
- **PENDING**：已排队待执行（比如 Run All 时排在后面的 cell，还没轮到但即将执行）；
- **RUNNING**：正在执行；
- **DONE**：执行成功，输出有效；
- **ERROR**：执行抛异常，输出是 traceback；
- **STALE**：上游 cell 改了，本 cell 的输出可能过期，需要重算。

`PENDING` 和 `RUNNING` 的区分让前端能显示不同提示：PENDING 显示"排队中"，RUNNING 显示转圈。Run All 时这种区分有意义——20 个 cell 按拓扑序跑，第 15 个看到第 10 个在 RUNNING，自己就是 PENDING。

## 状态转换图

```
IDLE ──run──→ RUNNING
PENDING ──run──→ RUNNING
RUNNING ──success──→ DONE
RUNNING ──exception──→ ERROR
DONE ──upstream_changed──→ STALE
STALE ──run──→ RUNNING
ERROR ──run──→ RUNNING
任意 ──code_edited──→ STALE（若曾执行过）
```

关键转换：

1. **IDLE/PENDING → RUNNING**：用户点 Run 或被上游重算触发，开始执行；
2. **RUNNING → DONE**：执行无异常，输出存好；
3. **RUNNING → ERROR**：捕获到异常，存 traceback；
4. **DONE → STALE**：上游任一 cell 的 defs 变了（代码改了或重算产出新值），本 cell 标 stale；
5. **STALE → RUNNING**：重算触发；
6. **ERROR → RUNNING**：用户改完代码重新 Run，从错误状态重新执行。

注意 `is_runnable` 属性只允许 IDLE/PENDING/STALE 三种状态触发执行：

```python
@property
def is_runnable(self) -> bool:
    return self.status in (CellStatus.IDLE, CellStatus.PENDING, CellStatus.STALE)
```

RUNNING 状态的 cell 不能再触发执行（避免重入），ERROR 状态也不在列表里——错误状态的 cell 要先重置（改代码或手动 reset）才能重新 run。

## Cell 类的状态操作

`Cell` 提供两个方法操作状态：

```python
def reset_runtime_state(self) -> None:
    self.status = CellStatus.IDLE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}

def mark_stale(self) -> None:
    self.status = CellStatus.STALE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}
```

两个方法都清空运行时数据（output/stdout/exception/namespace），区别只在置什么状态。`mark_stale` 用于上游变化时标下游过期，`reset_runtime_state` 用于彻底重置一个 cell。清空 namespace 很关键——下游 cell 通过 namespace 取依赖值，stale cell 的旧 namespace 不能留着，否则下游可能读到过期值。

## 后端如何维护状态

`NotebookSession` 处理 `run_cell` 消息时驱动状态转换：

```python
def _handle_run_cell(self, msg: dict) -> list[dict]:
    cell_id = msg["cell_id"]
    self._executor.run_cell(cell_id)
    self._update_component_ids()
    return self._collect_results()
```

`executor.run_cell` 内部完成状态流转：置 RUNNING → 执行 → 置 DONE 或 ERROR。执行完调 `_collect_results` 把所有 cell 的当前状态打包成 `cell_result` 消息列表返回。概念上的流程是这样：

```python
# 概念伪代码（executor 内部）
cell.status = CellStatus.RUNNING          # 前端立即显示转圈
try:
    result = execute(cell.code, namespace)
    cell.status = CellStatus.DONE
    cell.output = result
except Exception as e:
    cell.status = CellStatus.ERROR
    cell.exception = e
# 之后传播 stale 给下游
for downstream in graph.successors(cell_id):
    graph.get_cell(downstream).mark_stale()
```

执行前先置 RUNNING 并广播（前端立即显示转圈），执行完置 DONE/ERROR 再广播结果。最后把下游 cell 标 STALE——但注意，刚执行成功的 cell 的下游不是单纯标 stale 就完事，marimo 的 reactive 策略是**自动重算下游**而非仅标 stale。教学版 executor 的 `run_descendants` 就做这件事：UI 事件触发时调它，沿依赖图往下重算。

## 前端同步

前端 `useNotebook` hook 收到 `cell_result` 消息时更新对应 cell 的状态和结果：

```typescript
case "cell_result":
  setCells(prev => prev.map(c =>
    c.id === msg.cell_id
      ? {...c, status: msg.status, result: msg.result}
      : c
  ));
  break;
```

收到 `state` 消息时整体替换。状态变化驱动 React 重渲染，状态图标、输出区域、stale 高亮都自动更新。前端不需要自己推断"这个 cell 现在该是什么状态"——状态权威在后端，前端只是镜像。这种"后端为单一事实源"的设计避免了前后端状态不一致的麻烦。

一个常见陷阱：如果前端也维护一份本地状态（比如乐观更新），就要小心和后端推送冲突。教学版不做乐观更新，所有状态都等后端 `cell_result` 确认后才改，简单但牺牲了一点即时反馈——点 Run 后到收到 RUNNING 状态前，按钮不会有变化。生产版可以乐观地先把本地状态置 RUNNING 再等后端确认，体验更跟手。

## 为什么要 STALE 而非直接重算

纯 reactive（任何上游变就立即重算）在拖滑块时会导致下游每帧重算，卡顿。引入 STALE 中间态让前端能显示"过期"提示，由用户决定何时重算，或由 debounce 后的自动重算处理。这是响应式与可控性的折中。

具体场景：cell A 定义 `x = ui.slider(0, 100)`，cell B 定义 `y = x ** 2`。拖动滑块时 A 的值每帧都在变，如果纯 reactive，B 每帧都要重算一次 `x ** 2`——这个例子计算量小没问题，但如果 B 是 `plt.plot(data[x:])` 这种重计算，每帧重算就卡死了。STALE 让 B 显示"过期"标记，等滑块停稳（debounce 200ms）再触发一次重算，体验顺滑。

状态机虽小，但让前后端对"cell 现在什么情况"有统一语言，避免了"前端显示 running 但后端早结束了"这种不同步问题。六个状态加上几条转换规则，就把 notebook 执行的复杂时序理清了。
