# 消息协议设计：请求、响应、事件

WebSocket 只提供传输通道，上面跑什么消息、什么格式、怎么区分类型，需要协议设计。marimo 教学版的协议定义在 `protocol.py`，是一套简单的 JSON 文本帧协议。传输层解决了"字节怎么传"，协议层要解决"传的是什么"。

## 三类消息

所有消息分三类，每类下又有若干子类型，用 `type` 字段区分：

**请求（Request）**——前端发给后端，要求执行某操作：

| type | 携带字段 | 语义 |
|------|---------|------|
| `get_state` | 无 | 请求当前完整 notebook 状态快照 |
| `update_cell` | `cell_id`, `code` | 更新某 cell 的代码（不执行，只重建依赖图） |
| `run_cell` | `cell_id` | 执行某 cell（可能触发下游重算） |
| `run_all` | 无 | 按拓扑序执行所有 cell |
| `add_cell` | `code`（可选） | 新增一个 cell，后端分配 cell_id |
| `remove_cell` | `cell_id` | 删除某 cell |
| `ui_event` | `component_id`, `value` | UI 组件事件（滑块值变化、按钮点击等） |

**响应与事件（Response/Event）**——后端发给前端：

| type | 携带字段 | 语义 |
|------|---------|------|
| `state` | `cells`, `edges` | 完整状态快照（响应 `get_state` 或重连时） |
| `cell_result` | `cell_id`, `status`, `output`, `stdout`, `exception`, ... | 某 cell 执行结果 |
| `graph_changed` | `cells`, `edges` | 图结构变化（cell 增删或依赖改变） |
| `error` | `message` | 错误通知 |

注意 `state` 和 `graph_changed` 字段结构一样，区别只在语义：前者用于初始全量同步，后者用于增量通知"图变了，给你新图"。前端可以同一段代码处理两者。

## JSON 帧格式

每条消息是一个 JSON 对象，必有 `type` 字段：

```json
{"type": "run_cell", "cell_id": "c2"}
```

```json
{"type": "cell_result", "cell_id": "c2", "stdout": "hello\n", "output": 5, "status": "done"}
```

```json
{"type": "ui_event", "component_id": "c1:slider_0", "value": 42}
```

用 `type` 字段做枚举分发，比用 WebSocket 的 opcode 更灵活——能在一个通道上混跑多种消息类型，前端 `switch(msg.type)` 即可路由。

后端的分发逻辑在 `session.py` 的 `handle_message`，用一个字典把 type 映射到处理函数，未知 type 或处理抛异常都回 `error` 消息，不让连接挂掉：

```python
handler = {"get_state": self._handle_get_state, "run_cell": self._handle_run_cell, ...}.get(msg_type)
if handler is None:
    return [make_error_message(f"未知消息类型: {msg_type}")]
try:
    return handler(msg)
except Exception as e:
    return [make_error_message(f"{type(e).__name__}: {e}")]
```

每条请求返回零或多条响应（列表），由 WebSocket 协程逐条发出。

## serialize_output：输出序列化

cell 执行后的 Python 对象要序列化成 JSON 能承载的形式。`serialize_output` 做这件事，实际代码比想象的稍复杂：

```python
def serialize_output(output: Any) -> Any:
    if output is None:
        return None
    if _is_ui_component(output):
        return output.to_dict()
    try:
        json.dumps(output)
        return output
    except (TypeError, ValueError):
        return repr(output)
```

四档处理：None 直接发 `null`（前端不渲染输出区）；UI 组件调 `to_dict()` 序列化成组件描述（前端据此渲染交互控件）；JSON 可序列化的（数字、字符串、列表、字典）原样发，前端拿到原始结构能交互式渲染；其余（numpy 数组、自定义类等）退回 `repr(obj)` 发字符串，前端当文本显示。

生产版会针对 matplotlib 图、pandas 表等做特殊处理（转 base64 PNG、HTML 表），教学版只做这四档。注意第 3 档没有包一层 `{"data": obj, "type": "json"}`，而是直接发原值——前端靠 `output` 字段本身的类型判断怎么渲染，简化了协议但牺牲了显式类型信息。

## UI 组件序列化

UI 组件是 marimo 的特色，序列化要特别处理。`_extract_components` 从 cell 的命名空间里捞出所有 UIComponent 实例，每个组件序列化时带上 `var_name`（变量名）：

```python
def _extract_components(cell: Cell) -> list[dict[str, Any]]:
    components: list[dict[str, Any]] = []
    for var_name, value in cell.namespace.items():
        if _is_ui_component(value):
            comp_dict = value.to_dict()
            comp_dict["var_name"] = var_name
            components.append(comp_dict)
    return components
```

前端发 `ui_event` 时用 `component_id` = `cell_id:var_name` 的格式定位组件。后端 `_handle_ui_event` 据此拆分出 cell_id 和 var_name，找到组件对象调 `set_value(new_value)`，再调 `run_descendants(cell_id)` 重算依赖这个 cell 的下游——这就是滑块拖动驱动重算的完整链路。

## make_cell_info / make_state_message

`make_cell_info` 把一个 cell 打包成前端需要的全部字段：

```python
def make_cell_info(cell: Cell) -> dict[str, Any]:
    return {
        "cell_id": cell.cell_id,
        "code": cell.code,
        "defs": sorted(cell.defs),
        "refs": sorted(cell.refs),
        "status": cell.status.value,
        "output": serialize_output(cell.output),
        "stdout": cell.stdout,
        "exception": repr(cell.exception) if cell.exception else None,
        "exception_type": type(cell.exception).__name__ if cell.exception else None,
        "components": _extract_components(cell),
    }
```

字段不少：代码、defs、refs、状态、输出、stdout、异常、异常类型、UI 组件列表。前端拿到一个 `cell_info` 就能完整渲染这个 cell，不用再发第二条消息问。`exception_type` 单独发是为了前端按异常类型做不同高亮。

`make_state_message` 把整图打包，用于初始同步或重连：

```python
def make_state_message(graph: CellGraph) -> dict[str, Any]:
    cells = [
        make_cell_info(graph.get_cell(cid)) for cid in graph.topological_order()
    ]
    edges: list[list[str]] = []
    for cid in graph.cell_ids:
        for succ in sorted(graph.successors(cid)):
            edges.append([cid, succ])
    return {"type": "state", "cells": cells, "edges": edges}
```

cells 按拓扑序排，前端按顺序渲染就能保证依赖在上游、被依赖在下游的视觉顺序。edges 是依赖边列表。`make_graph_changed_message` 结构完全一样，只是 `type` 换成 `"graph_changed"`。

## 为什么不用 protobuf / msgpack

教学版选 JSON 是因为浏览器原生支持 `JSON.parse`、Python 标准库带 `json`，零依赖、可读、好调试。protobuf 更省带宽但需要 schema 编译，msgpack 更快但调试不直观。对教学项目，JSON 的简单性压倒性能考虑。

具体权衡：JSON 是文本，`print(msg)` 直接能看懂，DevTools 网络面板里消息一目了然，零依赖；protobuf 是二进制，要靠 schema 反序列化才能看，还要装库 + 编译 `.proto`，但省带宽、有强 schema 能编译期查类型。对教学版几十条消息/秒的量级，JSON 的简单性压倒性能考虑。

生产版 marimo 在大 notebook 下会感受到 JSON 序列化开销，但协议设计本身不变，只是换序列化器。这套协议的精髓在于：**用 `type` 字段做枚举、用 JSON 做载体、用一条 WebSocket 连接复用所有消息类型**。简单、可扩展、好调试。
