# 为什么 WebSocket：实时双向通信

notebook 前端（浏览器里的 React）和后端（Python 进程）需要持续交换数据：用户改代码、点运行，后端执行后把输出推回来，UI 组件事件要传给 Python 回调。HTTP 是请求-响应模型，不适合这种场景。marimo 选 WebSocket，这一章解释为什么。

## notebook 的通信需求

列出 notebook 运行时的典型交互：

1. **用户编辑 cell 代码** → 通知后端更新内部状态；
2. **用户点 Run** → 后端执行该 cell，可能触发下游 cell 重算；
3. **执行完成** → 后端把 stdout、返回值、异常推给前端渲染；
4. **UI 组件交互**（滑块拖动、按钮点击）→ 前端发事件，后端调用对应 Python 回调，可能改变其他 cell 状态；
5. **图结构变化**（加/删 cell、改依赖）→ 后端通知前端重排布局。

这些交互有两个共同特征：**频繁** 和 **双向**。一次 Run All 可能触发十几个 cell 依次执行，每个完成都要推结果；一个滑块拖动可能每秒发几十个事件。

## HTTP 轮询的问题

用 HTTP 也能做：前端定时 `GET /state` 拉最新状态，`POST /run` 触发执行。但问题很多：

- **延迟**：轮询间隔 100ms 就有 50ms 平均延迟，滑块拖动会卡；
- **浪费**：没事件时也在空轮询，耗带宽和 CPU；
- **推送难**：后端执行完想主动推结果，HTTP 做不到，只能前端不停问"好了吗"；
- **状态管理复杂**：每次请求无状态，要靠 session ID 关联，容易出竞态。

长轮询（long-polling）能缓解推送问题，但实现复杂、连接频繁建断、 header 开销大。SSE（Server-Sent Events）能推送但只能单向。都不如 WebSocket 干净。

## WebSocket 的契合点

WebSocket 在一条 TCP 连接上提供**全双工**帧通信：

- **建一次连接，持续用**：没有反复握手，开销低；
- **双向主动推送**：前端能随时发消息，后端也能随时推消息，不用等对方问；
- **低延迟**：消息即发即收，适合滑块这种实时交互；
- **自带状态**：连接本身就是 session，不用额外 session ID（教学版仍用 session 对象管理状态，但连接断开即 session 结束）。

marimo 的典型消息流：

```
前端 ──run_cell(id=2)──→ 后端
后端 执行 cell 2
后端 ──cell_result(id=2, stdout="...", output=...)──→ 前端
后端 发现 cell 3 依赖 cell 2，自动重算
后端 ──cell_result(id=3, ...)──→ 前端
后端 ──graph_changed(...)──→ 前端
```

一条连接上多个消息交织，HTTP 要做到这点得开多条请求或长轮询，复杂得多。

## 教学版的简化

生产版 marimo 还要处理多 notebook、多用户、连接复用、心跳保活等。教学版只做单连接、单 notebook：

- 一个 WebSocket 连接对应一个 `NotebookSession`；
- 连接断开即 session 销毁，不做持久化恢复；
- 不做心跳（依赖 TCP 超时）；
- 消息是 JSON 文本帧，不用二进制协议。
