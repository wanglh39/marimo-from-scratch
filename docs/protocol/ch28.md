# 为什么 WebSocket：实时双向通信

notebook 前端（浏览器里的 React）和后端（Python 进程）需要持续交换数据：用户改代码、点运行，后端执行后把输出推回来，UI 组件事件要传给 Python 回调。HTTP 是请求-响应模型，不适合这种场景。marimo 选 WebSocket，这一章解释为什么。

## notebook 的通信需求

先把 notebook 运行时的典型交互列清楚，这是选型的依据，每一条都对应一种真实信息流：

1. **用户编辑 cell 代码** → 通知后端更新内部状态（不一定立即执行，只改代码和依赖图）；
2. **用户点 Run** → 后端执行该 cell，可能触发下游 cell 重算；
3. **执行完成** → 后端把 stdout、返回值、异常推给前端渲染；
4. **UI 组件交互**（滑块拖动、按钮点击）→ 前端发事件，后端调用对应 Python 回调，可能改变其他 cell 状态；
5. **图结构变化**（加/删 cell、改依赖）→ 后端通知前端重排布局；
6. **执行进度** → 长任务时后端持续推送进度条、中间输出，前端实时刷新。

这些交互有两个共同特征：**频繁** 和 **双向**。一次 Run All 可能触发十几个 cell 依次执行，每个完成都要推结果；一个滑块拖动可能每秒发几十个事件。粗略估算：一个 20 cell 的 notebook 跑一遍 Run All，后端要推 20 条 `cell_result` + 若干 `graph_changed`，与此同时前端也在发 `update_cell`。这种"双方都在主动说话"的场景，正是 WebSocket 的主场。

更关键的是第 4 条——UI 组件事件。marimo 的滑块 `ui.slider` 拖动时，前端要把新值发给后端，后端更新组件状态后重算依赖它的下游 cell，再把新输出推回前端。这是一来一回的紧耦合循环，延迟稍大用户就能感觉到卡顿。

## HTTP 轮询的问题

用 HTTP 也能做：前端定时 `GET /state` 拉最新状态，`POST /run` 触发执行。但问题很多：

- **延迟**：轮询间隔 100ms 就有 50ms 平均延迟，滑块拖动会卡；
- **浪费**：没事件时也在空轮询，耗带宽和 CPU；
- **推送难**：后端执行完想主动推结果，HTTP 做不到，只能前端不停问"好了吗"；
- **状态管理复杂**：每次请求无状态，要靠 session ID 关联，容易出竞态。

长轮询（long-polling）能缓解推送问题：前端发请求后后端挂住不回，直到有事件才响应，前端收到立刻发下一个请求。但实现复杂、连接频繁建断、header 开销大。SSE（Server-Sent Events）能推送但只能单向。都不如 WebSocket 干净。

## 三种方案对比

把候选方案摆在一起看更清楚：

| 方案 | 双向 | 服务端主动推 | 延迟 | 协议开销 | 实现复杂度 |
|------|------|------------|------|---------|-----------|
| HTTP 轮询 | 靠频繁请求模拟 | ✗ | 高（取决于轮询间隔） | 每次带完整 header | 低 |
| HTTP 长轮询 | 靠挂住请求模拟 | ✓ | 中 | 连接频繁建断 | 中 |
| SSE | ✗ 单向 | ✓ | 低 | 一次握手后轻量 | 中 |
| WebSocket | ✓ 全双工 | ✓ | 极低 | 帧头 2-10 字节 | 中 |

SSE 看似能解决推送，但 notebook 的 UI 事件是前端→后端的频繁消息，SSE 走不了，还得再开一条 HTTP 通道发上行，等于"两条腿走路"。WebSocket 一条连接全双工，对称、统一，协议层面就为双向通信设计。

还有一个常被忽略的点：HTTP/2 虽然多路复用缓解了连接数问题，但仍然是请求-响应语义，服务端主动推要走 Server Push，浏览器支持有限且语义不适合这种频繁双向交互。WebSocket 不依赖 HTTP/2，在 HTTP/1.1 上也能工作。

## WebSocket 的契合点

WebSocket 在一条 TCP 连接上提供**全双工**帧通信。握手阶段借用 HTTP Upgrade 头，升级成功后这条 TCP 就不再走 HTTP 协议，改走 WebSocket 的帧协议：

- **建一次连接，持续用**：没有反复握手，开销低；
- **双向主动推送**：前端能随时发消息，后端也能随时推消息，不用等对方问；
- **低延迟**：消息即发即收，适合滑块这种实时交互；
- **自带状态**：连接本身就是 session，不用额外 session ID（教学版仍用 session 对象管理状态，但连接断开即 session 结束）；
- **帧头小**：小消息帧头只有 2 字节，比 HTTP 每次几百字节 header 省很多。

握手过程简单说：前端发一个带 `Upgrade: websocket` 头的 HTTP 请求，后端回 `101 Switching Protocols`，之后这条 TCP 两端都切到 WebSocket 帧协议。对教学版来说，FastAPI 的 `websocket.accept()` 封装了这步，不用关心细节。

marimo 的典型消息流：

```
前端 ──run_cell(id=2)──→ 后端
后端 执行 cell 2
后端 ──cell_result(id=2, stdout="...", output=...)──→ 前端
后端 发现 cell 3 依赖 cell 2，自动重算
后端 ──cell_result(id=3, ...)──→ 前端
后端 ──graph_changed(...)──→ 前端
```

一条连接上多个消息交织，HTTP 要做到这点得开多条请求或长轮询，复杂得多。

## 教学版的实现

看 `webapp.py` 里 WebSocket 端点的真实代码，理解最简形态：

```python
@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket) -> None:
    await websocket.accept()
    session = NotebookSession()
    try:
        while True:
            msg = await websocket.receive_json()
            responses = session.handle_message(msg)
            for resp in responses:
                await websocket.send_json(resp)
    except WebSocketDisconnect:
        pass
```

就这十几行，把 WebSocket 的核心用足了：

1. `accept()` 完成 HTTP→WebSocket 升级握手；
2. 一个连接对应一个 `NotebookSession`，连接即 session；
3. `while True` 持续收消息——连接不断就一直挂着，正是"长连接"；
4. `receive_json` / `send_json` 用 JSON 文本帧，收一条处理一条，回零或多条；
5. `WebSocketDisconnect` 捕获断开，循环退出，session 随之销毁（Python GC 回收）。

注意 `handle_message` 是同步的，返回消息列表后由这个协程逐条 `send_json` 发出。教学版不做异步执行引擎，cell 执行阻塞在这条消息处理里——执行期间收不了新消息。这对教学演示够用，生产版会把执行放到独立任务队列，WebSocket 只负责收发。

## 连接生命周期

把连接从建立到断开的完整生命周期画出来：

```
浏览器                            FastAPI
  │                                  │
  │── HTTP Upgrade /ws ─────────────→│
  │←── 101 Switching Protocols ──────│
  │                                  │
  │══ WebSocket 双工通道建立 ════════│
  │                                  │
  │── {type:get_state} ─────────────→│  新建 NotebookSession
  │←── {type:state, cells:[...]} ────│
  │                                  │
  │── {type:run_cell, cell_id:c1} ──→│  执行
  │←── {type:cell_result, ...} ──────│  推结果
  │←── {type:cell_result, ...} ──────│  下游重算结果
  │                                  │
  │   ... 持续交互 ...               │
  │                                  │
  │── (TCP FIN / 网络断) ────────────│  抛 WebSocketDisconnect
  │                                  │  session 销毁
```

整条生命期里 session 对象一直活着，持有 `CellGraph` 和 `Executor`，所有 cell 的变量值、依赖关系、执行状态都在内存里。连接断开，这些全部销毁——这是教学版的简化取舍，下一章的协议、第三十一章的重连会展开讲。

## 教学版的简化

生产版 marimo 还要处理多 notebook、多用户、连接复用、心跳保活等。教学版只做单连接、单 notebook：

- 一个 WebSocket 连接对应一个 `NotebookSession`；
- 连接断开即 session 销毁，不做持久化恢复；
- 不做心跳（依赖 TCP 超时）；
- 消息是 JSON 文本帧，不用二进制协议。
