# slider 完整实现

Slider 是 marimo 教学版中第一个、也是最典型的 UI 组件。它对应前端的一个 `<input type="range">` 控件，允许用户在指定范围内拖动选择数值。通过剖析 Slider 从后端定义到前端渲染、再到事件回传的完整链路，可以理解所有 UI 组件的共同工作模式。

## Slider 类的定义

在 `backend/components/ui.py` 中，`Slider` 继承自 `UIComponent`，构造函数接收四个参数：

```python
class Slider(UIComponent):
    def __init__(self, min, max, step, value):
        self.component_type = "slider"
        self.min = min
        self.max = max
        self.step = step
        self._value = value
        self.props = {"min": min, "max": max, "step": step}
```

这里有一个设计要点：`min`、`max`、`step` 被同时存为实例属性和塞进 `props` 字典。存为实例属性是为了在 Python 侧能方便地访问，比如 `slider.max`；塞进 `props` 是为了通过 `to_dict()` 传给前端。而 `_value` 只存一份，因为它既是 Python 侧的当前值，也是要同步给前端的当前值，两者必须始终一致。构造函数不设置 `component_id`，这个字段留给 session 在 cell 执行后填充。

## 工厂函数 slider()

用户代码调用的是 `ui.slider(min, max, step, value)`，这个工厂函数实现极其简单：

```python
def slider(min=0, max=10, step=1, value=0):
    return Slider(min, max, step, value)
```

工厂函数的价值不在于逻辑复杂，而在于它提供了一个稳定的 API 边界。未来如果需要在创建组件时注册全局监听器、或者根据 session 配置调整默认值，只需修改工厂函数，用户代码无需改动。

## 前端渲染：input range

前端在 `CellView.tsx` 中有一个子组件 `UIComponentView`，它根据 `component.type` 分发到不同的渲染分支。对于 `"slider"`，渲染逻辑是：

```tsx
case "slider":
  return (
    <input
      type="range"
      min={component.props.min}
      max={component.props.max}
      step={component.props.step}
      value={component.value}
      onChange={(e) => onUIEvent(component.id, parseFloat(e.target.value))}
    />
  );
```

这段代码把 `props` 里的三个配置项直接映射到 HTML `<input>` 的属性，把后端传来的 `value` 作为控件的当前值。关键在 `onChange`：每当用户拖动滑块，浏览器触发 change 事件，回调函数取出新的数值，调用 `onUIEvent` 把组件 ID 和新值发送回后端。

## onChange 与 ui_event 消息

`onUIEvent` 最终通过 WebSocket 发送一条 `ui_event` 消息，格式为：

```json
{
  "type": "ui_event",
  "component_id": "cell_3:slider",
  "value": 7
}
```

后端 session 收到这条消息后，根据 `component_id` 找到对应的组件对象，把它的 `_value` 更新为 7，然后触发依赖该组件的 cell 重新执行。这条从浏览器拖动到 Python 变量更新的链路，看似简单，但它跨越了三次序列化边界：浏览器 DOM 事件 → WebSocket 文本帧 → Python 对象字段。Slider 的实现之所以能保持简洁，正是因为 `UIComponent` 基类和消息层已经把这些边界处理封装好了，具体组件只需声明自己的 `props` 和前端渲染规则。
