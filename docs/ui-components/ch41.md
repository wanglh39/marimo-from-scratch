# 组件组合与布局

除了 Slider，marimo 教学版还实现了 Button 和 Checkbox 两种组件。它们的设计模式与 Slider 完全一致，但在交互语义上有重要区别。这一章我们看这三种组件如何协作，以及组件如何作为 cell 的输出。理解了单组件的工作机制后，组合使用时的依赖追踪、布局渲染、状态隔离等问题，才是真实 notebook 场景中更常遇到的。

真实数据分析里，单个滑块很少够用。常见的场景是：一个滑块调阈值、一个复选框切换显示模式、一个按钮触发导出，三者协作完成一个交互式仪表盘。这种组合不是简单地把三个控件堆在一起——它们之间的依赖关系、重跑范围、状态同步都需要框架支持。marimo 的组件系统通过"每个组件独立绑定变量、依赖图自动追踪"来处理组合，用户不需要手动管理控件间的关系。本章会展开这种自动管理的细节，以及教学版在布局能力上的局限。组件组合是 reactive binding 从"单组件演示"走向"真实应用"的关键一步，理解了组合机制，就能用 marimo 搭建有实际用途的交互式 notebook。

## Button 实现

Button 的语义是"点击触发一次动作"，它没有持续的数值状态，只有一个瞬时的点击事件。在 `backend/components/ui.py` 中：

```python
class Button(UIComponent):
    def __init__(self, label: str = "Click", value: int = 0) -> None:
        super().__init__("button", value, {"label": label})
```

`_value` 是一个点击计数器，每次前端回传时自增。前端渲染为一个 `<button>` 元素，`onClick` 触发时发送的值是当前计数加一。后端 `set_value` 直接赋值，不做加法——加法在前端算好了。这种"前端算新值、后端直接赋"的模式与 Slider 一致，保持了 `_handle_ui_event` 的统一逻辑：收到值就 `set_value`，不区分组件类型。

用户代码可以检查 `btn.value` 是否变化来决定是否执行某段逻辑。这种"计数器"模式比布尔标志更健壮——连续点击不会被合并成一次。如果用布尔标志（点击就翻转 true/false），快速连点两次会回到原状态，下游 cell 看不到变化，不会重跑。计数器每次都递增，每次点击都产生新值，每次都触发重跑。这种设计借鉴了 React 里"计数器 state 触发重渲染"的模式，保证了每次用户操作都被框架感知。

`button` 工厂函数默认 `value=0`，且不暴露 `value` 参数——强制初值从 0 开始。这是合理的，用户不应该能预设点击次数，计数器语义就是"从 0 开始数"。`label` 参数控制按钮上显示的文字，默认 `"Click"`。前端把 `label` 渲染为按钮的文本内容，用户看到的就是这个字。Button 的 `props` 只有 `label` 一项，比 Slider 的 `min`/`max`/`step` 简单，因为按钮没有"范围"概念。

Button 与 Slider 的一个微妙区别是事件触发频率。Slider 拖动时，浏览器可能连续触发多次 change 事件（每经过一个步长一次）；Button 点击是一次动作一个事件。这意味着 Slider 可能产生高频事件流，需要节流；Button 天然低频，不需要。教学版都没做节流，但如果要优化，Slider 是首要目标。Button 的另一个特点是"无状态"——按钮的 `value` 计数器虽然存在，但用户代码很少真的去读它，更多时候只是把按钮当作"触发重跑的开关"。比如 `if btn.value > 0:` 表示"点击过至少一次就执行"，但更常见的用法是让按钮的存在本身触发某个依赖 cell 的重跑。

## Checkbox 实现

Checkbox 对应 `<input type="checkbox">`，表示一个布尔选择：

```python
class Checkbox(UIComponent):
    def __init__(self, label: str = "", value: bool = False) -> None:
        super().__init__("checkbox", value, {"label": label})
```

前端渲染时，`checked` 属性绑定到 `component.value`，`onChange` 回调读取 `e.target.checked` 得到布尔值回传。Checkbox 常用于控制显示/隐藏逻辑，比如 `if show_advanced.value:` 决定是否执行某个 cell 的内容。与 Button 的计数器不同，Checkbox 的值在 true/false 间翻转，连续两次点击会回到原状态——但这对 checkbox 是正确的语义，因为 checkbox 表达的是"当前是否选中"这个状态，而不是"发生了几次切换"。

注意 checkbox 的 `onChange` 回调发送的是 `e.target.checked`（布尔值），而不是 `e.target.value`（字符串）。这是 HTML 表单的一个坑：`<input type="checkbox">` 的 `value` 属性总是 `"on"`（除非显式设置），真正反映选中状态的是 `checked` 属性。前端代码正确地读了 `checked`，避免了把字符串 `"on"` 当布尔值传给后端的错误。如果传错类型，后端 `set_value("on")` 会把字符串赋给 `_value`，下游 `if show_advanced.value:` 永远为真（非空字符串都 truthy），复选框就失效了。这种类型保真度是跨语言边界的常见陷阱，前端代码必须对每个控件类型用对的属性。

Checkbox 的 `label` 默认是空字符串，这与 Button 默认 `"Click"` 不同。复选框常与旁边的文字标签配合使用，但标签文字可能由外部布局决定，所以默认留空。Slider 则完全没有 label 参数——滑块的语义由范围和值自解释，不需要额外文字。这些默认值的差异体现了每种控件的交互惯例。

Checkbox 与 Slider 在值变化频率上也有差异。Slider 拖动时可能连续产生多个值（每经过一个步长一次），Checkbox 点击一次只翻转一次值。这意味着 Checkbox 不会产生高频事件流，不需要节流。但 Checkbox 的值只有两个状态，下游 cell 的重跑结果也只有两种——这限制了它的表达能力，适合"开关"类需求，不适合"连续调节"。选择哪种组件取决于交互语义：要调连续参数用 Slider，要切开关用 Checkbox，要触发动作用 Button。三种组件的语义不重叠，各自有最佳使用场景。

## 多组件协作

一个 cell 可以创建多个组件，它们作为独立的变量共存于同一命名空间：

```python
min_val = ui.slider(0, 50, 1, 0)
max_val = ui.slider(50, 100, 1, 100)
use_range = ui.checkbox("使用范围", True)
```

每个组件有独立的 `component_id`（分别是 `cell_x:min_val`、`cell_x:max_val`、`cell_x:use_range`），前端为每个组件渲染独立的控件。`_extract_components` 遍历命名空间时会把三个组件都收进 `components` 列表，前端 `CellView` 用 `cell.components.map(...)` 渲染出三个控件。渲染顺序就是变量定义顺序，因为 Python 3.7 加的字典保持插入顺序，命名空间遍历按定义顺序产出。

当用户拖动 `min_val`，只有引用了 `min_val` 的后代 cell 重跑；拖动 `max_val` 只触发 `max_val` 的后代。这种细粒度的依赖追踪避免了"一个控件变化导致全 notebook 重跑"的低效。多个组件也可以共同被一个 cell 引用，比如 `filtered = data[(data["x"] >= min_val.value) & (data["x"] <= max_val.value)]`，此时 `min_val` 或 `max_val` 任一变化都会触发这个 cell 重跑——因为 cell 的 `refs` 同时包含 `min_val` 和 `max_val`，依赖图上这个 cell 是两个 slider 所在 cell 的共同后代。AST 分析器在分析这行代码时，会识别出 `min_val` 和 `max_val` 都是外部引用，把它们加入 `refs`，依赖图据此建边。

这种"多源依赖"是 reactive binding 威力的体现：一个 cell 可以依赖任意多个上游组件，依赖图自动处理拓扑排序，用户不需要手动指定"先重跑谁再重跑谁"。如果 `cell_5` 依赖 `min_val` 和 `max_val`，`cell_6` 又依赖 `cell_5` 的结果，那么 `min_val` 变化时拓扑排序保证 `cell_5` 先于 `cell_6` 执行，`cell_6` 看到的是 `cell_5` 用新 `min_val` 算出的结果。用户只管写依赖关系，框架管执行顺序，这是 reactive 系统相对于手动回调的核心便利。

多组件协作时有一个边界情况：两个组件互相依赖。比如 cell A 定义 `a = ui.slider(value=b.value)`，cell B 定义 `b = ui.slider(value=a.value)`。AST 分析会把 `a` 的 refs 设为 `{b}`，`b` 的 refs 设为 `{a}`，依赖图出现环。marimo 在建图时会检测环并报错，拒绝这种循环依赖。这是正确的——循环依赖的语义无法定义，"a 变导致 b 变导致 a 变"是无限循环。用户必须打破循环，比如把其中一个改成不依赖对方的初值。教学版的环检测在 `CellGraph.add_cell` 里做，真实 marimo 也禁止循环依赖，但会给出更友好的错误提示，指出是哪几个 cell 构成了环。

## 组件作为 cell 输出

组件不仅可以在 cell 中作为变量使用，也可以直接作为 cell 的输出。当 cell 最后一行表达式是一个 UIComponent 时，executor 会把它作为 cell 的 `output`，前端在 CellView 中渲染出对应控件。判断逻辑在 `CellView.tsx` 里检查输出的 `_ui` 标记是否为真。`_ui: True` 是 `UIComponent.to_dict()` 加上的，前端据此区分"输出是个 UI 组件，渲染成控件"还是"输出是个普通值，渲染成文本"。

这种模式下，组件既是输入控件又是输出展示——比如一个 slider 既是用户调节参数的工具，又作为 cell 的可见输出展示当前值。这与传统 notebook 里"控件"和"输出"分离的模式不同，marimo 让两者统一为同一个 Python 对象，简化了心智模型。在 Jupyter 里，控件用 `display(widget)` 显示，输出用 `print(result)` 显示，两者是不同的 API；marimo 里都是同一个对象，作为变量是控件，作为表达式输出也是控件，无需区分。

考虑这个 cell：

```python
threshold = ui.slider(0, 100, 1, 50)
threshold
```

第一行创建组件并赋给 `threshold`，第二行把 `threshold` 作为表达式输出。executor 执行时，第一行把组件塞进命名空间，第二行作为最后一条表达式语句，其值（组件对象）被赋给 `cell.output`。`_extract_components` 同时把组件收进 `cell.components` 列表。前端渲染时，`cell.components` 里的控件渲染在代码块下方的 `cell-components` 区域，`cell.output` 里的控件又渲染在 `cell-output` 区域——同一个组件被渲染了两次。

这看起来是 bug，但其实是教学版的简化处理。真实 marimo 会去重，只渲染一次。教学版保留双渲染，恰好让学习者看到组件的两种角色：作为命名空间中的变量（出现在 components 列表）和作为 cell 输出（出现在 output 字段）。两者数据来源相同，`to_dict()` 输出一致，前端用同一个 `UIComponentView` 渲染，交互事件都走同一条 `onUIEvent` 链路。理解了这种双重身份，就理解了为什么 `to_dict()` 要加 `_ui` 标记——它让前端能统一处理两种来源的组件。

输出提取的机制在 executor 里：执行 cell 时，executor 用 `ast.parse` 解析代码，检查最后一条语句是否是表达式语句（`ast.Expr`）。如果是，就把前面的语句用 `exec` 执行，最后一条用 `eval` 求值，求值结果赋给 `cell.output`。如果最后一条是赋值语句或 if 语句，则没有输出。这套机制让 `threshold`（裸变量作为最后一行）能成为输出，而 `threshold = 50`（赋值）不会。这与 Python REPL 的行为一致——REPL 里打一个表达式会显示其值，打一个赋值不会。marimo 复用了这个直觉：cell 最后一行是表达式就有输出，否则没有。组件作为输出只是这个机制的一个应用，输出也可以是普通值、DataFrame、图表等，序列化时 `serialize_output` 会判断类型决定如何处理。

## 布局与局限

组合使用时，多个组件按创建顺序在前端纵向排列。`cell.components.map(...)` 按 `_extract_components` 遍历命名空间的顺序渲染，而命名空间是字典（Python 3.7 加保持插入顺序），所以渲染顺序就是组件变量的定义顺序。教学版没有实现复杂的网格布局、HBox/VBox 容器、tabs 等，这保持了实现的简洁，也符合教学项目的定位。

真实 marimo 有 `mo.vstack`、`mo.hstack`、`mo.tabs` 等布局组件，它们本身也是 UIComponent 的变体，把子组件的渲染信息打包进自己的 props，前端根据 type 渲染成对应的 flex 容器。教学版省略了这些，但 `UIComponent` 基类加 `to_dict()` 加前端 switch 的模式已经为布局组件的扩展预留了空间——新增布局组件只需新增子类和前端分支，不需要改消息协议。这种"骨架可扩展"的设计让教学版虽然功能简陋，却展示了真实 marimo 的扩展机制。

以 `vstack` 为例，它的实现思路是：定义一个 `VStack(UIComponent)` 子类，`props` 里存一个 `"children"` 列表，每个元素是子组件的 `to_dict()` 结果。`to_dict()` 输出的 `type` 是 `"vstack"`，前端 switch 里加一个 `case 'vstack'` 渲染成 `<div style="display:flex;flex-direction:column">`，里面 map 渲染 children。后端不需要知道 children 里的组件如何渲染——那是前端的事；前端不需要知道 children 里的组件值如何回传——那走统一的 ui_event 通道。布局组件是"容器"，它只管排列，不管内容，这种职责分离让布局可以任意嵌套：vstack 里套 hstack，hstack 里套 tabs，深度不限。教学版没实现这些，但理解了这个思路，就能想象真实 marimo 的布局系统如何工作。

教学版的另一个局限是没有组件销毁机制。cell 被删除时，组件对象随命名空间一起被回收，但前端不会收到显式的"组件已销毁"消息，而是通过下一次 `state` 或 `cell_result` 消息里 `components` 列表不再包含该组件来间接感知。前端 React 的 `key={comp.id}` 机制保证列表不再包含某项时对应的 DOM 被卸载。这种"靠下次全量状态同步来清理"的模型简单但有一个窗口期：在用户删除 cell 到下一次状态同步之间，前端可能短暂显示已不存在的组件。教学版接受这个时序问题，真实 marimo 用更精细的增量消息解决了它。

多 session 之间的状态隔离是组件系统的另一层保障。每个 `NotebookSession` 初始化时创建自己的 `CellGraph` 和 `Executor`，并通过 `inject("ui", ui_module)` 注入 ui 模块。不同 session 的命名空间完全独立，A session 里的 `threshold` 组件和 B session 里的 `threshold` 组件是不同对象，有不同的 `component_id`（因为 cell_id 不同），互不影响。这种隔离是后端能同时服务多个用户的前提。如果组件状态是全局共享的，A 拖动滑块就会影响 B 的 notebook，这是不可接受的。教学版每个 WebSocket 连接对应一个 `NotebookSession`，连接关闭时 session 被丢弃，所有组件状态随之释放，不会有跨连接的泄漏。

## 三种组件的统一与差异

回顾三种组件，它们的共同点是：都继承 `UIComponent`，都用 `to_dict()` 序列化，都通过 `ui_event` 回传值，都靠 `run_descendants` 触发后代重跑。差异只在三处：`component_type` 字符串、`props` 字典的内容、前端渲染分支。这种"统一骨架加局部差异"的结构，正是 `UIComponent` 基类的价值——它把 reactive binding 的所有机制封装在基类和 session/executor 里，具体组件只负责声明自己的外观。新增第四种组件（比如 dropdown）的工作量被压缩到写一个子类和一个前端 case 分支，这就是良好抽象的回报。基类承担了所有跨组件的通用逻辑，子类只需填充自己的特化部分。

三种组件的值类型各不相同：Slider 是 float，Checkbox 是 bool，Button 是 int 计数器。这些类型在 JSON 序列化时都能无损往返——JSON 原生支持数字和布尔。如果组件值是复杂类型（比如 datetime 或 DataFrame），就需要自定义序列化，教学版不涉及。值类型的选择不是任意的，它必须满足"前端能产生、JSON 能传输、后端能消费"三重要求。Slider 的 float 来自 `<input type="range">` 的数值属性，Checkbox 的 bool 来自 `checked` 属性，Button 的 int 来自前端加一计算——每种都对应前端控件的天然输出类型。

从教学角度，这三种组件覆盖了 UI 控件的三个基本语义类别：连续数值调节（Slider）、布尔状态切换（Checkbox）、离散动作触发（Button）。大部分复杂控件都能归入这三类或它们的组合。比如下拉选择框是"离散值选择"，类似 Button 的离散性但值是选项而非计数；文本输入框是"连续字符串"，类似 Slider 但值域是字符串。理解了这三类的基础实现，扩展到其他控件类型就是套用同一模式，改改 `props` 和前端渲染分支而已。

如果读者想练习扩展组件系统，可以尝试实现一个 `Dropdown`（下拉选择框）。后端需要：定义 `Dropdown(UIComponent)` 子类，`props` 存 `{"options": ["a", "b", "c"]}`，`_value` 存当前选中项；写一个 `dropdown(options, value)` 工厂函数。前端需要在 `UIComponentView` 的 switch 里加 `case 'dropdown'`，渲染成 `<select>` 加若干 `<option>`，`onChange` 读 `e.target.value` 回传。做完这个练习，会深刻体会到"开闭原则"在组件系统里的体现——你完全没有改 session、protocol、executor，只加了子类和前端分支，新组件就完整接入了 reactive binding。教学版选这三种，既覆盖了语义空间，又保持了实现规模适中，适合在有限篇幅里讲透组件系统的全貌。
