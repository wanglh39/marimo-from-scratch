# reactive binding

reactive binding 是 marimo 最核心的交互机制：用户拖动一个 slider，依赖这个 slider 的所有 cell 自动重新执行并更新输出。这一章我们从 `component_id` 的构造开始，完整追踪一次值变化引发的数据流。

## component_id 的构造

当用户在某个 cell 中写下 `threshold = ui.slider(0, 100, 1, 50)`，cell 执行完毕后，session 会遍历该 cell 命名空间中所有 `UIComponent` 实例，对每一个设置 `component_id`，格式为 `"cell_id:var_name"`。例如这个 cell 的 ID 是 `cell_2`，变量名是 `threshold`，那么 `component_id` 就是 `"cell_2:threshold"`。这个 ID 有两层含义：`cell_2` 说明组件由哪个 cell 创建，`threshold` 说明它绑定到哪个变量名。前端回传事件时携带这个 ID，后端就能同时定位到"哪个 cell 的哪个变量发生了变化"。

## 前端交互到 ui_event

用户拖动滑块，前端的 `onChange` 回调触发，构造一条 `ui_event` 消息通过 WebSocket 发送：

```json
{"type": "ui_event", "component_id": "cell_2:threshold", "value": 73}
```

session 的消息处理器收到 `ui_event` 后，执行三步操作。第一步，解析 `component_id` 得到 `cell_id="cell_2"` 和 `var_name="threshold"`。第二步，在 `cell_2` 的执行命名空间中找到 `threshold` 这个变量，把它的 `_value` 更新为 73。这一步是纯 Python 内存操作，不涉及任何重新执行。第三步，调用 `executor.run_descendants("cell_2")`，触发依赖链。

## run_descendants 与后代重跑

executor 维护着一张依赖图，记录每个 cell 引用了哪些其他 cell 的变量。当 `cell_2` 的 `threshold` 值变化后，executor 查找所有引用了 `threshold` 的 cell，这些被称为 `cell_2` 的后代。例如 `cell_5` 中有 `filtered = data[data["score"] > threshold]`，它引用了 `threshold`，因此是 `cell_2` 的后代。executor 按拓扑顺序依次重新执行这些后代 cell：先把 `threshold` 的新值 73 注入到 `cell_5` 的命名空间，然后执行 `cell_5` 的代码，得到新的 `filtered`，再把 `cell_5` 的输出发送给前端。如果 `cell_7` 又依赖 `filtered`，它也会被递归重跑。

## 完整数据流

把整条链路画出来：

```
用户拖动 slider
  → 浏览器 onChange
  → WebSocket 发送 ui_event(cell_2:threshold, 73)
  → session 更新 threshold._value = 73
  → executor.run_descendants("cell_2")
  → 拓扑排序后代 cell_5, cell_7
  → 依次执行，注入新值
  → 每个 cell 的输出发送回前端
  → 前端更新对应 CellView
```

这条链路的关键特征是**单向数据流**：值从前端流向后端，再从后端流回前端，中间没有任何双向绑定的隐式回环。每个环节都是显式的、可追踪的。这与 Vue 的双向绑定 `v-model` 形成对比——marimo 选择了更显式的模型，因为 notebook 的执行语义本身是有方向的：上游变量变化驱动下游 cell 重跑，而不是两个控件互相同步。理解了这条数据流，就理解了 marimo 交互能力的全部基础。
