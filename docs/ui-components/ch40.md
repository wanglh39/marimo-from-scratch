# reactive binding

reactive binding 是 marimo 最核心的交互机制：用户拖动一个 slider，依赖这个 slider 的所有 cell 自动重新执行并更新输出。这一章我们从 `component_id` 的构造开始，完整追踪一次值变化引发的数据流，并把链路上每个环节的实现细节展开。

要理解 reactive binding 的价值，先看没有它时的痛点。在传统 notebook 里，若 cell A 定义了 `threshold = 50`，cell B 写 `filtered = data[data["score"] > threshold]`，用户想把 threshold 改成 73，必须回到 cell A 改代码、重跑 cell A、再重跑 cell B。每次调参都是手动操作。reactive binding 的目标是：把 `threshold` 变成一个滑块，用户拖动滑块，cell B 自动重跑，新结果立刻显示。用户不需要知道"重跑"这件事发生了——他只看到拖动滑块、结果跟着变。这种"调参即结果"的体验是 reactive notebook 相对传统 notebook 的根本优势，它让数据分析的探索循环从"改代码—运行—看结果"缩短为"拖控件—看结果"。本章将完整拆解这条链路的每一环，让"自动重跑"的魔法变得可追踪、可理解。

reactive binding 这个名字里，"reactive"指值变化自动传播，"binding"指组件与变量名的绑定。两者结合就是：组件值变化等同于变量赋新值，变量赋新值触发依赖该变量的 cell 重跑。整条链路不依赖任何用户写的回调函数，全由框架隐式完成。这种隐式性是双刃剑：好处是用户代码简洁，坏处是调试时不易看到"谁触发了谁"。marimo 通过依赖图让这条链路可追踪——任何时候都能查图知道"这个 cell 依赖哪些上游、被哪些下游依赖"。

reactive 系统里有三种常见语义：事件驱动（值变化触发回调）、数据流（值变化自动传播给依赖者）、信号（值是时间序列，可被采样）。marimo 的 reactive binding 属于数据流语义——值变化自动传播给依赖 cell，不是显式回调，也不是时间序列。这与 React 的 state 属于同一家族：React 里 setState 触发依赖该 state 的组件重渲染，marimo 里 set_value 触发依赖该变量的 cell 重跑。两者都是"值变化驱动下游更新"的单向数据流，只是 React 的下游是组件，marimo 的下游是 cell。理解这个类比有助于从 React 经验迁移到 marimo。

## component_id 的构造

当用户在某个 cell 中写下 `threshold = ui.slider(0, 100, 1, 50)`，cell 执行完毕后，session 会遍历该 cell 命名空间中所有 `UIComponent` 实例，对每一个设置 `component_id`，格式为 `"cell_id:var_name"`。这一步在 `session.py` 的 `_update_component_ids` 中完成：

```python
def _update_component_ids(self) -> None:
    for cell_id in self._graph.cell_ids:
        cell = self._graph.get_cell(cell_id)
        for var_name, value in cell.namespace.items():
            if isinstance(value, UIComponent):
                value.component_id = f"{cell_id}:{var_name}"
```

例如这个 cell 的 ID 是 `cell_2`，变量名是 `threshold`，那么 `component_id` 就是 `"cell_2:threshold"`。这个 ID 有两层含义：`cell_2` 说明组件由哪个 cell 创建，`threshold` 说明它绑定到哪个变量名。前端回传事件时携带这个 ID，后端就能同时定位到"哪个 cell 的哪个变量发生了变化"。

为什么 ID 不在组件构造时就设置？因为构造时还不知道变量名。Python 的赋值语句 `threshold = ui.slider(...)` 先执行右侧 `ui.slider(...)` 构造对象，此时对象不知道自己将被赋给哪个变量；然后解释器把对象绑定到变量名 `threshold`，但这一步不会通知对象本身。要拿到变量名，只能等 cell 执行完毕后，从 cell 的命名空间（`cell.namespace` 字典）里反向查找：遍历命名空间的每个键值对，值是 `UIComponent` 实例的，键就是变量名。这就是 `_update_component_ids` 的逻辑。

这种"事后补 ID"的方案有一个隐含约束：组件必须作为 cell 的顶层变量存在，才能被绑定。如果用户写 `data["slider"] = ui.slider(...)`，组件被塞进了字典，命名空间里只有 `data` 这个键，`_update_component_ids` 找不到组件，它的 `component_id` 会一直是 `None`，前端渲染时守卫会跳过它。教学版接受这个限制，真实 marimo 通过更复杂的引用追踪部分缓解了它。对教学而言，这个限制反而让"组件是顶层变量"这个约定更清晰，学习者一开始就养成正确习惯。

`component_id` 的唯一性由 cell_id 和变量名共同保证。cell_id 由 session 的 `_cell_counter` 递增生成，全局唯一；变量名在同一 cell 的命名空间里唯一。两者组合 `"cell_id:var_name"` 因此全局唯一，不会有两个组件共享同一 ID。这保证了前端用 ID 作为 React `key` 时不会冲突，也保证了 ui_event 回传时后端能无歧义地定位组件。如果用户在 cell 里写了 `s = ui.slider(); s = ui.slider()`，两次构造的 slider 都叫 `s`，但命名空间里只保留最后赋值的那个，`_update_component_ids` 只会给最后这个设 ID，前一个组件失去引用被垃圾回收。这是 Python 赋值语义的自然结果，框架不需要特殊处理。

`_update_component_ids` 在多个时机被调用：`_handle_get_state`（前端首次连接获取状态时）、`_handle_run_cell`（手动运行某个 cell 后）、`_handle_run_all`（运行全部 cell 后）、`_handle_ui_event`（处理完 UI 事件后）。每次 cell 执行后都重新设置一遍 ID，是因为执行可能改变命名空间——比如用户把 `threshold = ui.slider(...)` 改成了 `threshold = 100`，此时 `threshold` 不再是组件，遍历时自然跳过它。反复重设 ID 看似低效，但组件数量通常很少，遍历开销可忽略。

一个微妙的问题是：重设 ID 会覆盖旧 ID。如果某个组件的 `component_id` 已经是 `"cell_2:threshold"`，重设时还是设成 `"cell_2:threshold"`，值不变，无副作用。但如果用户把变量改名了——`threshold` 改成 `cutoff`——重设后 ID 变成 `"cell_2:cutoff"`。前端如果还持有旧 ID `"cell_2:threshold"` 的引用（比如某个未完成的渲染），就会失配。教学版不处理这个边界，因为前端每次收到新状态就整体替换，旧引用自然消失。真实 marimo 需要更精细的组件生命周期管理来处理重命名场景。

## 前端交互到 ui_event

用户拖动滑块，前端的 `onChange` 回调触发，构造一条 `ui_event` 消息通过 WebSocket 发送：

```json
{"type": "ui_event", "component_id": "cell_2:threshold", "value": 73}
```

session 的消息处理器 `_handle_ui_event` 收到后，执行三步操作。第一步，解析 `component_id` 得到 `cell_id="cell_2"` 和 `var_name="threshold"`，用 `split(":", 1)` 分割。第二步，在 `cell_2` 的执行命名空间中找到 `threshold` 这个变量，调用 `set_value` 把它的 `_value` 更新为 73。这一步是纯 Python 内存操作，不涉及任何重新执行，瞬间完成。第三步，调用 `executor.run_descendants("cell_2")`，触发依赖链。这一步才是 reactive 的核心，下一节展开。三步合起来构成了"收到事件—更新状态—传播变化"的完整响应。

注意第二步和第三步的顺序：先改值，再重跑后代。这个顺序很重要。如果先重跑后代再改值，后代 cell 执行时读到的还是旧值，重跑就白跑了。先改值保证后代重跑时全局命名空间里的 `threshold` 已经是新值。而 `threshold` 所在的 `cell_2` 本身不需要重跑——它只是定义了组件，组件值变化不改变 cell 的代码语义。这是 reactive binding 与普通 cell 重跑的关键区别。

如果用户快速连续拖动滑块，比如从 50 拖到 73，中间经过 51、52、...、72，每个值都会触发一次 ui_event 吗？教学版没有做节流，所以理论上会。但 WebSocket 消息处理是同步的——后端处理完 51 的 ui_event（包括所有后代重跑）后才会处理 52 的。如果后代重跑很快，用户会看到结果从 51 一直跳到 73；如果后代重跑慢，消息会在后端排队，用户拖到 73 后，后端还在处理 51，界面会延迟更新。教学版没有优化这个问题，真实 marimo 会丢弃中间值只处理最新的，避免无意义的中间重跑。这叫"事件合并"或"latest-wins"策略。

## run_descendants 与后代重跑

executor 维护着一张依赖图，记录每个 cell 引用了哪些其他 cell 的变量。当 `cell_2` 的 `threshold` 值变化后，executor 查找所有引用了 `threshold` 的 cell，这些被称为 `cell_2` 的后代。`run_descendants` 的实现里，`self._graph.descendants(cell_id)` 做的是一次图遍历——从 `cell_2` 出发，沿着依赖边走，能到达的所有 cell 都是后代。遍历用 BFS 或 DFS 均可，关键是收集所有可达节点。如果图里有环（cell A 依赖 B，B 又依赖 A），遍历会死循环——但依赖图在构建时就保证无环（有环的 cell 会被检测并报错），所以遍历总是终止的。`run_descendants` 的实现：

```python
def run_descendants(self, cell_id: str) -> list[str]:
    descendants = self._graph.descendants(cell_id)
    if not descendants:
        return []
    order = self._graph._topological_sort_subset(descendants)
    for cid in order:
        self._cleanup_cell_vars(cid)

    executed: list[str] = []
    short_circuited = False
    for cid in order:
        cell = self._graph.get_cell(cid)
        if short_circuited or self._has_failed_upstream(cid):
            cell.mark_stale()
            continue
        self._execute_cell(cell)
        executed.append(cid)
        if cell.has_error:
            short_circuited = True
    return executed
```

这段代码做了几件事。首先 `self._graph.descendants(cell_id)` 在依赖图上做一次图遍历，收集所有后代 cell。然后 `_topological_sort_subset` 对这些后代做拓扑排序，保证被依赖的 cell 先执行——如果 cell_5 依赖 cell_4 的结果，cell_4 必须先重跑。接着 `_cleanup_cell_vars` 清理每个后代 cell 之前定义的变量——因为这些 cell 即将重新执行，旧变量应该先从全局命名空间移除，避免残留状态干扰新执行结果。最后按拓扑顺序依次执行每个 cell，遇到错误则短路，把后续 cell 标记为 STALE。

例如 `cell_5` 中有 `filtered = data[data["score"] > threshold]`，它引用了 `threshold`，因此是 `cell_2` 的后代。executor 先把 `threshold` 的新值 73 注入到 `cell_5` 的命名空间（实际上 `threshold` 一直存在于全局命名空间，`set_value` 已经改了它，`cell_5` 执行时自然读到新值），然后执行 `cell_5` 的代码，得到新的 `filtered`，再把 `cell_5` 的输出发送给前端。如果 `cell_7` 又依赖 `filtered`，它也会被递归重跑。整条链路 `cell_2 → cell_5 → cell_7` 按拓扑顺序依次执行，每个 cell 都用上游的新结果算出自己的新结果。

注意 `run_descendants` 不会重跑 `cell_2` 本身——`cell_2` 只是定义了 `threshold` 这个组件，组件的值已经通过 `set_value` 更新，无需重新执行 cell 代码。这是 reactive binding 与普通 cell 重跑的关键区别：组件值变化是"外部输入"而非"代码执行结果"，跳过源头 cell 是正确的优化。如果重跑 `cell_2`，会重新执行 `threshold = ui.slider(...)`，构造一个全新的 slider 对象，旧对象的 `_value` 更新就丢了——这显然不对。

短路机制是 `run_descendants` 的一个重要特性。如果 `cell_5` 重跑时出错（比如 `threshold` 值太大导致 `data["score"] > threshold` 结果为空，后续操作报错），`short_circuited` 被置为 `True`，`cell_7` 不会执行而是被标记为 STALE。这避免了用错误结果继续计算。STALE 状态在前端显示为特殊图标，提示用户"这个 cell 的结果可能过期，因为上游出错了"。用户修复上游 cell 后，下次重跑会清除 STALE 标记。

`_cleanup_cell_vars` 这一步容易被忽略但很关键。它把后代 cell 之前定义的变量从全局命名空间移除。为什么要移除？假设 `cell_5` 之前定义了 `filtered`，重跑时如果代码改了不再定义 `filtered` 而改定义 `filtered_v2`，不移除的话旧的 `filtered` 会残留在命名空间里，可能被其他 cell 误引用。清理保证重跑后命名空间只包含当前代码真正定义的变量。这体现了"重跑即重新执行"的语义——不是在旧状态上增量，而是从干净状态开始。

`_has_failed_upstream` 检查是另一道防线。即使没有短路，某个 cell 的上游如果处于 ERROR 或 STALE 状态，这个 cell 也不应执行，而是直接标记 STALE。这处理了依赖图里某个分支出错但另一个分支正常的情况——正常分支照常执行，出错分支的后代全部 STALE。这种"按分支短路"比全局短路更精细，让正常计算不被错误打断。

## 完整数据流

把整条链路画出来：

```
用户拖动 slider
  → 浏览器 onChange 触发
  → Number(e.target.value) 得到数值 73
  → send({ type: 'ui_event', component_id: 'cell_2:threshold', value: 73 })
  → WebSocket 发送文本帧
  → session._handle_ui_event 接收
  → split(":", 1) 解析得 cell_id="cell_2", var_name="threshold"
  → cell.namespace["threshold"].set_value(73)
  → executor.run_descendants("cell_2")
    → graph.descendants("cell_2") 得 [cell_5, cell_7]
    → _topological_sort_subset 拓扑排序
    → _cleanup_cell_vars 清理旧变量
    → 依次执行 cell_5, cell_7
    → 每个 cell 的 output/components 更新
  → _update_component_ids 刷新组件 ID
  → _collect_results 收集所有 cell 最新状态
  → 返回 [cell_result, cell_result, ...] 给前端
  → 前端 useNotebook 更新 cells state
  → React 重新渲染 CellView
  → 用户看到 cell_5, cell_7 的新输出
```

这条链路的关键特征是**单向数据流**：值从前端流向后端，再从后端流回前端，中间没有任何双向绑定的隐式回环。每个环节都是显式的、可追踪的。这与 Vue 的双向绑定 `v-model` 形成对比——marimo 选择了更显式的模型，因为 notebook 的执行语义本身是有方向的：上游变量变化驱动下游 cell 重跑，而不是两个控件互相同步。

链路里有一个细节值得注意：`_collect_results` 收集的是所有 cell 的状态，不只是重跑的那几个。前端收到后整体替换本地 state。这意味着即使某个 cell 没有重跑，它的状态也会被重新发送一遍。对于小 notebook 这无所谓，对于大 notebook 这是带宽浪费。教学版选全量推送是为了前端实现简单——整体替换比 diff 合并容易得多。真实 marimo 做增量推送，只发变化的 cell_result。

时序上，整条链路是同步阻塞的：`_handle_ui_event` 调用 `run_descendants`，后者同步执行所有后代 cell，全部完成后才返回消息列表。这意味着如果某个后代 cell 执行耗时（比如训练一个模型），用户拖动滑块后会感觉界面"卡住"直到计算完成。教学版没有异步执行或后台任务机制，所有计算都在 WebSocket 消息处理里同步完成。真实 marimo 支持异步 cell（用 async def），长计算可以不阻塞其他交互。教学版的同步模型虽然简单，但不适合重计算场景——这是教学项目与生产工具的明确分界。

## 与 v-model 和 Streamlit 的对比

Vue 的 `v-model` 是双向绑定：`<input v-model="text">` 让 input 的值与 `text` 变量互相同步，input 变了 `text` 变，`text` 变了 input 也变。这种模型适合表单场景，但不适合 notebook——notebook 里没有"控件 A 和变量 B 互相同步"的需求，只有"变量 B 变了，依赖 B 的 cell C 重跑"这种单向需求。marimo 的 `set_value` 加 `run_descendants` 正是这种单向模型：前端事件改 `_value`，`_value` 变化驱动后代重跑，没有反向回流。如果硬要类比，marimo 的模型更像 Vue 的"props 向下流动"而非 `v-model` 的双向同步。

Streamlit 的模型也是单向的，但它的重跑粒度是整个脚本：任意 `st.slider` 值变化，脚本从头到尾重跑一次。对于小脚本这无所谓，但对于有几十个 cell 的 notebook，全量重跑会重复计算大量无关 cell。比如脚本里有一个耗时的数据加载步骤和一个滑块，拖动滑块会重新加载数据，除非用 `@st.cache_data` 装饰器缓存。marimo 的 `run_descendants` 只重跑依赖子图，未受影响的 cell 保持原状——数据加载 cell 不依赖滑块，就不会重跑。这正是维护依赖图的意义所在。

依赖图的构建是 reactive binding 能精准重跑的前提。每个 cell 提交时，`analyze_cell` 用 AST 分析提取代码的 `defs`（定义的变量名）和 `refs`（引用的外部变量名）。图根据这些信息建边：如果 cell B 的 refs 包含 cell A 的 defs 里的变量，就有一条 A 到 B 的边。这条边意味着"B 依赖 A，A 变化时 B 要重跑"。AST 分析是静态的——只看代码文本，不执行代码，所以速度快且安全。代价是它看不到动态依赖：如果 cell B 用 `getattr(obj, name)` 访问变量，AST 看不出 `name` 是什么，这种依赖会被漏掉。教学版的 AST 分析器只处理显式变量名引用，对动态访问无能为力，这是静态分析的固有局限。

理解了这条数据流，就理解了 marimo 交互能力的全部基础。后续章节的 Button、Checkbox 等组件，只是前端渲染分支和 props 不同，事件回传与后代重跑的链路与 Slider 完全一致。reactive binding 的真正复杂度不在某个具体组件，而在依赖图的维护和增量执行的调度——这些在 core 模块的章节里已经展开，本章关注的是 UI 组件如何接入这条已有的执行管线。组件系统与执行引擎的解耦，使得两者可以独立演化：新增组件类型不需要改执行引擎，优化执行引擎也不影响组件接口，这种解耦是 marimo 架构能保持简洁的关键。

给学习者一个心智模型：把 marimo notebook 想象成一个电子表格。每个 cell 是一个单元格，组件是单元格里的输入框，依赖图记录了"哪些单元格引用了哪些"。改一个输入框的值，所有引用它的单元格自动重算。电子表格的这套模型经过几十年验证是直观且强大的，marimo 把它带到了 Python notebook 世界，只是"单元格"变成了能执行任意 Python 代码的 cell，"引用"变成了变量名依赖。理解了这个类比，reactive binding 就不再神秘——它就是电子表格的自动重算，只是粒度从单元格变成了 cell。
