# 组件设计理念

marimo 的 UI 组件系统建立在一条核心原则上：**Python 对象与前端的控件是一一对应的**。当用户在 cell 中写下 `slider = ui.slider(0, 10, 1, 5)`，他拿到的不是一个抽象的描述符，而是一个真实的 Python 对象，这个对象既能在后端被序列化传输给前端，又能在 Python 代码里被当作普通变量读取。这种"双向同构"的设计，是整个 reactive notebook 可用性的基石。

## 为什么组件是 Python 对象

在传统的 Web 框架里，UI 控件往往是一段 HTML 模板字符串，或者是一个需要回调函数的事件处理器。marimo 选择了完全不同的路径：每一个 UI 组件都是一个继承自 `UIComponent` 的 Python 类实例。这样做有三个直接好处。第一，组件可以携带状态——`_value` 字段保存当前值，前端回传新值时直接修改这个字段，无需重新构造对象。第二，组件可以作为函数参数传递，也可以参与任何 Python 表达式运算，比如 `slider.value * 2` 就是一个普通的算术。第三，组件的生命周期由 Python 的引用计数自然管理，cell 被删除时组件随之被回收，不会出现悬空控件。

## UIComponent 基类

`UIComponent` 是所有具体组件的父类，定义在 `backend/components/ui.py` 中。它的核心字段有四个：`component_id` 用于唯一标识一个组件实例，`component_type` 是一个字符串标签（如 `"slider"`、`"button"`），`_value` 存储当前值，`props` 是一个字典，存放该组件特有的配置参数。基类提供了一个关键方法 `to_dict()`，它把上述字段打包成一个 JSON 可序列化的字典：

```python
def to_dict(self):
    return {
        "id": self.component_id,
        "type": self.component_type,
        "value": self._value,
        "props": self.props,
    }
```

这个方法就是后端向前端传递组件状态的唯一出口。每当 cell 执行完毕，executor 会收集该 cell 输出的所有 UIComponent，调用各自的 `to_dict()`，把结果塞进发送给前端的消息里。

## to_dict 序列化的意义

序列化看起来只是简单的字段打包，但它承担了一个重要职责：**隔离前后端的数据契约**。前端只需要知道 `type` 来决定渲染哪种 HTML 控件，读取 `props` 来配置控件属性，监听交互事件后回传新的 `value`。后端则只需要在收到回传时把 `_value` 更新为最新值。这种松耦合使得新增一种组件类型时，后端只需新增一个子类，前端只需新增一个渲染分支，两者通过 `to_dict()` 的输出格式自然对接，不需要修改任何中间层代码。

## 工厂函数与 session 注入

用户代码里并不直接 `UIComponent(...)`，而是通过 `ui.slider()`、`ui.button()` 这样的工厂函数创建组件。这些工厂函数被组织成一个模块对象，由 executor 通过 `inject("ui", ui_module)` 注入到 cell 的执行命名空间。这种注入机制保证了每个 session 拿到的 `ui` 模块是隔离的——不同用户的 notebook 不会共享组件状态。工厂函数本身只负责构造对象并返回，组件的 `component_id` 此时还是空的，留待 session 在 cell 执行完成后统一设置为 `"cell_id:var_name"` 的形式，这一步是 reactive binding 能够精准定位后代 cell 的关键，我们将在第四十章详细展开。
