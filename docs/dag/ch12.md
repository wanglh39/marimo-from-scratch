# 图论基础

在进入 `CellGraph` 的源码之前，我们需要先把几个图论概念弄清楚。marimo 把每个 cell 看作图中的一个节点，把 cell 之间的变量依赖关系看作有向边，从而把整本 notebook 建模成一张有向图。理解这张图的性质，是理解后续增量执行、短路、拓扑排序等所有机制的前提。这一章不涉及任何执行逻辑，只讲图的数学定义和它在 marimo 里的具体含义，为后面四章打好词汇基础。如果你对图论已经熟悉，可以跳到最后一节看 marimo 的具体映射；如果不太熟，请耐心读完，因为这些词汇在后续每一章都会反复出现。图论是计算机科学里最实用的数学分支之一，从编译器数据流分析、任务调度到版本控制都在用，reactive notebook 只是又一个应用场景。

## 有向图

有向图（Directed Graph）由一组顶点 $V$ 和一组有向边 $E$ 组成，每条边是一个有序对 $(u, v)$，表示从 $u$ 指向 $v$。形式化地，$G = (V, E)$，其中 $V$ 是有限集，$E \subseteq V \times V$。与无向图不同，有向边的方向有语义：$(u, v)$ 和 $(v, u)$ 是两条不同的边，分别表示"u 指向 v"和"v 指向 u"。在无向图里交换一对顶点的顺序不改变边，在有向图里则会得到反向的边，这是两者最根本的区别。有向图的入度（in-degree）指指向某顶点的边数，出度（out-degree）指从该顶点出发的边数；无向图只有度数不分出入。

在 marimo 中，顶点是 cell，边 $(A, B)$ 表示"cell A 定义了某个变量，而 cell B 引用了这个变量"，也就是 B 依赖 A，数据从 A 流向 B。边的方向与数据流方向一致，这一点很重要，后面求"后代"时就是顺着数据流方向往下找。如果把边方向定义反了（比如定义成"引用者指向定义者"），那么后代和祖先的含义也会互换，所有下游查询都要改成上游查询——方向选错不会导致错误，但会让代码读起来别扭，所以一开始就约定"边沿数据流方向"是值得的。这个约定也和自然语言一致："A 喂给 B 数据"画成 $A \to B$，箭头跟着数据走。

在内存里，`CellGraph` 并不显式存一个 `set[tuple]` 形式的边集，而是用两张邻接表分别存"向下游"和"向上游"两个方向，这样查询前驱和后继都是 $O(1)$ 的字典查找：

```python
class CellGraph:
    def __init__(self) -> None:
        self._cells: dict[str, Cell] = {}
        self._downstream: dict[str, set[str]] = defaultdict(set)
        self._upstream: dict[str, set[str]] = defaultdict(set)
```

`_downstream[A]` 存放所有满足 $A \to B$ 的 $B$，`_upstream[B]` 存放所有满足 $A \to B$ 的 $A$。同一条边在两张表里各登记一次，空间换时间。这种"双向邻接表"是后续 `predecessors`/`successors` 直接返回、`descendants`/`ancestors` 做 BFS 的基础。顶点集则由 `self._cells` 承担，键是 cell id，值是 `Cell` 对象——既当顶点集合用，又附带每个 cell 的元信息（代码、状态、输出）。用 `defaultdict(set)` 是为了省去"键不存在时初始化空集合"的样板代码，任何键第一次访问自动得到空 set。

为什么选邻接表而不是邻接矩阵？邻接矩阵用 $|V| \times |V|$ 的二维数组存边，查"u 和 v 之间有没有边"是 $O(1)$，但空间是 $O(V^2)$，对稀疏图浪费严重。notebook 的依赖图通常很稀疏——每个 cell 只依赖少数几个 cell，边数 $|E|$ 远小于 $|V|^2$。邻接表空间 $O(V + E)$，查"u 的所有邻居"是 $O(\text{度数})$，正好匹配 marimo 的查询模式（总是要遍历某个 cell 的所有上下游，而不是查单条边是否存在）。所以邻接表是自然选择。打个数量级的比方：一本 100 个 cell 的 notebook，每个 cell 平均依赖 3 个变量，边数约 300，邻接表存几百条；邻接矩阵却要 $100 \times 100 = 10000$ 个格子，绝大多数是 0，纯浪费。

举个最小的例子：cell `c1` 定义 `x`，cell `c2` 引用 `x`，那么 $V = \{c1, c2\}$，$E = \{(c1, c2)\}$，`_downstream = {c1: {c2}}`，`_upstream = {c2: {c1}}`。如果再来一个 cell `c3` 也引用 `x`，就多一条边 $(c1, c3)$，`_downstream[c1]` 变成 $\{c2, c3\}$。一个 cell 可以扇出到多个消费者，也可以扇入多个生产者，图的结构完全由 `defs`/`refs` 的交集决定。注意一个 cell 不能同时由两个 cell 定义同一个变量——这会被 `DuplicateDefinitionError` 拦截，所以对每个被引用变量，它的定义者唯一，图不会出现"一个变量两个源头"的歧义边。这个唯一性是后续 `var_to_cell` 能做成单值映射的前提。从顶点的度数还能读出 cell 的角色：入度为 0 的是"源 cell"（不依赖任何 cell，通常是数据加载或常量定义），出度为 0 的是"汇 cell"（产出不被任何 cell 消费，通常是最终展示或写文件），既有入度又有出度的是"中间 cell"。源 cell 是执行的起点，Kahn 算法从它们开始摘；汇 cell 是执行的终点，通常承载用户最关心的最终结果。理解这三类角色的分布，能帮你快速把握一本 notebook 的数据流骨架。

## DAG

DAG 是 Directed Acyclic Graph 的缩写，即有向无环图。"无环"意味着不存在一条从某个顶点出发、经过若干条边又回到自身的路径。形式化地，图中不存在长度 $\ge 1$ 的路径 $v_0 \to v_1 \to \dots \to v_k = v_0$。环可以是自环（$v \to v$，长度 1）也可以是更长回路；DAG 三者皆禁。检测环是图论经典问题，方法有 DFS 染色（白灰黑三色标记）、Kahn 算法看拓扑序是否完整等，marimo 用后者因为它顺便产出执行序。

为什么 notebook 必须是 DAG？假设 cell A 依赖 cell B，cell B 又依赖 cell A：A 要先执行才能给 B 提供变量，B 又要先执行才能给 A 提供变量，两者互相等待，无法排出一个合理的执行顺序。这不仅是工程上的麻烦，而是逻辑上的矛盾——不存在任何一个全序能同时满足"A 在 B 前"和"B 在 A 前"。因此 marimo 在构建图之后会显式检测环，一旦发现就抛出 `CyclicDependencyError`，拒绝执行：

```python
class CyclicDependencyError(GraphError):
    pass
```

DAG 比一般有向图多了一个关键性质：它一定存在拓扑序（下一节证明），因此一定存在合法的执行顺序。这把"能不能跑"这个问题从运行时挪到了构建时——只要图是 DAG，执行引擎就永远不必担心"跑着跑着发现缺依赖"。线性脚本（传统 notebook 按 cell 出现顺序执行）相当于隐式假定了一个拓扑序，但那个序未必合法：用户可能把引用写在定义前面，传统 notebook 就会报 `NameError`。marimo 用 DAG 自动算出合法序，从根本上消除了这类错误。这是 reactive notebook 相对传统 notebook 的核心优势之一：执行顺序由依赖关系自动决定，而不是由 cell 在文件里的物理位置决定。

DAG 还天然支持增量计算：改了某个 cell，只需重跑它和它的后代（沿 `_downstream` 可达的顶点），其余 cell 的结果不变可以复用。如果图里有环，"后代"会把环上所有 cell 都包含进来，增量就退化成全量甚至无限循环，所以无环性也是增量执行正确性的前提。从偏序关系的角度看，DAG 的边定义了顶点集上的一个偏序 $\prec$（$u \prec v$ 当且仅当存在路径 $u \to^+ v$），拓扑序就是这个偏序的任意一个线性扩展。偏序允许有不可比较的元素（两个互不依赖的 cell 谁先跑都行），线性扩展就是给这些不可比较的对也指定一个顺序，使之成为全序。这个抽象很有用：后面讲拓扑排序的"多种合法序"就是同一个偏序的不同线性扩展。

DAG 的另一个有用性质：最长路径长度有限。因为无环，任何路径不会重复访问顶点，路径长度至多 $|V| - 1$。这保证了沿依赖链的传播（如 stale 标记的级联）一定会终止，不会无限往下传。在有环图里这条性质不成立，一条"路径"可以绕环无限走，这正是环导致增量计算不终止的图论根源。所以在 marimo 里，"无环"不只是为了能排出执行序，更是为了让"改一个 cell，影响有限传播后停下"这个增量语义成立。

这种"无环"不只是为了能排出执行序，更是为了让"改一个 cell，影响有限传播后停下"这个增量语义成立。从信息流的角度，DAG 把 notebook 变成了一个"数据流图"：每个 cell 是一个处理节点，边是数据通道，一次执行就是数据从源 cell 沿边流到汇 cell 的过程。改一个 cell 等于往它注入新数据，新数据沿边向下游传播，直到所有后代都更新。无环保证这个传播过程是单向的、有限的，不会回流震荡。这正是 reactive 编程范式（如 React 的数据流、Excel 的单元格依赖）的共同数学骨架：用 DAG 建模数据流，用拓扑序驱动计算，用传递闭包界定增量范围。

## 拓扑排序

拓扑排序（Topological Sort）是把 DAG 的所有顶点排成一个线性序列 $v_1, v_2, \dots, v_n$，使得对任意一条边 $(u, v)$，$u$ 都排在 $v$ 前面。这样的序列就是一个合法的执行顺序：每个 cell 执行时，它依赖的所有 cell 都已经执行过了。形式化地，拓扑序是一个双射 $\sigma: V \to \{1, \dots, n\}$，满足对所有 $(u, v) \in E$ 有 $\sigma(u) < \sigma(v)$。拓扑序不一定唯一，也不一定存在（有环图就没有）。

一个 DAG 可能有多种拓扑序。比如 $A \to B$、$A \to C$（B、C 互不依赖），那么 $[A, B, C]$ 和 $[A, C, B]$ 都是合法拓扑序。当且仅当图的偏序本身就是全序（即任意两个顶点都可比，图是一条链）时，拓扑序唯一。marimo 用 `sorted` 对同一入度层里的节点按 id 排序，保证每次得到同一个序列，从而让执行结果可复现——这一点在测试和协作场景里很重要，否则两次运行 cell 执行顺序不同，可能因为副作用（如写文件、打印、随机数）产生不同结果。可复现性是科学计算 notebook 的刚需，稳定拓扑序是满足它的基础设施之一。

`CellGraph.topological_order` 用的就是 Kahn 算法，核心代码如下：

```python
def topological_order(self) -> list[str]:
    in_degree = {
        cid: len(self._upstream.get(cid, set())) for cid in self._cells
    }
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set())):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    if len(order) != len(self._cells):
        remaining = set(self._cells) - set(order)
        raise CyclicDependencyError(
            f"检测到循环依赖，涉及 cell: {sorted(remaining)}"
        )
    return order
```

思路是反复"摘掉入度为 0 的顶点"：先统计每个顶点的入度（依赖了多少个 cell），把入度为 0 的全部放进队列——它们没有任何上游，可以最先执行。每次从队列取出一个顶点放进结果序列，并把它的所有出边删掉（即把每个后继的入度减一），若某个后继入度减到 0 就入队。重复直到队列为空。若结果序列长度等于顶点总数，说明全部摘完，得到拓扑序；若小于顶点总数，说明剩下的顶点入度永远降不到 0，它们处在环里——这就是环检测的判据。Kahn 算法的时间复杂度是 $O(V + E)$，每个顶点和每条边各处理一次。我们会在第 17 章更详细地拆解它的不变量。

除了 Kahn，还有一种基于 DFS 的拓扑排序：对每个未访问顶点做后序 DFS，最后把后序序列反转。两者都能得到合法拓扑序，但默认序不同。marimo 选 Kahn 是因为它天然按"入度层"产出，配合 `sorted` 容易做稳定排序；DFS 后序的稳定性取决于访问起点的选择，实现起来更绕。另外 Kahn 在检测环时能直接给出"哪些顶点在环里"（就是没被摘掉的 `remaining`），DFS 版需要额外记录递归栈才能定位环，工程上不如 Kahn 直接。Kahn 还有一个好处：它产出的序按"依赖层"分组，同一层的顶点互不依赖，天然适合并行执行——虽然教学版 marimo 是串行的，但生产级系统可以利用这个分层做并行调度。逆拓扑序（把拓扑序反转）则对应"从下游往上游"的顺序，用于 stale 标记的传播：从被改的 cell 出发，沿逆拓扑序往前标记，能保证标记一个 cell 时它的所有下游都已标记完，便于级联失效的批量处理。所以同一个 Kahn 算法，正跑给执行序，反跑给失效序，一体两面。

## cell 间依赖为什么构成 DAG

从语义上看，每个 cell 显式声明了自己定义的变量（`defs`）和引用的变量（`refs`）。这两组集合由 `ast_analyzer.analyze_cell` 静态分析得到，不运行代码：

```python
def analyze_cell(code: str) -> tuple[set[str], set[str]]:
    if not code.strip():
        return set(), set()
    tree = ast.parse(code)
    defs = _extract_top_level_defs(tree)
    refs = _extract_refs(tree, defs)
    return defs, refs
```

`defs` 收集顶层赋值、函数定义、类定义、导入等绑定的名字；`refs` 收集所有 `Load` 上下文的 `Name` 节点，再减去 cell 内部局部变量和内置名（`builtins`）。边的产生规则是：若 cell B 的 `refs` 里有变量 $x$，而 cell A 的 `defs` 里有 $x$，则连一条 $A \to B$。用集合记号，对任意两个不同 cell $A, B$，若 $\text{defs}(A) \cap \text{refs}(B) \ne \emptyset$，则 $A \to B \in E$。这条规则只依赖静态分析得到的符号集合，不依赖运行时值。静态分析的好处是快且安全：不用真跑代码就能知道依赖，避免了"跑一半才报错"的风险，也避免了动态分析里运行时副作用污染依赖判断的问题。

看一个完整例子。假设有三个 cell：

```python
c1:  import numpy as np          # defs={np},        refs={}
c2:  x = np.arange(10)           # defs={x},        refs={np}
c3:  y = x.sum()                 # defs={y},        refs={x}
```

分析边：`c2.refs` 有 `np`，`c1.defs` 有 `np`，连 $c1 \to c2$；`c3.refs` 有 `x`，`c2.defs` 有 `x`，连 $c2 \to c3$；`c3.refs` 里的 `sum` 是属性访问不产生 `Name` 节点，`x` 已处理。最终 $E = \{(c1, c2), (c2, c3)\}$，是一条链，显然无环。拓扑序唯一为 $[c1, c2, c3]$，正是数据流要求的执行顺序。

再看一个有分叉的例子：

```python
c1:  a = 1                      # defs={a}, refs={}
c2:  b = 2                      # defs={b}, refs={}
c3:  c = a + b                  # defs={c}, refs={a, b}
```

边：$c1 \to c3$（a）、$c2 \to c3$（b）。c1、c2 互不依赖，可任意序；c3 必须最后。合法拓扑序有 $[c1, c2, c3]$ 和 $[c2, c1, c3]$ 两种，marimo 按 id 排序选前者。这展示了 DAG 比线性脚本强的地方：传统 notebook 要求 c1、c2、c3 按物理排列顺序执行，若用户把 c3 放在 c1 前面就会报错；marimo 自动算出 c3 最后跑，用户怎么排列 cell 都行。这种"执行顺序与物理排列解耦"是 reactive notebook 交互体验的基础——用户可以随意拖动 cell 组织叙述逻辑，不必担心执行顺序。

只要用户不写出循环引用（这通常意味着逻辑矛盾），自然得到一张 DAG。即便用户不小心造出环，`_rebuild` 之后的拓扑排序也会立即报错，把问题挡在执行之前。这就是 marimo 用图来组织 cell 的根本原因：把"执行顺序"这个原本隐式、易错的问题，转化成一个有明确算法解的图论问题。传统 notebook 把执行顺序交给用户手动维护（靠 cell 排列顺序和手动重跑），marimo 把它交给 Kahn 算法自动计算——用户只负责写每个 cell 的逻辑，依赖和顺序由图来管。这种分工让用户的心智负担大幅降低，也消除了"忘了重跑上游 cell 导致下游用旧值"这类传统 notebook 最常见的隐患。传统 notebook 里，用户改了一个 cell 后必须手动从该 cell 起往下逐个重跑，漏跑一个就用旧值，多跑一个浪费时间，全靠人肉记忆维护一致性，notebook 一长就极易出错。marimo 用 DAG 把这个负担接管：改了哪个 cell，图自动算出该重跑哪些，按拓扑序自动执行，用户只管改，剩下交给图。这就是"reactive"一词的字面含义——系统对变化自动做出正确反应，而支撑这个自动反应的数学骨架就是 DAG。

## 小结

这一章建立了词汇表：有向图 $(V, E)$、DAG、拓扑排序，以及它们在 marimo 里的对应物——`_cells`/`_downstream`/`_upstream`、无环性、`topological_order`。核心要点是：notebook 是一张以 cell 为顶点、以变量定义-引用关系为边的有向图，且必须是 DAG 才能谈执行顺序；DAG 保证拓扑序存在、最长路径有限、增量计算终止。后续四章都在这张图上做文章：第 13 章讲怎么从 cell 集合把图建出来，第 14 章讲怎么检测环，第 15 章讲怎么查祖先/后代，第 16 章讲怎么把图画出来辅助调试。把这些图论基础记牢，后面读源码时每个方法的作用就能一眼看穿——`_rebuild` 是建图，`topological_order` 是求线性扩展，`descendants` 是求传递闭包，全是这章定义的概念的直接实现。把这些基础内化后，后续读 `_rebuild`、`topological_order`、`descendants` 的源码时，你看到的不再是一堆字典和循环操作，而是"建图、求线性扩展、求传递闭包"这些图论意图的直接落地，代码的意义不言自明。
