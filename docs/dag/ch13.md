# 从 cell 构建 DAG

`CellGraph` 是 marimo 后端管理依赖关系的核心数据结构。它不执行任何代码，只负责维护"有哪些 cell、它们之间谁依赖谁"，并对外提供查询接口。构建图的关键方法是 `_rebuild`，每当 cell 集合或某个 cell 的 `defs`/`refs` 发生变化时，它都会被调用，把整张图从头重建一次。教学版采用全量重建，实现简单且不易出错；生产版 marimo 做了增量优化，但语义一致。

## 第一步：构建 var_to_cell 映射

`_rebuild` 首先遍历所有 cell，收集每个被定义的变量到定义它的 cell 的映射：

```python
var_to_cell: dict[str, CellId] = {}
for cell in self._cells.values():
    for var in cell.defs:
        if var in var_to_cell:
            raise DuplicateDefinitionError(var)
        var_to_cell[var] = cell.cell_id
```

如果同一个变量被两个 cell 定义，就抛出 `DuplicateDefinitionError`。为什么要禁止？因为执行时该变量到底取哪个 cell 的值取决于执行顺序，结果不可预测，属于用户应当显式解决的冲突。这一步同时完成了"去重检查"和"建立反向索引"两件事：之后给定一个被引用的变量名，就能 $O(1)$ 查到它的定义者。

## 第二步：根据 defs∩refs 构建边

有了 `var_to_cell`，就可以连边。规则是：对每个 cell B，看它引用的每个变量 $x$，若 $x$ 在 `var_to_cell` 中对应 cell A，则连一条 $A \to B$。

```python
self._edges.clear()
for b in self._cells.values():
    for var in b.refs:
        if var in var_to_cell:
            a = var_to_cell[var]
            if a != b.cell_id:
                self._edges.add((a, b.cell_id))
```

边的方向是"定义者→引用者"，与数据流方向一致。若一个 cell 同时定义并引用同名变量（如 `x = x + 1`），`a == b` 的情况会被跳过，不画自环。未被任何 cell 定义的引用（比如 `import` 进来的模块、内置函数）不会产生边，这是合理的——它们不构成 cell 间依赖。

## _rebuild 的整体流程

一次完整的 `_rebuild` 做三件事：清空旧边、构建 `var_to_cell`（含重复定义检查）、按 `defs∩refs` 填新边。之后 `predecessors`/`successors` 直接查 `_edges`，`descendants`/`ancestors` 在 `_edges` 上做 BFS，`topological_order` 在 `_edges` 上跑 Kahn 算法。所有查询都基于这一次重建出的静态结构，直到下一次 cell 内容变更才再次重建。这种"重建便宜、查询频繁"的取舍，使得上层执行引擎可以放心地反复问"这个 cell 的后代是谁""整张图的拓扑序是什么"，而不必担心一致性。
