# 从 cell 构建 DAG

`CellGraph` 是 marimo 后端管理依赖关系的核心数据结构。它不执行任何代码，只负责维护"有哪些 cell、它们之间谁依赖谁"，并对外提供查询接口。构建图的关键方法是 `_rebuild`，每当 cell 集合或某个 cell 的 `defs`/`refs` 发生变化时，它都会被调用，把整张图从头重建一次。教学版采用全量重建，实现简单且不易出错；生产版 marimo 做了增量优化，但语义一致。这一章逐步拆解 `_rebuild` 的三个阶段，并用完整例子走一遍，让你清楚每条边是怎么从代码里长出来的。建图是整个 reactive 系统的起点：图建错了，后面所有执行决策全错，所以这一步的正确性至关重要。

`_rebuild` 由 `add_cell` 和 `remove_cell` 触发，这两个是外部修改图的唯一入口：

```python
def add_cell(self, cell: Cell) -> None:
    if cell.cell_id in self._cells:
        raise GraphError(f"cell '{cell.cell_id}' 已存在")
    self._cells[cell.cell_id] = cell
    self._rebuild()

def remove_cell(self, cell_id: str) -> None:
    if cell_id not in self._cells:
        raise GraphError(f"cell '{cell_id}' 不存在")
    del self._cells[cell_id]
    self._rebuild()
```

注意每次增删都立即 `_rebuild`，保证图永远反映当前 cell 集合的真实依赖。这意味着图不会有"脏"状态——任何时刻拿到的 `_downstream`/`_upstream` 都和 `_cells` 里的 `defs`/`refs` 完全一致。代价是每次增删都 $O(V \cdot \bar{d})$（$\bar{d}$ 是平均每个 cell 的符号数），对教学规模完全可接受。生产版会做差分：只重算受影响 cell 的边，避免整图重建，但需要小心维护增量一致性，复杂度高。教学版选全量重建正是为了把"图永远正确"这个不变量放在首位，让后续查询逻辑可以放心假设图是最新的。全量重建还有一个隐性好处：没有增量更新带来的"忘了清某条旧边"的 bug 类，调试时图的状态完全由当前 cell 集合决定，可预测性强。增量重建虽然快，但要维护"哪些边受影响、哪些不变"的簿记，一旦簿记有漏，图就悄悄错了，而且这种错很难复现和定位。教学版宁可慢一点也要全量，把正确性放在第一位，等理解透了再优化。这也是教学代码的普遍取舍：先写显然正确的版本，再在保持接口不变的前提下优化内部实现。

从调用频率看，`_rebuild` 在一次编辑会话里可能被调几十次（每次增删 cell），但每次重建后会有大量查询（执行引擎一次增量执行就要查几十次后代和拓扑序）。所以重建成本被查询次数摊薄，全量重建的 $O(V \cdot \bar{d})$ 相对查询带来的 $O(V+E)$ 节省并不显著。只有当 notebook 极大（几千 cell）且编辑极频繁时，增量重建才有明显收益，教学规模下全量重建完全够用。换句话说，全量重建的"慢"是理论上的，实际在几百 cell 的规模下耗时不到一毫秒，用户根本感知不到，优化它属于过早优化。

还要理解 `Cell` 数据结构本身。一个 cell 携带静态信息（`code`、`defs`、`refs`）和运行时状态（`status`、`output`、`namespace` 等），`_rebuild` 只读静态部分：

```python
@dataclass
class Cell:
    cell_id: str
    code: str
    defs: set[str] = field(default_factory=set)
    refs: set[str] = field(default_factory=set)
    status: CellStatus = CellStatus.IDLE
    output: Any = None
    ...
```

`defs`/`refs` 由 `ast_analyzer.analyze_cell` 在 cell 创建时填好，`_rebuild` 直接拿来用，不再重新分析代码。所以建图成本只含集合运算，不含 AST 解析——AST 解析在更早的 cell 构造阶段就完成了。这种分层让 `CellGraph` 的职责很纯粹：它只管图论，不管语法。`CellStatus` 有 IDLE/PENDING/RUNNING/DONE/ERROR/STALE 六种状态，但建图阶段完全不看状态，只看 `defs`/`refs` 这两个静态集合。即使一个 cell 处于 ERROR（代码有语法错误），只要它的 `defs`/`refs` 被填了（可能填成空集），图里照样有它的顶点，只是没有边连进连出。这种"静态与运行时分离"是 reactive 系统的重要设计原则：依赖图由静态分析决定，不随运行时状态变化，这样图的结构在一次执行内是稳定的，查询结果可缓存、可复现。如果依赖关系依赖运行时值（比如根据某个变量决定引用谁），就退化成动态依赖，静态分析无能为力，marimo 教学版不支持这种场景。

理解了 `Cell` 的静态/运行时分层，就能明白为什么 `_rebuild` 只读 `defs`/`refs` 而不读 `code`：`code` 是源码字符串，`defs`/`refs` 是从 `code` 里提炼出的符号集合，提炼工作由 `ast_analyzer` 在更早阶段完成。`CellGraph` 拿到的已经是"消化过"的符号，不必再 parse 一次。这种流水线（源码 → AST → 符号集合 → 图）让每层职责单一，也方便单独测试：可以不写真实代码，直接构造一个 `Cell(defs={'x'}, refs={'y'})` 来测图的构建逻辑，绕开 AST 分析的复杂性。

## 第一步：构建 var_to_cell 映射

`_rebuild` 首先把两张邻接表清空，然后遍历所有 cell，收集每个被定义的变量到定义它的 cell 的映射：

```python
def _rebuild(self) -> None:
    self._downstream = defaultdict(set)
    self._upstream = defaultdict(set)

    var_to_cell: dict[str, str] = {}
    for cell_id, cell in self._cells.items():
        for var in cell.defs:
            if var in var_to_cell:
                raise DuplicateDefinitionError(
                    f"变量 '{var}' 同时定义于 cell "
                    f"'{var_to_cell[var]}' 和 '{cell_id}'"
                )
            var_to_cell[var] = cell_id
```

`var_to_cell` 是一个反向索引：键是变量名，值是定义它的 cell id。如果同一个变量被两个 cell 定义，就抛出 `DuplicateDefinitionError`。为什么要禁止？因为执行时该变量到底取哪个 cell 的值取决于执行顺序，结果不可预测，属于用户应当显式解决的冲突。比如 `c1: x = 1` 和 `c2: x = 2`，下游 `c3: print(x)` 到底打印 1 还是 2 取决于 c1、c2 谁后执行——这种歧义 marimo 直接在构建期拒绝，逼用户重命名或合并。这和编程语言里"同一作用域重复定义"的处理思路一致：要么覆盖（命令式），要么报错（函数式），marimo 选报错，因为 reactive 语义下覆盖会导致隐式状态突变，违背"显式优于隐式"。

这一步同时完成了"去重检查"和"建立反向索引"两件事：之后给定一个被引用的变量名，就能 $O(1)$ 查到它的定义者。`var_to_cell` 只在 `_rebuild` 内部存活，不作为成员保留，因为它的职责就是辅助第二步连边，连完即可丢弃。注意它只收集 `defs` 里的名字，`refs` 里引用了但无人定义的变量（如 `import` 进来的模块、内置函数）不会出现在 `var_to_cell` 中，自然也不会产生边——这是合理的，它们不构成 cell 间依赖。清空邻接表用重新赋值 `defaultdict(set)` 而非 `.clear()`，是为了让旧的 `defaultdict` 对象可被垃圾回收，避免持有旧引用的角落。

为什么用反向索引而不是每次连边时遍历所有 cell 找定义者？因为连边阶段要对每个 cell 的每个引用变量查一次定义者，若每次线性扫所有 cell 的 `defs`，总成本是 $O(V \cdot \bar{r} \cdot V \cdot \bar{d})$，平方级。有了 `var_to_cell` 这个哈希索引，每次查询降到 $O(1)$，总成本 $O(V \cdot \bar{r})$，线性级。这是经典的"空间换时间"：先用一轮扫描建索引，再用索引加速后续大量查询。这种模式在编译器符号表、数据库索引里到处都是，`var_to_cell` 就是 notebook 依赖图的"符号表"。从正确性角度，`var_to_cell` 的构建是幂等的：给定同一组 cell，无论遍历顺序如何，得到的 `var_to_cell` 内容一样（除了触发 `DuplicateDefinitionError` 的先后）。但报错消息里"先定义的"和"后定义的"取决于迭代顺序，这只影响消息措辞，不影响检测本身——总会报错，用户总能看到两个冲突的 cell id。

## 第二步：根据 defs∩refs 构建边

有了 `var_to_cell`，就可以连边。规则是：对每个 cell B，看它引用的每个变量 $x$，若 $x$ 在 `var_to_cell` 中对应 cell A，则连一条 $A \to B$。源码里这条边要同时登记到两张邻接表：

```python
    for cell_id, cell in self._cells.items():
        for var in cell.refs:
            upstream_id = var_to_cell.get(var)
            if upstream_id is not None and upstream_id != cell_id:
                self._downstream[upstream_id].add(cell_id)
                self._upstream[cell_id].add(upstream_id)
```

`upstream_id is not None` 过滤掉无人定义的引用（内置函数、外部模块），`upstream_id != cell_id` 跳过自环。边登记两次：`_downstream[A].add(B)` 记录"A 的下游有 B"，`_upstream[B].add(A)` 记录"B 的上游有 A"。这种双向登记让 `predecessors` 和 `successors` 都能 $O(1)$ 直接返回，不必遍历边集。冗余存储的代价是空间翻倍，但图本身很小，这点空间完全可忽略，换来的是所有方向查询都常数时间。用 `.get(var)` 而非 `[var]` 是为了优雅处理"引用了无人定义的变量"——返回 None 就跳过，不抛 KeyError。

若一个 cell 同时定义并引用同名变量（如 `x = x + 1`），`a == b` 的情况会被跳过，不画自环。为什么不画自环？因为自环会让该 cell 在拓扑排序里入度永远不为 0（自己依赖自己），被误判成环。而语义上 `x = x + 1` 里的右侧 `x` 是引用"上一次执行的本 cell 的 x"，属于 cell 内部状态，不是跨 cell 依赖，所以不该产生边。未被任何 cell 定义的引用（比如 `import` 进来的模块、内置函数 `print`/`range`）不会产生边，这是合理的——它们不构成 cell 间依赖。这种"自环跳过、外部引用跳过"的过滤让图只反映真正的跨 cell 数据流，干净且语义明确。从工程角度，这两个过滤条件是 `_rebuild` 里最容易被忽略的细节，但少了任何一个都会出问题：漏掉 `is not None` 会对着 `None` 建边报错；漏掉 `!= cell_id` 会把 `x = x + 1` 误判成环。所以理解这两个过滤的语义，是读懂连边循环的关键。调试时若发现"明明没有跨 cell 依赖却多了一条边"或"自更新 cell 被报循环依赖"，首先查的就是这两个条件有没有写对。还要注意一个细节：一个 cell 的 `refs` 里同一个变量可能出现多次（比如 `x + x`），但 `refs` 是 `set`，重复自动去重，所以对同一个上游 cell 只连一条边，不会重复添加。同理 `defs` 也是集合，一个 cell 里 `x = 1; x = 2` 两次定义 `x` 只产生一个 `defs` 条目（取最后一次绑定，这是 Python 语义），不会触发 `DuplicateDefinitionError`——那个错误针对的是跨 cell 的同名定义，不是单 cell 内的重新赋值。区分"单 cell 内重赋值"（合法）和"跨 cell 同名定义"（非法）是理解 `var_to_cell` 去重检查的关键。从用户视角，`DuplicateDefinitionError` 的报错时机值得留意：它在 `_rebuild` 里抛出，而 `_rebuild` 在 `add_cell` 末尾调用，所以是"添加第二个同名定义 cell 的瞬间"报错，而非"添加第一个"时。也就是说，第一个定义 `x` 的 cell 能正常加入，加第二个时才报错。这符合直觉——单独一个定义 `x` 的 cell 没问题，问题出在"第二个也想定义 x"。报错消息里会列出两个 cell id，用户删掉或重命名其中一个即可。注意删掉后要重新 `_rebuild`（`remove_cell` 会自动触发），图才恢复一致。从实现细节看，`_rebuild` 里 `var_to_cell` 用普通 `dict` 而非 `defaultdict`，因为它的写入路径是显式的 `var_to_cell[var] = cell_id`，不需要默认值工厂；而 `_downstream`/`_upstream` 用 `defaultdict(set)` 是因为连边时可能首次访问某个键，需要自动初始化空集再 `add`。这种"按写入模式选字典类型"的细节体现了对数据流量的考量：读多写少的用普通 dict，写时可能首次触达的用 defaultdict。理解这些选择能帮你写出更地道的 Python 图代码。从整体看，`_rebuild` 虽然只有十几行，却浓缩了"建符号表、查重、连边、双向登记"四个语义动作，每行都有明确职责。读这十几行时，建议按"先看两个 for 循环的职责（建索引、连边），再看每个 if 的过滤条件（去重、跳空、跳自环），最后看数据结构选择（dict vs defaultdict）"的层次来读，能把紧凑的代码拆成清晰的心智模型。这种"分层读紧凑代码"的能力，是读源码的核心技能，`_rebuild` 是个很好的练习对象。从源码风格看，`_rebuild` 用下划线前缀表示是内部方法，外部只该调 `add_cell`/`remove_cell`，这种命名约定把"何时重建"的控制权收在类内部，防止外部在不当时机调用导致图状态错乱。这种"封装重建时机"是类设计的基本功，`_rebuild` 的下划线正是这道封装的标记。

看一个完整建图过程。三个 cell：

```python
c1:  import numpy as np      # defs={np}, refs={}
c2:  x = np.arange(10)       # defs={x}, refs={np}
c3:  y = x.sum()             # defs={y}, refs={x}
```

第一步 `var_to_cell = {np: c1, x: c2, y: c3}`。第二步：c1.refs 为空不连边；c2.refs 有 `np`，`var_to_cell[np]=c1`，连 $c1 \to c2$，`_downstream={c1:{c2}}`、`_upstream={c2:{c1}}`；c3.refs 有 `x`，`var_to_cell[x]=c2`，连 $c2 \to c3$，`_downstream={c1:{c2}, c2:{c3}}`、`_upstream={c2:{c1}, c3:{c2}}`。最终是一条链 $c1 \to c2 \to c3$，无环，拓扑序 $[c1, c2, c3]$。

再看一个有菱形依赖的例子：

```python
c1:  base = 10              # defs={base}, refs={}
c2:  a = base * 2           # defs={a},    refs={base}
c3:  b = base * 3           # defs={b},    refs={base}
c4:  total = a + b          # defs={total}, refs={a, b}
```

第一步 `var_to_cell = {base: c1, a: c2, b: c3, total: c4}`。第二步：c2 连 $c1 \to c2$；c3 连 $c1 \to c3$；c4 的 refs 有 a、b，连 $c2 \to c4$ 和 $c3 \to c4$。最终 `_downstream = {c1:{c2,c3}, c2:{c4}, c3:{c4}}`，是一个菱形：c1 扇出到 c2、c3，两者再汇入 c4。注意 c4 不会因为两条路径都能从 c1 到达而产生重复边——边是集合，`add` 自动去重，且 `_downstream`/`_upstream` 的值都是 `set`。菱形依赖在增量执行里很重要：改了 c1，c2、c3、c4 都要重跑，但 c4 只重跑一次，不会因为有两个上游而跑两次。这个"去重"是集合语义的自然结果，不需要额外代码处理。

再看一个涉及外部引用和自环的例子，体会过滤规则：

```python
c1:  import math            # defs={math}, refs={}
c2:  x = math.pi            # defs={x},    refs={math}
c3:  x = x + 1              # defs={x},    refs={x}  (自环，跳过)
c4:  print(math.floor(x))   # defs=set(),  refs={math, x}
```

第一步 `var_to_cell = {math: c1, x: c3}`（注意 c2 也定义 x，会触发 `DuplicateDefinitionError`！这里假设只有 c3 定义 x，c2 改成别的名字）。边：c2 连 $c1 \to c2$（math）；c3 的 refs 有 x，`var_to_cell[x]=c3`，但 `upstream_id == cell_id` 跳过自环；c4 的 refs 有 math、x，连 $c1 \to c4$（math）和 $c3 \to c4$（x）。最终 c3 没有入边（自环跳过），c4 有两个上游 c1、c3。这个例子展示了自环跳过和外部引用（math 由 c1 定义，是 cell 间依赖，不是外部）的区别——`math` 虽是 import 来的，但 import 在 c1 里，所以是 cell 间依赖；真正的"外部"是 `print`、`floor` 这类内置/属性，不产生 `Name` 节点或被 `_BUILTIN_NAMES` 过滤。

## _rebuild 的整体流程

一次完整的 `_rebuild` 做三件事：清空旧的两张邻接表、构建 `var_to_cell`（含重复定义检查）、按 `defs∩refs` 填新边到 `_downstream`/`_upstream`。之后 `predecessors`/`successors` 直接查邻接表，`descendants`/`ancestors` 在邻接表上做 BFS，`topological_order` 在邻接表上跑 Kahn 算法。所有查询都基于这一次重建出的静态结构，直到下一次 cell 内容变更才再次重建。

```python
def predecessors(self, cell_id: str) -> set[str]:
    return set(self._upstream.get(cell_id, set()))

def successors(self, cell_id: str) -> set[str]:
    return set(self._downstream.get(cell_id, set()))
```

注意它们返回的是 `set(...)` 拷贝，防止调用方修改内部结构。这种"重建便宜、查询频繁"的取舍，使得上层执行引擎可以放心地反复问"这个 cell 的后代是谁""整张图的拓扑序是什么"，而不必担心一致性。重建虽然每次全量，但只扫两轮 cell（一轮建 `var_to_cell`，一轮连边），常数很小；查询则全是基于已建好的邻接表，`predecessors`/`successors` 是 $O(1)$ 字典查找，`descendants`/`ancestors` 是 $O(V+E)$ 的 BFS，`topological_order` 是 $O(V+E)$ 的 Kahn。把昂贵的重建集中在写时（增删 cell），让读时（查询）尽量便宜，是这类依赖图数据结构的常见设计。这种"写少读多"的访问模式在 reactive 系统里特别明显：用户偶尔增删改 cell，但执行引擎一次增量执行就要查几十次后代和拓扑序。

还要注意 `_rebuild` 不检测环——环检测推迟到 `topological_order` 调用时才发生。这意味着你可以构建出一个"带环的图"对象而不立即报错，只有当有人请求拓扑序（通常是要执行）时才抛 `CyclicDependencyError`。这种惰性检测让"编辑中"的中间状态可以暂时有环，只有真正要执行时才强制无环，对交互式编辑更友好。设想用户正在把一段长代码拆成几个 cell，拆到一半时依赖关系暂时成环是正常的，若每次 `_rebuild` 都立刻报错会严重打断编辑流程；把检测推迟到运行时，用户就能从容地完成重构再点运行。惰性检测是"编辑态"和"运行态"分离的体现：编辑时宽容，运行时严格。

最后提一个教学版简化：`_rebuild` 不处理 cell 代码变更（只处理增删整个 cell）。真实场景里用户改了 cell 代码后，`defs`/`refs` 会变，需要重新 `analyze_cell` 并触发 `_rebuild`。教学版把这个职责放在外层（调用方改完 cell 后手动调一次 `_rebuild` 或重新 add），保持 `CellGraph` 接口最小。生产版会有 `update_cell` 方法封装"改代码→重新分析→重建"的完整流程。理解了这个分层，就知道为什么 `_rebuild` 只依赖 `cell.defs`/`cell.refs` 而不自己调 `analyze_cell`——职责分离。从测试角度，`_rebuild` 的全量重建特性让它很好测：构造一组 cell，调一次 `add_cell`/`remove_cell`，断言 `_downstream`/`_upstream` 等于预期。因为重建是全量的，不必担心"前一次重建的残留影响本次"，每次测试都是干净起点。这种"无状态重建"的可测性是全量重建的又一隐性收益——增量重建要测"连续多次增删后的图状态"，测试用例更难构造，因为状态依赖调用历史。教学版选全量重建，连测试都变简单了，这对教学项目尤为重要：学生写测试时不必模拟复杂的调用序列，一次 add 就能验证整张图。
