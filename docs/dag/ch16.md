# DAG 可视化与调试

依赖图出问题时，最有效的排查手段往往是"把图画出来看一眼"。`CellGraph` 虽然没有内置图形渲染，但它暴露了足够多的原始数据，让上层可以方便地打印、导出或可视化。这一章介绍如何用这些原始数据排查常见的依赖问题。所有调试都基于 `_cells`、`_downstream`、`_upstream` 这三个内部结构，以及 `predecessors`/`successors`/`descendants`/`ancestors` 这些查询方法。掌握这些手法，遇到"改了 cell 没反应""报了环不知道在哪""cell 一直 STALE"等问题时就能快速定位。调试依赖问题的总思路是：从图的"地面真相"（边集合）开始查，确认边对了再查派生查询（后代、拓扑序），自底向上缩小范围。

## 边列表

`_downstream` 是一个 `dict[str, set[str]]`，键是 cell id，值是它直接指向的 cell id 集合；每条隐含的边 $(a, b)$ 满足 $b \in \text{\_downstream}[a]$。最直接的调试方式就是把所有边打印出来：

```python
for a, succs in graph._downstream.items():
    for b in succs:
        print(f"{a} -> {b}")
```

或者等价地用 `_upstream` 反向遍历。看到边就能判断依赖是否符合预期。比如你期望 cell `c1` 定义 `x`、cell `c2` 引用 `x`，那么应当存在边 `(c1, c2)`，即 `c2 in graph._downstream[c1]`；如果没有，多半是 `c2` 的 `refs` 没正确提取出 `x`（静态分析漏了），或者 `c1` 的 `defs` 没包含 `x`。反过来，如果出现了意料之外的边，说明某个 cell 的 `refs`/`defs` 被多识别了符号，需要回去检查 `ast_analyzer` 的符号提取逻辑。

举一个对照预期与实际的例子。三个 cell：

```python
c1:  data = [1, 2, 3]      # defs={data}, refs={}
c2:  total = sum(data)     # defs={total}, refs={data}  (sum 是内置，被过滤)
c3:  avg = total / len(data)  # defs={avg}, refs={total, data}
```

预期边：`c1 -> c2`（data）、`c1 -> c3`（data）、`c2 -> c3`（total）。打印 `_downstream` 应得到 `{c1: {c2, c3}, c2: {c3}}`。若实际打印出 `{c1: {c2, c3}, c2: {c3}, c3: {c1}}`，多了一条 `c3 -> c1`，说明 c3 的 `refs` 误把某个 c1 定义的符号识别进去了，或 c1 的 `defs` 多收了符号——这时回去查 `analyze_cell` 对每个 cell 的输出。边的集合是图的"地面真相"，所有高级查询都从它派生，所以从边开始查是最可靠的入口。建议把"打印边列表"作为调试依赖问题的第一步，确认了边集正确再去查更复杂的查询逻辑。打印时按 cell id 排序输出更易读，避免字典插入顺序干扰判断。还可以把每个 cell 的 `defs`/`refs` 一起打印，形成"cell → 定义了什么 → 引用了什么 → 连出哪些边"的完整画像，这样漏依赖和多依赖一眼可见：如果 B 引用了 x 但边里没有 B 的上游定义 x，就是漏依赖；如果 B 没引用 y 却连出了依赖 y 的边，就是多依赖。把静态符号和动态边并排对照，是定位符号提取 bug 的最快路径。还可以写一个断言函数自动检查"每个 cell 的每条出边都对应一个真实被引用的变量"，在测试里调用，把人工对照自动化：对每条边 $(a, b)$，检查是否存在变量 $x \in \text{defs}(a) \cap \text{refs}(b)$，若不存在说明这条边来历不明，是 bug。这种"边可解释性检查"能在 CI 里及早发现建图逻辑错误，比人工打印排查更可靠。进一步还可以检查"每个被引用的变量都有定义者或属于外部"：对每个 cell 的每个 ref，要么在某个 cell 的 defs 里，要么属于内置/外部，否则就是"引用了未定义变量"，虽然不一定是图 bug，但可能是用户笔误或 cell 顺序问题。把这两类检查做成测试夹具，能在每次改 `ast_analyzer` 或 `_rebuild` 后自动验证建图一致性，防止回归。

## 打印每个 cell 的直接邻居

除了原始边，按 cell 维度打印上下游更易读：

```python
for cid in graph._cells:
    preds = graph.predecessors(cid)
    succs = graph.successors(cid)
    print(f"{cid}:  preds={sorted(preds)}  succs={sorted(succs)}")
```

对前面三个 cell，输出大致是：

```
c1:  preds=[]  succs=['c2', 'c3']
c2:  preds=['c1']  succs=['c3']
c3:  preds=['c1', 'c2']  succs=[]
```

这种视图能快速定位几类典型 cell。"孤岛 cell"：`preds` 和 `succs` 都为空，通常是纯展示（只输出不依赖任何 cell 变量，如 `print("hello")`）或出错的 cell（代码有语法错误，`defs`/`refs` 都空）。"扇出大户"：`succs` 很长，一个 cell 被很多 cell 依赖，改它影响面大，修改时要格外谨慎，最好先跑 `descendants` 看全貌。"扇入大户"：`preds` 很长，一个 cell 依赖很多 cell，容易因上游任一出错而 STALE，排查它的错误时要从 `ancestors` 里逐个查谁出了问题。配合 `descendants`/`ancestors` 还能看传递影响：

```python
print("c1 的全部后代:", sorted(graph.descendants("c1")))
print("c3 的全部祖先:", sorted(graph.ancestors("c3")))
```

对上面例子，`descendants(c1) = {c2, c3}`（改 c1 要重跑 c2、c3），`ancestors(c3) = {c1, c2}`（c3 的所有输入来源）。这两个传递闭包比直接邻居更能反映真实影响范围，是判断"改动成本"的依据。比如要重构 c1，先看 `descendants(c1)` 有多大——若只波及一两个 cell，放心改；若波及几十个，就要谨慎，可能要分步迁移，每步验证下游输出不变。这种"先看影响面再动手"的习惯能避免改一个 cell 导致整本 notebook 雪崩。还可以把直接邻居和传递闭包的差值打印出来，看"哪些是间接依赖"：`descendants(c) - successors(c)` 给出 c 的非直接后代，即隔了至少两层的下游。这个差值在调试"为什么改了 c，隔了好几层的某个 cell 也重跑了"时很有用——确认它是 c 的间接后代而非误连边。同理 `ancestors(c) - predecessors(c)` 给出间接祖先。把这些集合差异打印出来，能把"直接依赖"和"传递依赖"分层展示，理解链路更深的问题。从输出格式看，按 cell id 排序能让同一 notebook 的两次打印结果一致，便于 diff 对比——改了一个 cell 后重新打印，diff 出来的就是这次改动对图的影响，聚焦变化部分而非全图重看。调试时养成"改前打印一次、改后打印一次、diff 看变化"的习惯，能精确锁定每次改动对依赖图的影响范围，比一次性看全图更高效。这和版本控制 diff 的思路一致：关注变化而非全量。

## 调试依赖问题

常见问题有几类，每类有对应的排查路径。掌握这个分类能让你遇到问题时快速对号入座，而不是盲目打印。

第一类是**漏依赖**：cell B 明明用了变量 `x`，却没连边，导致改了定义 `x` 的 cell A 后 B 没重跑，结果陈旧。排查时先打印 B 的 `refs`，确认 `x` 是否在里头；若不在，问题在 `ast_analyzer._extract_refs`——可能 `x` 出现在属性访问、字符串、或被 `internal_locals` 误减。再打印 `var_to_cell`（在 `_rebuild` 里临时加日志），确认 `x` 是否被某个 cell 定义；若没有，可能定义 `x` 的 cell 的 `defs` 漏了。漏依赖的典型症状是"改了上游 cell，下游 cell 输出没变"，用户会感到 notebook"不 reactive 了"。这是最危险的 bug，因为它静默地给出错误结果而不报错，用户可能基于陈旧结果继续推导，错上加错。

第二类是**多依赖**：出现了不该有的边，通常是 `refs` 把属性访问的目标、字符串里的名字、或内置名也当成了引用。比如 `obj.method` 里 `method` 不是 `Name` 节点不会被收，但若代码写成 `getattr(obj, "method")`，字符串 `"method"` 也不会被收——正常。可若 `refs` 里出现了 `print`、`len` 这类内置名，说明 `_BUILTIN_NAMES` 过滤失效。排查时打印出问题 cell 的 `refs`，逐个核对每个名字是否真的是跨 cell 依赖。多依赖的典型症状是"改了无关 cell，这个 cell 也被重跑了"，浪费算力。它不会导致错误结果（多跑只是多算一次），但会让增量执行退化成接近全量，失去 reactive 的效率优势。

第三类是**环**：`topological_order` 抛 `CyclicDependencyError` 时会带上 `remaining` 里的 cell id：

```python
try:
    order = graph.topological_order()
except CyclicDependencyError as e:
    print(e)  # 检测到循环依赖，涉及 cell: ['c1', 'c2', 'c3']
```

逐个检查这些 cell 的 `defs`/`refs`，画出它们之间的边，找到环上某条边断开即可。注意 `remaining` 可能包含环外但依赖了环的 cell，真正成环的是其中入度（在子图里）永远不为 0 的那些，可以再跑一次子集 Kahn 精确定位，但通常肉眼就能看出。环的典型症状是"点运行直接报循环依赖错误"，比较显眼，难的是定位哪几个 cell 成环，靠异常里的 cell id 列表就能锁定。修复后重新 `topological_order` 验证通过即可。排查环时一个实用技巧是"逐个禁用边"：临时把环上某条边对应的依赖（某个 cell 的某个 ref）去掉，再跑 `topological_order`，若通过说明这条边是环的关键边，修复就聚焦在"怎么断开这条依赖"上。也可以用 `graphviz` 把 `remaining` 子图画出来，肉眼找环比读 cell id 列表更直观——三个圆圈互相指箭头一眼就看出是环。

第四类是**重复定义**：`DuplicateDefinitionError` 会指出变量名和两个 cell id。找到两个定义它的 cell，删掉或重命名其中一个。常见起因是把同一段代码复制成两个 cell 忘了改变量名，或重构时遗留了旧定义。重复定义的典型症状是"加 cell 时直接报错"，错误消息会明确指出变量名和两个 cell，最容易修。这四类问题覆盖了依赖图调试的绝大多数场景，记住"漏、多、环、重"四个字就能快速分类。还有第五类隐性问题：**stale 不传播**。改了上游 cell，下游本该标 STALE 却没标，导致用户看到的是陈旧结果却以为是最新的。这通常是执行引擎没正确调 `descendants` 收集受影响 cell，而非图本身的问题。排查时手动跑 `descendants(改动的cell)`，看返回集合是否包含期望的下游；若包含但下游没标 STALE，问题在执行引擎的 stale 传播逻辑而非图查询。把图查询和执行引擎的 stale 传播分开排查，能快速定位是"图算错了"还是"引擎没用对图的结果"。具体做法：在执行引擎里加日志，打印"调用了 descendants(c) 得到 S，把 S 里的 cell 标记为 STALE"，然后对比实际被标记 STALE 的 cell 集合是否等于 S。若不等，说明引擎的标记逻辑有漏；若等但用户仍看到陈旧结果，说明引擎没真正重跑那些 STALE cell。把"图查询→标记 stale→重跑 stale"三步分开打日志，能精确定位断在哪一环。

还有一类问题不是 bug 而是性能：**后代集合过大**，改一个小 cell 却要重跑大半个 notebook。这通常不是图错了，而是依赖设计不合理——太多 cell 依赖了同一个"核心 cell"，改核心就雪崩。排查时看 `descendants(核心cell)` 的大小，若异常大，考虑把核心 cell 拆成几个更细粒度的 cell，让下游只依赖它真正需要的那部分，缩小影响面。这是用图论指导架构重构：依赖图不只用来排错，也用来评估架构的"耦合度"——扇出大户就是高耦合点，是重构的首选目标。从架构度量角度，依赖图的统计量能反映 notebook 的健康度：平均度数反映耦合密度，最大扇出反映"关键节点"风险，连通分量数反映"是否分裂成互不相关的几块"（若是，考虑拆成多个 notebook）。把这些统计量做成 dashboard，能在 notebook 变大前预警"耦合过高""单点依赖过多"等架构问题，比等出 bug 再查更主动。依赖图因此不只是运行时基础设施，也是 notebook 工程质量的度量工具。从教学角度，让学生自己算这些统计量并讨论"什么样的依赖图是健康的"，能培养他们对软件耦合的直觉。比如"平均度数 2-3 比较健康，超过 5 说明 cell 间纠缠太深""最大扇出超过 10 说明有个上帝 cell 改它就雪崩""连通分量多于 1 说明 notebook 混了几个无关项目该拆开"。这些经验法则没有硬指标，但把依赖图画出来配合统计量讨论，比空谈"低耦合高内聚"具体得多。依赖图把抽象的架构原则变成了可测的数字和可视的形状，是教架构思维的绝佳载体。最后强调一点：调试依赖问题时，"先确认图对，再查执行"是黄金顺序。很多看似"执行引擎的 bug"其实是图建错了——后代集合漏了某个 cell，执行引擎再正确也会漏跑。所以遇到执行异常，第一步永远是打印 `_downstream`/`_upstream` 确认图符合预期，而不是去读执行引擎代码。这个顺序能省下大量在错误代码层排查的时间，是依赖图调试的核心心法。最后，把这一章的手法整理成一个调试清单，遇到依赖问题按序执行：第一步打印 `_downstream` 全部边，对照预期找漏边或多边；第二步按 cell 打印前后邻居，定位孤岛、扇出扇入大户；第三步对疑似问题 cell 打印 `descendants`/`ancestors`，确认传递影响范围；第四步若报环，读 `CyclicDependencyError` 的 `remaining` 高亮排查；第五步若报重复定义，读 `DuplicateDefinitionError` 的变量名和两个 cell id。这五步覆盖了绝大多数依赖问题，按序走通常能在十分钟内定位根因。把这个清单写成脚本或 REPL 快捷函数，遇到问题一键调用，能把调试流程标准化，减少"每次都从头想怎么查"的认知开销。教学项目里把这个清单和对应的打印函数一起提供，让学生从一开始就养成结构化调试习惯，而非随机打印。结构化调试的本质是"把经验固化成流程"，依赖图因为结构清晰、查询明确，特别适合这种固化，一旦养成习惯，排查任何依赖问题都有一套可重复的步骤，不再依赖灵光一现。这也让依赖图调试成为最适合教给新手的调试场景：步骤明确、反馈直观、无需猜测。

## 可视化建议

若想画成图，可以用 `graphviz` 把 `_downstream` 导出成 DOT：

```python
lines = ["digraph G {"]
for a, succs in graph._downstream.items():
    for b in succs:
        lines.append(f'  "{a}" -> "{b}";')
lines.append("}")
print("\n".join(lines))
```

对前面三个 cell 输出：

```
digraph G {
  "c1" -> "c2";
  "c1" -> "c3";
  "c2" -> "c3";
}
```

把这段 DOT 喂给 `dot -Tpng` 或在线 graphviz 渲染，就能直观看到整本 notebook 的数据流。教学项目里，把这张图和 cell 源码并排展示，是讲清"notebook 为什么不是线性脚本"的最佳教具——学生能直接看到 c1 扇出到 c2、c3，c2 又汇入 c3，这种拓扑结构是线性脚本无法表达的。进一步还可以把 cell 的 `status`（IDLE/DONE/STALE/ERROR）作为节点颜色，把"一次增量执行后哪些 cell 被重跑"可视化出来：重跑的标红，复用的标绿，学生就能看到 reactive 系统如何只动该动的部分。调试时这张状态图也很有用——如果某个该重跑的 cell 没变红，说明 `descendants` 漏了它，回到上一节排查漏依赖。

还可以给边加标签显示是哪个变量触发的依赖，这需要在建图时额外记录"边由哪个变量产生"（当前 `_downstream` 只存 cell id 不存原因）。教学版没存，但调试时可以临时改 `_rebuild` 把边映射成 `(变量名)` 一起打印，这样看到 `c1 -> c2 [label="data"]` 就立刻知道是 `data` 变量连的边，排查漏依赖和多依赖时更精准。这种"带标签的依赖图"在生产级 reactive 系统里很常见，是解释"为什么 A 依赖 B"的关键信息。更进一步，还可以把边的标签做成交互式：鼠标悬停在边上高亮两个 cell 里相关的变量名，让用户一眼看清依赖的来源，这对理解复杂 notebook 的数据流极有帮助。可视化是 reactive 系统可解释性的重要组成——图本身是抽象的，但画出来就变成了人人能读的工程文档。在教学场景里，强烈建议把依赖图可视化做成实时更新：用户每改一个 cell，图跟着重画，边实时增减。这种"所见即所得"的反馈能帮学生建立对 reactive 的直觉——他们改一行代码，立刻看到图里多了一条边或少了一条边，理解"代码结构如何映射成依赖结构"就不再抽象。更进一步，可以在图上叠加"上次执行的重跑高亮"和"本次将要重跑的预览"，让学生看到增量执行的动态过程，这是讲清 reactive 比传统 notebook 优势的最直观教具。调试生产 notebook 时，这张图也是沟通利器：把复杂 notebook 的依赖图截图发给同事，比口头描述"谁依赖谁"清晰十倍。
