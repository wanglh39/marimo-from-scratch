# DAG 可视化与调试

依赖图出问题时，最有效的排查手段往往是"把图画出来看一眼"。`CellGraph` 虽然没有内置图形渲染，但它暴露了足够多的原始数据，让上层可以方便地打印、导出或可视化。这一章介绍如何用这些原始数据排查常见的依赖问题。

## edges 列表

`_edges` 是一个 `set[tuple[CellId, CellId]]`，每条边是有序对 `(定义者, 引用者)`。最直接的调试方式就是把所有边打印出来：

```python
for a, b in graph._edges:
    print(f"{a} -> {b}")
```

看到边就能判断依赖是否符合预期。比如你期望 cell `c1` 定义 `x`、cell `c2` 引用 `x`，那么应当存在边 `(c1, c2)`；如果没有，多半是 `c2` 的 `refs` 没正确提取出 `x`（静态分析漏了），或者 `c1` 的 `defs` 没包含 `x`。反过来，如果出现了意料之外的边，说明某个 cell 的 `refs`/`defs` 被多识别了符号，需要回去检查 cell 的代码分析逻辑。边的集合是图的"地面真相"，所有高级查询都从它派生。

## 打印每个 cell 的直接邻居

除了原始边，按 cell 维度打印上下游更易读：

```python
for cid in graph._cells:
    preds = graph.predecessors(cid)
    succs = graph.successors(cid)
    print(f"{cid}:  preds={preds}  succs={succs}")
```

这种视图能快速定位"孤岛 cell"（既无前驱也无后继，通常是纯展示或出错的 cell）、"扇出大户"（一个 cell 被很多 cell 依赖，改它影响面大）、"扇入大户"（一个 cell 依赖很多 cell，容易因上游出错而 STALE）。

## 调试依赖问题

常见问题有几类。第一类是**漏依赖**：cell B 明明用了变量 `x`，却没连边。排查时打印 B 的 `refs`，确认 `x` 是否在里头；再打印 `var_to_cell`，确认 `x` 是否被某个 cell 定义。第二类是**多依赖**：出现了不该有的边，通常是 `refs` 把属性访问、字符串里的名字也当成了引用，需要回看符号提取逻辑。第三类是**环**：`topological_order` 抛 `CyclicDependencyError` 时会带上环上的 cell id，逐个检查这些 cell 的 `defs`/`refs`，把环上的某条边断开即可。第四类是**重复定义**：`DuplicateDefinitionError` 会指出变量名，找到两个定义它的 cell，删掉或重命名其中一个。

## 可视化建议

若想画成图，可以用 `graphviz` 把 `_edges` 导出成 DOT：

```python
lines = ["digraph G {"]
for a, b in graph._edges:
    lines.append(f'  "{a}" -> "{b}";')
lines.append("}")
```

渲染后能直观看到整本 notebook 的数据流。教学项目里，把这张图和 cell 源码并排展示，是讲清"notebook 为什么不是线性脚本"的最佳教具。
