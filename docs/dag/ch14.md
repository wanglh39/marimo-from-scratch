# 循环依赖检测

环是 notebook 里最危险的错误之一：它让"谁先执行"这个问题无解。`CellGraph` 在每次 `_rebuild` 之后、对外提供拓扑序之前，都会显式检测图中是否存在环。检测手段就是 Kahn 算法本身——它能顺便产出拓扑序，如果产不出完整的序，就说明有环。这一章先讲环为什么必须禁止，再一步步演示 Kahn 算法如何把环揪出来，最后讲异常处理和修复策略。理解环检测不只是为了排错，更是为了理解为什么 marimo 能保证执行一定终止、增量一定收敛。环检测是 reactive 系统安全性的守门人，没有它，整个执行模型都建不起来。

## 为什么循环依赖不允许

考虑三个 cell：

```
cell A:  y = x + 1
cell B:  z = y + 1
cell C:  x = z + 1
```

数据流是 $C \to A \to B \to C$，形成一个环。要执行 A 必须先有 `x`，而 `x` 由 C 产生；要执行 C 必须先有 `z`，而 `z` 由 B 产生；要执行 B 必须先有 `y`，而 `y` 由 A 产生。三个 cell 互相等待，不存在任何合法的执行顺序。从图论角度，环上的顶点不可能出现在任何拓扑序里，因为拓扑序要求每条边的起点排在终点前面，环里每个点既是某条边的起点又是另一条边的终点，矛盾。因此检测环等价于检测"拓扑序是否能覆盖所有顶点"。

更形式化地，设环为 $v_0 \to v_1 \to \dots \to v_{k-1} \to v_0$。若存在拓扑序 $\sigma$，则由每条边 $v_i \to v_{i+1}$ 得 $\sigma(v_i) < \sigma(v_{i+1})$（$\sigma(v)$ 表示 $v$ 在序列中的位置），链式相加得 $\sigma(v_0) < \sigma(v_1) < \dots < \sigma(v_0)$，即 $\sigma(v_0) < \sigma(v_0)$，矛盾。所以环上顶点不可能被任何拓扑序覆盖。反过来，DAG 一定存在拓扑序（Kahn 算法构造性证明了这点）。于是"无环"与"存在完整拓扑序"等价，这就是检测算法的理论基础。这个等价性很重要：它意味着我们不需要单独写一个"找环"的算法，只要跑一遍拓扑排序看输出是否完整即可，一石二鸟。这也是为什么 marimo 把环检测和拓扑排序放在同一个方法里——它们本就是同一个算法的两种产出。从实现简洁性看，这种"复用拓扑排序做环检测"避免了维护两套图遍历代码，减少 bug 面。代价是环检测要等到有人请求拓扑序才发生（惰性），不能在 `_rebuild` 时立刻报错——但前文已述这反而是交互友好性的来源。所以这个设计在简洁性、正确性、交互性三方面都占优，唯一的"代价"是环检测不能在构建期主动触发，而那正是我们想要的惰性语义。

环不只是理论问题，工程上它会让增量执行退化：改了环上任一 cell，它的后代集合（沿 `_downstream` 可达）会包含环上所有 cell，于是"重跑后代"变成"重跑整个环"，而且因为互相依赖，重跑一次后状态又会变，触发再次重跑，陷入无限循环。所以在执行前就把环挡住，既保证了可执行性，也保证了增量计算的终止性。换句话说，环检测同时守护两个不变量：执行序存在（正确性）和增量传播收敛（终止性）。这两个不变量是 reactive 系统能用的底线，环检测就是守住底线的门卫。从历史角度看，环检测在任务调度、编译器数据流分析、电子表格重算里都是核心问题。Excel 就允许循环引用但用迭代法求不动点（若收敛），marimo 选了更严格的"直接禁止"——因为 Python cell 的副作用和不确定性远超 Excel 公式，迭代求不动点既不保证收敛也不保证唯一，不如直接拒绝让用户显式拆解。这种"严格优于宽容"的选择让 marimo 的执行语义更可预测，代价是用户遇到反馈回路要自己改写成显式迭代或递归，不能指望系统自动求解。

还要区分"环"和"菱形"。菱形依赖（$A \to B$、$A \to C$、$B \to D$、$C \to D$）不是环——D 有两条路径从 A 到达，但没有任何路径能回到 A。菱形是合法且常见的，增量执行时改 A 会重跑 B、C、D，D 只跑一次。新手有时会把"一个 cell 被多个路径依赖"误当成环，其实只要沿任何方向走都回不到起点就不是环。环的判据是存在闭合回路，不是存在多路径汇合。这个区分很重要，因为菱形是 reactive 系统的正常工作模式，若误判成环会把合法 notebook 拒之门外。从算法角度，区分环和菱形可以用"强连通分量"（SCC）来精确刻画：环上顶点属于大小 $\ge 2$ 的 SCC，菱形里各顶点的 SCC 都是单元素集。Kahn 算法检测的正是"是否存在大小 $\ge 2$ 的 SCC"——剩余顶点集就是所有非平凡 SCC 的并集。教学版不显式算 SCC，但 `remaining` 恰好给出了非平凡 SCC 的顶点，等价于环检测。理解 SCC 视角能帮你把"环"和"互相可达"等同起来：环就是一组互相能到达的顶点，比"有回路"更准确地抓住了循环依赖的本质。

## Kahn 算法检测环

Kahn 算法的思路是反复"摘掉入度为 0 的顶点"。具体步骤：

1. 统计每个顶点的入度，把入度为 0 的全部放进队列。
2. 每次从队列取出一个顶点 $u$ 放进结果序列，并把 $u$ 的所有出边删掉——即把 $u$ 的每个后继的入度减一，若减到 0 就入队。
3. 重复直到队列为空。

若最终结果序列的长度等于顶点总数，说明所有顶点都被摘掉了，图是 DAG；若长度小于顶点总数，说明剩下的顶点入度永远降不到 0，它们一定处在某个环里——这就是环存在的判据。直观理解：环上每个顶点至少有一条入边来自环内另一个顶点，只要环内顶点没被摘掉，这条入边就一直存在，入度永远 $\ge 1$，永远进不了队列。而环外能摘的顶点摘完后，环内顶点的入度最多减到"来自环内的入边数"，仍 $\ge 1$，所以它们永远卡在队列外。这个"卡住"正是环的图论特征：没有入口可以从外面摘进来。从不变量的角度看，Kahn 算法维护的不变量是"队列里的顶点入度都为 0（在当前剩余图里）"和"已摘掉的顶点构成已排序前缀"。每次摘一个顶点并削减其出边，保持这两个不变量。循环结束时，要么所有顶点都进了前缀（DAG），要么剩下的顶点入度全 $\ge 1$（有环）。这个不变量推理是 Kahn 正确性的标准证明，理解了它就能确信算法不会漏判或误判环。

用前面 $C \to A \to B \to C$ 的例子走一遍。初始入度：A 的 `refs={x}` 由 C 定义，入度 1；B 的 `refs={y}` 由 A 定义，入度 1；C 的 `refs={z}` 由 B 定义，入度 1。三个顶点入度全是 1，没有入度为 0 的，队列为空，循环不执行，`order` 长度 0 ≠ 顶点数 3，判定有环，`remaining = {A, B, C}`。整个过程一步就停，因为没有任何"入口"可以开始摘。这种"全卡住"是最纯粹的环：每个顶点都依赖另一个，没有任何一个能先跑。

再看一个部分有环的例子：$A \to B \to C \to B$（A 是入口，B、C 成环）。初始入度：A=0，B=1（来自 A）+1（来自 C）=2，C=1（来自 B）。队列初始 `[A]`。取出 A，order=`[A]`，A 的下游是 B，B 入度 2-1=1，未到 0 不入队。队列空，循环结束。order 长度 1 ≠ 3，`remaining = {B, C}`——正好是环上的两个顶点。A 被正常摘掉，因为它不在环里且有入度 0 入口；B、C 卡住因为它们互相依赖。这个例子说明 Kahn 能精确区分环上和环外顶点：环外的能摘就摘，环上的永远摘不掉。`remaining` 因此既包含环上顶点，也包含"依赖了环但不在环上"的顶点（它们也永远等不到环内 cell 执行完）。

再走一个更复杂的例子，体会"环外依赖环"的情况。图：$A \to B \to C \to B$（B、C 成环），外加 $C \to D$（D 依赖环里的 C）。初始入度：A=0，B=2（A、C），C=1（B），D=1（C）。队列 `[A]`。取 A，order=`[A]`，B 入度 2-1=1。队列空，结束。order 长度 1 ≠ 4，`remaining = {B, C, D}`。注意 D 也在 `remaining` 里，虽然 D 不在环上，但它依赖的 C 永远执行不了，所以 D 也永远执行不了，被一并报告。这提醒我们：`remaining` 是"无法排序的顶点"，包含环上和被环阻塞的所有下游，不只是最小环。若只想知道最小环，需要进一步在 `remaining` 子图里找入度（子图内）全 $\ge 1$ 的强连通分量，但教学版不做这步精化，直接报告 `remaining` 已经足够定位问题。

marimo 在 `topological_order` 里跑完 Kahn 后做这个判断：

```python
def topological_order(self) -> list[str]:
    in_degree = {
        cid: len(self._upstream.get(cid, set())) for cid in self._cells
    }
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set())):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    if len(order) != len(self._cells):
        remaining = set(self._cells) - set(order)
        raise CyclicDependencyError(
            f"检测到循环依赖，涉及 cell: {sorted(remaining)}"
        )
    return order
```

`remaining` 是入度永远降不到 0 的顶点集合，它一定包含所有环上顶点（也可能包含一些"依赖了环但不在环上"的顶点，比如某个 cell 引用了环里的变量，它也永远等不到环内 cell 执行完）。`sorted(remaining)` 让异常消息里的 cell id 顺序稳定，便于阅读和测试。注意 `sorted` 还用在队列初始化和每次入队前的下游遍历，这两处排序保证拓扑序本身稳定可复现，与环检测无关但同样重要。入度统计用 `len(self._upstream.get(cid, set()))`，对没有上游的 cell 返回 0，自然成为初始队列的种子。从数据结构选择看，用 `deque` 而非 list 做队列，是为了 `popleft` 的 $O(1)$；用 dict 存入度而非数组，是因为 cell id 是字符串不是连续整数，dict 更自然。`sorted` 在三处出现（初始队列、每次入队前的下游遍历、`remaining` 排序），前两处保证拓扑序稳定，第三处保证错误消息稳定，都是可复现性的基础设施。这些看似琐碎的排序选择，合起来保证了"同一张图永远产出同一个拓扑序或同一个错误消息"，是工程可靠性的细节基石。

## CyclicDependencyError

检测到环后，`CellGraph` 抛出 `CyclicDependencyError`，并把 `remaining` 里的 cell id 一并带出，方便前端高亮显示是哪些 cell 组成了环。这个异常在执行之前就被抛出，不会执行任何 cell，因此不会出现"执行了一半发现顺序不对"的脏状态。异常类本身很简单，继承自 `GraphError`：

```python
class GraphError(Exception):
    pass

class CyclicDependencyError(GraphError):
    pass
```

调用方（执行引擎）捕获 `CyclicDependencyError` 后，通常把环上的 cell 标记为 ERROR 状态，并把异常消息回传给前端，让用户看到具体是哪些 cell 互相依赖。用户修复环（通常是把某个 cell 的定义改成引用，或拆开循环）后，下一次 `_rebuild` 重新检测，通过即可恢复执行。把错误信息回传前端高亮是关键体验：用户不用自己去翻依赖关系，直接看到哪几个 cell 互相套着，修复目标明确。`GraphError` 作为基类，还统一了 `DuplicateDefinitionError` 等其他图相关错误，调用方可以用一个 `except GraphError` 兜底处理所有图构建问题。

修复环的常见手法有几种。最直接的是"断开一条边"：找到环上某个 cell，把它引用的某个变量改成不依赖环内其他 cell，比如引入一个外部输入参数。第二种是"合并 cell"：如果两个 cell 本就该一起算，合并成一个 cell 就消除了它们之间的环。第三种是"重新审视建模"：环往往意味着把反馈回路写成了同步依赖，而反馈回路本质上需要迭代求解或异步更新，不适合 reactive 的一次性求值模型，可能要改用显式循环或递归 cell。把环检测放在构建阶段而非执行阶段，是 marimo"静态优先于动态"设计哲学的体现：能靠分析符号就发现的问题，绝不留到运行时才暴露。静态检测的代价是会有"假环"——某些动态不会真成环但静态分析看不出，但教学版接受这个保守策略，换来的是运行时零意外。假环的典型场景是条件引用：`if cond: y = x` 里静态看 c 引用了 x，但运行时 cond 为 False 时根本不引用，若 x 恰好依赖 y 就静态成环但动态不成环。静态分析无法知道 cond 的值，只能保守地认为有依赖，可能误报环。教学版接受这种保守性，因为动态依赖分析要部分执行代码，违背"静态优先"原则且实现复杂。生产版 marimo 通过让用户显式标注"条件定义"来缓解，但教学版宁可有假环也不引入动态分析的复杂性。

值得注意的细节：`_rebuild` 本身不调用 `topological_order`，所以构建图时不会抛环错误，只有显式请求拓扑序（执行引擎要跑 notebook 时）才会检测。这种惰性检测让用户在编辑过程中可以暂时有环——比如正在把一段代码拆成几个 cell，中间状态可能有环——只有点"运行"时才强制无环，对交互式编辑更友好。这也意味着 `add_cell` 一个会成环的 cell 不会立即报错，只有后续调 `topological_order` 才报；测试时如果想在建图时就检测，需要显式调一次 `topological_order`。惰性检测把"编辑宽容、运行严格"两种模式分开，是交互式工具的常见设计：编辑时允许中间非法状态，只在提交/运行时校验，避免频繁报错打断用户思路。这也和 Excel 的行为类似：你可以在单元格里写循环引用，Excel 不在你输入时报错，只在重算时提示循环，给用户留出调整空间。marimo 延续了这种"延迟校验"哲学，把环检测的时机交给用户（点运行才查），而不是交给系统（每次编辑都查），在严谨性和交互流畅性之间取了平衡。

还有一个实践要点：环检测的报错信息要尽量可操作。`CyclicDependencyError` 的消息里直接列出涉及的 cell id，前端拿到后高亮这些 cell，用户一眼看到"就是这三个 cell 互相套着"，修复目标明确。如果只报一个笼统的"存在循环依赖"而不说哪些 cell，用户得自己排查，体验很差。所以 `sorted(remaining)` 这个看似不起眼的排序，其实是可调试性的关键——它把图论算法的副产品（没摘掉的顶点）转化成了用户可读的错误定位信息。好的错误消息不只是说"错了"，更要说"哪里错了、怎么改"，`remaining` 正是提供"哪里"的素材。从用户体验角度，环检测报错后理想的前端行为是：高亮 `remaining` 里的 cell，用红色边框标出它们之间的依赖边，让用户直接看到一个"红色闭环"，点击任一红边能跳到对应的变量引用处。这种"可视化定位"比纯文本错误消息效率高一个量级——用户不用在脑里重建图，直接看到环的形状。教学版只抛文本异常，但理解了这个理想体验，就知道为什么 `remaining` 要尽量精确：它越精确，前端高亮越聚焦，用户修复越快。若 `remaining` 把一堆无关 cell 也包进来，高亮一片红，用户反而难定位真正的环。所以未来优化方向是在 `remaining` 子图里跑强连通分量分解，只报告真正的 SCC 顶点，让错误定位更精准。教学版不做这步，因为 `remaining` 已经足够让用户开始排查，且 SCC 分解增加代码复杂度，与教学简洁性目标冲突。从教学价值看，环检测是理解"为什么 reactive 必须基于 DAG"的最佳切入点：学生亲手造一个环、看报错、读 `remaining`、修复环，这个循环能让他们切身感受到无环性对执行模型的意义，比单纯讲理论深刻得多。把环检测放在构建期而非运行期，还让测试更容易：测试可以直接构造一个带环的 cell 集合，调 `topological_order` 断言抛 `CyclicDependencyError`，不必真的跑执行引擎，单元测试轻量且确定。
