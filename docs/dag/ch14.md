# 循环依赖检测

环是 notebook 里最危险的错误之一：它让"谁先执行"这个问题无解。`CellGraph` 在每次 `_rebuild` 之后、对外提供拓扑序之前，都会显式检测图中是否存在环。检测手段就是 Kahn 算法本身——它能顺便产出拓扑序，如果产不出完整的序，就说明有环。

## 为什么循环依赖不允许

考虑三个 cell：

```
cell A:  y = x + 1
cell B:  z = y + 1
cell C:  x = z + 1
```

数据流是 $C \to A \to B \to C$，形成一个环。要执行 A 必须先有 `x`，而 `x` 由 C 产生；要执行 C 必须先有 `z`，而 `z` 由 B 产生；要执行 B 必须先有 `y`，而 `y` 由 A 产生。三个 cell 互相等待，不存在任何合法的执行顺序。从图论角度，环上的顶点不可能出现在任何拓扑序里，因为拓扑序要求每条边的起点排在终点前面，环里每个点既是某条边的起点又是另一条边的终点，矛盾。因此检测环等价于检测"拓扑序是否能覆盖所有顶点"。

## Kahn 算法检测环

Kahn 算法的思路是反复"摘掉入度为 0 的顶点"。具体步骤：

1. 统计每个顶点的入度，把入度为 0 的全部放进队列。
2. 每次从队列取出一个顶点 $u$ 放进结果序列，并把 $u$ 的所有出边删掉——即把 $u$ 的每个后继的入度减一，若减到 0 就入队。
3. 重复直到队列为空。

若最终结果序列的长度等于顶点总数，说明所有顶点都被摘掉了，图是 DAG；若长度小于顶点总数，说明剩下的顶点入度永远降不到 0，它们一定处在某个环里——这就是环存在的判据。marimo 在 `topological_order` 里跑完 Kahn 后做这个判断：

```python
if len(order) != len(self._cells):
    raise CyclicDependencyError(...)
```

## CyclicDependencyError

检测到环后，`CellGraph` 抛出 `CyclicDependencyError`，并把环上的 cell id 一并带出，方便前端高亮显示是哪些 cell 组成了环。这个异常在执行之前就被抛出，不会执行任何 cell，因此不会出现"执行了一半发现顺序不对"的脏状态。用户修复环（通常是把某个 cell 的定义改成引用，或拆开循环）后，下一次 `_rebuild` 重新检测，通过即可恢复执行。把环检测放在构建阶段而非执行阶段，是 marimo"静态优先于动态"设计哲学的体现：能靠分析符号就发现的问题，绝不留到运行时才暴露。
