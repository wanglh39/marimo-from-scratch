# 依赖查询：祖先与后代

构建出 DAG 之后，执行引擎最常问的两个问题是："这个 cell 依赖了哪些 cell？"以及"哪些 cell 依赖了这个 cell？"。前者叫祖先（ancestors），后者叫后代（descendants）。`CellGraph` 用 BFS 在 `_edges` 上实现这两类查询，它们是增量执行和影响分析的基础。

## 直接依赖：predecessors 与 successors

最简单的是直接相邻的 cell。`predecessors(c)` 返回所有满足 $A \to c$ 的 $A$，即直接给 $c$ 提供变量的 cell；`successors(c)` 返回所有满足 $c \to B$ 的 $B$，即直接消费 $c$ 产出的变量的 cell。实现就是遍历 `_edges` 过滤，$O(E)$。这两个方法主要用于调试和展示，真正的执行决策需要传递闭包，也就是下面的祖先与后代。

## descendants：BFS 顺数据流而下

`descendants(c)` 返回 $c$ 的所有后代，即从 $c$ 出发沿边方向能到达的所有顶点。实现是标准 BFS：

```python
def descendants(self, c):
    seen, queue = set(), [c]
    while queue:
        u = queue.pop(0)
        for v in self.successors(u):
            if v not in seen:
                seen.add(v)
                queue.append(v)
    return seen
```

后代的意义是：一旦 $c$ 的执行结果变了，这些 cell 都可能受影响、需要重跑。所以 `run_cell` 在增量执行时，要执行的集合正是 $\{c\} \cup \text{descendants}(c)$。`run_descendants` 更纯粹，只跑后代不跑 $c$ 本身，用于 UI 组件值变化时——组件的新值已经由前端注入，$c$ 不必重跑，只需更新它的消费者。

## ancestors：BFS 逆数据流而上

`ancestors(c)` 反过来，沿边反方向 BFS，返回 $c$ 的所有祖先。它的用途是影响分析：当用户问"如果我改了这个 cell，哪些上游 cell 的输出会显示在我的变量里"，或者做"删除这个 cell 是否安全"的检查时，都需要祖先集合。教学版 marimo 主要在调试和可视化里用到 ancestors，执行路径上用得更多是 descendants。

## 为什么用 BFS 而不是 DFS

BFS 和 DFS 都能求传递闭包，选 BFS 主要是因为迭代式队列实现简单、不依赖递归栈，对深链条更友好。两种方式的时间复杂度都是 $O(V+E)$。注意 descendants 和 ancestors 都把起点自身排除在外（或按需包含），调用方要清楚这一点，避免在增量执行时漏跑当前 cell。配合 `execution_order_from`，这些查询共同把"该跑哪些、按什么顺序跑"这件事变成纯粹的图论计算。
