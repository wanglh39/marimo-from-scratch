# 依赖查询：祖先与后代

构建出 DAG 之后，执行引擎最常问的两个问题是："这个 cell 依赖了哪些 cell？"以及"哪些 cell 依赖了这个 cell？"。前者叫祖先（ancestors），后者叫后代（descendants）。`CellGraph` 用 BFS 在邻接表上实现这两类查询，它们是增量执行和影响分析的基础。这一章从直接邻居讲到传递闭包，再讲到把闭包排成执行序的 `execution_order_from`，配合代码走读把每一步讲透。理解这些查询的语义和实现，是理解 reactive 系统为什么能"改一个 cell 自动重跑该跑的"的关键。可以说，前面建图、检测环都是为了这几个查询能正确快速地工作——查询才是图存在的目的。

## 直接依赖：predecessors 与 successors

最简单的是直接相邻的 cell。`predecessors(c)` 返回所有满足 $A \to c$ 的 $A$，即直接给 $c$ 提供变量的 cell；`successors(c)` 返回所有满足 $c \to B$ 的 $B$，即直接消费 $c$ 产出的变量的 cell。实现就是查邻接表，$O(1)$：

```python
def predecessors(self, cell_id: str) -> set[str]:
    return set(self._upstream.get(cell_id, set()))

def successors(self, cell_id: str) -> set[str]:
    return set(self._downstream.get(cell_id, set()))
```

`_upstream[c]` 存的就是所有指向 c 的边的起点，`_downstream[c]` 存的就是所有从 c 出发的边的终点，`_rebuild` 时已经双向登记好了，这里直接返回拷贝。返回 `set(...)` 而非内部引用，是为了防止调用方修改邻接表破坏图的不变量——若直接返回内部 `set`，调用方 `.add()` 或 `.discard()` 会污染图的状态，后续查询就错乱了。这个防御性拷贝是必要的，虽然每次查询多一次浅拷贝，但集合通常很小，成本可忽略。这两个方法主要用于调试和展示，真正的执行决策需要传递闭包，也就是下面的祖先与后代。

举个例子，对链 $c1 \to c2 \to c3$：`predecessors(c2) = {c1}`，`successors(c2) = {c3}`，`predecessors(c1) = set()`（入口 cell 无上游），`successors(c3) = set()`（出口 cell 无下游）。直接邻居只看一步，看不到 $c1$ 对 $c3$ 的间接影响——那是后代的职责。直接邻居的价值在于快速判断"这个 cell 是不是孤岛"（前后都空）、"它直接依赖谁"（看 predecessors），但任何涉及"改了它会波及谁"的决策都必须用传递闭包，因为影响会沿链传播不止一步。`get(cell_id, set())` 的默认值处理让查一个不存在的 cell id 也不报错，返回空集，调用方不必先检查存在性。这种"宽容返回"在图查询里是常见约定：查不存在的顶点的邻居返回空集而非抛异常，让调用方可以用统一的循环处理所有 cell 而不必特判。直接依赖虽然简单，却是所有高级查询的积木：`descendants` 就是反复套 `successors` 做 BFS，`topological_order` 的入度统计也靠 `_upstream` 的长度。所以把直接邻居查对、查快，是整个查询体系的基础。从命名角度，`predecessors`（前驱）和 `successors`（后继）借用了图论标准术语：前驱是指向当前顶点的顶点，后继是当前顶点指向的顶点。注意它和"祖先/后代"的区别：前驱后继只看一步（直接邻居），祖先后代看任意步（传递闭包）。初学者容易混淆这两对概念，记住"前驱后继是邻居，祖先后代是族谱"就不会搞错。在 marimo 源码里，前驱后继用 `_upstream`/`_downstream` 直接查，祖先后代用 `_bfs` 传递查，实现层次也对应了语义层次。

## descendants：BFS 顺数据流而下

`descendants(c)` 返回 $c$ 的所有后代，即从 $c$ 出发沿边方向能到达的所有顶点。形式化地，$\text{descendants}(c) = \{v \in V \mid c \to^+ v\}$，其中 $\to^+$ 表示长度 $\ge 1$ 的可达关系（传递闭包去掉自反）。实现是标准 BFS，委托给 `_bfs`：

```python
def descendants(self, cell_id: str) -> set[str]:
    return self._bfs(cell_id, self._downstream)

def _bfs(self, start: str, adj: dict[str, set[str]]) -> set[str]:
    visited: set[str] = set()
    queue: deque[str] = deque(adj.get(start, set()))
    while queue:
        node = queue.popleft()
        if node in visited:
            continue
        visited.add(node)
        queue.extend(adj.get(node, set()))
    return visited
```

`_bfs` 从 `adj[start]`（即 start 的直接邻居）初始化队列，注意起点自身不在队列里，所以返回的 `visited` 不含 start——这是"后代不含自身"的语义保证。循环里 `popleft` 取队首，若已访问过就跳过（处理菱形依赖时同一个顶点可能被多次入队），否则标记访问并把它的邻居全部入队。用 `deque` 的 `popleft` 是 $O(1)$，比列表 `pop(0)` 的 $O(n)$ 快。`visited` 集合既记录已访问顶点，又作为最终返回值，一物两用。`queue.extend(adj.get(node, set()))` 把当前节点的所有邻居一次性入队，是 BFS 的批量扩展写法，比逐个 append 更简洁。从不变量看，`_bfs` 维护的不变量是"visited 里的顶点都已处理完其邻居入队，queue 里的顶点待处理"。循环结束时 queue 空、visited 包含所有从 start 可达的顶点（不含 start 自身），正是传递闭包去掉自反的定义。这个不变量保证 BFS 不会漏顶点（每个可达顶点最终都进过 queue）也不会重复处理（visited 去重），是正确性的标准论证。

走一个例子。图 $c1 \to c2 \to c3$、$c1 \to c4$（c1 扇出到 c2、c4，c2 再到 c3）。求 `descendants(c1)`：初始队列 `deque({c2, c4})`。取出 c2，visited={c2}，入队 c3，队列=`[c4, c3]`。取出 c4，visited={c2,c4}，c4 无下游，队列=`[c3]`。取出 c3，visited={c2,c4,c3}，c3 无下游，队列空。返回 `{c2, c3, c4}`——c1 的所有下游，正确。注意 c3 虽然只被 c2 入队一次，但若图里还有另一条路径到 c3（比如 $c4 \to c3$），c3 会被入队两次，第二次靠 `if node in visited: continue` 跳过，避免重复处理。这正是菱形依赖下后代集合不重复的原因。从集合论角度，`descendants` 求的是关系 $\to$ 的传递闭包 $\to^+$ 在起点上的像，BFS 是计算传递闭包的经典方法之一（另还有 Floyd-Warshall 等矩阵法，但对单源查询 BFS 更高效）。因为图是 DAG，传递闭包不会包含起点自身（无环保证没有回到自身的路径），所以"后代不含自身"是 DAG 的自然性质，不需要额外排除。在有环图里这条不成立——起点的后代可能包含起点自己（绕环一圈回来），这也是环破坏增量语义的又一体现。

后代的意义是：一旦 $c$ 的执行结果变了，这些 cell 都可能受影响、需要重跑。所以 `run_cell` 在增量执行时，要执行的集合正是 $\{c\} \cup \text{descendants}(c)$。`run_descendants` 更纯粹，只跑后代不跑 $c$ 本身，用于 UI 组件值变化时——组件的新值已经由前端注入，$c$ 不必重跑，只需更新它的消费者。这就是 reactive 系统的核心：一个 cell 改了，自动且只重跑受影响的下游，既不漏跑（保证正确）也不多跑（保证效率）。漏跑会导致下游用旧值算出错误结果，多跑会浪费算力且可能因副作用产生意外，后代集合恰好是"刚好该跑的那些"。这个"刚好"是 reactive 区别于"全量重跑"和"手动指定重跑"的关键：它由图论自动算出，既正确又最小。从复杂度看，一次 `descendants` 是 $O(V+E)$，对一本几百 cell 的 notebook 是微秒级，远小于真正重跑 cell 的成本（可能秒级甚至分钟级）。所以花 $O(V+E)$ 算出"只重跑这 5 个 cell"而不是全量重跑 200 个，省下的执行时间是图查询成本的千万倍——这是 reactive 系统用图论换性能的核心收益。从实现角度，`descendants` 返回的集合会被 `execution_order_from` 进一步排序成执行序，所以它不只影响"跑哪些"，还影响"按什么序跑"。如果 `descendants` 漏了一个后代，那个 cell 既不会被重跑也不会被排序，彻底脱离增量更新，是最危险的 bug。所以 `descendants` 的正确性比性能更重要——宁可慢一点也不能漏。BFS 的 `visited` 去重保证不漏不多，是正确实现的首选。从边界情况看，`descendants` 对叶子 cell（无下游）返回空集，对孤立 cell 也返回空集，这两种"无后代"语义一致，调用方不必区分。对不存在于图的 cell id，`_bfs` 的 `adj.get(start, set())` 返回空初始队列，循环不执行，返回空集——又是"宽容返回空集"的约定，和 `predecessors`/`successors` 一致。这种统一的"查不到就返回空"约定让上层代码不必处处判空，简化了调用方逻辑。唯一要小心的是：`descendants(c)` 不含 c 自身，若执行集合需要包含 c，必须显式 `| {c}`，`execution_order_from` 正是这么做的，而 `run_descendants`（只跑后代）则故意不含 c，用于"值已由外部注入"的场景。从命名一致性看，`descendants`/`ancestors` 是名词复数（返回集合），`predecessors`/`successors` 也是，而 `execution_order_from`/`topological_order` 是带 order 的（返回有序列表）。这种命名约定让调用方一看方法名就知道返回的是无序集合还是有序序列，不必查文档。教学版严格遵守这个约定，是可读性的细节投资。从测试角度，这几个查询都很好测：构造一个已知图，断言 `descendants(c)` 等于预期集合即可，因为它们是纯函数（只读图不改图），无副作用，测试用例干净。从性能调优角度，若 notebook 极大且查询极频繁，可把 `descendants`/`ancestors` 的结果缓存（因为图在两次 `_rebuild` 之间不变，传递闭包也不变），但教学版不缓存，因为图小查询快，缓存反而增加复杂度和"缓存失效"的 bug 面。缓存的正确做法是把缓存挂在 `_rebuild` 里清空，保证一致性，但这是生产级优化，教学版保持"每次现算"的简单实现。理解了缓存的可能性，就知道这些查询的性能上限在哪——即便不缓存，$O(V+E)$ 也已经很快，缓存只是锦上添花。从教学价值看，这几个查询方法是"图论如何直接驱动执行决策"的最佳示例：学生看到 `execution_order_from` 就两行——求后代、排子集——却完成了"改一个 cell，自动重跑该跑的、按对的顺序跑"这个 reactive 的核心承诺，能深刻体会到把执行问题转化为图论问题的威力。这几行代码因此是整个 reactive 实现里"性价比最高"的部分——用最少的代码兑现了最核心的承诺。

## ancestors：BFS 逆数据流而上

`ancestors(c)` 反过来，沿边反方向 BFS，返回 $c$ 的所有祖先。形式化地，$\text{ancestors}(c) = \{v \in V \mid v \to^+ c\}$。实现只是把 `_bfs` 的邻接表换成 `_upstream`：

```python
def ancestors(self, cell_id: str) -> set[str]:
    return self._bfs(cell_id, self._upstream)
```

`_upstream` 存的是反向边（B 的上游是 A 等价于边 $A \to B$），所以在 `_upstream` 上做 BFS 就等于在原图上逆边方向走，正好得到祖先。代码复用 `_bfs` 是关键——同一个 BFS 函数，传 `_downstream` 得后代，传 `_upstream` 得祖先，体现了双向邻接表设计的收益。如果没有双向邻接表，求祖先就得先反向建图再 BFS，或者每次遍历整个 `_downstream` 找指向当前节点的边，都麻烦得多。双向登记一次，受益于所有方向查询，这是 `_rebuild` 里多存一份 `_upstream` 的根本动机。这种"用空间换代码复用和查询速度"的取舍在图算法里很常见。

它的用途是影响分析：当用户问"如果我改了这个 cell，哪些上游 cell 的输出会显示在我的变量里"，或者做"删除这个 cell 是否安全"的检查时，都需要祖先集合。删除 cell $c$ 安全的条件之一是 `descendants(c)` 为空——没有别的 cell 依赖它，删了不会让别人失依赖；若要查"删了 $c$ 之后哪些变量会变成未定义"，就看 $c$ 的 `defs` 是否出现在其他 cell 的 `refs` 里，等价于 `descendants(c)` 非空。教学版 marimo 主要在调试和可视化里用到 ancestors，执行路径上用得更多是 descendants。但在更完整的 reactive 系统里，ancestors 还用于"这个 cell 的所有输入"展示（类似函数签名），帮助用户理解一个复杂 cell 到底吃了哪些上游产出。ancestors 和 descendants 是对偶概念：一个看上游闭包，一个看下游闭包，合起来就把 cell 在图里的"影响范围"完整描述了。在 DAG 上两者还有个有趣关系：$v \in \text{descendants}(u)$ 当且仅当 $u \in \text{ancestors}(v)$，即"v 是 u 的后代"等价于"u 是 v 的祖先"。这个对偶性来自有向边的方向定义，也是为什么同一个 `_bfs` 函数换张邻接表就能在两个方向间切换——数学上的对偶直接映射成代码上的对称。从性能角度，`ancestors` 和 `descendants` 共用 `_bfs`，维护成本只有一份：优化 `_bfs`（比如换更快的队列实现）两个查询同时受益。这是代码复用的经典收益，也是双向邻接表设计的回报——若只存 `_downstream`，求 ancestors 就得每次反向遍历全图，无法复用同一个 BFS，代码量和 bug 面都翻倍。所以"多存一份 `_upstream`"这个看似冗余的设计，实则是为了对称性和复用性付出的微小空间代价，换来的是查询代码的统一和维护的简化。

## 从闭包到执行序：execution_order_from

光知道"该跑哪些 cell"还不够，还要知道"按什么顺序跑"。`execution_order_from(c)` 把 $\{c\} \cup \text{descendants}(c)$ 这个集合排成合法执行序，方法是在子集上跑一遍 Kahn：

```python
def execution_order_from(self, cell_id: str) -> list[str]:
    affected = self.descendants(cell_id) | {cell_id}
    return self._topological_sort_subset(affected)

def _topological_sort_subset(self, subset: set[str]) -> list[str]:
    in_degree = {
        cid: len(self._upstream.get(cid, set()) & subset) for cid in subset
    }
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set()) & subset):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    return order
```

关键细节是入度和下游都要 `& subset`：子集内一个 cell 可能有上游在子集外（比如 c 的某个上游不在 affected 里），但那些上游已经执行过不必再跑，所以只数子集内的入度。这样排出的序保证子集内每条边的起点在终点前，且不引入子集外的 cell。`run_cell` 拿到这个序依次执行，就完成了增量更新。注意这里不检测环——因为 `affected` 是从已通过环检测的整图里取的子集，子集必然也无环，所以 `_topological_sort_subset` 不需要 `len(order) != len(subset)` 的检查，直接返回即可。这个"子集无环"的推理依赖整图已通过 `topological_order` 检测，是调用顺序保证的隐式前提。

举个例子，图 $c1 \to c2 \to c3$，改了 c1。`descendants(c1) = {c2, c3}`，`affected = {c1, c2, c3}`，子集 Kahn 排出 `[c1, c2, c3]`，依次重跑。若只改了 c2，`descendants(c2) = {c3}`，`affected = {c2, c3}`，c1 不在 affected 里（它没受影响），排出的序是 `[c2, c3]`，c1 的旧结果被复用。这就是增量执行的精髓：只动该动的，按合法序动。对比全量重跑 `[c1, c2, c3]`，省了 c1 一次执行，当 c1 是个耗时计算（如训练模型）时收益巨大。`execution_order_from` 把"影响范围"和"执行顺序"两件事一次算出，是增量执行引擎最核心的调用。它和 `topological_order` 的区别在于作用域：后者排整本 notebook 的所有 cell，用于首次全量执行；前者只排受影响的子集，用于后续增量执行。两者底层都是 Kahn，但 `_topological_sort_subset` 多了 `& subset` 的过滤，保证只动子集内的 cell。这种"全量 Kahn + 子集 Kahn"的组合，让执行引擎在首次跑全图、之后跑增量之间无缝切换，共用同一套拓扑排序逻辑。从代码复用看，两个排序方法结构几乎一样，差别只在 `& subset`，本可以合并成一个带可选 subset 参数的方法。教学版保留两个方法是为了语义清晰：`topological_order` 明确表示"排整图"，`_topological_sort_subset` 明确表示"排子集"，调用方一眼看出意图。这种"宁可少量重复也要语义明确"的取舍在教学代码里是合理的，生产版可能更倾向合并以减少重复。

## 为什么用 BFS 而不是 DFS

BFS 和 DFS 都能求传递闭包，选 BFS 主要是因为迭代式队列实现简单、不依赖递归栈，对深链条更友好（Python 默认递归深度约 1000，极长依赖链会爆栈，BFS 用显式 `deque` 没这限制）。两种方式的时间复杂度都是 $O(V+E)$：每个顶点至多入队一次（靠 `visited` 去重），每条边至多被扫描一次（从起点的邻居遍历产生）。空间复杂度 $O(V)$（`visited` 加队列）。BFS 还有一个附带好处：它按"距离起点多少步"的层次推进，调试时打印访问顺序能直观看到依赖的层级，DFS 的深潜顺序则不那么直观。对于 reactive 系统，BFS 的层次性也和"stale 传播"的直觉一致：先标记直接下游 stale，再标记下游的下游，逐层扩散。

注意 descendants 和 ancestors 都把起点自身排除在外（`_bfs` 初始队列是 `adj[start]` 不含 start），调用方要清楚这一点，避免在增量执行时漏跑当前 cell——所以 `execution_order_from` 显式 `| {cell_id}` 把自身加回来。配合 `execution_order_from`，这些查询共同把"该跑哪些、按什么顺序跑"这件事变成纯粹的图论计算，执行引擎只需调用两个方法就拿到完整计划，不必自己维护任何依赖状态。这种把执行决策完全外包给图查询的设计，让执行引擎的代码非常薄，核心逻辑全在图里，便于测试和推理。如果要给 reactive 系统总结一句心法，那就是："图负责算该跑谁，引擎负责真去跑"——职责分明，图论和执行解耦。
