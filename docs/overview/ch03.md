# reactive 编程范式

要理解 marimo，必须先理解 reactive 编程范式。这个词听起来抽象，但其实每个人都有过切身体验——就在 Excel 里。

## 从电子表格理解 reactive

打开 Excel，在 A1 填 `1`，B1 填 `=A1+10`，此时 B1 显示 `11`。现在把 A1 改成 `100`，B1 **自动**变成 `110`。你不需要"重新运行 B1"，也不需要告诉 Excel "B1 依赖 A1"——它从公式里自己分析出来了。

这就是 reactive 的核心：**数据流驱动计算**。每个格子是一个计算节点，公式里的引用声明了依赖，当某个格子的值变化时，所有直接或间接依赖它的格子会按依赖顺序自动重算。整个过程不需要用户干预，系统自动维护一致性。

Excel 还悄悄做了两件聪明事：第一，它只重算受影响的格子，没动过的格子不重算（增量计算）；第二，如果 A1 改了但 B1 的公式没引用 A1，B1 不会被重算（短路）。这两点正是 marimo 执行引擎要复现的关键能力。

## FRP：函数式响应编程

学术界把这种范式叫做 **FRP（Functional Reactive Programming）**，它把随时间变化的值抽象为"信号"（signal），用纯函数描述信号之间的变换。经典公式：

```
b = f(a)        // b 是一个信号，它的值始终等于 f 作用于 a 的当前值
```

`a` 变了，`b` 自动变，无需手动刷新。FRP 强调**声明式**：你只描述"b 依赖 a 的什么关系"，不描述"什么时候去更新 b"。更新时机和传播路径由运行时系统决定。

在 notebook 场景里，每个 cell 就是一个信号，cell 的输出值随它引用的变量的变化而变化。marimo 做的，就是把 FRP 的思想落地到 Python notebook 上。

## reactive 在 notebook 中的体现

把 notebook 映射到 reactive 模型，对应关系非常自然：

- **cell = 计算节点**：每个 cell 是一个纯函数，输入是它引用的变量，输出是它定义的变量和显示内容。
- **变量引用 = 数据流边**：cell A 定义了 `x`，cell B 引用了 `x`，就有一条从 A 指向 B 的边。
- **修改一个 cell = 触发一次更新**：系统沿着依赖图传播这次变更，重算所有下游 cell。

关键在于，这些"依赖关系"不需要用户显式声明，marimo 通过 **AST 静态分析**自动从代码里提取每个 cell 的 defs（定义了哪些变量）和 refs（引用了哪些变量），从而自动构建出整张依赖图。这是 reactive 能"零标注"工作的前提。

## 与命令式编程的对比

命令式编程里，语句是一条条"指令"，按书写顺序执行，每条指令改变程序状态。你改了第 10 行，第 20 行不会自动重跑，状态是否一致全靠你自己维护——这正是 Jupyter 的模型。

reactive 编程里，语句是一个个"声明"，描述数据之间的约束关系，执行顺序由依赖图决定，状态由系统保证一致。你改了任一声明，系统自动重算所有受影响的声明——这是 marimo 的模型。

两种范式并非对立，而是不同抽象层次。命令式适合描述"怎么做"的细节，reactive 适合描述"是什么"的关系。notebook 的本质是探索数据之间的关系，因此 reactive 是更贴切的模型。marimo 的贡献，就是让 Python 这种命令式语言在 notebook 场景下具备了 reactive 的体验，而又不强迫用户学一套新语法——你写的还是普通 Python，reactive 在幕后自动生效。
