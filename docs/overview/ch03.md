# reactive 编程范式

要理解 marimo，必须先理解 reactive 编程范式。这个词听起来抽象，但其实每个人都有过切身体验——就在 Excel 里。

## 从电子表格理解 reactive

打开 Excel，在 A1 填 `1`，B1 填 `=A1+10`，此时 B1 显示 `11`。现在把 A1 改成 `100`，B1 **自动**变成 `110`。你不需要"重新运行 B1"，也不需要告诉 Excel "B1 依赖 A1"——它从公式里自己分析出来了。

这就是 reactive 的核心：**数据流驱动计算**。每个格子是一个计算节点，公式里的引用声明了依赖，当某个格子的值变化时，所有直接或间接依赖它的格子会按依赖顺序自动重算。整个过程不需要用户干预，系统自动维护一致性。

Excel 还悄悄做了两件聪明事：第一，它只重算受影响的格子，没动过的格子不重算（增量计算）；第二，如果 A1 改了但 B1 的公式没引用 A1，B1 不会被重算（短路）。这两点正是 marimo 执行引擎要复现的关键能力。

可以用一张文字图把 Excel 的依赖传播画出来。假设有这样一个表格：

```
A1 = 1            （源数据）
B1 = A1 + 10      （依赖 A1）
C1 = B1 * 2       （依赖 B1，间接依赖 A1）
D1 = 999          （独立数据，不依赖任何人）
```

把 A1 从 1 改成 100，传播过程如下：

```
A1: 1 → 100   （被修改）
  ↓ 触发下游
B1: 11 → 110  （重算，因为依赖 A1）
  ↓ 触发下游
C1: 22 → 220  （重算，因为依赖 B1）
D1: 999       （不动，因为不依赖 A1）   ← 短路
```

只有 A1、B1、C1 三个格子重算，D1 被短路。这正是 marimo 的 `execution_order_from` 做的事：给定被修改的 cell，找出它的所有后代（descendants），只重算这个集合，其余短路。对应到本项目的代码：

```python
# backend/core/graph.py（节选）
def descendants(self, cell_id: str) -> set[str]:
    return self._bfs(cell_id, self._downstream)   # 沿下游边 BFS 收集所有后代
```

`_bfs` 沿下游邻接表做广度优先搜索，收集所有传递依赖的 cell。这个集合就是"需要重算的人"，集合之外一律不动。reactive 并不神秘——它就是"沿依赖图做 BFS，然后按拓扑序重算"。

## FRP：函数式响应编程

学术界把这种范式叫做 **FRP（Functional Reactive Programming）**，它把随时间变化的值抽象为"信号"（signal），用纯函数描述信号之间的变换。经典公式：

```
b = f(a)        // b 是一个信号，它的值始终等于 f 作用于 a 的当前值
```

`a` 变了，`b` 自动变，无需手动刷新。FRP 强调**声明式**：你只描述"b 依赖 a 的什么关系"，不描述"什么时候去更新 b"。更新时机和传播路径由运行时系统决定。

在 notebook 场景里，每个 cell 就是一个信号，cell 的输出值随它引用的变量的变化而变化。marimo 做的，就是把 FRP 的思想落地到 Python notebook 上。

FRP 有两个关键性质值得强调。第一是**声明式**：你写 `y = x + 10`，是在声明"y 和 x 的关系"，而不是命令"现在算一次 y"。关系一旦声明，无论 x 何时变化，y 都会跟着变。第二是**纯函数性**：信号的当前值只取决于它的输入信号的当前值，不取决于历史、不取决于执行顺序。这意味着同一个 DAG 无论以何种合法拓扑序执行，最终状态都一致——这是 marimo "确定性"原则的理论基础。

当然，Python 不是纯函数式语言，cell 里可以有 `print`、可以修改全局对象、可以发网络请求。marimo 的做法是：在语义模型上把 cell 当作纯函数对待（依赖只看 defs/refs），对真正的副作用（如 stdout）则显式捕获。本项目的执行引擎用 `contextlib.redirect_stdout` 把 cell 的打印重定向到缓冲区，作为 cell 的 `stdout` 输出：

```python
# backend/core/executor.py（节选）
buf = io.StringIO()
with contextlib.redirect_stdout(buf):
    exec(compile(tree, f"<cell:{cell.cell_id}>", "exec"), self._global_ns)
cell.stdout = buf.getvalue()
```

这样既允许副作用存在，又把它纳入 cell 的"输出"而非隐藏状态，保持了模型的可推理性。

## reactive 在 notebook 中的体现

把 notebook 映射到 reactive 模型，对应关系非常自然：

- **cell = 计算节点**：每个 cell 是一个纯函数，输入是它引用的变量，输出是它定义的变量和显示内容。
- **变量引用 = 数据流边**：cell A 定义了 `x`，cell B 引用了 `x`，就有一条从 A 指向 B 的边。
- **修改一个 cell = 触发一次更新**：系统沿着依赖图传播这次变更，重算所有下游 cell。

关键在于，这些"依赖关系"不需要用户显式声明，marimo 通过 **AST 静态分析**自动从代码里提取每个 cell 的 defs（定义了哪些变量）和 refs（引用了哪些变量），从而自动构建出整张依赖图。这是 reactive 能"零标注"工作的前提。

看本项目是怎么把这段话变成代码的。首先是 AST 分析，提取 defs/refs：

```python
# backend/core/ast_analyzer.py（节选）
def analyze_cell(code: str) -> tuple[set[str], set[str]]:
    if not code.strip():
        return set(), set()
    tree = ast.parse(code)
    defs = _extract_top_level_defs(tree)
    refs = _extract_refs(tree, defs)
    return defs, refs
```

`_extract_top_level_defs` 识别赋值、函数定义、导入等绑定；`_extract_refs` 收集所有变量读取，减去局部绑定和内置名（`print`、`len` 等）。结果是两个集合：这个 cell 定义了什么、引用了什么。

然后是 DAG 构建，把多个 cell 的 defs/refs 连成图：

```python
# backend/core/graph.py（节选）
def _rebuild(self) -> None:
    self._downstream = defaultdict(set)
    self._upstream = defaultdict(set)
    var_to_cell: dict[str, str] = {}
    for cell_id, cell in self._cells.items():
        for var in cell.defs:
            if var in var_to_cell:
                raise DuplicateDefinitionError(f"变量 '{var}' 重复定义")
            var_to_cell[var] = cell_id
    for cell_id, cell in self._cells.items():
        for var in cell.refs:
            upstream_id = var_to_cell.get(var)
            if upstream_id is not None and upstream_id != cell_id:
                self._downstream[upstream_id].add(cell_id)
                self._upstream[cell_id].add(upstream_id)
```

逻辑清晰：先建一张"变量 → 定义它的 cell"的表（并检测重复定义），再遍历每个 cell 的 refs，找到每个引用变量定义在哪个 cell，从而连出上下游边。整张图完全从代码静态分析得来，不依赖任何运行时信息。

## 与命令式编程的对比

命令式编程里，语句是一条条"指令"，按书写顺序执行，每条指令改变程序状态。你改了第 10 行，第 20 行不会自动重跑，状态是否一致全靠你自己维护——这正是 Jupyter 的模型。

reactive 编程里，语句是一个个"声明"，描述数据之间的约束关系，执行顺序由依赖图决定，状态由系统保证一致。你改了任一声明，系统自动重算所有受影响的声明——这是 marimo 的模型。

两种范式并非对立，而是不同抽象层次。命令式适合描述"怎么做"的细节，reactive 适合描述"是什么"的关系。notebook 的本质是探索数据之间的关系，因此 reactive 是更贴切的模型。

下表把两种范式在 notebook 场景下的差异并列对比：

| 维度 | 命令式（Jupyter） | reactive（marimo） |
|------|-------------------|---------------------|
| 基本单元 | 一条指令 | 一个声明（cell） |
| 执行触发 | 用户显式点击 | 数据变化自动触发 |
| 执行顺序 | 书写顺序或点击顺序 | 依赖图的拓扑序 |
| 状态维护 | 用户负责 | 系统负责 |
| 改一处后 | 手动重跑受影响代码 | 自动重算下游，短路无关 |
| 可复现性 | 依赖运行历史 | 只依赖源码 |

再看执行顺序的例子。假设三个 cell `x = 1`、`y = x + 10`、`z = y * 2`。命令式下你可以先跑第二个（报 `NameError`，因为 x 还没定义），再跑第一个——顺序完全由你。reactive 下系统看依赖图 A→B→C，永远按 A、B、C 的拓扑序执行，你改 A 后自动重算 B、C，不存在"先跑 B"这种操作。

marimo 的贡献，就是让 Python 这种命令式语言在 notebook 场景下具备了 reactive 的体验，而又不强迫用户学一套新语法——你写的还是普通 Python，reactive 在幕后自动生效。用户的心智模型从"我该按什么顺序点运行"变成了"我要描述什么数据关系"，这个转变看似微小，却让 notebook 从"易错的草稿本"变成了"可信赖的交互式计算文档"。
