# marimo 设计哲学

marimo 不是一个偶然出现的工具，它的每一处设计都源自四条明确的原则。这四条原则既是设计目标，也是评判实现是否"够 marimo"的标尺。本章逐一阐述这四大原则、它们的动机，以及它们如何互相支撑。

## 原则一：Reactivity（响应式）

**含义**：notebook 中任一 cell 的代码被修改后，所有依赖它的 cell 自动重新执行，结果自动更新，无需用户手动点击运行。

**动机**：直接消除 Jupyter 的隐藏状态问题。当系统而非用户负责维护一致性时，"忘了重跑某个 cell"这类错误从根本上不可能发生。

**实现方式**：对每个 cell 做 AST 静态分析，提取 defs 与 refs，构建全局 DAG。cell 修改时，沿 DAG 找出所有下游节点，按拓扑序重算，并对无关分支短路。

落到代码上，响应式的核心是 `Executor.run_cell`：改了某个 cell 后，只重算它和它的后代。

```python
# backend/core/executor.py（节选）
def run_cell(self, cell_id: str) -> list[str]:
    order = self._graph.execution_order_from(cell_id)
    for cid in order:
        self._cleanup_cell_vars(cid)
    short_circuited = False
    for cid in order:
        cell = self._graph.get_cell(cid)
        if short_circuited or self._has_failed_upstream(cid):
            cell.mark_stale()
            continue
        self._execute_cell(cell)
        if cell.has_error:
            short_circuited = True
    return executed
```

三个关键动作：第一，`execution_order_from` 只返回被改 cell 及其后代的拓扑序，无关 cell 不在列表里（短路）；第二，执行前先清掉这些 cell 旧定义的变量，避免残留污染；第三，一旦某个 cell 出错，后续后代全部 `mark_stale()` 而非强行执行（错误传播）。这三点合起来，就是"改一处、自动传播、算到哪坏到哪、坏掉的后代标记为过期"。

## 原则二：No hidden state（无隐藏状态）

**含义**：notebook 在任意时刻呈现的代码与内存状态必须一致——你看到什么代码，就对应什么执行结果，不存在"屏幕显示 A 但内存里是 B"的情况。

**动机**：隐藏状态是 Jupyter 调试痛苦的根源。消除它，notebook 才可信赖、可复现、可分享。

**实现方式**：这是 Reactivity 的直接推论。既然任何修改都会自动传播到所有下游，状态就不会"过期"。但仅靠 reactive 还不够，marimo 还禁止了"乱序执行"——用户不能选择性地重跑某个 cell，执行完全由依赖图驱动。此外，cell 不允许产生隐式的全局副作用，从语义上杜绝状态漂移。

本项目中，"无隐藏状态"具体由两处代码保证。第一是 `CellStatus` 状态机，每个 cell 的状态永远明确（`IDLE`/`PENDING`/`RUNNING`/`DONE`/`ERROR`/`STALE`）。不存在"看起来成功其实是旧值"的隐式状态——前端根据 `status` 渲染不同视觉标记，用户一眼就能区分"新鲜"和"过期"。第二是 `mark_stale` 方法，出错 cell 的后代不是"保留旧输出"，而是被显式清空并标记：

```python
# backend/core/cell.py（节选）
def mark_stale(self) -> None:
    self.status = CellStatus.STALE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}
```

清空 `output`、`stdout`、`namespace`，意味着 stale cell 不会展示任何"可能过期的结果"。这比 Jupyter 的"留着旧输出让人误以为是对的"要诚实得多。

## 原则三：Pure Python（纯 Python）

**含义**：notebook 的存储格式是普通 `.py` 文件，每个 cell 是一个被 `cell` 装饰器标记的函数。没有 JSON、没有嵌入输出、没有自定义二进制格式。

**动机**：让 notebook 重新成为版本控制的一等公民。`git diff` 可读、`git merge` 可行、`ruff`/`black` 可格式化、任意编辑器可打开、CI 可直接 lint。

**实现方式**：存储层把 notebook 序列化为带轻量标记的 `.py`，输出只在运行时产生并保存在内存里，不写回源文件。源文件只描述"计算逻辑"，不描述"计算结果"，这正是纯函数思想的体现。

本项目的序列化器 `graph_to_py` 是这条原则的直接实现。它遍历拓扑序，把每个 cell 写成一个被 `@app.cell` 装饰的函数，函数参数是 refs，返回值是 defs：

```python
# backend/storage/serializer.py（节选）
def graph_to_py(graph: CellGraph) -> str:
    lines: list[str] = [_HEADER]
    for cell_id in graph.topological_order():
        cell = graph.get_cell(cell_id)
        refs_str = ", ".join(sorted(cell.refs))
        defs_list = sorted(cell.defs)
        lines.append("@app.cell")
        lines.append(f"def _({refs_str}):")
        # ... 写入 cell.code 和 return defs，绝不写 output / stdout / 图片
    return "\n".join(lines)
```

几个设计决策：函数名统一用 `_`，避免改 cell 顺序产生无意义 diff；按拓扑序输出，保证文件自上而下可顺序执行；输出结果完全不写入，只写源码。反向的解析器 `py_to_graph` 用 AST 把这些函数还原成 `Cell` 对象，形成双向无损转换。

## 原则四：Deterministic（确定性）

**含义**：给定同一份 notebook 源码和同一份输入数据，无论在何时、何地、以何种顺序触发执行，最终状态和输出都完全一致。

**动机**：可复现是科学计算和工程交付的共同底线。确定性让 notebook 可以作为可信的交付物，而非"在我机器上能跑"的一次性脚本。

**实现方式**：执行由 DAG 拓扑序唯一决定（对同一组 cell，拓扑序虽不唯一但结果等价，因为每个 cell 是纯函数）；随机性、时间等非确定源需通过显式的 seed 或 mock 注入。Deterministic 是前三条原则共同作用的结果，而非独立实现的功能。

确定性的代码根基是拓扑排序的"结果等价性"。本项目的 `topological_order` 在选下一个节点时用 `sorted` 保证确定性——即便不排序，只要每个 cell 是纯函数，不同合法拓扑序的结果也等价；排序进一步让"执行轨迹"本身也确定，便于调试和对比。

## 四条原则如何互相支撑

这四条原则并非孤立，它们构成一个自洽的闭环：

- **Reactivity** 是机制，**No hidden state** 是机制带来的保证。
- **Pure Python** 让源码成为"单一事实来源"，使 Reactivity 有确定的依赖图可分析。
- **Deterministic** 是 Reactivity + Pure Python + 纯函数 cell 共同推出的最终属性。

抽掉任何一条，另外三条都会松动：没有 Pure Python，源码和状态混在一起，reactive 无法干净分析依赖；没有 Reactivity，Pure Python 只是一个格式更好的 Jupyter，状态仍会漂移；没有 Deterministic，reactive 的自动重算就不可信赖。四者缺一不可，这正是 marimo 设计的内在一致性所在。

可以用一个反例加深理解。假设我们放松"Pure Python"，允许把输出写回 `.py` 文件（像 Jupyter 那样）。那么改一个 cell 后，序列化会把新输出写进文件，文件的依赖结构可能被输出里的字符串干扰（比如输出里恰好包含 `import` 字样），AST 分析的输入就不再是"纯源码"而是"源码 + 上次输出"。Reactivity 的依赖图变得不稳定，No hidden state 也无从保证——你看到的文件既含旧输出又含新代码，状态一致性崩塌。这就是为什么 marimo 坚持"源文件只写逻辑不写结果"。

再看一个放松"Reactivity"的反例。假设允许用户手动选择重跑某个 cell（像 Jupyter 那样）。那么用户可以重跑 cell B 而不重跑它依赖的 cell A，B 用到的就是旧的 A 输出，隐藏状态立刻出现。No hidden state 和 Deterministic 同时失效。这就是为什么 marimo 禁止选择性重跑，一切由 DAG 驱动。

四条原则的关系可以画成一张依赖图：

```
Pure Python ──→ 提供可分析的源码 ──→ Reactivity
                                        │
                                        ↓
                                   No hidden state
                                        │
                                        ↓
                                   Deterministic
```

Pure Python 是地基，Reactivity 是建在地基上的引擎，No hidden state 是引擎的运行保证，Deterministic 是三者共同推出的最终属性。本项目的每一行代码，都可以归入这四条原则的某一条或多条之下——后续章节会不断回到这张图，把抽象原则映射到具体实现。
