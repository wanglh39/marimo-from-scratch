# marimo 设计哲学

marimo 不是一个偶然出现的工具，它的每一处设计都源自四条明确的原则。这四条原则既是设计目标，也是评判实现是否"够 marimo"的标尺。本章逐一阐述这四大原则、它们的动机，以及它们如何互相支撑。

## 原则一：Reactivity（响应式）

**含义**：notebook 中任一 cell 的代码被修改后，所有依赖它的 cell 自动重新执行，结果自动更新，无需用户手动点击运行。

**动机**：直接消除 Jupyter 的隐藏状态问题。当系统而非用户负责维护一致性时，"忘了重跑某个 cell"这类错误从根本上不可能发生。

**实现方式**：对每个 cell 做 AST 静态分析，提取 defs 与 refs，构建全局 DAG。cell 修改时，沿 DAG 找出所有下游节点，按拓扑序重算，并对无关分支短路。这一机制是本项目的核心，后续章节会逐层展开其实现细节。

## 原则二：No hidden state（无隐藏状态）

**含义**：notebook 在任意时刻呈现的代码与内存状态必须一致——你看到什么代码，就对应什么执行结果，不存在"屏幕显示 A 但内存里是 B"的情况。

**动机**：隐藏状态是 Jupyter 调试痛苦的根源。消除它，notebook 才可信赖、可复现、可分享。

**实现方式**：这是 Reactivity 的直接推论。既然任何修改都会自动传播到所有下游，状态就不会"过期"。但仅靠 reactive 还不够，marimo 还禁止了"乱序执行"——用户不能选择性地重跑某个 cell，执行完全由依赖图驱动。此外，cell 不允许产生隐式的全局副作用（如原地修改某变量而不声明），从语义上杜绝状态漂移。

## 原则三：Pure Python（纯 Python）

**含义**：notebook 的存储格式是普通 `.py` 文件，每个 cell 是一个被 `cell` 装饰器标记的函数或一段带标记的代码块。没有 JSON、没有嵌入输出、没有自定义二进制格式。

**动机**：让 notebook 重新成为版本控制的一等公民。`git diff` 可读、`git merge` 可行、`ruff`/`black` 可格式化、任意编辑器可打开、CI 可直接 lint。

**实现方式**：存储层把 notebook 序列化为带轻量标记的 `.py`，输出（图表、表格、文本）只在运行时产生并保存在内存或单独的缓存目录里，不写回源文件。源文件只描述"计算逻辑"，不描述"计算结果"，这正是纯函数思想的体现。

## 原则四：Deterministic（确定性）

**含义**：给定同一份 notebook 源码和同一份输入数据，无论在何时、何地、以何种顺序触发执行，最终状态和输出都完全一致。

**动机**：可复现是科学计算和工程交付的共同底线。确定性让 notebook 可以作为可信的交付物，而非"在我机器上能跑"的一次性脚本。

**实现方式**：执行由 DAG 拓扑序唯一决定（对同一组 cell，拓扑序虽不唯一但结果等价，因为每个 cell 是纯函数）；随机性、时间等非确定源需通过显式的 seed 或 mock 注入，系统提供机制鼓励而非强制。Deterministic 是前三条原则共同作用的结果，而非独立实现的功能。

## 四条原则如何互相支撑

这四条原则并非孤立，它们构成一个自洽的闭环：

- **Reactivity** 是机制，**No hidden state** 是机制带来的保证。
- **Pure Python** 让源码成为"单一事实来源"，使 Reactivity 有确定的依赖图可分析。
- **Deterministic** 是 Reactivity + Pure Python + 纯函数 cell 共同推出的最终属性。

抽掉任何一条，另外三条都会松动：没有 Pure Python，源码和状态混在一起，reactive 无法干净分析依赖；没有 Reactivity，Pure Python 只是一个格式更好的 Jupyter，状态仍会漂移；没有 Deterministic，reactive 的自动重算就不可信赖。四者缺一不可，这正是 marimo 设计的内在一致性所在。
