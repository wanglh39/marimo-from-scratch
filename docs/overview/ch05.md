# 整体架构总览

本章从宏观俯瞰整个 marimo-from-scratch 项目的架构，建立"模块—职责—数据流"的全景图，为后续深入每一层做铺垫。理解了这张地图，再读具体代码就不会迷失在细节里。

## 分层架构

项目采用清晰的四层架构，自底向上依次为：

```
┌─────────────────────────────────────────────┐
│  frontend   (React + WebSocket 客户端)        │   ← UI 渲染、cell 编辑、结果展示
├─────────────────────────────────────────────┤
│  server     (FastAPI + WebSocket)             │   ← 协议层、session 管理、消息路由
├─────────────────────────────────────────────┤
│  storage    (.py 文件读写、cell 序列化)        │   ← notebook 持久化、纯 Python 格式
├─────────────────────────────────────────────┤
│  core       (AST 分析、DAG、执行引擎)         │   ← reactive 核心：依赖、调度、执行
└─────────────────────────────────────────────┘
```

- **core（执行引擎）**：最底层也是最核心的一层。负责对 cell 源码做 AST 静态分析，提取 defs/refs；构建并维护全局 DAG；在 cell 变更时按拓扑序调度重算，做增量执行与短路。这一层完全不关心 UI 和网络，是纯 Python 的算法层。
- **storage（文件格式）**：负责 notebook 的持久化。把一组 cell 序列化为带 `cell` 装饰器标记的 `.py` 文件，并能反向解析回来。输出结果不写入源文件，保持 Pure Python 特性。
- **server（WebSocket 服务）**：基于 FastAPI 提供 HTTP 接口和 WebSocket 长连接。管理多用户 session，把前端发来的编辑/执行请求路由到对应 session 的 executor，并把执行结果流式推回前端。
- **frontend（React 前端）**：用 React 实现的 notebook UI。每个 cell 是一个编辑器 + 输出区，通过 WebSocket 与 server 双向通信，展示代码、运行结果、错误和 UI 控件。

分层的关键约束是**依赖方向只能自上而下**：frontend 依赖 server 的协议，server 依赖 core 和 storage，core 不依赖任何人。这保证了 core 可以独立测试、独立复用——你完全可以拿 `CellGraph` 和 `Executor` 去做一个不带 UI 的批处理脚本，而不需要装 FastAPI 或 React。本项目的 `App` 类就演示了这一点，它只用 core 层就能让 `.py` notebook 在命令行里跑起来：

```python
# backend/app.py（节选）
class App:
    def cell(self, func):
        self._funcs.append(func)
        return func
    def run(self) -> None:
        graph = self._build_graph()
        executor = Executor(graph)
        executor.inject("ui", ui_module)
        executor.run_all()
```

这种可剥离性是分层架构的价值所在：core 是纯算法，server 是 core 的网络壳，frontend 是 server 的 UI 壳，每层都能单独取用。

## 数据流：一次编辑的完整旅程

当用户在前端修改了某个 cell 的代码并保存，数据流如下：

1. **frontend**：CodeMirror 检测到 cell 内容变更，打包成 `{cell_id, new_code}` 消息，通过 WebSocket 发往 server。
2. **server**：收到消息，找到该 WebSocket 所属的 session，把请求转交该 session 的 executor。
3. **core / executor**：对 `new_code` 做 AST 分析，得到新的 defs/refs；更新 DAG 中该节点的依赖边；找出所有下游受影响节点（闭包）；按拓扑序排序；对每个节点执行其代码，短路掉无关分支。
4. **core → server**：每个 cell 执行完毕，把输出（值、stdout、图表数据、错误）回传给 server。
5. **server → frontend**：server 通过 WebSocket 把结果增量推回前端。
6. **frontend**：对应 cell 的输出区更新，用户立即看到新结果。

整条链路里，**DAG 是单一事实来源**：谁依赖谁、该重算谁、按什么顺序算，全部由 DAG 决定。server 和 frontend 只是 DAG 状态的"投影"。

这条数据流在代码里有一个清晰的汇聚点：`NotebookSession.handle_message`。它把前端发来的不同消息类型路由到对应处理函数。以"修改 cell 代码"为例，`_handle_update_cell` 先用 `analyze_cell` 做静态分析，再用新 defs/refs 重建图中的该节点：

```python
# backend/server/session.py（节选）
def _handle_update_cell(self, msg: dict) -> list[dict]:
    cell_id = msg["cell_id"]
    new_code = msg["code"]
    defs, refs = analyze_cell(new_code)
    new_cell = Cell(cell_id=cell_id, code=new_code, defs=defs, refs=refs)
    self._graph.remove_cell(cell_id)
    self._graph.add_cell(new_cell)
    return [make_graph_changed_message(self._graph)]
```

注意这里只更新图结构、返回新的依赖关系，并不立即执行——执行由前端发 `run_cell` 消息触发。这种"改图"和"执行"的分离，让前端可以先展示新的依赖关系（哪些 cell 变成了 stale），再由用户决定何时重算，符合交互直觉。执行后的结果通过 `protocol.py` 的 `make_cell_result_message` 序列化成 JSON 推回前端，一条消息携带 cell 的全部可见状态：状态码、输出值、stdout、异常、UI 组件。前端收到后直接渲染，无需再请求任何东西——这种"一次消息、全量状态"的设计简化了前后端协议，避免了增量同步的复杂状态机。

## 项目目录结构

```
marimo/
├── backend/
│   ├── core/            # cell.py, ast_analyzer.py, graph.py, executor.py
│   ├── storage/         # serializer.py, parser.py
│   ├── server/          # webapp.py, session.py, protocol.py
│   ├── components/      # ui.py (Slider/Button/Checkbox)
│   └── app.py           # 命令行运行入口
├── frontend/src/        # App.tsx, useNotebook.ts, components/
├── docs/                # 本文档
└── tests/               # 镜像目录结构的测试
```

目录结构遵循"镜像测试"约定：`tests/` 下的路径与 `backend/` 下的路径一一对应，比如 `backend/core/graph.py` 的测试在 `tests/core/test_graph.py`。这样找测试文件和找源文件一样直接，降低心智负担。

## 里程碑 M1–M5 对应模块

项目按五个里程碑渐进交付，每个里程碑对应一个可独立验证的能力切片：

- **M1 — AST 静态分析**：实现对单段代码提取 defs/refs，对应 `core/ast_analyzer.py`。验收：给定任意 Python 代码片段，正确输出其定义和引用的变量集合。例如 `analyze_cell("y = x + 10")` 返回 `({"y"}, {"x"})`。
- **M2 — DAG 构建与拓扑排序**：把多个 cell 的 defs/refs 组装成 DAG，实现拓扑排序与环检测，对应 `core/graph.py`。验收：能检测出循环依赖并抛 `CyclicDependencyError`，能给出合法执行序。
- **M3 — 执行引擎（增量 + 短路）**：实现按拓扑序执行 cell、变更后只重算下游、短路无关分支，对应 `core/executor.py`。验收：改一个 cell，只有依赖链上的 cell 重跑，其余不动。
- **M4 — 存储层**：实现 notebook ↔ `.py` 的双向序列化，对应 `storage/`。验收：`py_to_graph(graph_to_py(g))` 得到的图与 `g` 含相同的 cell 集合；`.py` 可被 ruff 格式化。
- **M5 — Server + Frontend**：打通 WebSocket 链路，前端可编辑 cell、实时看到 reactive 更新，对应 `server/` 与 `frontend/`。验收：浏览器里拖动 `ui.slider`，依赖它的 cell 输出实时变化。

五个里程碑自底向上、逐层闭环，每一层都建立在前一层的确定性之上。这种渐进式交付保证了任何时刻项目都处于可运行状态：M1 完成时能做静态分析，M2 完成时能排执行序，M3 完成时能在命令行跑 reactive notebook，M4 完成时能存盘重载，M5 完成时能在浏览器里交互。后续章节将按这个顺序，逐层深入每一层的实现原理与代码细节。
