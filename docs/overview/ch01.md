# 什么是 marimo

## 一个像电子表格的 Python notebook

marimo 是一个 **reactive Python notebook**。所谓 reactive，指的是"响应式"——当你修改了某一个 cell（单元格）之后，所有依赖它的 cell 都会自动重新计算并更新结果，就像 Excel 电子表格一样：改一个格子，引用它的格子立刻跟着变。

在传统编程里，变量是一次性赋值的，后面的代码改了前面的定义，你必须手动重新运行所有受影响的代码才能看到新结果。而在 marimo 里，你只需要改一个 cell，整个 notebook 的状态会自动收敛到一致。这种"改一处、自动传播"的体验，正是 reactive 编程范式带给 notebook 的核心价值。

为了建立直觉，先看一个最小的 marimo notebook 长什么样。它就是一个普通的 `.py` 文件，每个 cell 用 `@app.cell` 装饰器标记：

```python
from backend.app import App
app = App()

@app.cell
def _():
    x = 1
    return (x,)

@app.cell
def _(x):
    y = x + 10
    return (y,)

@app.cell
def _(y):
    y
    return
```

三个 cell 依次定义 `x`、`y = x + 10`、显示 `y`。第二个 cell 的参数 `(x)` 显式声明了它依赖 `x`，第三个 cell 的参数 `(y)` 声明依赖 `y`。当你把第一个 cell 里的 `x = 1` 改成 `x = 100` 并保存时，后两个 cell 会**自动**重跑，`y` 立刻变成 `110`。你不需要点"运行全部"，也不需要记得"我改了 x，得重跑 y"——系统替你记着依赖关系，替你触发重算。

这正是 Excel 的工作方式：A1 填 `1`，B1 填 `=A1+10`，改 A1 为 `100`，B1 自动变 `110`。marimo 把这种体验搬到了 Python notebook 里，"格子"换成"cell"，"公式"换成"一段 Python 代码"。

```
传统 notebook（命令式）：        marimo（响应式）：
  cell1: x = 1                     cell1: x = 1
  cell2: y = x + 10                cell2: y = x + 10   ← 依赖 x
  cell3: print(y)                  cell3: y            ← 依赖 y

  改 cell1 后：                    改 cell1 后：
  必须手动重跑 cell2、cell3        系统自动重跑 cell2、cell3
  否则 y 还是旧值                  y 立即更新为新值
```

左侧把"保持一致"的责任推给人，右侧把它交给系统。这种差异在几十个 cell 的真实 notebook 里，会演变成"调试两小时 vs 调试两分钟"的鸿沟。

值得强调的是，marimo 的 reactive 不是靠运行时追踪变量读写实现的（那样太慢且易错），而是靠**编译期静态分析**：在 cell 保存的瞬间，系统用 AST 解析出它定义和引用了哪些变量，据此更新依赖图。即便你从不运行某个 cell，系统也知道它"将来"会依赖谁——依赖关系是代码本身的属性，不是运行历史的副产物。这是 marimo 能做到"零标注 reactive"的技术基石。

## 三个核心能力

marimo 把自己定位为一个"下一代 notebook"，它围绕三个核心能力构建：

1. **Reactive（响应式执行）**：基于静态分析自动建立 cell 之间的依赖关系，构成有向无环图（DAG）。任一 cell 修改后，仅重算其下游依赖，既保证一致性又避免冗余计算。
2. **Pure Python（纯 Python 文件即 notebook）**：notebook 本身就是一个 `.py` 文件，用 `cell` 装饰器标记每个 cell。可以用 `git diff` 正常查看改动、用 `ruff`/`black` 格式化，彻底告别 JSON 格式的 `.ipynb`。
3. **Notebook 即 Web App**：同一个 `.py` 文件，既能作为交互式 notebook 用于探索，也能一键转化为带 UI 控件的 Web 应用部署给最终用户。

下面分别用真实代码说明这三点。

**Reactive 的落地。** `CellGraph` 用每个 cell 的 `defs` 与 `refs` 自动连边：若 cell A 的 `defs` 与 cell B 的 `refs` 有交集，则 B 依赖 A。改了 cell A 后，执行引擎只重算 A 及其后代：

```python
# backend/core/graph.py（节选）
def execution_order_from(self, cell_id: str) -> list[str]:
    affected = self.descendants(cell_id) | {cell_id}
    return self._topological_sort_subset(affected)
```

`descendants` 用 BFS 沿下游边收集所有传递依赖的 cell，没落在 `affected` 集合里的 cell 完全不会被触碰——这就是"短路"。若还存在一个 `z = 999` 的 cell 且无人引用它，改 `x` 时 `z` 不会重跑。

**Pure Python 的落地。** 存储层把 notebook 写成带 `@app.cell` 装饰器的普通 Python 文件，输出结果不写回源文件。生成的文件能被 `ruff format` 格式化、能被 `git diff` 逐行审查——notebook 重新成为版本控制的一等公民。函数名统一用 `_`，真正的身份标识是参数（refs）和返回值（defs），这样调整 cell 顺序不会产生无意义的 diff。

**Notebook 即 Web App 的落地。** 本项目提供 `ui.slider`、`ui.button`、`ui.checkbox` 等组件，它们是普通的 Python 对象，在 cell 里创建，值变化时触发依赖它的 cell 重跑：

```python
@app.cell
def _():
    s = ui.slider(0, 100, value=50)
    return (s,)

@app.cell
def _(s):
    print(s.value * 2)
    return
```

拖动滑块时，第二个 cell 自动重跑并打印新值。同一份代码，在浏览器里是带滑块的交互应用，在命令行里 `python notebook.py` 也能跑——notebook 和 app 是同一份代码。

## 与 Jupyter 的本质区别

Jupyter 是当下最流行的 notebook 工具，但它的执行模型是**命令式**的：cell 之间没有显式依赖关系，执行顺序完全由用户点击决定。这导致了一个臭名昭著的问题——**隐藏状态**：你看到的代码和实际运行的内存状态可能完全不一致，因为你可以乱序执行、反复执行某个 cell，而 notebook 不会告诉你哪些 cell 的输出已经"过期"了。

marimo 的本质区别在于：它把 notebook 当作一个**纯函数的集合**来看待。每个 cell 的输出只取决于它引用的变量，而变量来源于其他 cell 的定义。通过 AST 静态分析，marimo 能精确知道每个 cell 定义了哪些变量（defs）、引用了哪些变量（refs），从而自动构建依赖图。执行时按拓扑排序进行，任何修改都会触发依赖链上所有受影响 cell 的重算，并短路掉无关分支。

这种"纯函数集合"的视角，落地为 `analyze_cell` 函数——它对一段代码做 AST 解析，返回 `(defs, refs)`：

```python
# backend/core/ast_analyzer.py（节选）
def analyze_cell(code: str) -> tuple[set[str], set[str]]:
    if not code.strip():
        return set(), set()
    tree = ast.parse(code)
    defs = _extract_top_level_defs(tree)
    refs = _extract_refs(tree, defs)
    return defs, refs
```

给定 `y = x + 10`，它返回 `defs={"y"}`、`refs={"x"}`。给定 `import numpy as np`，它返回 `defs={"np"}`、`refs=set()`。这些信息纯粹来自静态分析，不需要运行代码——依赖关系从代码本身长出来，而不是要用户手写"这个 cell 依赖那个 cell"。

下表把两种工具的核心差异并列对比：

| 维度 | Jupyter | marimo |
|------|---------|--------|
| 执行模型 | 命令式，用户点击驱动 | 响应式，依赖图驱动 |
| 依赖关系 | 无显式记录 | AST 静态分析自动提取 defs/refs |
| 改一个 cell 后 | 用户自行决定重跑哪些 | 系统自动重跑所有下游，短路无关分支 |
| 状态一致性 | 不保证，可能有隐藏状态 | 保证，屏幕即内存 |
| 文件格式 | `.ipynb`（JSON，含输出与 base64） | `.py`（纯 Python，不含输出） |
| notebook → app | 通常要重写（Streamlit/Dash） | 同一份代码即可 |

再举一个具体场景。假设你有数据清洗 notebook：cell A 加载数据，cell B 过滤异常值，cell C 画分布图。在 Jupyter 里，改了 cell A 的数据源路径，必须记得从 A 开始往下逐个重跑，漏跑一个图表就是错的。在 marimo 里，改 cell A 后 B 和 C 自动重跑，且如果还有个 cell D 在算完全无关的另一份数据，它不会被波及。前者要求你维护一张"谁依赖谁"的心智地图，后者把这张地图交给代码自己分析出来。

简单说：**Jupyter 把 notebook 当作一串可独立运行的代码块，marimo 把 notebook 当作一张会自动重算的计算图**。前者把"保持状态一致"的责任推给了人，后者把这个责任交给了系统。这正是本项目"从零实现 marimo"要复现的核心思想——后续章节会逐层拆解，这张"会自动重算的计算图"是如何用几百行 Python 从无到有搭起来的。
