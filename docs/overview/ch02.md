# Jupyter 的痛点

Jupyter Notebook 在数据科学领域统治了十几年，几乎成了"数据探索"的代名词。但任何一个用过 Jupyter 超过三个月的人，都会对它的某些"坑"刻骨铭心。这些痛点并非偶然，而是源于 Jupyter 的底层执行模型——**一个可变的全局命名空间 + 用户驱动的执行顺序**。本章梳理 Jupyter 的四大痛点，它们正是 marimo 诞生的直接动机。

## 痛点一：隐藏状态

这是 Jupyter 最著名的问题，俗称"out-of-order execution"。考虑下面三行 cell：

```
[1] x = 1
[2] y = x + 10      # y = 11
[3] x = 100
```

如果你现在回到 `[2]` 重新运行，`y` 会变成 `110`。但如果你**不**重跑 `[2]`，notebook 显示的 `y` 仍是 `11`，而 `x` 已经是 `100`。屏幕上的代码和内存里的状态对不上——这就是"隐藏状态"。

更糟的是，你可以删除一个 cell 的源码，但它定义的变量仍然活在内核里；你可以把 cell 顺序拖来拖去，但执行顺序由 `In[ ]` 的编号决定，和视觉顺序无关。调试时你永远在问自己："这个变量到底现在是多少？我是不是漏跑了哪个 cell？" 这种心智负担在长 notebook 里会指数级放大。

隐藏状态还会以更隐蔽的方式出现。比如你在 cell 5 里写 `import pandas as pd`，后来觉得这个 cell 太乱就删掉了，但 `pd` 仍然活在内核里——cell 20 里的 `pd.read_csv(...)` 照常运行。你以为代码自包含，其实它依赖一个已经看不见的幽灵。把 notebook 发给同事，对方从头运行直接 `NameError: name 'pd' is not defined`，而你百思不得其解："在我机器上明明能跑啊。"

marimo 从机制上消灭了这类问题。它的执行引擎在改任意 cell 后，会沿依赖图重算所有受影响 cell，并把出错或过期的 cell 显式标记为 `STALE`。本项目的 `CellStatus` 枚举覆盖了 cell 生命周期的一切可能状态：

```python
# backend/core/cell.py（节选）
class CellStatus(Enum):
    IDLE = "idle"
    PENDING = "pending"
    RUNNING = "running"
    DONE = "done"
    ERROR = "error"
    STALE = "stale"
```

`STALE` 表示"上游出错，我没法算"，`ERROR` 表示"我自己出错了"。不存在"屏幕显示成功但其实是旧值"的中间态——要么是 `DONE` 的最新值，要么明确告诉你"过期了"。用户永远不需要猜"这个 cell 的输出是不是最新的"。

## 痛点二：.ipynb 的 JSON 格式

Jupyter 的 `.ipynb` 文件本质上是一个巨大的 JSON，里面塞满了源码、输出、图片的 base64 编码、执行计数、元数据。一个典型的 cell 条目大致长这样：

```json
{
  "cell_type": "code",
  "execution_count": 1,
  "outputs": [{"data": {"image/png": "iVBORw0KG...(几千行 base64)..."}, ...}],
  "source": ["x = 1\n", "y = x + 10\n", "y"]
}
```

这带来三个子问题：

- **diff 不友好**：改一行代码，git diff 里混着几千行的 base64 图片变化，根本看不清改了什么。一次改 `x = 1` 到 `x = 2`，diff 里可能滚出 3000 行，因为重新跑后图片的 base64 完全变了。
- **merge 几乎不可能**：两个人同时改 notebook，合并冲突时面对的是一坨 JSON，没有语义级别的三方合并工具。冲突标记插在 JSON 中间，连 JSON 都不再是合法的，得手动修。
- **代码审查失效**：PR 里贴一个 `.ipynb`，reviewer 只能看 rendered 的 HTML，没法像看普通 `.py` 那样逐行评论。静态分析工具（ruff、mypy）也对 `.ipynb` 束手无策。

结果是 notebook 成了版本控制的二等公民，"reproducible science"成了一句空话。

marimo 的解法是把 notebook 存成普通 `.py`。本项目的序列化器 `graph_to_py` 只写源码，不写输出——改 `x = 1` 到 `x = 2`，`git diff` 只有一行：

```diff
-    x = 1
+    x = 2
```

干净、可审查、可合并、可被 ruff 格式化。输出（图表、表格）只在运行时产生，留在内存或单独的缓存目录里，绝不污染源文件。

## 痛点三：执行顺序依赖 cell 排列

Jupyter 里 cell 的物理排列没有任何强制力。你可以把数据加载放在最后，把画图放在最前，只要按某个特定顺序点击运行就能跑通。这导致 notebook **不可重放**：重启内核后从头到尾顺序执行，往往直接报错——因为某个 cell 依赖的变量在它上方并未定义。用户不得不在 notebook 顶部写一句"请按顺序运行"，但这只是君子协定，系统并不保证。

更隐蔽的是，这种"可跑通但不可重放"的 notebook 在分享时极具欺骗性：作者按他的肌肉记忆点了一遍，能跑；读者按从上到下的顺序跑，崩了。两人对同一份代码的理解完全不同。

marimo 用拓扑排序根治了这个问题。执行顺序不由 cell 在文件里的位置决定，而由依赖图的拓扑序决定。本项目的 `topological_order` 用 Kahn 算法实现，无论 cell 在文件里怎么排列，总是返回一个"先定义后引用"的合法顺序：

```python
# backend/core/graph.py（节选）
def topological_order(self) -> list[str]:
    in_degree = {cid: len(self._upstream.get(cid, set())) for cid in self._cells}
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set())):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    if len(order) != len(self._cells):
        raise CyclicDependencyError(f"检测到循环依赖")
    return order
```

如果出现循环依赖（cell A 依赖 B、B 又依赖 A），直接抛 `CyclicDependencyError`，而不是像 Jupyter 那样默默让你跑出一个半对半错的状态。这意味着 marimo notebook 天然可重放：任何人、任何时间、从上到下跑或让系统自己排序跑，结果一致。

## 痛点四：notebook 和 app 是两套代码

数据科学家在 notebook 里探索出一段逻辑后，想把它做成可交互的 Web 应用给业务方用，通常要**重写一遍**：用 Streamlit 或 Dash 重新组织 UI、重新接数据、重新画图。notebook 是探索态，app 是交付态，两者之间有一道巨大的鸿沟。代码重复、逻辑漂移、维护双份是常态。

举个典型场景：你在 notebook 里写了一段"根据阈值过滤数据并画图"的逻辑，业务方说"我想自己调阈值"。于是你开一个新仓库，用 Streamlit 重写：`st.slider` 调阈值、`st.dataframe` 显示表、`st.pyplot` 画图。逻辑复制了一份，以后改了过滤算法，notebook 和 app 两边都得改，迟早不同步。

marimo 的解法是让 UI 控件成为 notebook 的一等公民。本项目的 `ui` 模块提供 `slider`、`button`、`checkbox`，在 notebook 里直接用：

```python
@app.cell
def _():
    threshold = ui.slider(0, 100, value=50)
    return (threshold,)

@app.cell
def _(threshold):
    filtered = data[data["score"] > threshold.value]
    filtered
    return (filtered,)
```

拖动滑块时，第二个 cell 自动重跑，表格立刻更新。这同一份 `.py` 文件，在浏览器里打开就是带滑块的交互应用，在命令行里 `python notebook.py` 就是批处理脚本。探索和交付是同一份代码，零重复。

这四个痛点归结为一点：**Jupyter 把本该由系统保证的"一致性、可复现性、可交付性"全部甩给了用户**。marimo 的目标，就是用 reactive 执行模型 + 纯 Python 文件格式 + notebook 即 app 的设计，从根上消除这些痛点。下表总结四个痛点与 marimo 对策的对应关系：

| Jupyter 痛点 | 根因 | marimo 对策 | 落地模块 |
|--------------|------|-------------|----------|
| 隐藏状态 | 用户驱动执行 + 可变命名空间 | DAG 驱动 + STALE 标记 | `core/executor.py` |
| .ipynb JSON | 格式混入输出与元数据 | 纯 .py，输出不落盘 | `storage/serializer.py` |
| 不可重放 | 执行顺序 ≠ 书写顺序 | 拓扑序执行 + 环检测 | `core/graph.py` |
| notebook ≠ app | UI 与探索逻辑割裂 | UI 组件即 Python 对象 | `components/ui.py` |
