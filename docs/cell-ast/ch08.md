# AST 遍历实战

上一章我们说明了为什么选 AST，这一章动手遍历。理解后续的 defs/refs 提取，必须先看清 AST 长什么样、`Name` 节点的 `ctx` 又如何区分读写。这一章的目标是建立"代码 ↔ AST 节点"的直觉，让你看到一段 Python 代码就能大致脑补出它的树形，反之亦然。这种直觉是写提取器的前提——提取规则本质上是"看到某类节点就做某件事"，不熟悉节点结构就无从下手。

建立这种直觉没有捷径，只能多 dump 多看。建议的做法是：拿一段自己常写的代码，`ast.dump` 看它的树，然后对照本章的结构描述验证理解。反复几次后，你会发现自己能"看代码猜树形"——看到 `for` 就想到 `For(target, iter, body)`，看到 `import` 就想到 `Import(names=[alias])`。到这一步，写提取器的 `isinstance` 分支就成了机械劳动，不再需要频繁翻文档。本章就是把这个"对照表"给你列全，省去你逐个 dump 的时间。

## `ast.parse`：源码到树

`ast.parse` 是从文本到结构的第一步，理解它的输出是理解后续所有提取的基础。它只做语法分析，不做语义检查——比如 `x + 1` 里 `x` 是否定义它不关心，只把 `x` 解析成 `Name` 节点。这种"只管语法不管语义"的定位，让它既快又安全，也意味着提取器拿到的树是"纯结构"，所有语义判断（这是读还是写、这是顶层还是嵌套）要我们自己从节点类型和 ctx 推导。这恰好是我们想要的：语义判断的逻辑掌握在我们手里，可以按 reactive 的需求定制（比如把 builtins 过滤掉、把形参当局部），而不被解析器的默认行为束缚。这种"结构归解析器、语义归我们"的分工，是 AST 方案灵活性的来源。

```python
import ast
code = "y = x + 1"
tree = ast.parse(code)
print(ast.dump(tree, indent=2))
```

输出大致是：

```
Module(body=[
  Assign(
    targets=[Name(id='y', ctx=Store())],
    value=BinOp(
      left=Name(id='x', ctx=Load()),
      op=Add(),
      right=Constant(value=1)
    )
  )
])
```

可以看到，顶层是一个 `Module`，它的 `body` 是语句列表。这里只有一条 `Assign`，其 `targets` 是要赋值的名字（`y`，`ctx=Store`），`value` 是右侧表达式（一个 `BinOp`，左操作数是 `x`，`ctx=Load`）。`Constant(1)` 是字面量，不是 `Name`，所以不会被误当成变量。

这棵树的结构值得逐层读一遍。最外层 `Module` 是所有 `ast.parse` 结果的根，它的 `body` 永远是语句列表。这里列表只有一个元素 `Assign`，对应那行赋值。`Assign` 有两个字段：`targets` 是赋值目标列表（之所以是列表，因为 `a = b = 1` 有两个目标），`value` 是右侧表达式。目标 `Name(id='y', ctx=Store())` 表示"把 `y` 写入"；右侧 `BinOp` 是二元运算，由 `left`、`op`、`right` 三部分组成，`left` 是 `Name(id='x', ctx=Load())` 表示"读取 `x`"，`op` 是 `Add()`，`right` 是 `Constant(value=1)`。注意 `1` 是 `Constant` 不是 `Name`，所以不会被当变量——这正是 AST 不误判字面量的原因。

`ast.dump` 是调试 AST 的利器：`indent=2` 让输出带缩进，层级关系一目了然。开发提取器时，遇到拿不准的代码就 `ast.dump` 一下看树形，比翻文档快得多。这是实际开发中最高频的调试手段——写提取规则前先 dump，确认节点类型和字段名再动手。注意 `dump` 默认会省略一些空字段（如 `lineno`），若要看行号信息需传 `show_attributes=True`。另外 `dump` 的输出不是合法的 Python 字面量，只供人读，不能拿来 `eval` 重建树。

一个实用的经验是：把 `ast.dump` 的输出当成"语法构造的 X 光片"。当你疑惑"为什么这段代码的 refs 多了个意料之外的名字"时，dump 一下立刻能看到那个名字挂在哪个节点下、ctx 是什么，问题往往瞬间清晰。反过来，当你想确认提取规则覆盖了某种写法，就拿那种写法的最小例子 dump，看它的节点类型是否被你的 `isinstance` 分支命中。这种"看树写规则、拿规则验树"的循环，是开发 AST 分析器的核心工作流，比对着文档空想高效得多。

## `ast.walk`：遍历所有节点

`ast.walk(tree)` 是一个生成器，按深度优先吐出树里的每一个节点。我们常用它做"地毯式扫描"。它不挑节点类型、不维护状态，每调用一次都从根开始全新遍历，是"无状态扫描"的典型。这种无状态让它可以安全地在提取器里多次调用（比如先扫 Load 再扫 Store），不必担心前一次的残留影响后一次。不过教学版的 `_extract_refs` 把 Load 和 Store 在一次 `walk` 里同时收集，连多次调用都省了——一次遍历拿齐两类名字，再靠集合运算分类。

之所以叫"地毯式"，是因为它不挑节点类型，把树里每一个节点都访问一遍。这种"先全扫再筛"的策略适合"我要找所有某类节点"的需求，比如"所有 Load 的 Name"。如果需求是"只看顶层语句"，就不该用 `walk`（它会给出所有层级的语句），而该直接遍历 `tree.body`。选 `walk` 还是直接遍历 `body`，取决于你要的信息分布在"全树"还是"只顶层"——这是写提取器时最常做的选择。

```python
for node in ast.walk(tree):
    print(type(node).__name__)
# Module, Assign, Name, BinOp, Name, Add, Constant
```

输出顺序是"先父后子、深度优先"：从 `Module` 进入，先访问其唯一子节点 `Assign`，再下钻到 `Assign` 的 `targets` 里的 `Name(y)`，回溯后访问 `value` 即 `BinOp`，依次往下。对提取 refs 来说，顺序不重要——我们只关心"有没有 `Load` 的 `Name`"，不关心它出现在第几层。但对某些需要按出现先后处理的分析（比如海象运算符 `:=` 在表达式中间绑定变量，后续同一表达式才能引用），顺序就有意义了。

对提取 refs 来说，只要在循环里挑出 `isinstance(node, ast.Name) and isinstance(node.ctx, ast.Load)` 的节点，就能拿到所有"被读取"的名字。对提取 defs，则要更精细地看**顶层语句**的类型——用 `for stmt in tree.body` 而不是 `ast.walk`，因为函数体里的赋值不算 cell 的 def。这一点下一章详述。`walk` 的好处是"不漏一个节点"，代价是"分不清层级"，所以 defs 提取不用它，而 refs 提取（要扫全树找所有 Load）正好适合。

`walk` 还有一个容易忽略的特性：它不保证对同一棵树多次调用给出相同顺序吗？实际上它保证——每次都按同样的深度优先顺序遍历，所以结果是确定的。但这个顺序对提取 defs/refs 无关紧要，因为我们只关心"集合里有没有某个名字"，不关心它被访问的先后。只有在需要"先绑定后引用"这类顺序敏感的分析里（比如检查变量是否在绑定前被使用），才要把顺序纳入考虑，那时通常改用 `NodeVisitor` 自己控制遍历。教学版的提取器只做集合收集，`walk` 的顺序无关，所以用起来毫无负担。

## `Name.ctx` 的三种取值

`Name` 节点代表一个标识符的使用，它的 `ctx` 字段是判断语义的关键。在整个提取器里，`Name` 是被访问最频繁的节点类型——几乎每段代码都有变量读写。理解 `Name` 和它的 `ctx`，就理解了提取器八成的工作。反过来说，如果提取器在某段代码上出错，最先该排查的就是 `Name` 节点的 ctx 是否被正确判断。

理解 `Name` 节点在整棵树里的角色很重要：它是唯一承载"变量名"的节点类型。其他节点如 `FunctionDef` 的函数名是裸字符串（`stmt.name`），不是 `Name` 节点；`Attribute` 的属性名也是字符串（`node.attr`）。所以"扫所有变量名的使用"等价于"扫所有 `Name` 节点"，这是一条很干净的规则。如果你在提取器里发现漏了某个名字，第一反应应该是"它是不是不是 `Name` 节点"——比如函数名要从 `FunctionDef.name` 取，不能靠扫 `Name`。

| ctx      | 含义       | 典型出现位置                |
|----------|------------|-----------------------------|
| `Load`   | 读取变量   | 表达式、函数调用参数        |
| `Store`  | 写入变量   | 赋值左侧、for 循环目标      |
| `Del`    | 删除变量   | `del x` 中的 `x`            |

同一个名字在不同位置会有不同 ctx。例如 `x = x + 1` 里，右侧的 `x` 是 `Load`，左侧的 `x` 是 `Store`。再如 `for i in range(10): ...`，循环变量 `i` 的 `Name` 节点 ctx 是 `Store`，而 `range` 是 `Load`。`ctx` 不是字符串而是一个小类实例，所以判断要写 `isinstance(node.ctx, ast.Load)`，不能写 `node.ctx == "Load"`——后者永远为假，是初学者常犯的错误。

这个"用 isinstance 而非 ==" 的要求，源于 Python 枚举式设计的惯例。`ctx` 的三种取值是三个独立的小类（`ast.Load`/`ast.Store`/`ast.Del`），不是字符串常量。用 `isinstance` 判断能正确处理子类情况（虽然标准库的这三种没有子类，但习惯上仍用 `isinstance`），且在 IDE 里能做类型检查。写成 `node.ctx == "Load"` 不会报错但永远返回 `False`，因为 `Load` 实例不等于字符串 `"Load"`——这种静默错误极难发现，是 AST 编程的经典陷阱。

`Del` 在教学版里不特殊处理：`del x` 既不算 def 也不算 ref，因为我们只关心"执行后留下什么"和"执行前需要什么"，删除只是把已有绑定抹掉，不引入新依赖。理解 `ctx` 是理解整棵树语义的钥匙：看到 `Store` 就知道这里在绑定，看到 `Load` 就知道这里在读取，提取规则几乎就是"按 ctx 分流"。

`ctx` 的设计本身值得品味。Python 为什么要在 `Name` 节点上挂一个 ctx 而不是用不同的节点类型（如 `NameLoad`/`NameStore`）？因为同一个名字在语法上就是同一个标识符，只是"用法"不同，把用法做成 ctx 字段比拆成多个节点类型更紧凑，也方便遍历时统一用 `isinstance(node, ast.Name)` 捕获所有名字用法、再按 ctx 细分。这是标准库在"类型爆炸"和"表达力"之间做的权衡，我们作为使用者直接享受这个设计即可。

## 不同语句的 AST 结构

理解几种常见语句的树形，对后面写提取器很有帮助。下面每种都给出代码、`ast.dump` 的关键部分和提取规则。建议你边读边在 REPL 里 `ast.dump` 验证，建立手感。这一节列的七种语句覆盖了 notebook 里九成以上的写法——把它们的结构烂熟于心，写提取器时就不必频繁翻文档，遇到陌生代码也能快速 dump 后对号入座。这七种之外还有 `If`/`While`/`Try`/`Match` 等语句，但它们不直接产生绑定（条件分支和循环体里的赋值由 `Assign` 分支处理），所以提取器不必为它们写专门分支。这是提取器分支数能保持在十几个的原因：只处理"产生绑定"的语句，不处理"控制流"语句。

**函数定义** `def f(a): return a`：

```
FunctionDef(name='f', args=arguments(args=[arg(arg='a')]), body=[Return(...)])
```

`FunctionDef.name` 是字符串 `'f'`（不是 `Name` 节点），形参 `a` 在 `args` 里。函数名 `f` 是 cell 的 def，但函数体内的 `a` 是局部变量，不算 cell 的 ref。`AsyncFunctionDef` 结构完全一样，只是节点类型不同。类定义 `class C: ...` 对应 `ClassDef(name='C', ...)`，`C` 进 defs，类体内的方法名是类的属性、不是 cell 的 def。注意函数名是裸字符串而非 `Name` 节点，所以提取 defs 时直接取 `stmt.name` 即可，不必走 `ctx` 判断。

函数定义是"为什么用 AST"的最佳佐证。用正则处理 `def f(x): return x + 1`，要把 `f` 归入 defs、把 `x` 排除出 refs，需要识别"这是函数定义""`x` 是形参"——这两步都要求理解 `def` 语法结构，正则做不到。AST 把这些结构信息直接挂在节点字段上：`FunctionDef.name` 给函数名，`FunctionDef.args` 给形参，`FunctionDef.body` 给函数体。提取器只需"取 `name` 进 defs，取 `args` 进局部"，三行搞定，且对任意复杂的函数签名（默认参数、`*args`、`**kwargs`、仅位置参数）都正确，因为 `args` 字段已经把这些都解析好了。

**导入** `import numpy as np`：

```
Import(names=[alias(name='numpy', asname='np')])
```

绑定名是 `asname`（若存在）否则是 `name`，即 `np`。注意 `import a.b.c` 绑定的是顶层名 `a`，所以源码里取 `alias.name.split('.')[0]`。`from m import x as y` 对应 `ImportFrom`，绑定 `y`（`asname`）或 `x`（`name`）。导入语句的提取规则看似简单，但 `asname or name` 这个表达式要小心：`asname` 为 `None` 时回退到 `name`，而 `name` 永远非空，所以不会出错。

导入语句有个正则特别容易翻车的点：`import a.b.c` 绑定的是 `a` 不是 `a.b.c`，但正则看到 `a.b.c` 可能把 `a`、`b`、`c` 都当名字。AST 的 `alias.name` 是完整点分字符串 `'a.b.c'`，我们用 `split('.')[0]` 取顶层，语义精确。`from m import x, y, z` 的多个绑定也整齐挂在 `stmt.names` 列表里，遍历即可，不会像正则那样在逗号处纠结。

**for 循环** `for i in items: total += i`：

```
For(target=Name(id='i', ctx=Store()), iter=Name(id='items', ctx=Load()), body=[...])
```

`target` 里的 `i` 是 cell 的 def（循环结束后 `i` 仍可见），`iter` 里的 `items` 是 ref。`target` 也可能是 `Tuple`，如 `for k, v in d.items(): ...`，这时 `k`、`v` 都进 defs，靠 `_extract_target_names` 递归取出。Python 的 for 循环变量在循环结束后不销毁，这与某些语言不同，所以把它算作 cell 的 def 是正确的。

for 循环的"循环变量不销毁"是 Python 一个有争议的设计（它偶尔导致 `i` 在循环后意外被引用），但对依赖分析来说它简化了规则：`for` 的 `target` 一律算 def，不必区分"循环中"和"循环后"。如果 Python 像 Rust 那样循环后销毁 `i`，我们就得把 `i` 算成"仅在循环体内可见的局部"，提取规则会复杂得多。所以这个语言设计恰好让我们的分析更简单。

**增量赋值** `x += 1`：

```
AugAssign(target=Name(id='x', ctx=Store()), op=Add(), value=Constant(1))
```

`AugAssign.target` 的 ctx 是 `Store`，但它同时意味着"先读后写"，所以 `x` 既要进 defs 也要进 refs——这是下一章的重点之一。这是 AST 里少数"ctx 不完全反映语义"的地方，需要特殊处理。

`AugAssign` 的"先读后写"语义源于它等价于 `x = x <op> value`。CPython 的解析器把 `x += 1` 的 `x` 标成 `Store`，是因为赋值目标是 `x`；但"先读"这一步没有在 ctx 上体现，它隐含在 `AugAssign` 这个节点类型本身。所以提取器不能只看 ctx，还要看节点类型：遇到 `AugAssign` 就知道 target 既是读也是写。这是"ctx 是重要信号但不完整"的典型例子，提醒我们不要把 ctx 当唯一依据，节点类型同样关键。

**带注解赋值** `x: int = 0`：

类型注解在数据科学代码里越来越常见（pandas 的 `Series[int]`、pydantic 模型字段），提取器必须覆盖。注解本身（`int`）是 `Load` 的 `Name`，但它是 builtin 会被过滤，所以不会污染 refs。如果注解用了自定义类型（`x: MyType = 0`），`MyType` 会进 refs——这是正确的，因为 cell 依赖 `MyType` 的定义。

```
AnnAssign(target=Name(id='x', ctx=Store()), annotation=Name(id='int', ctx=Load()), value=Constant(0))
```

`x` 进 defs；`annotation` 里的 `int` 是 `Load`，但它是 builtin 会被过滤。注意 `x: int`（无 value）也合法，此时 `value=None`，`x` 仍算 def。类型注解在数据科学代码里越来越常见，必须覆盖。

**海象运算符** `(y := x + 1)`：

```
NamedExpr(target=Name(id='y', ctx=Store()), value=BinOp(...))
```

`:=` 在表达式中间绑定 `y`，`y` 进 defs。它是 Python 3.8 引入的，出现在 `if (n := len(s)) > 10:` 这类场景里，提取时要把 `NamedExpr.target` 当成绑定目标。海象运算符打破了"赋值只在语句层"的旧规则，让绑定可以发生在任意表达式深度，提取器必须额外覆盖这一节点类型。

海象运算符对依赖分析是个小麻烦：它让"表达式"和"语句"的界限模糊了——以前可以假设"赋值只在顶层语句、表达式只读不写"，现在表达式中间也能绑定。提取器要额外扫 `NamedExpr` 节点，把它的 target 算进 defs。好在 `ast.walk` 会访问到 `NamedExpr`，加一个 `isinstance` 分支即可。这个例子说明，语言每加一个语法糖，提取器都要跟进——但 AST 方案跟进的成本很低（加一个分支），正则方案可能要重写一大块。

**with 语句** `with open(f) as fh: ...`：

```
With(items=[withitem(context_expr=Call(...), optional_vars=Name(id='fh', ctx=Store()))], body=[...])
```

`optional_vars`（即 `as fh` 的 `fh`）进 defs；`context_expr` 里的 `open` 是 Load 但属 builtin。若没有 `as`，`optional_vars` 为 `None`，不产生绑定。`with` 在文件操作和上下文管理器场景里很常见，漏掉 `optional_vars` 会导致 `fh` 不进 defs，下游引用 `fh` 的 cell 就找不到定义。

`with` 语句还有一个多上下文管理器的形式：`with a as x, b as y: ...`，这时 `stmt.items` 有两个元素，每个都有自己的 `optional_vars`。提取器遍历 `stmt.items` 逐个处理，自然覆盖这种形式。这种"遍历列表"的处理模式在提取器里反复出现——`Assign.targets` 是列表、`Import.names` 是列表、`With.items` 是列表——因为 Python 允许一条语句绑定多个名字，AST 就用列表装，提取器就遍历。

掌握了这些结构，我们就能针对每种节点写出准确的提取规则。下一章把这些规则组装成完整的 `analyze_cell`。建立这种"代码到节点"的映射感之后，读提取器的 `isinstance` 分支就不再像看天书，而是"对应一种已知的语法构造"。

最后给一个排查思路：如果某段代码的提取结果出乎意料，最快的定位办法是 `ast.dump` 看树，再对照本节列的结构找差异。常见 surprises 包括：推导式里的变量比你以为的多一层 `comprehension` 节点、海象运算符的绑定目标嵌在表达式深处、`with` 的 `optional_vars` 在没有 `as` 时是 `None` 而非空列表。这些细节文档里都有，但 dump 一下比翻文档快十倍。养成"结果不对先 dump"的习惯，能省下大量调试时间。
