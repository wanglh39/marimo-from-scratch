# 完整分析示例

前面几章分别讲了 `Cell` 结构、AST 遍历和 defs/refs 提取。这一章把所有东西串起来，看一个多 cell notebook 从代码到依赖关系的完整流程。这是整部教程的"合龙"章节——如果你只读一章，就读这一章，它会让你看清静态分析如何变成 reactive 执行的地基。

合龙章节的价值在于验证各部分能否协作。前面几章分别讲了 `Cell` 怎么定义、AST 怎么遍历、defs/refs 怎么提，但它们单独正确不代表拼起来正确——协作时的数据流、字段填充顺序、集合运算的配合，都只有在端到端例子里才能看清。这一章选的例子刻意覆盖了 import、函数定义、推导式、跨 cell 引用等常见写法，让你在一步到位的演示里确认每条规则都按预期工作。读完之后，你应该能拿任意一段 notebook 代码，手动模拟出它的 defs/refs 和依赖图。

## 示例 notebook

假设有三个 cell：

```python
# cell_1
import numpy as np
PI = 3.14159

# cell_2
def circle_area(r):
    return PI * r * r

# cell_3
areas = [circle_area(r) for r in range(5)]
mean_area = sum(areas) / len(areas)
```

我们依次对每个 cell 调用 `analyze_cell`，再把结果填进 `Cell.defs` 和 `Cell.refs`。在真实代码里这一步由 `create_cell` 完成：

```python
from backend.core import create_cell
c1 = create_cell("cell_1", "import numpy as np\nPI = 3.14159")
c2 = create_cell("cell_2", "def circle_area(r):\n    return PI * r * r")
c3 = create_cell("cell_3", "areas = [circle_area(r) for r in range(5)]\nmean_area = sum(areas) / len(areas)")
```

每个 `create_cell` 内部都跑了 `ast.parse` + `_extract_top_level_defs` + `_extract_refs`，返回的 `Cell` 已带好静态字段。注意此时三个 cell 的运行时字段都是默认值（`status=IDLE`、`namespace={}`），还没执行任何代码。静态分析在执行前就完成了——这是 reactive 与传统"跑一遍才知道依赖"的根本区别。

这个时序细节值得强调。在传统 Jupyter 里，依赖关系是执行后隐式形成的：你跑完 cell_1，`np` 和 `PI` 进了 `globals()`；跑 cell_2 时解释器从 `globals()` 拿到 `PI`，依赖就"发生"了。但这种方式无法在执行前知道依赖，所以编辑后没法自动重算——你不知道谁用了 `PI`，除非翻遍所有 cell。marimo 把依赖分析提前到执行前，靠的就是 `create_cell` 在构造时就把 `defs`/`refs` 算好。这个"提前"是 reactive 一切能力的起点。

## 逐 cell 分析

逐 cell 分析就是把 `analyze_cell` 依次应用到每段代码，再验证结果。这一步在真实系统里自动完成，但手动走一遍能看清每条规则如何作用。下面每个 cell 都列出顶层语句、defs 和 refs 的推导过程，最后给结果。这种"先列语句、再推 defs、再推 refs"的固定格式，也是你调试提取器时该用的思路——结果不对就按这个格式逐步排查，定位是哪一步偏了。

手动分析的价值不只是验证，更是建立信心。当你能对一段陌生代码手动推出 defs/refs，且与 `analyze_cell` 的输出一致，你就真正理解了提取器的行为。这种理解在调试时无价——遇到结果不符预期，你能立刻判断"是提取器错了还是我的预期错了"，而不会两眼一抹黑。所以建议你拿自己的 notebook 代码，先手动推一遍，再跑 `analyze_cell` 对比，把这个"手动 vs 自动"的校验变成习惯。

**cell_1**：

- 顶层语句：`Import(numpy as np)`、`Assign(PI = 3.14159)`。
- defs：`{"np", "PI"}`。`Import` 分支取 `asname or name` 得 `np`；`Assign` 取 `targets[0]` 得 `PI`。
- refs：`3.14159` 是 `Constant`，没有 `Name`，故 refs 为空。
- 结果：`defs={"np","PI"}, refs=set()`。

cell_1 的分析最简单，但它揭示了一个要点：`import` 语句的绑定名取 `asname or name`，所以 `import numpy as np` 绑定 `np` 而非 `numpy`。如果写成 `import numpy`（无 `as`），绑定名就是 `numpy`，下游要用 `numpy.array` 而非 `np.array`。这个区别看似琐碎，但建图时若把绑定名取错，下游的 refs 就找不到匹配的 defs，依赖边漏掉，reactive 失效。

cell_1 没有任何外部依赖，它是 DAG 的源点，可以第一个执行。

**cell_2**：

- 顶层语句：`FunctionDef(name="circle_area")`。
- defs：`{"circle_area"}`。`FunctionDef.name` 是字符串直接进 defs。
- refs：函数体里 `PI`、`r` 都是 `Load`。`r` 是形参，属于局部；`PI` 不是局部，也不是 builtin。
- 结果：`defs={"circle_area"}, refs={"PI"}`。

cell_2 的分析展示了"形参是局部"这条规则如何作用。`circle_area(r)` 的 `r` 是形参，在函数体里以 `Load` 出现，但它被 `_extract_refs` 的 `internal_locals` 机制归为局部（`r` 的 `Store` 在形参声明里，不在顶层 defs，所以 `r ∈ all_stores - defs`），从而从 refs 减掉。`PI` 则没有对应的 `Store`，不被当局部，留在 refs 里。这条"形参当局部"的规则，让函数定义 cell 的 refs 只含真正的外部依赖，不被形参污染。

注意 `np` 没有出现在 cell_2 的 refs 里——`circle_area` 函数体根本没用到 `np`。这体现了 AST 分析的精确：依赖只看实际引用的名字，而不是"同在一个 notebook 里"。若用正则扫"所有名字"，`np` 会被误判成依赖，cell_2 就会无谓地等 cell_1 的 `np` 就绪，破坏响应式的细粒度。这种"只依赖真正用到的"特性，让 marimo 的重算范围比"Run All"小得多。

注意 `np` 没有出现在 cell_2 的 refs 里——`circle_area` 函数体根本没用到 `np`。这体现了 AST 分析的精确：依赖只看实际引用的名字，而不是"同在一个 notebook 里"。若用正则扫"所有名字"，`np` 会被误判成依赖，cell_2 就会无谓地等 cell_1 的 `np` 就绪，破坏响应式的细粒度。这种"只依赖真正用到的"特性，让 marimo 的重算范围比"Run All"小得多。

这个精确性还有一个好处：它让"未使用导入"自动浮现。如果 cell_1 导入了 `np` 但没有任何 cell 的 refs 含 `np`，调度器能发现 `np` 是死定义，提示用户清理。虽然教学版没实现这个检查，但有了准确的 defs/refs，这类静态检查都是顺手的事。正则方案因为 refs 不可信，连这种基本检查都做不了。

**cell_3**：

- 顶层语句：`Assign(areas = [...])`、`Assign(mean_area = ...)`。
- defs：`{"areas", "mean_area"}`。
- refs：`circle_area`（Load）、`range`、`sum`、`len`、`areas`。其中 `range`/`sum`/`len` 是 builtins 被过滤；推导式里的 `r` 是局部被过滤；`areas` 出现在第二个赋值右侧，是真实引用。
- 结果：`defs={"areas","mean_area"}, refs={"circle_area","areas"}`。

cell_3 的分析展示了推导式和 builtins 过滤的协作。推导式 `[circle_area(r) for r in range(5)]` 里，`r` 是推导式局部变量，不泄漏到外层；`range` 是 builtin 被过滤；`circle_area` 是真实依赖保留。三条规则同时作用在一个表达式上，最终 refs 只剩 `circle_area`。这种"多规则协作"是真实代码的常态，也是为什么提取器要同时处理这么多边界——少处理一条，某个规则就漏网，结果就错。

`areas` 同时是本 cell 的 def 和 ref，这种"自引用"在单 cell 内是正常的（第二个赋值用到了第一个赋值的产物），不构成跨 cell 依赖。

自引用的处理体现了"跨 cell 边只看别人的 defs"这条规则的重要性。建图时，对 cell_3 的每个 ref，我们去查"除了 cell_3 自己，还有哪个 cell 的 defs 含这个名字"。`areas` 只有 cell_3 自己定义，所以不产生跨 cell 边；`circle_area` 由 cell_2 定义，产生 cell_2 → cell_3。如果不排除"自己"，cell_3 会产生自环，拓扑排序时要么报环错要么无限循环。这条"排除自己"的规则虽小，却是建图正确性的必要条件。

## 构建依赖关系

建图的规则只有一条：后继的 refs 与前驱的 defs 有交集就连边。这条规则简单到可以一行代码实现，但它背后是"数据流动"的本质——一个 cell 用了另一个 cell 产出的变量，就必须在对方之后跑。规则虽简单，但有几个细节容易出错：一是要排除自己（cell 的 refs 与自己的 defs 有交集不算边，那是自引用）；二是同一个变量被多个 cell 定义时要报错（marimo 不允许重复定义，否则 DAG 里该听谁的？）；三是 refs 里的 builtins 和局部变量已经在前一步过滤掉了，建图时不必再管。把这些细节处理好，建图逻辑也就十几行。有了每个 cell 的 defs/refs，DAG 的边按"后继的 refs ∩ 前驱的 defs ≠ ∅"建立：

| 后继   | refs                          | 命中的前驱 defs        | 依赖边            |
|--------|-------------------------------|------------------------|-------------------|
| cell_2 | `{PI}`                        | cell_1 的 `PI`         | cell_1 → cell_2   |
| cell_3 | `{circle_area, areas}`        | cell_2 的 `circle_area`| cell_2 → cell_3   |
|        |                               | cell_3 自己的 `areas`  | 自环忽略          |

cell_1 没有依赖任何 cell（refs 为空），是 DAG 的源；cell_2 依赖 cell_1；cell_3 依赖 cell_2。`areas` 虽然在 cell_3 的 refs 里，但它是 cell_3 自己的 def，不构成跨 cell 依赖，构建图时只看"别的 cell"的 defs。

"只看别的 cell 的 defs"这条规则，等价于"排除自己的 defs"。实现上通常是对每个 cell B，遍历所有其他 cell A（A ≠ B），检查 `B.refs ∩ A.defs` 是否非空。这个 O(n²) 的双循环对几十个 cell 的 notebook 完全够用；若 notebook 上千个 cell，可以建一个"名字 → 定义它的 cell"的倒排索引，把复杂度降到 O(n)。教学版用双循环，简单且对教学规模足够。

最终拓扑序为 `cell_1 → cell_2 → cell_3`，这正是正确的执行顺序。用文字画一下这张图：

```
cell_1 (np, PI) ──PI──> cell_2 (circle_area) ──circle_area──> cell_3 (areas, mean_area)
```

每个箭头上的标签就是触发依赖的变量名。如果用户改了 cell_1 里的 `PI`，调度器会沿箭头找到 cell_2（refs 含 `PI`）和 cell_3（传递依赖），只重算这两个，而不会动 cell_1 自己以外的无关 cell。这就是 reactive 相比线性执行的核心收益：改动的影响范围由依赖图精确界定，而非"从头跑一遍"。

注意这条链是"传递依赖"：cell_3 并不直接引用 `PI`，但它依赖 cell_2，而 cell_2 依赖 `PI`，所以 `PI` 变了 cell_3 也得重算。调度器做这个判断靠的是图的传递闭包，不是只看直接前驱。教学版在每次编辑后从改动 cell 出发做一次 BFS/DFS 沿下游传播标记，等价于算传递闭包但更高效（只走受影响的子图）。如果图很大但改动影响范围很小，这种"按需传播"比全量重算闭包快得多。

## 响应式重算示例

前面建好了图，现在看图怎么用。响应式的核心场景是"用户改了一个 cell，哪些 cell 要重算"。这个场景把静态分析和运行时调度连起来：静态分析给出图的结构，调度器在图上做传播和排序。假设用户把 cell_1 的 `PI` 从 `3.14159` 改成 `3.14`，流程是：

1. `create_cell("cell_1", new_code)` 重新分析，`defs` 仍是 `{"np","PI"}`，但 `code` 变了。
2. 调度器对比新旧 `defs`，发现 `PI` 的定义 cell 没换（还是 cell_1），但 cell_1 的 `code` 变了，标记 cell_1 需重跑。
3. 沿 DAG 找 cell_1 的下游：cell_2（refs 含 `PI`）、再下游 cell_3。把它们标记为 `STALE`。
4. 按拓扑序执行：cell_1 → cell_2 → cell_3。每个 cell 跑完后更新自己的 `namespace`，下游合并上游 `namespace` 注入 `globals()`。
5. 若 cell_1 改的是 `np` 的别名（比如换成 `import numpy`），`defs` 变成 `{"numpy","PI"}`，下游 refs 里的 `np` 就找不到定义了——调度器会报"未定义变量 np"，提示用户修正。

这就是 reactive notebook 的核心收益：**只重算真正受影响的 cell**，而不必从头跑整个 notebook。在一个有几十个 cell 的数据分析 notebook 里，一次小改动可能只触发两三个 cell 重算，省下的时间随 notebook 规模线性增长。而这一切的起点，就是本章演示的静态依赖分析——没有准确的 defs/refs，调度器无从知道"谁受影响"，reactive 就退化成"Run All"。

这个"保守上界"的性质在响应式重算里也有体现。步骤 3 里"沿 DAG 找下游"是沿传递依赖传播，它把所有"可能受影响"的 cell 都标记重算，不管中间分支是否真的会走那条路。这种"全标记"是保守的——可能多算了几个实际不受影响的 cell，但绝不会漏算。漏算会导致用户看到陈旧结果（正确性 bug），多算只是慢一点（性能问题）。reactive 系统宁可慢也不错，所以选保守策略。如果将来要做更精确的影响分析（比如用类型信息排除某些分支），那是优化层的事，建立在保守分析正确的基础之上。

步骤 2 里"对比新旧 defs"是一个值得细看的优化点。如果用户只改了代码里的常量或表达式（如 `3.14159` 改成 `3.14`），`defs`/`refs` 不变，调度器知道图的拓扑没变，只需重算改动 cell 及其下游，不必重建图。但如果用户把 `PI = 3.14159` 改成 `TAU = 6.28`，`defs` 从 `{"np","PI"}` 变成 `{"np","TAU"}`，下游 cell_2 的 refs 仍含 `PI` 却找不到定义了——这是"依赖结构变了"的情况，调度器要报"未定义变量 PI"。区分这两种情况靠的就是 `defs` 集合的前后对比，开销极小但价值很大。

## 一个更复杂的 cell

前面三个 cell 都比较短，现在看一个综合多种语法的单 cell，检验提取器在更真实代码上的表现。真实数据分析 cell 往往就是这样：import 加载库、初始化累加器、循环处理、汇总结果，一条流水线写在一个 cell 里。这种 cell 内部逻辑复杂但对外只暴露最终结果，提取器要正确识别它的"内部流转"和"对外接口"。再看一个单 cell，综合函数定义、import、for 循环、增量赋值：

```python
import pandas as pd
total = 0
for row in pd.read_csv("data.csv").itertuples():
    total += row.value
summary = {"total": total, "n": row}
```

分析过程：

这个 cell 的分析过程展示了"一条语句贡献多个 defs/refs"的常见模式。`For` 语句既贡献 def（`row`）又贡献 ref（`pd`）；`AugAssign` 同时贡献 defs 和 refs（`total`）。每条语句的提取不是"非 def 即 ref"，而是"可能两者都有"。提取器要为每种语句类型想清楚"它绑定谁、它读取谁"，两条都要答，不能只答一条。

- `Import(pandas as pd)` → defs 加 `pd`。
- `Assign(total = 0)` → defs 加 `total`。
- `For(target=row, iter=...)` → defs 加 `row`；iter 里 `pd` 是 Load → refs 加 `pd`。
- 循环体 `AugAssign(total += row.value)`：`total` 读改写 → defs 和 refs 都加 `total`；`row` 是 Load → refs 加 `row`（但 `row` 已在 defs 中，作为本 cell 内部流转，不影响跨 cell 依赖）。
- `Assign(summary = {...})` → defs 加 `summary`；右侧 `total`、`row` 是 Load → refs 加 `total`、`row`。

汇总：`defs = {"pd", "total", "row", "summary"}`，`refs = {"pd", "total", "row"}`。减去本 cell 自己的 defs 后，对外部 cell 的真实依赖为 `refs - defs = ∅`（`pd` 虽是 import，但若上游无人定义 `pd`，它不构成跨 cell 边；`total`/`row` 都由本 cell 自己定义）。这个 cell 可以独立执行，是 DAG 的另一个源。注意 `row` 在循环结束后仍可见（Python 的 for 循环不销毁循环变量），所以 `summary` 里引用 `row` 合法，且 `row` 算 cell 的 def 而非 ref。

这个例子还展示了"内部流转"的概念：`total` 和 `row` 在本 cell 内部被先写后读，它们同时出现在 defs 和 refs 里，但 `refs - defs` 后对外部依赖为零。这种"内部流转"在数据分析代码里很常见——一个 cell 内部做完整的一轮处理，只把最终结果（`summary`）对外暴露。reactive 系统正确识别了这种自给自足的 cell，不会因为它内部读写了多个变量就误判它依赖外部。这再次归功于"跨 cell 边只看别人的 defs"这条规则。

"内部流转"的识别对 reactive 性能很重要。如果误把 `total`/`row` 当外部依赖，这个 cell 就会等待不存在的上游，或者被误标记为依赖其他 cell 而在那些 cell 变动时无谓重算。正确识别它"自给自足"后，调度器知道它可以独立执行，不受其他 cell 编辑影响——除非用户改了它自己的代码。这种"独立 cell"在数据分析 notebook 里很常见（一个 cell 做完整的数据加载和清洗），正确识别它们能让 reactive 的重算范围最小化。

## 小结

这一章把前面所有章节串成一条完整的流水线。回顾这条流水线，每一步的输入输出都清晰可追溯，这正是好设计的样子——不是每步都炫技，而是每步都简单且衔接自然。如果哪一步你觉得"看不懂在干嘛"，说明那一步的抽象没做好，要么职责不单一，要么命名不达意。本章的流水线每步都能一句话说清："解析给树""提顶层绑定""提全树引用""填进 Cell""连边""排序"，这就是好抽象的标志。完整流程是：**源码 → `ast.parse` → 顶层 defs + 全树 refs → 填入 Cell → 按 refs∩defs 连边 → 拓扑排序**。AST 分析把"谁依赖谁"这件事从运行时提前到加载时，让 marimo 能在用户编辑任一 cell 后，只重算真正受影响的下游 cell，而不必从头跑整个 notebook。这正是 reactive notebook 相对传统线性 notebook 的核心优势，而它的地基就是本章演示的这套静态分析。整条链路里，`Cell` 是承载数据的容器，`analyze_cell` 是静态分析的引擎，`create_cell` 把两者粘合，DAG 与调度器则在它们之上构建响应式语义——每一层都只做一件事，层与层之间靠 `defs`/`refs` 这对集合契约衔接。理解了这条链路，你就理解了 marimo 的灵魂。

最后把这条链路里每一步的"输入→输出"列清楚，作为全篇收束：`ast.parse` 吃源码吐 AST 树；`_extract_top_level_defs` 吃树吐 defs 集合；`_extract_refs` 吃树和 defs 吐 refs 集合；`create_cell` 吃 cell_id 和代码吐一个填好静态字段的 Cell；建图逻辑吃所有 Cell 吐 DAG；调度器吃 DAG 和编辑事件吐重算计划。每一步的输出正好是下一步的输入，整条链没有"孤立"的环节。这种"管道式"的设计让每一步可独立测试、可单独替换实现，是整个 reactive 系统能保持简单且正确的结构原因。当你将来想扩展（比如加缓存、换分析器、支持新语法），只需找到对应的那一段管道替换，其余环节不动——这就是分层带来的可维护性红利。
