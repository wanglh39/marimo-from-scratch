# Cell 数据结构

在 marimo 中，notebook 由若干个 **cell**（单元格）组成。cell 是最小的计算单元：它拥有一段 Python 代码，执行后产出若干变量，并把这些变量暴露给后续 cell 使用。要构建 notebook 的依赖图（DAG），我们必须先有一个能同时承载"静态信息"和"运行时状态"的数据结构，这就是 `Cell`。

## 静态信息与运行时状态

`Cell` 的字段可以分成两类。

**静态信息**（在执行前就能通过 AST 分析得到）：

- `cell_id`：cell 的唯一标识，通常用 UUID 或序号。
- `code`：cell 内的源代码字符串。
- `defs`：该 cell **定义**的变量名集合，例如 `y = x + 1` 中 `defs = {"y"}`。
- `refs`：该 cell **引用**的变量名集合，上例中 `refs = {"x"}`。

`defs` 和 `refs` 是构建 DAG 的关键：如果 cell B 的 `refs` 与 cell A 的 `defs` 有交集，就说明 B 依赖 A，需要在 A 之后执行。

**运行时状态**（只有执行后才知道）：

- `status`：cell 当前所处的状态，见下文。
- `output`：最后一个表达式的求值结果（类似 REPL 的回显）。
- `stdout`：执行期间写到标准输出的内容。
- `exception`：执行抛出的异常对象，正常时为 `None`。
- `namespace`：cell 执行后**本 cell 产出**的变量字典，形如 `{"y": 2}`。它不是全局 `globals()`，而是该 cell 对外暴露的"礼物"。

把静态与动态分开存放，是为了让依赖分析可以在不真正执行代码的前提下完成——这正是 marimo 能够做"静态重排"的基础。

## CellStatus 状态机

`status` 字段用一个枚举表示，取值如下：

```
IDLE    ──┐
          ├──> RUNNING ──> DONE
PENDING ──┘                └──> ERROR

STALE：被短路，无需重算
```

- `IDLE`：尚未执行，等待调度。
- `PENDING`：已被调度器选中，即将运行。
- `RUNNING`：正在执行用户代码。
- `DONE`：执行成功，`namespace` 已就绪。
- `ERROR`：执行抛出异常，`exception` 已记录。
- `STALE`：上游未变化且本 cell 无需重算，被调度器短路跳过。

一次典型的执行轨迹是 `IDLE → PENDING → RUNNING → DONE`；如果代码出错则从 `RUNNING` 转到 `ERROR`。当 notebook 中某个 cell 被修改后，下游 cell 会被标记为 `STALE`（或重新进入 `IDLE`），等待新一轮调度。`STALE` 的引入是为了避免重复执行：如果输入没变，输出也不会变，干脆跳过。

## namespace 的作用

`namespace` 记录的是"本 cell 执行后产出了哪些变量、值是多少"。调度器在执行一个 cell 时，会把所有上游 cell 的 `namespace` 合并成一个执行环境，再注入到本 cell 的 `globals()` 中运行；运行结束后，再把本 cell 新增的绑定收集进自己的 `namespace`。这样每个 cell 都像纯函数一样：输入是上游的 `namespace`，输出是自己的 `namespace`，而 `defs`/`refs` 则是这个"函数签名"的静态近似。

通过这种设计，`Cell` 既是 AST 分析的产物（静态字段），又是执行引擎的工作对象（动态字段），为后续章节的依赖图构建打下了基础。
