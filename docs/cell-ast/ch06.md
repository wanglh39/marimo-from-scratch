# Cell 数据结构

在 marimo 中，notebook 由若干个 **cell**（单元格）组成。cell 是最小的计算单元：它拥有一段 Python 代码，执行后产出若干变量，并把这些变量暴露给后续 cell 使用。要构建 notebook 的依赖图（DAG），我们必须先有一个能同时承载"静态信息"和"运行时状态"的数据结构，这就是 `Cell`。

为什么需要这样一个统一的数据结构，而不是分开用两个对象表示"静态分析结果"和"运行时快照"？因为在 reactive 系统里，这两类信息的生命周期是交织的：用户每次编辑代码，静态字段要重新分析；每次执行，动态字段要更新；而调度器在做决策时，又要同时看静态的依赖关系和动态的状态标志。把它们放进同一个 `Cell` 对象，既避免了两个对象之间来回同步的麻烦，也让"一个 cell 的全部信息"有一个明确的归属。这是 marimo 在数据建模上的第一个关键选择。

把 cell 定义为"最小计算单元"还有一层含义：它是依赖图的节点粒度。我们不在更细的粒度（如单行、单表达式）上做依赖分析，也不在更粗的粒度（如整个 notebook）上。选 cell 这个粒度，是因为它正好对应用户心智里的"一个步骤"——用户把一个想法写进一个 cell，执行后看结果。依赖图在这个粒度上既有意义（步骤之间确实有数据流动）又不过细（不会把一行里的临时变量都建成节点）。这个粒度选择不是技术决定，而是对"用户怎么思考 notebook"的建模。

## 静态信息与运行时状态

`Cell` 的字段可以分成两类。这种分离是整个 reactive 系统的设计基石：静态字段在加载时由 AST 分析填充，动态字段在执行时由引擎更新，两者互不干扰。理解这种分离，也就理解了为什么 marimo 能做到"编辑后只重算受影响的 cell"——因为依赖关系是静态算好的，调度器不需要试运行就能知道改动会波及谁。

**静态信息**（在执行前就能通过 AST 分析得到）：

- `cell_id`：cell 的唯一标识，通常用 UUID 或序号。
- `code`：cell 内的源代码字符串。
- `defs`：该 cell **定义**的变量名集合，例如 `y = x + 1` 中 `defs = {"y"}`。
- `refs`：该 cell **引用**的变量名集合，上例中 `refs = {"x"}`。

`defs` 和 `refs` 是构建 DAG 的关键：如果 cell B 的 `refs` 与 cell A 的 `defs` 有交集，就说明 B 依赖 A，需要在 A 之后执行。这两个集合一旦在加载时算好，就不再随执行改变——除非用户编辑了 `code`，那时需要重新跑一次 AST 分析来刷新它们。这种"分析一次、反复使用"的特性，让依赖图可以在 notebook 加载时一次性建好，后续的每次编辑只需局部重算受影响 cell 的 `defs`/`refs`，开销极小。

用集合而非列表来存 `defs`/`refs`，还有一个语义上的理由：变量名之间没有顺序意义。`x = 1; y = 2` 和 `y = 2; x = 1` 在依赖层面等价，都定义了 `x` 和 `y`，谁先谁后不影响"本 cell 产出哪些名字"。集合天然表达"无序去重"，正好契合。如果用列表，还要自己去重、还要纠结顺序，徒增复杂。这种"选对数据结构让语义自然落地"的小决定，累积起来就是代码简洁的来源。

**运行时状态**（只有执行后才知道）：

- `status`：cell 当前所处的状态，见下文。
- `output`：最后一个表达式的求值结果（类似 REPL 的回显）。
- `stdout`：执行期间写到标准输出的内容。
- `exception`：执行抛出的异常对象，正常时为 `None`。
- `namespace`：cell 执行后**本 cell 产出**的变量字典，形如 `{"y": 2}`。它不是全局 `globals()`，而是该 cell 对外暴露的"礼物"。

把静态与动态分开存放，是为了让依赖分析可以在不真正执行代码的前提下完成——这正是 marimo 能够做"静态重排"的基础。传统 Jupyter 不做这种分离：它只有一个全局 `globals()` 字典，所有 cell 往里写、从里读，依赖关系完全隐式，所以它无法在编辑后自动重算下游，只能让用户手动"Run All"。marimo 的 reactive 能力，根子上就来自这个"静态可分析"的字段划分。

这种分离还带来一个不那么明显但同样重要的好处：静态字段可以做哈希和比较，从而支持增量分析。调度器在用户编辑某个 cell 后，只需重新分析这一个 cell 的 `defs`/`refs`，再对比旧值，就能判断"依赖结构是否变了"。如果只是 `code` 里的常量改了（比如 `PI = 3.14159` 改成 `PI = 3.14`），`defs`/`refs` 不变，下游只需重算无需重建图；如果删掉了一个定义，`defs` 变了，调度器就要检查是否有下游引用了被删的名字，进而报错或触发图重构。这种"按需重建"的策略，让编辑大 notebook 也能保持流畅，而不会每次按键都全量重算。

下面是 `backend/core/cell.py` 中的真实定义，用 `dataclass` 让字段声明一目了然：

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Any


class CellStatus(Enum):
    IDLE = "idle"
    PENDING = "pending"
    RUNNING = "running"
    DONE = "done"
    ERROR = "error"
    STALE = "stale"


@dataclass
class Cell:
    cell_id: str
    code: str
    defs: set[str] = field(default_factory=set)
    refs: set[str] = field(default_factory=set)

    status: CellStatus = CellStatus.IDLE
    output: Any = None
    stdout: str = ""
    exception: BaseException | None = None
    namespace: dict[str, Any] = field(default_factory=dict)
```

注意几个细节：`defs`/`refs` 用 `set[str]` 而非列表，因为变量名只关心"有没有"不关心"出现几次"，集合的并集运算也正好契合依赖合并；`namespace` 用 `dict` 而非集合，因为除了名字还要携带值；可变默认值必须走 `field(default_factory=...)`，否则所有 cell 会共享同一个集合实例——这是 dataclass 的常见陷阱，初学者很容易踩到。选用 `dataclass` 而非手写 `__init__`，是因为它自动生成 `__init__`/`__repr__`/`__eq__`，对于主要用途是"装数据"的类来说足够且省事；若后续需要不可变性，改成 `@dataclass(frozen=True)` 也只是一行的事。`__eq__` 的自动生成让两个 cell 可以按字段值比较，在测试里很有用——断言"分析后的 cell 等于预期"比逐字段比较简洁。

## CellStatus 状态机

`status` 字段用一个枚举表示，取值如下：

```
IDLE    ──┐
          ├──> RUNNING ──> DONE
PENDING ──┘                └──> ERROR

STALE：被短路，无需重算
```

- `IDLE`：尚未执行，等待调度。
- `PENDING`：已被调度器选中，即将运行。
- `RUNNING`：正在执行用户代码。
- `DONE`：执行成功，`namespace` 已就绪。
- `ERROR`：执行抛出异常，`exception` 已记录。
- `STALE`：上游未变化且本 cell 无需重算，被调度器短路跳过。

一次典型的执行轨迹是 `IDLE → PENDING → RUNNING → DONE`；如果代码出错则从 `RUNNING` 转到 `ERROR`。当 notebook 中某个 cell 被修改后，下游 cell 会被标记为 `STALE`（或重新进入 `IDLE`），等待新一轮调度。`STALE` 的引入是为了避免重复执行：如果输入没变，输出也不会变，干脆跳过。这与 React 里 `useMemo` 的记忆化思想一致——既然依赖没变，就复用上次的输出，省下重算的开销。在 notebook 场景里这尤其重要：一个跑几秒的数据加载 cell，如果其上游没变，就没必要每次编辑都重跑。

为什么是六个状态而不是更少？可以设想只用三个：`TODO`/`RUNNING`/`DONE`。问题是少了 `STALE`，调度器就无法区分"这个 cell 上轮跑过、这轮不用跑"和"这个 cell 还没跑过"——前者可以复用 `namespace`，后者必须执行。少了 `PENDING`，就无法区分"已选中待执行"和"还没被选中"，多线程调度时会重复挑中同一个 cell。少了 `ERROR`，就无法区分"成功完成"和"跑过但出错了"，下游该不该重算就判断不了。每个状态都对应调度器需要区分的一种处境，少一个就会在某些场景下决策失灵。状态机的状态数不是越少越好，而是"刚好够区分所有需要区分的处境"。

用枚举而非字符串来表示状态，有两个好处：一是拼写错误在编译期就能被 IDE 抓住（写成 `CellStatus.IDEL` 会直接报错，而字符串 `"idel"` 则会悄悄混过去，等到运行时才暴露问题）；二是状态机转换可以写成 `cell.status = CellStatus.RUNNING`，意图清晰，IDE 还能做自动补全。用枚举而非整数常量也有类似好处：`CellStatus.DONE` 比 `status == 3` 可读得多，且不会和其他模块的常量冲突。`Cell` 还提供了两个状态相关的便捷属性：

```python
@property
def has_error(self) -> bool:
    return self.status is CellStatus.ERROR

@property
def is_runnable(self) -> bool:
    return self.status in (CellStatus.IDLE, CellStatus.PENDING, CellStatus.STALE)
```

`is_runnable` 把"哪些状态可以被调度器挑中"集中到一处，避免调用方散落写 `if status == IDLE or status == PENDING ...`。用 `is` 比较枚举成员比 `==` 更严格也更符合习惯，因为枚举成员是单例，身份比较既快又语义明确。把这类判断封装成属性而非裸露的布尔运算，是为了让状态机的规则有唯一的定义点——将来若要新增一个可运行状态，只改 `is_runnable` 一处即可。

状态机与调度器的协作方式值得展开。调度器每一轮做三件事：先扫描所有 cell，把 `is_runnable` 为真的挑出来排进待执行队列（状态从 `IDLE`/`STALE` 转到 `PENDING`）；再依次执行，执行前转 `RUNNING`，成功转 `DONE`、失败转 `ERROR`；最后把未波及的 cell 保持原状。`STALE` 在这里扮演"已分析但无需重跑"的角色——它的 `namespace` 仍有效，下游可以直接复用。如果不用 `STALE` 而是把所有未波及 cell 都留在 `DONE`，调度器就无法区分"刚跑完的"和"上一轮跑完现在仍有效的"，要么全重跑要么全不跑，失去细粒度。所以六个状态不是冗余，而是精确刻画了 cell 在 reactive 生命周期里的每一种处境。

## 状态重置与标记过期

执行引擎在重跑一个 cell 之前，需要把上一次的运行时残留清掉。`Cell` 把这件事封装成两个方法，避免外部直接挨个字段赋值。这种封装的必要性在于：运行时字段有五个（`status`/`output`/`stdout`/`exception`/`namespace`），如果让调用方自己清，很容易漏掉一两个，留下"状态变了但数据没清"的矛盾态。集中到一个方法里，"清哪些字段"这个决策只做一次，之后所有调用都走同一条路径，不会漂移。

```python
def reset_runtime_state(self) -> None:
    self.status = CellStatus.IDLE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}

def mark_stale(self) -> None:
    self.status = CellStatus.STALE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}
```

`reset_runtime_state` 把 cell 打回 `IDLE`，准备从头跑；`mark_stale` 则把它标记为 `STALE`，表示"暂时不用跑，但旧输出已失效"。两者都清空 `output`/`stdout`/`exception`/`namespace`——这一点很重要：一个过期的 `namespace` 如果残留，会被下游 cell 当成有效输入合并，导致拿到陈旧数据，这是 reactive 系统里最隐蔽的 bug 来源之一。把清空逻辑收进方法而不是裸露在外，是为了保证"只要状态变了，运行时字段一定一起清"，不会出现状态是 `STALE` 但 `namespace` 还留着旧值的矛盾态。这种"状态与数据一致"的不变量，是调度器能正确工作的前提。如果允许外部直接写 `cell.status = CellStatus.STALE` 而不清 `namespace`，就开了一个出 bug 的口子——某个调用方忘了清，下游就拿到陈旧数据。封装成方法后，"改状态"的唯一入口是这两个方法，不变量由方法内部保证，外部无法破坏。这是面向对象封装的经典价值：不是藏数据，是保不变量。

## namespace 的作用

`namespace` 记录的是"本 cell 执行后产出了哪些变量、值是多少"。它是一个 dict，键是变量名、值是运行时对象。调度器在执行一个 cell 时，会把所有上游 cell 的 `namespace` 合并成一个执行环境，再注入到本 cell 的 `globals()` 中运行；运行结束后，再把本 cell 新增的绑定收集进自己的 `namespace`。这样每个 cell 都像纯函数一样：输入是上游的 `namespace`，输出是自己的 `namespace`，而 `defs`/`refs` 则是这个"函数签名"的静态近似。

"纯函数"这个类比虽然不严格（cell 可能有副作用，比如写文件、打印），但它抓住了 reactive 建模的核心：把每个 cell 看成"输入→输出"的映射，依赖图就是这些映射之间的数据流。只要 cell 的副作用不影响其他 cell 的输入（不直接改全局变量、不依赖执行顺序），这个模型就成立。marimo 鼓励用户写"近乎纯"的 cell——每个 cell 只通过 `defs`/`refs` 与外界交互，副作用局限在 cell 内部——这样 reactive 的重算才安全。如果用户写了依赖执行顺序的代码（比如 cell B 假设 cell A 先跑过才能读某个全局变量），reactive 的重排可能打破这个假设，这是 reactive notebook 相对线性 notebook 的一个约束。

为什么 `namespace` 只装"本 cell 产出"而不装"执行时见到的所有变量"？因为如果装后者，下游 cell 就会透过本 cell 间接看到上游的上游的变量，依赖关系会变得隐式且难以追踪。只装本 cell 自己 `defs` 对应的绑定，依赖图就能完全由 `refs ∩ defs` 决定，干净且可静态推导。这与传统 Jupyter 的全局 `globals()` 形成鲜明对比：Jupyter 里所有变量混在一个字典，改了一个 cell 后哪些变量受影响全靠人脑追，而 marimo 的 `namespace` 让每个 cell 的"输出接口"显式且可枚举。

namespace 的合并机制具体是这样的：调度器要执行 cell B 时，先找出 B 在 DAG 上的所有直接前驱，把它们的 `namespace` 逐个 `.update()` 进一个临时字典，再把这字典作为 `globals()` 注入 B 的执行环境。B 跑完后，从执行环境的 `globals()` 里挑出 B 的 `defs` 列的那些名字，装进 B 自己的 `namespace`。注意"挑出 defs 列的"这一步——它保证 B 的 `namespace` 只含 B 自己产出的变量，而不会把从上游继承来的变量也装进去。这样下游 C 合并前驱 namespace 时，拿到的永远是"每个 cell 只暴露自己产出"的干净视图，传递依赖不会透过中间层泄漏。如果某个前驱处于 `STALE`，它的 `namespace` 仍是上轮的有效值，直接复用即可——这正是 `STALE` 状态存在的意义。

## create_cell 工厂函数

实际创建 cell 时，我们几乎不会手写 `Cell(cell_id=..., code=..., defs=..., refs=...)`——`defs` 和 `refs` 应该由 `code` 自动算出。手写的话，调用方要自己调 `analyze_cell` 再传进 `Cell`，两步分离容易传错（比如把 defs 和 refs 传反）。工厂函数把两步合一，消除这个出错机会。`backend/core/__init__.py` 提供了一个工厂函数把这件事封起来：

```python
from .ast_analyzer import analyze_cell
from .cell import Cell, CellStatus


def create_cell(cell_id: str, code: str) -> Cell:
    defs, refs = analyze_cell(code)
    return Cell(cell_id=cell_id, code=code, defs=defs, refs=refs)
```

调用方只需给 `cell_id` 和 `code`，`defs`/`refs` 由 `analyze_cell`（下一章起详述）静态分析得到，运行时字段保持默认值。这样 cell 的构造与 AST 分析耦合在唯一一处，后续若要给分析器加缓存或换实现，只改这个函数即可。工厂模式在这里的另一个好处是：它把"创建一个 cell"这个高频操作简化成两个参数，调用方不需要关心分析器的存在，降低了心智负担。在整个 reactive 链路里，`create_cell` 是入口：notebook 加载时对每个代码块调一次，用户编辑时对被改的 cell 再调一次，其余 cell 保持不动。

关于缓存有一个值得注意的设计点。`analyze_cell` 是纯函数（同样的 `code` 永远返回同样的 `defs`/`refs`），所以理论上可以加一个 `code → (defs, refs)` 的缓存。教学版没加，是因为 notebook 里同一段代码重复出现的概率极低，缓存命中率不高，反而增加内存开销。生产版可以考虑用 `functools.lru_cache` 包一层，在用户频繁撤销/重做同一编辑时能省掉重复解析。这种"先不加缓存、需要时再加"的顺序，是性能优化的通用节奏——过早优化往往让代码变复杂却收不到实际收益。

通过这种设计，`Cell` 既是 AST 分析的产物（静态字段），又是执行引擎的工作对象（动态字段），为后续章节的依赖图构建打下了基础。回顾这一章的设计决策：用 dataclass 装字段、用 Enum 表状态、把静态与动态分开、用 namespace 隔离传递依赖、用工厂函数封构造——每一步都是为了一个目标：让依赖关系可静态推导，让执行可增量重算。这两点合起来，就是 reactive notebook 的技术内核。如果用一句话概括 `Cell` 的设计哲学，那就是"把 cell 当成一个带签名的纯函数：签名（defs/refs）静态可算，调用（namespace）运行时填充，调度器靠签名排顺序、靠调用结果传数据"。这个比喻贯穿了 marimo 的整个 reactive 设计，后续章节的 DAG 和调度器都是在这个比喻上展开的。
