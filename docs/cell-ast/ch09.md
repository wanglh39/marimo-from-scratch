# 提取 defs 与 refs

有了前两章的基础，现在实现 `ast_analyzer.py` 的核心：给定一段代码，返回 `defs` 和 `refs` 两个集合。我们的目标是函数 `analyze_cell(code) -> (defs, refs)`，例如 `analyze_cell("y = x + 1")` 应返回 `({"y"}, {"x"})`。这一章把上一章的节点知识落成可运行的代码，每一分支都对应一种已讨论过的 AST 结构。读完这一章，你应该能独立看懂 `backend/core/ast_analyzer.py` 的全部逻辑。

这一章的代码组织遵循"入口薄、内层厚"的原则：`analyze_cell` 只做参数校验和调度，真正的提取逻辑在 `_extract_top_level_defs` 和 `_extract_refs` 两个内部函数里，后者又调用 `_extract_bindings` 和 `_extract_target_names`。这种分层让每层函数的职责单一——入口管流程，中层管"遍历哪种结构"，内层管"从某个节点取名字"。读代码时可以自顶向下逐层深入，也可以先看入口再按需跳进内层，不会一上来就陷在细节里。

## 入口：analyze_cell

入口函数是整个提取器的门面，它的简洁程度直接影响调用方的心智负担。真实实现的入口很简洁，把"空代码""语法错误"两个边界先挡掉，再分两步提取。这种"入口薄"的设计让调用方只需关心"给代码、拿结果"，不必处理内部细节。两个边界处理也有讲究：空代码返回空集而非报错，是因为空 cell 在 notebook 里合法（用户可能刚插入一个空 cell 还没写代码），不该当错误对待；语法错误则抛 `AnalysisError` 而非 `SyntaxError`，是为了让上层捕获时拿到统一的异常类型，附带行号信息，能向用户显示"第几行有问题"。这种"把底层异常包成领域异常"的做法，在整个项目里反复出现，是错误处理的统一风格。

```python
import ast
import builtins

_BUILTIN_NAMES = set(dir(builtins))


def analyze_cell(code: str) -> tuple[set[str], set[str]]:
    if not code.strip():
        return set(), set()
    try:
        tree = ast.parse(code)
    except SyntaxError as e:
        raise AnalysisError(f"语法错误: {e.msg} (行 {e.lineno})") from e
    defs = _extract_top_level_defs(tree)
    refs = _extract_refs(tree, defs)
    return defs, refs
```

`_BUILTIN_NAMES` 在模块加载时算一次缓存起来，避免每次调用都 `dir(builtins)`。这是一个小但重要的优化：`analyze_cell` 在用户每次编辑时都会被调用，把内置名表做成模块级常量，省去了重复构建集合的开销。模块级常量还保证了所有调用用同一个集合对象，不会因重复构建产生多个副本浪费内存。`analyze_cell` 把 `SyntaxError` 包成项目自己的 `AnalysisError`，附带行号，让上层能向用户报出"第几行语法错"——这种"包装底层异常、附带上下文再抛"的做法，让前端能显示对用户友好的错误信息，而不是裸的 Python traceback。

注意 `defs` 先算，因为 `refs` 的计算需要知道哪些 `Store` 名是"顶层 def"、哪些是"函数内部局部"，这依赖 `defs` 的结果。这个顺序依赖看似不起眼，却是两个函数能协作的关键：`_extract_refs` 接收 `defs` 作为参数，用它把"全树所有 Store 名"分成"顶层绑定"和"局部变量"两类。

入口函数的简洁也值得学习。它把"空代码""语法错误"两个边界在最外层挡掉，主干逻辑（`_extract_top_level_defs` 和 `_extract_refs`）就不用再操心这些情况，可以假设拿到的 `tree` 一定是非空合法 AST。这种"入口做防御、内部做逻辑"的分层，让每个函数的职责单一、前置条件清晰。如果把空代码检查塞进 `_extract_top_level_defs`，那个函数就要同时操心"树是不是空"和"怎么提 defs"两件事，可读性立刻下降。

## defs：顶层绑定

`defs` 收集的是"执行完这个 cell 后，会在 cell 作用域里新建或覆盖的变量名"。这个定义里"cell 作用域"是关键限定——它指的是模块级作用域，相当于把 cell 当成一个 `.py` 文件顶层来分析。函数内、类内、推导式内的绑定都不算，因为它们在 cell 执行后不可见。理解了这个限定，就理解了为什么提取只遍历 `tree.body` 而不递归进函数体。"新建或覆盖"这个措辞也值得注意：defs 不区分"首次定义"和"重新赋值"，`x = 1` 和 `x = 2` 都让 `x` 进 defs。这是因为依赖分析只关心"执行后 `x` 的值来自本 cell"，不关心它之前是否存在。关键在于**只看顶层语句**——函数体里的局部变量不算 cell 的 def。因此我们遍历 `tree.body`（而不是 `ast.walk`），对每种语句类型取出绑定名。这种"只看顶层"的实现选择，把"cell 作用域"这个语义概念直接映射成了"遍历 `tree.body`"这个代码动作——没有额外的标记或追踪，结构本身就表达了语义。这是 AST 相比正则的深层优势：正确的实现往往是最直接的实现，不需要打补丁。

```python
def _extract_top_level_defs(tree: ast.Module) -> set[str]:
    defs: set[str] = set()
    for stmt in tree.body:
        defs |= _extract_bindings(stmt)
    return defs
```

为什么用 `tree.body` 而不是 `ast.walk`？因为 `walk` 会递归进入函数体、循环体，把局部变量也吐出来；而 `tree.body` 只给顶层的语句节点，天然把"cell 作用域"和"嵌套作用域"隔开。这是"只看顶层"这个语义最直接的实现。真正的分支判断在 `_extract_bindings` 里，按语句类型逐种处理：

`tree.body` 是一个列表，每个元素是一条顶层语句的 AST 节点。遍历它而不是 `walk`，意味着我们刻意"只看第一层"。这种刻意的浅遍历是 defs 提取正确的核心：它保证 `def f(): x = 1` 里的 `x` 不会进 defs，因为 `x` 的 `Assign` 节点挂在 `FunctionDef.body` 里，不在 `tree.body` 的直接子节点中。如果误用 `walk`，`x` 会被扫出来误算成 cell 的 def，下游 cell 就会以为能从本 cell 拿到 `x`，执行时却 `NameError`。这种"浅遍历 vs 深遍历"的选择，是 defs 与 refs 提取最核心的不对称，务必记牢。

```python
def _extract_bindings(stmt: ast.stmt) -> set[str]:
    bindings: set[str] = set()
    if isinstance(stmt, ast.Assign):
        for target in stmt.targets:
            bindings |= _extract_target_names(target)
    elif isinstance(stmt, ast.AnnAssign) and stmt.target is not None:
        bindings |= _extract_target_names(stmt.target)
    elif isinstance(stmt, ast.AugAssign):
        bindings |= _extract_target_names(stmt.target)
    elif isinstance(stmt, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
        bindings.add(stmt.name)
    elif isinstance(stmt, ast.Import):
        for alias in stmt.names:
            bindings.add(alias.asname or alias.name.split(".")[0])
    elif isinstance(stmt, ast.ImportFrom):
        for alias in stmt.names:
            if alias.name == "*":
                continue
            bindings.add(alias.asname or alias.name)
    elif isinstance(stmt, (ast.For, ast.AsyncFor)):
        bindings |= _extract_target_names(stmt.target)
    elif isinstance(stmt, (ast.With, ast.AsyncWith)):
        for item in stmt.items:
            if item.optional_vars is not None:
                bindings |= _extract_target_names(item.optional_vars)
    elif isinstance(stmt, ast.NamedExpr):
        bindings |= _extract_target_names(stmt.target)
    elif isinstance(stmt, ast.Expr) and isinstance(stmt.value, ast.NamedExpr):
        bindings |= _extract_target_names(stmt.value.target)
    return bindings
```

每条分支对应上一章讲过的一种 AST 结构。`Assign` 要遍历 `targets`（因为 `a = b = 0` 有两个目标）；`Import` 取 `asname or name.split('.')[0]` 处理 `import a.b as c` 两种情况；`ImportFrom` 跳过 `*`（星号导入无法静态分析，下一章详述）；`For`/`With` 取 `target`/`optional_vars`；`NamedExpr` 处理海象运算符。最后那个 `ast.Expr + NamedExpr` 分支是为了 `(y := 1)` 作为裸表达式语句出现的情况。这种"一个分支一种语句"的写法，好处是新增语法支持时只加一个 `elif`，不必动现有逻辑；坏处是分支较多，但每个都短小直白，可读性反而比一个巨大的正则好。

分支顺序在这里无关紧要，因为每种语句类型互斥（一个 `stmt` 不可能同时是 `Assign` 和 `FunctionDef`）。但有一个易错点：`AnnAssign` 分支带了 `and stmt.target is not None` 的守卫，因为 `x: int`（无赋值的纯注解）在旧版 Python 里 `target` 可能是 `None`，不加守卫会在 `_extract_target_names(None)` 上崩。这种"边界条件写在分支条件里"的做法，比在函数体里 `if stmt.target is None: return` 更紧凑，也让"这个分支只处理什么情况"一目了然。

## 解包：_extract_target_names

解包是 Python 赋值里最"结构化"的语法，也是正则最难处理的部分。`a, b = ...` 在正则眼里是"逗号分隔的两个名字"，但要正确解析它（区分 `a, b` 和 `a, b,`、处理嵌套 `((a, b), c)`、处理星号 `a, *b`）几乎要写一个小 parser。而 AST 已经把这些都解析好了，我们只需递归取 `Name` 的 `id`。这种"AST 解析、我们读取"的分工，是提取器能保持简洁的根本原因——复杂的语法分析外包给了标准库，我们只做"从结构里挑名字"这件简单的事。`_names_in_target` 递归处理解包：`Name` 返回 `{id}`，`Tuple`/`List` 返回各元素之和，`Starred` 取其内部。这样 `(a, b) = ...` 能同时拿到 `a` 和 `b`。

```python
def _extract_target_names(target: ast.expr) -> set[str]:
    names: set[str] = set()
    if isinstance(target, ast.Name):
        names.add(target.id)
    elif isinstance(target, (ast.Tuple, ast.List)):
        for elt in target.elts:
            names |= _extract_target_names(elt)
    elif isinstance(target, ast.Starred):
        names |= _extract_target_names(target.value)
    return names
```

`first, *rest = items` 里的 `rest` 是 `Starred` 节点，递归一层取出 `rest`。嵌套解包 `((a, b), c) = ...` 也能正确处理，因为 `Tuple` 分支会继续递归它的 `elts`。这个函数是"结构化优势"的典型体现：用正则处理嵌套解包几乎不可能，而递归三行就搞定。递归终止性来自 AST 的有限深度——任何合法代码的解包嵌套层数都是有限的。

`_extract_target_names` 的三个分支正好对应三种"赋值目标"的 AST 节点：`Name`（普通变量）、`Tuple`/`List`（解包容器）、`Starred`（星号解包）。注意它不处理 `Attribute`（如 `obj.x = 1`）和 `Subscript`（如 `d[k] = 1`），因为这两种目标的"名字"是 `obj`/`d`，它们是 `Load` 不是 `Store`，会由 refs 提取处理。把"绑定目标递归"和"读取名收集"分到两个函数，让各自的职责清晰：前者只管"等号左边能绑定哪些名字"，后者只管"全树读了哪些名字"。这种职责分离让两个函数可以独立测试和演进，是小型代码保持可维护性的关键。

## refs：所有 Load 名减去局部与 builtins

refs 提取与 defs 提取有一个对称的差异：defs 只看顶层（用 `tree.body`），refs 看全树（用 `ast.walk`）。这是因为"定义"只发生在顶层（函数内的赋值不算 cell 的 def），但"引用"可以发生在任意深度（函数体内读外部变量也算 cell 的依赖）。这个"defs 浅、refs 深"的不对称，是 Python 作用域规则的直接体现，也是提取器里最容易搞反的一点。搞反了会怎样？如果 defs 也用 `walk`，函数内局部变量会误进 defs，下游以为能拿到它们却 `NameError`；如果 refs 也只用 `tree.body`，函数体内读的外部变量会漏出 refs，依赖边缺失，重算不触发，用户看到陈旧结果。两个方向搞反都出 bug，所以这个不对称必须记牢。`refs` 的思路更直接：扫遍整棵树，收集所有 `ctx=Load` 的 `Name`，然后减去两样东西——**函数内部局部变量**和 **builtins**。与 defs 只看顶层不同，refs 要看全树，因为"引用"可以发生在任意深度——函数体内读外部变量、推导式里读外部序列，都是 cell 的依赖。所以这里用 `ast.walk` 而非 `tree.body`。真实实现把 `Load` 和 `Store` 一次性收集，再用 `Store - defs` 算出"非顶层局部"：

```python
def _extract_refs(tree: ast.Module, defs: set[str]) -> set[str]:
    all_loads: set[str] = set()
    all_stores: set[str] = set()
    for node in ast.walk(tree):
        if isinstance(node, ast.Name):
            if isinstance(node.ctx, ast.Load):
                all_loads.add(node.id)
            elif isinstance(node.ctx, ast.Store):
                all_stores.add(node.id)
        elif isinstance(node, ast.AugAssign) and isinstance(node.target, ast.Name):
            all_loads.add(node.target.id)
    internal_locals = all_stores - defs
    return (all_loads - internal_locals) - _BUILTIN_NAMES
```

为什么 `internal_locals = all_stores - defs`？因为 `all_stores` 包含了所有 `Store` 名——既有顶层的 `defs`，也有函数体、推导式里的局部赋值。减去 `defs` 后剩下的恰好是"非顶层的 Store"，即局部变量。这些局部变量若出现在 `all_loads` 里（比如函数体内读自己的形参），要从 refs 剔除，否则会误判成外部依赖。这个"一次遍历收集两类名、再用集合差集分类"的技巧，比维护一个作用域栈简单得多，代价是无法精确处理 `global`/`nonlocal`（下一章详述）。

集合运算在这里发挥了妙用：`all_stores - defs` 一行就完成了"区分顶层与局部"的分类，不必写一个带作用域栈的 visitor。这种简洁的代价是"粒度粗"——它把所有非顶层 Store 一律当局部，不管它实际属于哪一层函数。对于没有 `global`/`nonlocal` 的代码，这种粗粒度恰好正确；一旦有 `global`，就会错。这是"用集合运算换实现简单"的典型权衡：牺牲少数冷门语法的精度，换来主干代码的极简。教学版接受这个权衡，生产版若要精确就得换作用域栈方案。集合运算的另一个好处是"易测试"：`all_stores`/`defs`/`all_loads` 都是普通集合，可以单独断言它们的值，比测试一个带状态的 visitor 容易得多。这种"可测试性"是集合方案常被忽略的优点。

为什么减 builtins？考虑 `def f(x): return x + 1`，函数体里的 `x` 是 `Load`，但它不是 cell 的依赖，只是形参。`_collect_function_locals` 会进入每个 `FunctionDef`/`AsyncFunctionDef`，收集其形参和函数体内 `Store` 的名字，把它们标记为局部。注意：函数**名本身** `f` 是 cell 的 def，由上一节处理，不在这里。形参的 `Store` 体现在 `arg` 节点里，被 `all_stores` 捕获后归入 `internal_locals`，从而从 refs 剔除。

减 builtins 是为了让 `print`、`range`、`len`、`open` 这类全局可用名不算依赖——否则几乎每个 cell 都会"依赖" `print`，DAG 会被无意义的边塞满。想象一下：若不过滤 builtins，每个调用 `print` 的 cell 都会连一条边到某个不存在的"print 定义 cell"，图里全是这种噪声边，真正的数据依赖反而被淹没。

## AugAssign：读-改-写

`AugAssign` 是整个提取器里最需要"特殊照顾"的节点，因为它的语义和 ctx 字段不完全一致。理解它为什么需要特殊处理，就理解了"不能盲信 ctx"这条教训。这条教训的适用范围不限于 `AugAssign`：任何时候提取器只看 ctx 都可能漏，因为 ctx 反映的是"这个 Name 节点在此位置的语法角色"，而非"这个名字在语义上被读还是被写"。`AugAssign` 是最明显的例子，海象运算符 `:=` 也有类似情况（它的 target 是 Store 但在表达式中间）。所以写提取器时，要把 ctx 当"第一信号"而非"唯一信号"，遇到特殊节点类型还要结合节点类型做修正。这种"ctx 加节点类型"的双信号策略，是 AST 提取器里处理边界情况的通用手法。`x += 1` 是个特殊情况。它等价于 `x = x + 1`，对 `x` 既是读也是写。但 `ast.walk` 在 `AugAssign.target` 上看到的 ctx 是 `Store`，所以默认不会被 `Load` 扫描到，refs 会漏掉 `x`。上面 `_extract_refs` 里专门加了一条分支补救：

```python
elif isinstance(node, ast.AugAssign) and isinstance(node.target, ast.Name):
    all_loads.add(node.target.id)
```

这样 `x += 1` 得到 `defs={"x"}`、`refs={"x"}`，语义正确：本 cell 定义了 `x`（会覆盖旧值），同时也引用了 `x`（需要上游先提供初值）。若上游没人定义 `x`，运行时会 `NameError`，但那是执行阶段的事；静态分析只如实记录"本 cell 既读又写 x"。`AugAssign` 是 AST 里少数"ctx 不完全反映语义"的节点，需要这种特殊补救，理解了它就理解了提取器里最易错的一处。补救的逻辑很简单：在 `walk` 循环里加一个 `elif` 分支，遇到 `AugAssign` 就把 target 名补进 `all_loads`。一行代码，但漏了它 refs 就缺一个 `x`，下游依赖边就建不出来。

类似"ctx 不完全反映语义"的还有推导式的循环变量：它的 `Store` 看起来像绑定，但 Python 3 里它不泄漏到外层。教学版靠"它不在顶层 defs，所以被归入 internal_locals"间接处理了——推导式里的 `Store` 名落入 `all_stores`，减去 `defs` 后变成局部，于是它对应的 `Load` 也被从 refs 减掉。这种"靠集合差集顺带处理推导式"的巧合，让教学版不必专门写推导式分支，是集合运算的又一红利。

## 一个完整例子

看完所有规则，用几个小例子做端到端验证。这些例子覆盖了普通赋值、import、函数定义、增量赋值四种典型写法，每种都标注了预期结果和为什么。建议你拿这些例子在 REPL 里跑 `analyze_cell`，确认结果一致——这是检验提取器正确性的最快方式。如果某个例子结果不对，按"入口→defs→refs"的顺序逐步排查，定位是哪个环节偏了。这种"最小反例驱动的调试"在开发提取器时极其有效：不要拿一大段复杂代码调试，先把问题缩减到最小的能复现的例子，再逐步排查，问题定位会快得多。

```python
analyze_cell("y = x + 1")
# defs = {"y"},  refs = {"x"}

analyze_cell("import numpy as np\nv = np.array([1,2])")
# defs = {"np", "v"},  refs = set()   # np.array 是属性访问，不是 Name

analyze_cell("def f(a): return a + b")
# defs = {"f"},  refs = {"b"}         # a 是局部，b 是外部依赖

analyze_cell("x += 1")
# defs = {"x"},  refs = {"x"}
```

第二个例子值得细看：`np.array` 在 AST 里是 `Attribute(value=Name('np'), attr='array')`，`np` 是 `Load` 的 `Name`，但 `np` 同时是本 cell 的 def（来自 `import`），所以 `refs - defs` 后 `np` 被剔除，最终 refs 为空。这正确反映了"本 cell 自给自足，不依赖外部"。属性访问不产生独立的 `Name`，这是 AST 相比正则的又一胜利——正则会把 `array` 也当变量名扫出来。

这四个例子覆盖了提取器的主要分支：普通赋值（`Assign`）、导入（`Import`）、函数定义（`FunctionDef`）、增量赋值（`AugAssign`）。每种都验证了"对应分支被正确命中、结果符合预期"。如果将来给提取器加新语法支持（如 `match` 语句），也应该加一个这样的端到端例子，确认新分支工作。这种"每加一个分支加一个例子"的纪律，能让提取器在演进中不退化。这四个例子也覆盖了"refs 为空""refs 含外部名""refs 含自引用"三种典型结果形态，是检验下游建图逻辑的好素材。

这些结果正是 DAG 构建所需要的：cell 之间的边由"后继的 refs ∩ 前驱的 defs"决定。至此，`analyze_cell` 的主干已经完整，下一章处理那些让主干翻车的边界情况。回顾本章，提取器的实现不到 60 行（不含 `_BUILTIN_NAMES` 缓存），却覆盖了 Python 最常见的十几种语句。这种"少量代码覆盖大量语法"的效率，归功于 AST 把语法规则编码进了节点结构——我们只需按节点类型分流，不必重新解析。正则方案要达到同样的覆盖率，代码量至少是这里的五倍，且仍不正确。
