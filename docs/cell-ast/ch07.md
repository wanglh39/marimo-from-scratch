# 为什么用 AST 而非正则

要从一个 cell 的源代码里提取它定义和引用了哪些变量，最朴素的想法是用正则表达式。这一章我们解释为什么正则不可靠，以及为什么 AST（抽象语法树）才是正确的工具。这个选择不是品味问题，而是由 Python 语言的复杂度决定的——Python 的语法规则远比"一串字符"丰富，任何只看字符表面的方法都注定在边界情况上翻车。这一章的论证方式是"反例驱动"：不抽象地说正则不好，而是给具体的真实代码，让你看到正则在它上面给出错误结果。这种论证比抽象说理更有说服力，也更易记住。

提取变量名这件事在 reactive 系统里的地位，相当于编译器里的类型检查：它不直接产生运行结果，但决定了运行怎么组织。依赖图的所有边都来自这步提取，提取错一条边，要么导致漏算（该重算的没重算，用户看到陈旧结果），要么导致多算（不该重算的重算了，浪费算力）。前者是正确性 bug，后者是性能 bug，都伤体验。所以这步提取必须可靠——这正是本章花一整章论证"为什么不能用正则"的原因：一个不可靠的提取器会让整个 reactive 承诺落空。

## 正则的诱惑与陷阱

乍一看，提取变量名似乎很简单。这种"看似简单"正是正则方案的陷阱所在：它在简单案例上的成功让人放松警惕，等到真实代码暴露问题时，正则已经嵌进系统、改不动了。所以这一章的价值不只是"论证 AST 好"，更是"在你动手写提取器之前，把正则这条路堵死"，免得走弯路。

```python
re.findall(r'\b([a-zA-Z_]\w*)\s*=', code)   # "定义"
re.findall(r'\b([a-zA-Z_]\w*)\b', code)     # "引用"
```

这两行正则在简单代码上甚至能给出看起来正确的结果，让人产生"这事不难"的错觉。但这种做法在真实代码面前会迅速崩溃，原因至少有四点。这四点不是穷举，而是最常踩的坑——实际写正则提取器还会遇到更多（装饰器、类型注解、结构化匹配等），每多支持一种就要多加一条分支，最终正则比 AST 代码还长却仍不正确。下面逐个剖析，每个陷阱都配一段真实会出现在 notebook 里的代码。

**1. 嵌套作用域。** 代码 `def f(x): return x + 1` 里，`x` 是函数的形参，不是 cell 级别的引用；`f` 才是 cell 的定义。正则无法区分"顶层绑定"和"函数内部局部变量"，会把 `x` 误判成依赖。于是 DAG 会凭空多出一条"本 cell 依赖某个外部 x"的边，触发不必要的重算甚至报 `NameError`。在数据分析 notebook 里，函数定义随处可见——任何 `def clean(s): ...` 都会让正则把形参 `s` 当成外部依赖，依赖图很快就被虚假边塞满。

这个陷阱的根源是正则没有"作用域"概念。Python 的名字查找遵循 LEGB 规则，同一个名字在不同作用域里含义不同。正则只看字符，看不到"这个 `x` 在函数体内所以是局部"——要判断这一点，必须知道它被哪层 `def` 包裹，而这需要理解代码的嵌套结构，恰恰是正则做不到的。AST 则天然带嵌套：函数体是 `FunctionDef.body`，形参是 `FunctionDef.args`，谁在内谁在外一目了然。

**2. 多行语句与括号。** Python 允许跨行的赋值、隐式续行、括号包裹的元组解包：

```python
(a,
 b) = (1,
       2)
```

正则很难正确处理这种结构，要么漏掉 `b`，要么把行尾的逗号附近文本当成名字。更糟的是 `a = 1; b = 2` 这种同行多语句，简单的行级正则根本分不清边界。还有 `if (x := f()) > 0:` 这种海象运算符，赋值发生在表达式中间，正则的"等号左边是定义"假设直接失效。

**3. 字符串与注释中的假变量。** 代码 `s = "x = y"` 里，`x` 和 `y` 只是字符串内容，根本不是变量。正则会把它们一并扫出来，制造虚假依赖，导致 DAG 里出现不存在的边。注释 `# x depends on y` 同理：正则看不到 `#`，会把 `x`、`y` 当成代码里的名字。在 notebook 里，用户经常在注释里写"这里依赖上面的 df"之类的说明，正则会把这些自然语言里的名字全收进 refs，依赖图彻底失真。

**4. 语义上下文。** 同一个名字 `print`，在 `print = 5` 里是定义，在 `print(x)` 里是引用；在 `from m import *` 之后更是无法静态判断。正则只看字面，看不到上下文。再看 `x += 1`：它既是读也是写，正则匹配到 `x` 后无法决定该放进 defs 还是 refs，而正确答案恰恰是"两边都放"。还有属性访问 `np.array`——正则可能把 `np` 和 `array` 都当变量名，但 `array` 只是 `np` 的属性，不是独立变量。

下表把正则与 AST 在几类典型代码上的表现做对比，"✓"表示正确、"✗"表示错误：

| 代码片段                       | 期望 defs    | 期望 refs    | 正则结果              | AST 结果 |
|--------------------------------|--------------|--------------|-----------------------|----------|
| `def f(x): return x + 1`       | `{f}`        | `{}`         | ✗ 把 `x` 当 ref       | ✓        |
| `s = "x = y"`                  | `{s}`        | `{}`         | ✗ 把 `x,y` 当 ref     | ✓        |
| `# x = y` 后跟 `z = 1`          | `{z}`        | `{}`         | ✗ 把 `x,y` 当 ref     | ✓        |
| `x += 1`                       | `{x}`        | `{x}`        | ✗ 只归一类            | ✓        |
| `import numpy as np`           | `{np}`       | `{}`         | ✗ 把 `numpy` 当 ref   | ✓        |

每一行都是真实 notebook 里会出现的写法，正则在它们上全军覆没。更麻烦的是，正则的失败是"静默"的——它不报错，只是给出错误的集合，让你在后续的 DAG 构建里追查莫名其妙的依赖或缺失的边，调试成本极高。

为什么人们明知正则不可靠还是总想用它？因为对简单代码它"看起来能用"。`y = x + 1` 这种教学例子上，正则和 AST 给出一样的结果，让人产生"再加几个分支就够了"的错觉。于是正则越写越长：先加处理字符串的分支，再加处理注释的分支，再加处理多行的分支……每加一个分支都要小心别破坏之前的，最终变成一坨没人敢动的"正则怪物"。而 AST 的做法是"把语言规则交给解释器的解析器"，我们只读结果，不必重新实现规则。这是两种思路的根本分野：正则在重造轮子，AST 在复用已有的语义引擎。

## AST 的优势

AST 是 Python 解释器自己用来理解代码的结构化表示。用它做分析有一个天然优势：我们和分析器看的是同一棵树，不存在"我的规则和解释器的规则不一致"的风险。如果自己写解析（无论是正则还是手写 tokenizer），都要冒着与 CPython 语义偏离的风险——某个边界 CPython 这么处理、我那么处理，结果就分叉了。直接用 `ast` 模块，语义对齐由标准库保证，我们只消费结果。用 `ast.parse(code)` 得到的是一棵由节点组成的树，每个节点对应一种语法构造：`Assign`、`FunctionDef`、`For`、`Name`……每个节点的字段明确告诉你"这是赋值还是引用""目标是谁""作用域在哪一层"。换句话说，AST 把 Python 的语法规则编码进了数据结构，我们只需读这棵树就能还原代码的语义，不必自己重新实现一遍语法解析。

相比正则，AST 有三个决定性优势。这三个优势不是独立的，而是层层递进：结构化让多行/解包不再翻车，准确让字符串/注释不再干扰，能区分定义与引用让语义判断成为可能。三者合起来，才让提取器在真实代码上可靠。缺任何一个，都会有一整类代码让结果出错。

- **结构化**：解包、多行、嵌套都被解析成树形结构，不需要自己处理括号和续行。`(a, b) = ...` 会被解析成 `Assign(targets=[Tuple(elts=[Name('a'), Name('b')])])`，`a` 和 `b` 作为 `Store` 节点整整齐齐挂在 `targets` 下，遍历即可拿到。多行语句在解析阶段就被拼回逻辑行，续行符、括号都不再出现。
- **准确**：字符串字面量是 `Constant` 节点，不会和 `Name` 混淆；注释在解析阶段就被丢弃，根本不出现在树里。`s = "x = y"` 解析后只有一个 `Name('s', Store)`，字符串里的 `x`/`y` 不复存在。这意味着 AST 天然免疫于"字符串和注释里的假变量"这一整类陷阱。
- **能区分定义与引用**：`Name` 节点带一个 `ctx` 字段，`Load` 表示读取、`Store` 表示写入、`Del` 表示删除。这是正则永远拿不到的语义信息。`x = x + 1` 里左右两个 `x` 在 AST 中分别是 `Store` 和 `Load`，一目了然，而正则看到的是两个一模一样的 `x`。

除了这三点，AST 还有一个隐含优势：它与 Python 版本同步进化。每当语言新增语法（如 3.8 的海象运算符、3.10 的结构化匹配），CPython 的解析器随之更新，`ast` 模块也跟着加新节点类型。我们只需在提取器里加一个 `isinstance` 分支就能支持新语法，而正则方案要等有人手写出对应的模式才行。换言之，AST 把"跟上语言演进"这件事外包给了标准库，我们搭便车即可。

## Python `ast` 模块的工作流

使用标准库 `ast` 模块通常分三步。这三步的分工是：`parse` 把字符串变成结构化对象，`walk` 让我们能访问每个节点，`isinstance` 分支让我们对不同节点做不同处理。三步合起来就是"解析→遍历→分发"的经典分析流水线，几乎所有基于 AST 的工具（lint、类型检查、代码生成）都遵循这个模式。

```python
import ast
tree = ast.parse(code)          # 1. 源码 → AST
for node in ast.walk(tree):     # 2. 遍历节点
    if isinstance(node, ast.Name):
        ...                     # 3. 按 ctx 和节点类型提取信息
```

`ast.parse` 只做语法分析，不执行代码，因此安全且快速——哪怕代码里调用了不存在的函数也不会报错。这一点对 notebook 尤其重要：用户可能正在编辑一个 cell，代码暂时是半成品（比如 `df = load_data(` 还没写完），此时 `ast.parse` 会抛 `SyntaxError`，但绝不会触发任何真实调用；而正则虽然也不执行，却会给出错误的依赖信息，更隐蔽。安全性还意味着可以放心地对用户提交的任意代码做分析，不必担心副作用——这在多用户或服务端场景下是硬性要求。

安全性之外，"不执行"还带来一个语义上的好处：分析结果只取决于代码文本，与运行环境无关。同一段代码在空环境里和在一堆变量已定义的环境里，`analyze_cell` 给出同样的 `defs`/`refs`。这让依赖图可以离线构建、序列化、甚至跨机器复现，而不必把整个 notebook 跑一遍。试想如果依赖分析要靠执行（比如用 `trace` 模块追踪实际访问了哪些名字），那不仅慢，还会受数据内容影响——同一个 cell 跑不同数据可能访问不同分支的变量，依赖关系就飘忽不定。静态 AST 分析彻底避开了这个不确定性，这是 reactive 能做到"编辑后确定性重算"的前提。

性能上，`ast.parse` 是 C 实现的解析器，对几百行的 cell 也只需毫秒级。在 marimo 里，每次用户编辑 cell 都会重跑一次 `analyze_cell`，这个开销完全可以忽略，不会造成输入卡顿。相比之下，若用正则，虽然单次更快，但为了处理各种边界情况会越写越长、越写越慢，最终未必比 AST 便宜。

性能之外，可维护性是更关键的差距。正则方案每遇到一种新的边界写法，就要加一条分支，分支之间还可能冲突（处理字符串的分支可能误伤处理解包的）。维护者改一处要全盘测，心智负担随分支数线性增长。AST 方案每遇到新语法，加一个 `isinstance` 分支即可，分支之间互斥（一个节点只有一种类型），改一处不影响其他。这种"开-关式"的扩展性，让提取器能随 Python 语言演进持续加支持而不腐化。长期项目里，可维护性的差距比性能差距更致命。

`ast.walk` 会按深度优先遍历整棵树，让我们有机会对每种节点做不同处理。它是一个生成器，用法上配合 `isinstance` 分支判断节点类型，是 Python 里做静态分析的标准范式。这种"walk + isinstance"的组合之所以成为范式，是因为它把"遍历"和"处理"解耦了：`walk` 只管"走到每个节点"，`isinstance` 只管"遇到某类节点怎么办"，两者正交。换一种遍历策略（如只遍历顶层）不必改处理逻辑，加一种节点处理不必改遍历方式。这种正交性让提取器可以独立演进两个维度，是简单代码能保持灵活的根源。除了 `walk`，标准库还提供 `NodeVisitor`（写 `visit_xxx` 方法按类型分发）和 `NodeTransformer`（可改写树），但我们的需求只是"读"出 defs/refs，`walk` 加 `isinstance` 已经够用，写起来也更直白，不必引入额外的类层级。

选 `walk` 还是 `NodeVisitor` 是个小风格决定。`NodeVisitor` 的好处是"按节点类型自动分发"，不必写一长串 `isinstance`；坏处是要定义一个类、写 `visit_Name`/`visit_Assign` 等方法，对小型提取器来说仪式感偏重。`walk` 加 `isinstance` 更轻量，一个函数里搞定，适合教学。生产级分析器若要处理几十种节点，`NodeVisitor` 的分发会更整洁。两种风格没有对错，只看规模和偏好。教学版选 `walk` 是为了让代码尽量集中在一个函数里，读者一眼能看全。

基于这套工作流，我们就能把"提取 defs/refs"这件事做得既完整又可维护：每种语法构造对应一段明确的处理逻辑，新增一种构造只需要加一个 `isinstance` 分支，而不用去改越来越长的正则表达式。这正是 marimo 选择 AST 的根本原因——不是因为它更"高级"，而是因为它把 Python 语言的语义规则交给了我们，而这套规则正是正确推导依赖关系所必需的。正则只能看到字符，AST 能看到语义；reactive 系统依赖的是语义，所以工具必须能读语义。这个结论不是抽象的"AST 更高级"，而是有具体后果的工程判断：选正则，reactive 的依赖图不可信，重算范围或漏或多，用户体验崩坏；选 AST，依赖图可信，重算精确，reactive 承诺兑现。所以这一章不是在讨论"两种方案各有优劣"，而是在说"只有一种方案能用，另一种注定失败"。

最后提一个常被问到的疑问：既然 AST 这么好，为什么不直接用 `exec` 加 `trace` 在运行时追踪依赖？答案是：运行时追踪只能告诉你"这次执行"用了谁，不能告诉你"这段代码可能用谁"。一个 `if flag: x = y` 在 `flag` 为假时不碰 `y`，但静态上它仍然可能依赖 `y`——只要 `flag` 有可能为真。reactive 系统要的是"可能依赖"而非"实际依赖"，因为编辑后重算的决策必须保守（宁可多算不能漏算）。静态 AST 恰好给出"可能依赖"的上界：它把所有语法上可能被读的名字都收进 refs，不管运行时分支走哪条。这种保守性是 reactive 正确性的基石，而运行时追踪给不了。所以选 AST 不只是"快"或"安全"，更是"语义上正确"。

这个"保守上界"的性质值得再强调。reactive 的重算策略是"上游变了就重算下游"，如果依赖分析漏了一条边（该重算的没重算），用户会看到陈旧结果，这是正确性 bug，比多算更严重。所以提取器宁可多收名字（多算）也不能少收（漏算）。AST 的"收所有 Load 名再减局部和 builtins"天然偏保守——它不试图做数据流分析（那会漏掉条件分支里的引用），而是把所有语法上可能的引用都收进来。这种"宁多勿少"的策略，让 reactive 在正确性上有保障，代价是偶尔多算几个 cell，但多算只是性能问题，不是正确性问题。
