# 为什么用 AST 而非正则

要从一个 cell 的源代码里提取它定义和引用了哪些变量，最朴素的想法是用正则表达式。这一章我们解释为什么正则不可靠，以及为什么 AST（抽象语法树）才是正确的工具。

## 正则的诱惑与陷阱

乍一看，提取变量名似乎很简单：

```python
re.findall(r'\b([a-zA-Z_]\w*)\s*=', code)   # "定义"
re.findall(r'\b([a-zA-Z_]\w*)\b', code)     # "引用"
```

但这种做法在真实代码面前会迅速崩溃，原因至少有四点。

**1. 嵌套作用域。** 代码 `def f(x): return x + 1` 里，`x` 是函数的形参，不是 cell 级别的引用；`f` 才是 cell 的定义。正则无法区分"顶层绑定"和"函数内部局部变量"，会把 `x` 误判成依赖。

**2. 多行语句与括号。** Python 允许跨行的赋值、隐式续行、括号包裹的元组解包：

```python
(a,
 b) = (1,
       2)
```

正则很难正确处理这种结构，要么漏掉 `b`，要么把行尾的逗号附近文本当成名字。

**3. 字符串与注释中的假变量。** 代码 `s = "x = y"` 里，`x` 和 `y` 只是字符串内容，根本不是变量。正则会把它们一并扫出来，制造虚假依赖，导致 DAG 里出现不存在的边。

**4. 语义上下文。** 同一个名字 `print`，在 `print = 5` 里是定义，在 `print(x)` 里是引用；在 `from m import *` 之后更是无法静态判断。正则只看字面，看不到上下文。

## AST 的优势

AST 是 Python 解释器自己用来理解代码的结构化表示。用 `ast.parse(code)` 得到的是一棵由节点组成的树，每个节点对应一种语法构造：`Assign`、`FunctionDef`、`For`、`Name`……每个节点的字段明确告诉你"这是赋值还是引用""目标是谁""作用域在哪一层"。

相比正则，AST 有三个决定性优势：

- **结构化**：解包、多行、嵌套都被解析成树形结构，不需要自己处理括号和续行。
- **准确**：字符串字面量是 `Constant` 节点，不会和 `Name` 混淆；注释在解析阶段就被丢弃。
- **能区分定义与引用**：`Name` 节点带一个 `ctx` 字段，`Load` 表示读取、`Store` 表示写入、`Del` 表示删除。这是正则永远拿不到的语义信息。

## Python `ast` 模块的工作流

使用标准库 `ast` 模块通常分三步：

```python
import ast
tree = ast.parse(code)          # 1. 源码 → AST
for node in ast.walk(tree):     # 2. 遍历节点
    if isinstance(node, ast.Name):
        ...                     # 3. 按 ctx 和节点类型提取信息
```

`ast.parse` 只做语法分析，不执行代码，因此安全且快速——哪怕代码里调用了不存在的函数也不会报错。`ast.walk` 会按深度优先遍历整棵树，让我们有机会对每种节点做不同处理。

基于这套工作流，我们就能把"提取 defs/refs"这件事做得既完整又可维护：每种语法构造对应一段明确的处理逻辑，新增一种构造只需要加一个 `isinstance` 分支，而不用去改越来越长的正则表达式。这正是 marimo 选择 AST 的根本原因。
