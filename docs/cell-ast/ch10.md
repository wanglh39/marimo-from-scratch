# 作用域与边界情况

上一章给出了提取 defs/refs 的主干逻辑，但真实代码里有很多边界情况会让朴素的实现出错。这一章集中讨论作用域相关的问题，以及教学版做了哪些简化。写提取器的一大半工作量其实不在主干，而在这些边界——主干几十行就能写完，边界处理却要反复对照 Python 语言手册验证。理解这一章，你才会明白为什么 `analyze_cell` 看似简单却能在真实 notebook 上给出可信结果。

这一章的每个小节都遵循同一个叙事结构：先给一段会翻车的代码，再解释为什么翻车，最后说明教学版怎么处理（精确处理还是简化跳过）。这种"反例驱动"的讲法，比罗列规则更易记住——你看到一段具体代码出错，印象远比读一条抽象规则深。建议你边读边拿这些反例在 REPL 里跑 `analyze_cell`，验证教学版的行为与文中描述一致。

## 函数内部局部变量不算 cell 的 def

这一节标题用"不算"的否定式，是因为这是最常见的误判：把函数内赋值当成 cell 的 def。这个误判在朴素实现里几乎必然出现，因为"看到 `Store` 就算 def"是最直觉的规则。纠正它需要理解 Python 的作用域分层，而这正是 AST 结构能帮我们的地方。考虑：

```python
def make_counter():
    count = 0
    def step():
        nonlocal count
        count += 1
        return count
    return step
```

如果天真地把所有 `Store` 的 `Name` 都算作 cell 的 def，我们会把 `count`、`step` 都收进 defs，这是错的——它们是 `make_counter` 的局部变量，cell 执行结束后在外部不可见。正确的做法是：**只收集顶层语句直接产生的绑定**作为 defs；函数体内部的赋值由 `_collect_function_locals` 单独处理，仅用于从 refs 中剔除。

实现上，`_extract_top_level_defs` 遍历 `tree.body`，不递归进入 `FunctionDef`/`ClassDef` 的 `body`；而 `_extract_refs` 里 `internal_locals = all_stores - defs` 才会捕获函数体内的 `Store` 名，把它们从 refs 中减掉。两者配合，既不让局部变量污染 defs，也不让它们污染 refs。对上面这段代码，结果是 `defs={"make_counter"}`、`refs=set()`——`count`、`step` 都被正确地排除在外。如果误把它们算进 defs，下游 cell 就会以为能从本 cell 拿到 `count`，执行时却 `NameError`，这是典型的"静态信息与运行时不符"的 bug。

这个反例还揭示了"静态分析与运行时语义必须对齐"的原则。Python 的作用域规则决定了哪些名字在 cell 执行后仍可见，AST 提取必须复刻这套规则，否则 defs 就名不副实。`LEGB`（Local/Enclosing/Global/Builtin）是 Python 作用域查找的顺序，我们的提取器只关心其中"G"层——cell 作用域相当于模块级，函数内是"L"层、闭包嵌套是"E"层。只收顶层绑定，就是在精确地取"G"层而忽略"L"和"E"。

## 嵌套函数与闭包

嵌套函数让"局部"的层级变深，但我们的实现靠一个巧妙的不变量绕过了显式追踪层级。这个不变量是：任何不在顶层 defs 里的 Store 名都算局部。它之所以成立，是因为 Python 的赋值只会绑定到"最近一层作用域"，而最近一层如果不是顶层（cell 作用域），就一定是某个函数或推导式的局部——两者都属于"非顶层"，一律归为局部不会错。嵌套函数会让"局部"的层级变深。`def outer(): def inner(): x = 1` 里，`x` 是 `inner` 的局部，`inner` 是 `outer` 的局部，两者都不是 cell 的 def。我们的实现不显式追踪嵌套层级，而是靠一个简单不变量：**任何不在 `defs`（顶层绑定）里的 `Store` 名都算局部**。因为 `all_stores` 收集了所有层级的 `Store`，`all_stores - defs` 自然把 `outer` 里的 `inner`、`inner` 里的 `x` 一并归为局部。这种"不追踪层级、靠集合差集"的做法比写一个维护作用域栈的 visitor 简单得多，代价是无法精确处理 `global`/`nonlocal`（见后文）。在绝大多数 notebook 代码里，这种简化是值得的——作用域栈的复杂度换来的是处理极少数冷门写法的能力，性价比不高。

闭包还引出一个微妙问题：闭包捕获的自由变量算 cell 的 ref 吗？比如 `def f(): return x`，`x` 在函数里被读但没在函数里赋值，它是闭包捕获的外层变量。我们的实现把 `x` 收进 `all_loads`，又因为 `x` 不在 `all_stores`（函数内没赋值）所以不被当局部，最终 `x` 留在 refs 里——这正是想要的结果：`x` 是 cell 的外部依赖，上游必须先定义。这种"读但未在函数内赋值的名字就是外部依赖"的判断，靠的仍是集合差集，无需专门写闭包逻辑。这再次体现了"集合差集"策略的覆盖力：它不仅处理了嵌套赋值，还顺带正确处理了闭包捕获，一个机制解决两类问题。

## comprehension 变量是局部的

Python 3 里，列表/集合/字典推导式与生成器表达式都有自己的作用域，循环变量不会泄漏到外层：

推导式作用域是 Python 3 相对 Python 2 最重要的语义修正之一。在 Python 2 里 `[x for x in items]` 执行后 `x` 仍可见，这导致推导式外的代码可能意外引用到循环变量的最后一个值，是隐蔽 bug 的温床。Python 3 把推导式变成隐式函数，循环变量随调用销毁。我们的分析跟着 Python 3 语义，把推导式变量当局部，这是正确的选择——若目标代码跑在 Python 2 上，分析结果会与运行时不符，但 marimo 本身要求 Python 3，所以无妨。这个要求也简化了提取器：不必兼容两种语义，只按 Python 3 的"推导式有独立作用域"处理即可。

```python
squares = [x**2 for x in range(10)]
# 执行后 x 在外部不可见
```

因此推导式里的 `x` 既不是 cell 的 def，也不是 cell 的 ref。但 `ast.walk` 会把 `x` 当成 `Store` 的 `Name` 节点吐出来，如果不去处理，`x` 可能被误算进 defs。

推导式作用域的处理是教学版"靠集合差集顺带解决"策略的又一实例。我们没有专门写"遍历推导式节点、把 target 加入局部"的代码，而是靠 `all_stores - defs` 自动把推导式里的 `Store` 归为局部。这是因为推导式的 `target` 在 AST 里是 `Store` 的 `Name`，会被 `ast.walk` 收进 `all_stores`，而它不在顶层 `defs` 里，所以差集后变成局部。这种"不写专门代码却正确处理"的巧合，是集合运算的威力——它把多种不同来源的"局部性"统一成一个差集操作。代价是如果将来要精确区分"推导式局部"和"函数局部"（比如错误信息要指明来源），就得改成显式追踪。

教学版的做法：在收集局部变量时，把所有 `comprehension` 节点（`ListComp`、`SetComp`、`DictComp`、`GeneratorExp` 的 `generators` 字段）里的 `target` 名也加入局部集合，从而在 refs 计算时被减掉；同时在 `_extract_top_level_defs` 里，推导式不是顶层语句的"直接绑定目标"（它只是 `Assign.value` 的一部分），所以不会进入 defs。最终 `squares = [x**2 for x in range(10)]` 得到 `defs={"squares"}`、`refs=set()`（`range` 是 builtin 被过滤）。注意 `x` 的 `Store` 会落入 `all_stores`，但 `x` 不在 `defs` 里，所以 `x ∈ internal_locals`，即便 `x` 也以 `Load` 出现在 `x**2` 中，也会被减掉。Python 2 里推导式变量会泄漏到外层，Python 3 修正了这个陷阱，我们的分析也跟着 Python 3 的语义走。

## 星号导入无法静态分析

星号导入是静态分析的一道硬墙：不是我们不想处理，是信息在静态阶段根本不存在。理解这道墙，也就理解了静态分析的能力边界——有些事必须执行才能知道，承认这一点比假装能处理更诚实。这道墙不只挡住星号导入：`exec()` 注入的名字、`setattr()` 动态加的属性、`globals()[k] = v` 动态绑定的变量，静态分析都看不到。这些动态手法在 notebook 里偶尔出现（尤其从外部库加载变量时），教学版一律不特殊处理，靠运行时的 `NameError` 兜底。

```python
from module import *
```

星号导入会把 `module` 里所有公共名字绑定到当前作用域，但这些名字的列表只有在**运行时**才能拿到（取决于 `module.__all__` 或 `dir(module)`）。静态 AST 看不到这些名字，因此无法把它们填进 defs。

教学版的选择是**跳过**：遇到 `alias.name == '*'` 时既不加入 defs，也不报错。这意味着含星号导入的 cell 会被认为"不定义任何变量"，可能导致 DAG 漏边。这是有意为之的简化——正确处理需要导入并执行该模块，已经超出静态分析范畴。生产版 marimo 会对星号导入发出警告，建议用户改用具名导入。下表对比几种策略的权衡：

| 方案                       | 准确性 | 实现成本 | 副作用                     |
|----------------------------|--------|----------|-----------------------------|
| 跳过（教学版）             | 漏边   | 零       | 下游可能拿到旧值           |
| 运行时反射 `dir(module)`   | 准确   | 高       | 需真正导入，破坏纯静态     |
| 报错拒绝                   | 安全   | 低       | 用户体验差                 |

教学版选第一种，是因为 notebook 里星号导入本就不推荐（污染命名空间、难以追踪来源），漏边的概率低，且即使漏了，运行时若真用了未定义名会立刻 `NameError` 暴露，不会静默出错。

星号导入还牵出一个更深的问题：静态分析的能力边界在哪？凡是"要运行才知道"的信息（`__all__` 的内容、动态创建的属性、`exec` 注入的名字），静态分析都无能为力。这不只是 AST 的局限，任何不执行的方法都一样。承认这条边界，并把它明确告知用户（比如生产版发警告），比假装能处理而给出错误结果要诚实得多。教学版选择静默跳过，是为了代码简单；生产版选择警告，是为了让用户知道这里有缺口。两种做法都尊重了静态分析的边界，只是反馈力度不同。

## global / nonlocal 未处理

`global`/`nonlocal` 是 Python 作用域系统里最"反直觉"的两个声明：它们让函数内的赋值穿透到外层，打破默认的局部绑定规则。静态分析要正确处理它们，必须维护一个作用域栈并跟踪每层的 `global`/`nonlocal` 声明——这是教学版选择跳过的复杂度。

```python
counter = 0
def inc():
    global counter
    counter += 1
```

`global counter` 声明意味着函数内对 `counter` 的赋值其实作用于 cell 作用域。严格来说，这种情况下 `counter` 应该算 cell 的 def（因为 `inc()` 被调用后会改写它），而且 `counter` 在 `inc` 内部的 `Load` 也不应被当作局部剔除。完整处理需要识别 `Global`/`Nonlocal` 节点并调整作用域模型。教学版**不处理**这两个声明，把它们的影响忽略，以保持代码简单。这在大多数 notebook 场景下够用，因为 `global`/`nonlocal` 在数据分析代码里很少见。若用户真写了上面的代码，`counter` 会因为顶层那行 `counter = 0` 进 defs，`inc` 内部的 `counter` 会被当局部剔除——巧合下结果正确；但若去掉顶层那行，`counter` 就会从 defs 里漏掉。处理 `global`/`nonlocal` 需要一个真正的作用域栈，记录每层函数声明的 `global` 名单，然后在收集 `Store`/`Load` 时据此决定归属——这是生产级分析器的工作，教学版有意略过。

`global`/`nonlocal` 的处理难度在于它"逆转"了默认的作用域归属。正常情况下函数内赋值是局部，`global x` 一声明就变成写 cell 作用域，这要求分析器在收集 `Store` 时查一下当前函数有没有 `global x` 声明。这需要一个"进入函数时压栈、遇到 `Global` 节点时在栈顶记录、遇到 `Store` 时查栈"的机制，代码量不大但状态多，容易写错。教学版判定 notebook 里这种写法罕见，选择不处理，把精力集中在更常见的场景上。这是"按使用频率分配实现精力"的工程取舍。

## del 语句

`del` 在 notebook 里偶尔出现（释放大 DataFrame、清理临时变量），它的语义是"删除绑定"而非"创建"或"读取"，所以既不进 defs 也不进 refs。这个处理虽然简化，但在大多数场景下正确——`del` 主要影响内存管理，不影响依赖关系。如果用户 `del` 了一个下游正在用的变量，运行时会 `NameError`，暴露问题。

`del x` 把 `x` 从作用域抹掉，对应 `Name(id='x', ctx=Del)`。教学版不把 `Del` 计入 defs 或 refs：它既不创建绑定，也不"需要"上游提供 `x`（执行到 `del` 时 `x` 已经在本 cell 或上游存在）。严格建模里，`del` 会影响"执行后留下哪些变量"，但教学版假设 cell 不会 `del` 自己的输出，忽略这一支。若用户写了 `del df`，本 cell 的 `namespace` 里 `df` 会被运行时删掉，但静态 `defs` 仍含 `df`——这是已知的不精确，代价是极低的实现复杂度。

`del` 还有一个更微妙的语义：`del d[k]` 删的是字典元素不是变量，它的 `Subscript` 节点里 `d` 是 `Load` 不是 `Del`，所以 `d` 会正常进 refs。只有 `del name` 形式（`name` 是裸变量）才有 `Del` ctx。区分这两种 `del` 靠的是目标节点的类型：`Name` 是删变量，`Subscript`/`Attribute` 是删元素/属性。教学版不显式区分，因为对 `Del` 一律不处理，两种情况都不进 defs/refs，结果恰好都正确。

## builtins 过滤

builtins 过滤看似简单，却是让依赖图"干净"的关键一步。如果没有它，每个 cell 都会依赖 `print`/`len`/`range` 等内置名，图里全是噪声边，真正的数据依赖被淹没。过滤后，refs 只含"来自其他 cell 的变量"，依赖图只表达 cell 间的数据流，不含对语言内置的伪依赖。这种"干净"让图小而准，调度器重算的范围也最小。最后强调 builtins 过滤的意义。`print`、`open`、`range`、`len`、`Exception`……这些名字在任意 cell 里都是 `Load`，但它们不来自任何上游 cell，而是 Python 内置。如果不剔除，每个调用 `print` 的 cell 都会"依赖"一个不存在的 `print` cell，DAG 里满是虚假边。实现上用 `set(dir(builtins))` 作为过滤集，从 refs 中减去。注意：如果用户自己写了 `print = my_print` 重绑定，`print` 会出现在 defs 里，这时它就不再是 builtin 而是普通变量——教学版不区分这种重绑定，统一先减 builtins，对绝大多数场景足够。`_BUILTIN_NAMES` 在模块加载时算一次，约 150 个名字，包含 `__name__`、`__import__` 等双下划线名，它们被一并过滤也无妨。这种"统一减"的做法在用户重绑定 builtins 时会漏掉一条依赖边，但这种情况极罕见，且运行时会立刻 `NameError`，不会静默出错。

builtins 集合的大小值得留意。`dir(builtins)` 大约返回 150 个名字，除了常见的 `print`/`len`/`range`，还有所有异常类型（`ValueError`、`TypeError` 等）、双下划线名（`__name__`、`__import__`）、内置类型（`int`、`str`、`list`）。把它们全过滤掉是安全的，因为 notebook 代码几乎不会把 `int` 当成"来自某个 cell 的依赖"。唯一会出问题的是用户重绑定内置名（如 `list = my_list`），这时 `list` 应该算 ref 却被误减——教学版接受这个极小概率的不精确。实际上这个不精确几乎不影响体验：重绑定内置名后，下游用 `list` 的 cell 会从重绑定 cell 的 defs 里找到 `list`，依赖边照常建立；只是重绑定 cell 自己的 refs 里少了 `list`（被误减），但它本来也不该依赖外部的 `list`（它是定义方），所以结果恰好正确。

这些边界处理加在一起，才让 `analyze_cell` 在面对真实 notebook 代码时给出可信的 defs/refs。教学版有意在 `global`/`nonlocal`/`del`/星号导入上做了简化，换来的是不到 110 行的实现——这正是"教学"的取舍：先让主干跑通，把少数冷门情况留作练习。理解了这些边界的存在与取舍，你也就理解了静态分析在"精确"与"可实现"之间永恒的权衡。

回顾这一章的取舍清单：函数局部变量精确处理（靠集合差集）、嵌套函数靠同一套差集顺带覆盖、推导式靠差集顺带覆盖、星号导入跳过、`global`/`nonlocal` 忽略、`del` 忽略、builtins 统一减。其中"精确处理"的四项都是靠 `all_stores - defs` 这一个集合运算顺带完成的，几乎零额外代码；"跳过/忽略"的三项则是主动放弃精度换简单。这个分配体现了教学版的设计哲学：把实现精力投在高频场景，对低频冷门写法只保证"不崩"即可。生产版会把这张清单里的"忽略"逐个改成"精确处理"，代码量随之膨胀到几百行，但能覆盖到 99.9% 的真实代码。教学版与生产版的差距，主要就在这张清单的完成度上。
