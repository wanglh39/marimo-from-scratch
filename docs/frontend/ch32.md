# React 与 reactive：两种响应式的异同

marimo 前端用 React 19，而 marimo 本身主打 reactive notebook。两个"reactive"含义不同，但前端实现里它们要协作。理清异同，才能写出对的组件。这一章先把两个概念拆开对照，再讲它们在前端如何衔接，最后与 Vue 的响应式做横向对比，帮读者建立完整的响应式心智模型。

## 两种响应式

**React 的响应式**：UI 是状态的函数，`UI = f(state)`。状态变，React 自动 diff 虚拟 DOM、更新真实 DOM。响应的是**组件状态变化**，粒度是组件级。触发方式是 `setState` / `useState` 的 setter，React 调度后重新执行函数组件，diff 出最小变更集提交到 DOM。

**marimo notebook 的响应式**：cell 输出是代码和上游 cell 输出的函数，`output_cell = f(code, upstream_outputs)`。上游 cell 重算，下游自动重算。响应的是**依赖数据变化**，粒度是 cell 级。触发方式是用户改代码或拖滑块，后端按 DAG 拓扑序重算受影响 cell，结果通过 WebSocket 推回前端。

两者都遵循"声明依赖，自动更新"的理念，但作用域不同：React 管前端渲染，marimo 管后端计算。前端要做的，是把后端的 cell 响应式**投影**到 React 的组件响应式上。注意"投影"不是"复制"——前端不重算 cell 输出，只把后端算好的结果装进 state，让 React 据此重渲染。

## 状态驱动 UI

`useNotebook` hook 持有一份 notebook 状态，对应后端的 cell 列表与依赖图：

```typescript
export function useNotebook() {
  const [cells, setCells] = useState<CellInfo[]>([])
  const [edges, setEdges] = useState<[string, string][]>([])
  const [connected, setConnected] = useState(false)
  const wsRef = useRef<WebSocket | null>(null)
  // ...
  return { cells, edges, connected, send }
}
```

其中 `CellInfo` 是单个 cell 的完整描述，字段与后端消息一一对应：

```typescript
export interface CellInfo {
  cell_id: string
  code: string
  defs: string[]
  refs: string[]
  status: CellStatus
  output: unknown
  stdout: string
  exception: string | null
  exception_type: string | null
  components: UIComponentInfo[]
}
```

后端推来的 `cell_result`、`graph_changed`、`state` 消息都翻译成 `setCells` / `setEdges` 调用，触发 React 重渲染。后端 cell 状态变化 → 前端 state 变化 → React 重渲染，这条链就是两个响应式的衔接。关键在于前端**不自己算** cell 结果，只搬运后端结果——这保证了前后端状态最终一致，前端永远是后端状态的投影。

## 关键区别：谁触发更新

React 组件内部 `setState` 是同步触发（React 18+ 自动 batch）；而 marimo 的 cell 重算是后端异步执行后推消息触发。所以前端 cell 组件不能假设"我改了代码输出立即变"——改代码只是 `update_cell` 通知后端，输出要等后端 `run_cell` 执行完推 `cell_result` 才变。这是 notebook 响应式异步性的体现。

看 `App.tsx` 里 `handleUpdate` 的真实实现：

```tsx
const handleUpdate = (cellId: string, code: string) =>
  send({ type: 'update_cell', cell_id: cellId, code })
```

它只发消息，不修改任何 state。本地 cells 数组的 code 字段更新要等后端回 `state` 或 `graph_changed` 才发生（教学版采用非乐观更新策略，简化一致性推理）。对比 `handleRun`：

```tsx
const handleRun = (cellId: string) =>
  send({ type: 'run_cell', cell_id: cellId })
```

同样只发消息，cell 的 status 从 `idle` 变 `running` 再变 `done` 全由后端 `cell_result` 驱动。前端组件因此可以做成纯展示——读 `cell.status` 渲染对应图标，不需要自己维护"我正在跑"的本地 flag。

## 不可变更新

React 要求 state 不可变更新才能触发重渲染。`useNotebook` 里处理 `cell_result` 的写法是教科书例子：

```typescript
case 'cell_result':
  setCells((prev) =>
    prev.map((c) =>
      c.cell_id === msg.cell_id
        ? {
            ...c,
            status: msg.status,
            output: msg.output,
            stdout: msg.stdout,
            exception: msg.exception,
            exception_type: msg.exception_type,
            components: msg.components,
          }
        : c
    )
  )
  break
```

`prev.map` 返回新数组，匹配的 cell 用展开运算符 `{...c, ...}` 生成新对象，不匹配的返回原引用。这样 React 的引用比较能精确知道"只有这一个 cell 变了"，其余 cell 组件靠 `React.memo` 跳过重渲染。

不能直接 `cells[id].status = "done"`——React 不会感知，因为数组引用和对象引用都没变。这条规则在 notebook 场景尤其要紧，因为 cell 间有依赖关系，错误地 mutate 可能漏更新下游 cell 的 UI：比如 cell A 重算后 cell B 应变 stale，若直接 mutate A 的 status，B 的 stale 标记可能因 React 没察觉到变化而没刷出来。

## React 19 的相关特性

教学版用 React 19，主要用到：

- **Concurrent features**：`useTransition` 标记重渲染非紧急，让滑块拖动时不阻塞输入。notebook 里拖滑块会高频触发 `ui_event`，后端重算可能耗时，把结果回写标为 transition 能让滑块手感顺滑；
- **Automatic batching**：一次 `onmessage` 里多个 `setX` 自动合并一次渲染。`state` 消息同时 `setCells` 和 `setEdges`，batch 后只触发一次重渲染，避免中间态闪烁；
- **StrictMode**：开发时双调用帮发现副作用 bug。`useNotebook` 里建 WebSocket 的 effect 在 StrictMode 下会跑两次，所以 cleanup 必须 `ws.close()` 干净销毁，否则开发时会泄漏连接。

不需要 Suspense、Server Components 这些——notebook 前端是纯客户端 SPA，数据来自 WebSocket 不是 fetch。Server Components 的流式 SSR 在这里没意义，因为 notebook 的"流"是 WebSocket 双向消息，不是 HTTP 响应流。

## 与 Vue 响应式的对比

Vue 3 的响应式基于 Proxy 拦截，`reactive(obj)` 返回的代理对象**属性级**追踪依赖：读属性收集依赖、改属性触发更新。粒度比 React 细——React 是组件级重渲染，Vue 是 effect 级精确更新。

```typescript
// Vue 风格伪代码
const state = reactive({ count: 0 })
watchEffect(() => { console.log(state.count) }) // 自动追踪 count
state.count++ // 直接触发，无需 setState
```

对比 React：

```typescript
const [count, setCount] = useState(0)
useEffect(() => { console.log(count) }, [count])
setCount(count + 1) // 必须显式调 setter
```

React 强制 `setState` 是为了"不可变 + 显式触发"的工程纪律——避免散落的 mutation 让数据流难追踪。Vue 的 Proxy 自动追踪更灵活但隐式，大型项目里调试依赖来源更难。

对 marimo 前端而言，React 的纪律更合适：notebook 状态来自后端消息，用 `setState(prev => ...)` 模式能清晰表达"消息驱动状态"的数据流方向。若用 Vue，`cells[0].status = "done"` 这种 mutation 写法虽然简洁，但混入"前端自己改"和"后端消息改"两种来源后，调试时难分辨谁改了什么。React 的"所有变更走 setter"约束反而让数据流单一可追溯。

## 衔接总结

理解了"React 响应式管渲染、marimo 响应式管计算、消息协议连接两者"，写前端组件就有了主心骨：组件只管根据 state 渲染，state 变化交给 hook 根据后端消息驱动。组件不发起计算、不预测结果、不绕过 hook 直接改 state——这三条约束让前端代码保持简单，复杂度全收拢在 `useNotebook` 一个 hook 里。下一章讲编辑器组件如何在这种约束下与 CodeMirror 6 的命令式 API 共存。
