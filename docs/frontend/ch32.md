# React 与 reactive：两种响应式的异同

marimo 前端用 React 19，而 marimo 本身主打 reactive notebook。两个"reactive"含义不同，但前端实现里它们要协作。理清异同，才能写出对的组件。

## 两种响应式

**React 的响应式**：UI 是状态的函数，`UI = f(state)`。状态变，React 自动 diff 虚拟 DOM、更新真实 DOM。响应的是**组件状态变化**，粒度是组件级。

**marimo notebook 的响应式**：cell 输出是代码和上游 cell 输出的函数，`output_cell = f(code, upstream_outputs)`。上游 cell 重算，下游自动重算。响应的是**依赖数据变化**，粒度是 cell 级。

两者都遵循"声明依赖，自动更新"的理念，但作用域不同：React 管前端渲染，marimo 管后端计算。前端要做的，是把后端的 cell 响应式**投影**到 React 的组件响应式上。

## 状态驱动 UI

`useNotebook` hook 持有一份 notebook 状态：

```typescript
interface NotebookState {
  cells: Cell[];      // id, code, status, result, refs, defs
  edges: [string, string][];
  connected: boolean;
}
```

后端推来的 `cell_result`、`graph_changed`、`state` 消息都翻译成 `setCells` / `setEdges` 调用，触发 React 重渲染。后端 cell 状态变化 → 前端 state 变化 → React 重渲染，这条链就是两个响应式的衔接。

## 关键区别：谁触发更新

React 组件内部 `setState` 是同步触发（React 18+ 自动 batch）；而 marimo 的 cell 重算是后端异步执行后推消息触发。所以前端 cell 组件不能假设"我改了代码输出立即变"——改代码只是 `update_cell` 通知后端，输出要等后端 `run_cell` 执行完推 `cell_result` 才变。这是 notebook 响应式异步性的体现。

## 不可变更新

React 要求 state 不可变更新才能触发重渲染：

```typescript
setCells(prev => prev.map(c =>
  c.id === msg.cell_id ? {...c, status: msg.status} : c
));
```

不能直接 `cells[id].status = "DONE"`——React 不会感知。这条规则在 notebook 场景尤其要紧，因为 cell 间有依赖关系，错误地 mutate 可能漏更新下游 cell 的 UI。

## React 19 的相关特性

教学版用 React 19，主要用到：

- **Concurrent features**：`useTransition` 标记重渲染非紧急，让滑块拖动时不阻塞输入；
- **Automatic batching**：一次 `onmessage` 里多个 `setX` 自动合并一次渲染；
- **StrictMode**：开发时双调用帮发现副作用 bug。

不需要 Suspense、Server Components 这些——notebook 前端是纯客户端 SPA，数据来自 WebSocket 不是 fetch。

理解了"React 响应式管渲染、marimo 响应式管计算、消息协议连接两者"，写前端组件就有了主心骨：组件只管根据 state 渲染，state 变化交给 hook 根据后端消息驱动。
