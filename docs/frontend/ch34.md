# Cell 组件：CellView 结构、状态图标、defs/refs 标签

`CellView.tsx` 是单个 cell 的完整 UI，把编辑器、输出、状态、元信息、操作按钮组合在一起。它是 notebook 前端最复杂的组件，但仍可拆成清晰的子区域。这一章先看整体结构与渲染流程，再逐块拆解状态图标、defs/refs 标签、操作按钮、UI 组件区，最后讲为什么 CellView 设计成无状态纯展示组件。

## 整体结构

`CellView` 的真实实现骨架：

```tsx
export function CellView({ cell, onRun, onUpdate, onRemove, onUIEvent }: Props) {
  const outputIsUI =
    cell.output !== null &&
    typeof cell.output === 'object' &&
    (cell.output as Record<string, unknown>)?._ui === true

  return (
    <div className={`cell cell-${cell.status}`}>
      <div className="cell-header">
        <span className="cell-status">{STATUS_ICON[cell.status]}</span>
        <span className="cell-id">{cell.cell_id}</span>
        {cell.defs.length > 0 && (
          <span className="cell-tag tag-def">defs: {cell.defs.join(', ')}</span>
        )}
        {cell.refs.length > 0 && (
          <span className="cell-tag tag-ref">refs: {cell.refs.join(', ')}</span>
        )}
        <div className="cell-actions">
          <button className="btn-run" onClick={() => onRun(cell.cell_id)}>Run</button>
          <button className="btn-remove" onClick={() => onRemove(cell.cell_id)}>×</button>
        </div>
      </div>
      <CodeEditor
        value={cell.code}
        onChange={(code) => onUpdate(cell.cell_id, code)}
        onRun={() => onRun(cell.cell_id)}
      />
      {cell.components.length > 0 && (
        <div className="cell-components">
          {cell.components.map((comp) => (
            <UIComponentView key={comp.id} component={comp} onEvent={onUIEvent} />
          ))}
        </div>
      )}
      {(cell.stdout || cell.output !== null || cell.exception) && (
        <div className="cell-output">
          {cell.stdout && <pre className="output-stdout">{cell.stdout}</pre>}
          {cell.output !== null && !outputIsUI && (
            <pre className="output-value">
              {typeof cell.output === 'string'
                ? cell.output
                : JSON.stringify(cell.output, null, 2)}
            </pre>
          )}
          {outputIsUI && (
            <UIComponentView component={cell.output as UIComponentInfo} onEvent={onUIEvent} />
          )}
          {cell.exception && (
            <pre className="output-error">{cell.exception_type}: {cell.exception}</pre>
          )}
        </div>
      )}
    </div>
  )
}
```

四段从上到下：**header（工具栏）→ CodeEditor（编辑器）→ cell-components（UI 组件区）→ cell-output（输出区）**。根 div 的 className 带状态后缀 `cell-${cell.status}`，让 CSS 能按状态调边框颜色——error 红边、stale 黄虚边。`outputIsUI` 是个判断：cell 直接返回 UI 组件时（如 `return mo.slider(0,10)`），output 本身就是组件描述，要用 `UIComponentView` 渲染而非当普通值 JSON 展示。

## 渲染流程

CellView 的完整渲染流程：父组件 `App` 持有 `cells` 数组，`cells.map` 为每个 cell 实例化一个 CellView，key 用 `cell.cell_id` 保证重排时复用 DOM。React 重渲染时，CellView 函数体重新执行，读 `cell` 各字段渲染对应子区域。`cell.status` 变化 → 根 div className 变 → CSS 切换边框颜色；`cell.code` 变 → CodeEditor 的 value prop 变 → 同步 effect dispatch 更新编辑器内容；`cell.output` 变 → 输出区重渲染。整个流程纯数据驱动，CellView 不持有任何会影响渲染的本地 state。

## 状态图标

`STATUS_ICON` 是静态映射表，根据 `cell.status` 显示不同符号：

```tsx
const STATUS_ICON: Record<string, string> = {
  idle: '·',
  pending: '…',
  running: '→',
  done: '✓',
  error: '✗',
  stale: '○',
}
```

教学版用单字符简单直观，配合 CSS 上色：`.cell-done .cell-status { color: var(--green); }` 让 ✓ 绿色，`.cell-error .cell-status { color: var(--red); }` 让 ✗ 红色。生产版用 SVG 图标加 CSS 动画（running 转圈、stale 闪烁）。状态值 `CellStatus = 'idle' | 'pending' | 'running' | 'done' | 'error' | 'stale'` 来自后端 `cell_result.status` 或 `state` 消息，前端不自己算——单一数据源在后端。这意味着前端不需要在 run 时本地把 status 设成 running 再等后端确认，而是统一等后端消息推 status 变化。代价是 run 后到收到消息之间 UI 不变，但 WebSocket 往返通常 < 50ms，用户感知不到延迟。

## defs/refs 标签

显示 cell 的依赖关系，帮用户理解图结构：

```tsx
{cell.defs.length > 0 && (
  <span className="cell-tag tag-def">defs: {cell.defs.join(', ')}</span>
)}
{cell.refs.length > 0 && (
  <span className="cell-tag tag-ref">refs: {cell.refs.join(', ')}</span>
)}
```

defs 用绿色标签（"我产出这些变量"），refs 用蓝色（"我引用这些变量"）。CSS 里 `.tag-def { background: rgba(166,227,161,0.15); color: var(--green); }` 半透明绿底绿字，`.tag-ref` 同理蓝色。点击标签可以做"跳转到定义 cell"等导航功能，教学版只显示不交互。

这些标签数据来自后端解析函数签名得到，前端只渲染。改代码后 `update_cell` 通知后端，后端重新解析 refs/defs，下条 `state` 或 `cell_result` 消息里带新值，前端自动更新——用户改 `return (y,)` 成 `return (y, z)`，几毫秒后 z 标签就冒出来。这个"改代码 → 后端重解析 → 推新 defs → 前端刷标签"的闭环，是 marimo 响应式在前端可见的最直接体现。

## Run / Delete 按钮

Run 按钮触发 `onRun(cell.cell_id)`，父组件发 `run_cell` 消息。Delete 触发 `remove_cell`。教学版按钮放工具栏右侧，`cell-actions` 用 `margin-left: auto` 推到 header 末尾：

```tsx
<div className="cell-actions">
  <button className="btn-run" onClick={() => onRun(cell.cell_id)}>Run</button>
  <button className="btn-remove" onClick={() => onRemove(cell.cell_id)}>×</button>
</div>
```

`btn-remove` 用 × 字符而非"Delete"文字，节省空间。hover 时变红色提示危险操作。生产版常加确认对话框防误删，教学版直接删——后端 `remove_cell` 不可逆，但教学场景数据非生产，简化交互。

按钮状态联动可加：`cell.status === "running"` 时 Run 按钮置灰避免重复点击：

```tsx
<button
  className="btn-run"
  disabled={cell.status === 'running'}
  onClick={() => onRun(cell.cell_id)}
>
  {cell.status === 'running' ? '...' : 'Run'}
</button>
```

教学版当前没加这层，因为后端 `run_cell` 对正在跑的 cell 会幂等忽略，重复点不会出错，只是多发一条消息。但前端禁用能省一次往返，体验更顺。

## UI 组件区

`cell.components` 是 cell 里创建的 marimo UI 组件（如 `s = mo.slider(0, 10)` 里的滑块），与 `cell.output` 不同——output 是 cell 返回值，components 是 cell 执行过程中产出的交互组件。渲染：

```tsx
{cell.components.length > 0 && (
  <div className="cell-components">
    {cell.components.map((comp) => (
      <UIComponentView key={comp.id} component={comp} onEvent={onUIEvent} />
    ))}
  </div>
)}
```

key 用 `comp.id`，这个 id 由后端 `_update_component_ids` 基于位置稳定分配，保证重渲染时组件复用不丢内部状态（如滑块正在拖动的视觉位置）。`UIComponentView` 按 `comp.type` 分支渲染 slider/button/checkbox，事件通过 `onUIEvent` 上抛到 App 发 `ui_event` 消息。下一章详述。

## 编辑器与输出的衔接

`CodeEditor` 的 `onChange` 把代码变化向上抛，父组件发 `update_cell`；`onRun` 抛 Shift-Enter 触发运行。`CellOutput` 根据 `cell.result` 渲染 stdout/output/exception，下一章详述。三段之间没有直接通信，全部通过 props 上抛到 App，App 再通过 useNotebook 发消息——这是 React 推荐的"提升状态到父组件"模式。

## 为什么 CellView 无状态

CellView 本身不持有状态，全靠 props 驱动。这带来三个好处：

1. **可预测**：给定相同 `cell` prop，渲染结果必然相同，调试时只需检查 props 链；
2. **cell 间联动自然**：运行 cell A 触发 cell B 重算，B 的 UI 更新通过父组件单一 state 完成——A 的 onRun → App.send → 后端重算 B → 推 cell_result → useNotebook.setCells → B 的 CellView 重渲染。不需要 A 和 B 直接通信；
3. **性能可优化**：纯展示组件套 `React.memo` 后，props 不变就跳过重渲染。notebook 里改 cell A 代码时，cell B 的 props 不变（B 的 code/output/status 都没变），memo 直接跳过，避免无谓 diff。

若 CellView 自己持有"是否在编辑"等本地 state，cell 间联动就要绕道本地 state 同步，复杂度爆炸。把状态全提到 App，CellView 退化成纯函数，是 notebook 前端能保持简单的关键架构决策。下一章讲输出区如何渲染各种类型的结果。
