# 前后端状态同步：useNotebook hook 与 WebSocket onmessage

`useNotebook.ts` 是前端的状态中枢。它维护 cells、edges、connected 三块状态，通过 WebSocket 与后端保持同步。所有组件都从它读状态、通过它发消息。这一章拆解它的实现，重点是 WebSocket 消息处理的完整流程和"state 永远由后端驱动"的设计原则。

## hook 的对外接口

```typescript
export function useNotebook() {
  // ...
  return { cells, edges, connected, send }
}
```

返回三块状态和一个 `send` 函数。`cells` 是 `CellInfo[]`，每个 cell 的完整描述；`edges` 是 `[string, string][]`，依赖图的边列表；`connected` 是 WebSocket 连接状态布尔。`send` 是发消息的统一入口，组件用它发各种动作消息：

```tsx
// App.tsx 里的用法
const { cells, edges, connected, send } = useNotebook()

const handleRun = (cellId: string) =>
  send({ type: 'run_cell', cell_id: cellId })
const handleUpdate = (cellId: string, code: string) =>
  send({ type: 'update_cell', cell_id: cellId, code })
const handleRemove = (cellId: string) =>
  send({ type: 'remove_cell', cell_id: cellId })
const handleAdd = () => send({ type: 'add_cell', code: '' })
const handleRunAll = () => send({ type: 'run_all' })
const handleUIEvent = (componentId: string, value: unknown) =>
  send({ type: 'ui_event', component_id: componentId, value })
```

组件不直接改 state——state 永远由后端消息驱动回写。`send` 只往 WebSocket 写 JSON，不等响应。这种"动作发消息、状态等消息"的分离让数据流单向清晰。

## 内部状态与 WebSocket

```typescript
export function useNotebook() {
  const [cells, setCells] = useState<CellInfo[]>([])
  const [edges, setEdges] = useState<[string, string][]>([])
  const [connected, setConnected] = useState(false)
  const wsRef = useRef<WebSocket | null>(null)

  useEffect(() => {
    const protocol = location.protocol === 'https:' ? 'wss:' : 'ws:'
    const ws = new WebSocket(`${protocol}//${location.host}/ws`)
    wsRef.current = ws

    ws.onopen = () => {
      setConnected(true)
      ws.send(JSON.stringify({ type: 'get_state' }))
    }
    ws.onclose = () => setConnected(false)
    ws.onmessage = (event) => {
      const msg: ServerMessage = JSON.parse(event.data)
      switch (msg.type) {
        case 'state':
        case 'graph_changed':
          setCells(msg.cells)
          setEdges(msg.edges)
          break
        case 'cell_result':
          setCells((prev) =>
            prev.map((c) =>
              c.cell_id === msg.cell_id
                ? {
                    ...c,
                    status: msg.status,
                    output: msg.output,
                    stdout: msg.stdout,
                    exception: msg.exception,
                    exception_type: msg.exception_type,
                    components: msg.components,
                  }
                : c
            )
          )
          break
        case 'error':
          console.error('Server error:', msg.message)
          break
      }
    }

    return () => ws.close()
  }, [])

  const send = useCallback((msg: object) => {
    wsRef.current?.send(JSON.stringify(msg))
  }, [])

  return { cells, edges, connected, send }
}
```

mount 时建连接，协议根据页面是 http/https 选 ws/wss，URL 用 `location.host` 同源部署。`onopen` 立即 `setConnected(true)` 并发 `get_state` 请求全量状态——这是初始化的关键：前端启动时不知道后端有哪些 cell，必须主动要一次。`onclose` 设 disconnected，UI 顶部指示器变红闪烁。`onmessage` 把每条消息 JSON.parse 后交给 switch 处理。cleanup `ws.close()` 卸载时断开，防止泄漏。

`send` 用 `useCallback` 包裹空依赖，引用稳定，传给子组件不会触发无谓重渲染。`wsRef.current?.send` 的 `?.` 防止 ws 还没建好就发消息的边界情况。

## dispatch：消息到状态的翻译

`onmessage` 里的 switch 是消息到状态的翻译核心，四种消息类型对应四种处理：

**`state` 消息**：全量替换。后端把所有 cell 和边一次性发来，前端直接 `setCells(msg.cells)` / `setEdges(msg.edges)`。用于初始化（`get_state` 的响应）和重连场景。全量替换简单粗暴，但 state 消息频率低（只在启动和大幅变化时），性能不是问题。

**`graph_changed` 消息**：依赖关系变了（用户改了函数签名，refs/defs 变化），同样全量替换 cells 和 edges。教学版把 `state` 和 `graph_changed` 合并处理，因为两者数据结构相同。区别在语义：state 是"完整快照"，graph_changed 是"图结构变了但 cell 输出可能没重算"。后端发 graph_changed 时 cells 数组里各 cell 的 output/status 字段保持原值，只更新 defs/refs。

**`cell_result` 消息**：单个 cell 执行完成，只更新对应 cell，其余不动：

```typescript
case 'cell_result':
  setCells((prev) =>
    prev.map((c) =>
      c.cell_id === msg.cell_id
        ? { ...c, status: msg.status, output: msg.output,
            stdout: msg.stdout, exception: msg.exception,
            exception_type: msg.exception_type, components: msg.components }
        : c
    )
  )
  break
```

`prev.map` 返回新数组，匹配的 cell 用展开运算符生成新对象，不匹配的返回原引用。这样 React 能精确知道"只有这一个 cell 变了"，其余 cell 组件靠 `React.memo` 跳过重渲染。这是 notebook 性能的关键——Run All 时后端逐个推 cell_result，前端逐个更新，没变的 cell 不重渲染。

**`error` 消息**：服务端报错，`console.error` 记录，不改 state。教学版简化处理，生产版可弹 toast 通知用户。

## 动作函数与乐观更新

`App.tsx` 里的 `handleUpdate` 有个设计选择：

```tsx
const handleUpdate = (cellId: string, code: string) =>
  send({ type: 'update_cell', cell_id: cellId, code })
```

它只发消息，不本地改 `cells`。这意味着用户输入代码后，要等后端回 `state` 或 `graph_changed` 才看到本地 cells 更新——但 CodeEditor 内部 CM6 已经显示输入内容（CM6 自治 DOM），所以用户视觉上无延迟。cells state 的更新是为了让其他依赖 cell.code 的逻辑（如 defs/refs 解析）拿到新值，这些本来就要等后端解析，不乐观更新无妨。

对比乐观更新写法：

```typescript
const updateCell = (id, code) => {
  setCells(prev => prev.map(c => c.id === id ? {...c, code} : c))  // 乐观
  send({ type: 'update_cell', cell_id: id, code })
}
```

乐观更新先改本地 state 让编辑器立即响应，再发消息给后端。好处是 cells state 立即同步，坏处是若后端拒绝（如代码非法）本地已改，需回滚。教学版选非乐观更新，简化一致性推理——cells state 永远是后端确认后的状态，不会出现"前端显示新 code 但后端还是旧 code"的分歧。

`handleRun` 同样不乐观更新——运行结果是后端算的，前端不能预测，必须等 `cell_result` 回来。但可立即把 status 置 running 让 UI 即时反馈：

```typescript
const runCell = (id) => {
  setCells(prev => prev.map(c => c.id === id ? {...c, status: 'running'} : c))
  send({ type: 'run_cell', cell_id: id })
}
```

教学版没加这层，因为后端 `cell_result` 推回 status: 'running' 的延迟通常 < 50ms，用户感知不到。但高延迟网络下加这层能改善手感。

## 单向数据流

整套机制遵循**单向数据流**：

```
用户操作 → send 发消息 → 后端处理 → 后端推消息 → onmessage 改 state → React 重渲染
```

state 永远由后端消息驱动，前端不自己算 cell 结果、不自己判依赖、不自己改 status。这保证了前后端状态最终一致——前端是后端状态的投影，不会出现"前端显示 done 但后端其实 error"的分歧。即使 WebSocket 断开重连，前端发 `get_state` 拉全量状态，自动恢复一致。

这个设计的代价是延迟：每次操作都要等后端往返。对 notebook 场景可接受——cell 执行本来就有计算延迟，网络往返相对可忽略。对低延迟场景（如纯文本编辑）则用 CM6 内部 state 自治，不绕后端。

理解了 useNotebook，前端其他组件都只是"读 state + 调 send"的薄壳，复杂度全收拢在这个 hook 里。下一章讲交互细节如何在这套数据流上构建。
