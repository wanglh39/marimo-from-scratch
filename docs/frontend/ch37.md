# 交互设计：Shift-Enter、暗色主题、连接指示器

前几章讲了结构和数据流，这一章聚焦**人机交互细节**。好的 notebook 要让用户手指不离键盘就能跑完一轮实验。marimo 前端的交互设计围绕效率、清晰、容错三个目标。这一章讲 Shift-Enter 运行、暗色主题、连接指示器、Run All 与 Add Cell、UI 事件流、容错策略，最后总结交互设计原则。

## Shift-Enter 运行

notebook 的肌肉记忆。在 CodeMirror 里绑定，`CodeEditor.tsx` 的真实实现：

```tsx
keymap.of([
  {
    key: 'Shift-Enter',
    run: () => {
      onRunRef.current?.()
      return true
    },
  },
]),
```

`return true` 告诉 CM6 这个键已被处理，不要再冒泡（比如别换行）。`onRunRef.current` 读 ref 拿最新 onRun 回调，避免 stale closure。onRun 由 CellView 传入 `() => onRun(cell.cell_id)`，最终调 `useNotebook` 的 send 发 `run_cell` 消息。

完整事件流：用户按 Shift-Enter → CM6 keymap 匹配 → 调 onRunRef.current → CellView 的 onRun → App 的 handleRun → send({type: 'run_cell', cell_id}) → WebSocket 发消息 → 后端执行 cell → 推 cell_result → useNotebook 的 onmessage → setCells 更新该 cell → CellView 重渲染显示新输出。这条链贯穿前端三层（CodeEditor → CellView → App → useNotebook）和后端，是 notebook 最常用的操作路径，必须顺畅。

进阶行为是"运行并跳到下一个 cell"——Run 完焦点自动移到下方 cell，连续按 Shift-Enter 能逐个跑下去。教学版可选实现：

```typescript
run: () => {
  onRunRef.current?.()
  onNextCellRef.current?.()
  return true
}
```

`onNextCell` 由 App 层提供，根据当前 cell 在 cells 数组里的位置找下一个，调 `document.getElementById(nextCellId)?.focus()`。需要给每个 cell 的编辑器容器设可聚焦的 `tabindex`。这个细节让"跑一轮 notebook"变成连续按 Shift-Enter，效率显著提升。

## 暗色主题

`index.css` 定义暗色主题。notebook 用户长时间盯屏幕，暗色减轻眼疲劳。配色用 CSS 变量集中管理：

```css
:root {
  --bg: #1e1e2e;
  --bg-cell: #252537;
  --bg-output: #1a1a2a;
  --text: #cdd6f4;
  --text-dim: #6c7086;
  --accent: #89b4fa;
  --green: #a6e3a1;
  --red: #f38ba8;
  --yellow: #f9e2af;
  --border: #313244;
}
```

这套配色借鉴 Catppuccin Mocha，低饱和度不刺眼。三层背景微妙差异形成层次：`--bg`（页面）< `--bg-cell`（cell 卡片）< `--bg-output`（输出区），cell 浮于页面之上，输出区凹进 cell 之内。文字主色 `--text` 高对比，次要信息用 `--text-dim` 退后。状态色语义化：`--green` 成功、`--red` 错误、`--yellow` 警告、`--accent` 强调。

应用层样式：

```css
body { background: var(--bg); color: var(--text); }
.cell {
  background: var(--bg-cell);
  border-radius: 8px;
  border: 1px solid var(--border);
  overflow: hidden;
}
.cell-error { border-color: var(--red); }
.cell-stale { border-color: var(--yellow); border-style: dashed; }
.cell-output { background: var(--bg-output); border-top: 1px solid var(--border); }
.output-error { color: var(--red); }
.tag-def { background: rgba(166,227,161,0.15); color: var(--green); }
.tag-ref { background: rgba(137,180,250,0.15); color: var(--accent); }
```

cell 状态用边框颜色和样式区分：error 红实边、stale 黄虚边、正常灰实边。标签用半透明背景色 + 全色文字，既显眼又不喧宾夺主。

CodeMirror 也要配暗色主题，教学版用内联 `EditorView.theme` 融入 cell 背景：

```typescript
EditorView.theme({
  '&': { fontSize: '14px', backgroundColor: 'transparent' },
  '.cm-content': { fontFamily: "'Consolas', 'Monaco', monospace" },
  '.cm-gutters': { backgroundColor: 'transparent', border: 'none', color: '#666' },
  '&.cm-focused': { outline: 'none' },
}),
```

`backgroundColor: 'transparent'` 让编辑器融入 cell 背景，`outline: 'none'` 去掉聚焦轮廓保持简洁。生产版可加 `@codemirror/theme-one-dark` 获得更完整的语法高亮配色，教学版内联够用。

## 连接状态指示器

`App.tsx` 顶部一个指示器，让用户随时知道是否连着后端：

```tsx
<header className="app-header">
  <h1>marimo-from-scratch</h1>
  <span className={`connection ${connected ? 'connected' : 'disconnected'}`}>
    {connected ? '● connected' : '○ disconnected'}
  </span>
  <div className="header-actions">
    <button className="btn-primary" onClick={handleRunAll}>Run All</button>
    <button className="btn-primary" onClick={handleAdd}>+ Add Cell</button>
  </div>
</header>
```

```css
.connection { font-size: 13px; color: var(--text-dim); }
.connection.connected { color: var(--green); }
.connection.disconnected { color: var(--red); }
```

连接时绿色 `● connected`，断开时红色 `○ disconnected`。教学版没加闪烁动画，生产版可给 disconnected 加 `animation: pulse 1s infinite` 闪烁吸引注意。这个指示器虽小，却是用户信任系统的基础——不然点 Run 没反应时不知道是自己操作错还是连接断了。`connected` 状态来自 `useNotebook` 的 `ws.onopen` / `ws.onclose`，WebSocket 自动维护，无需前端轮询。

## Run All 与 Add Cell

`Run All` 发 `run_all` 消息，后端按拓扑序执行所有 cell，逐个推 `cell_result`，前端逐个更新——用户看到 cell 们从上到下依次变 running 再变 done，进度可视化。若某 cell 报错，后端策略决定是否继续下游（下游依赖报错 cell 的无法跑，独立的可继续），前端按收到的 cell_result 更新对应 cell。

`Add Cell` 发 `add_cell`，后端创建空 cell 并回 `graph_changed` 或 `state`，前端多渲染一个空 CellView。教学版没自动聚焦新 cell，生产版可加 `useEffect` 在 cells 长度增加时聚焦最后一个 cell 的编辑器，立即可输入。

## UI 事件流

marimo 区别于普通 notebook 的核心交互是 UI 组件事件流。以滑块为例完整链路：

1. 用户拖滑块 → `UIComponentView` 的 `onChange` 触发；
2. `onEvent(component.id, Number(e.target.value))` 上抛 → CellView 的 `onUIEvent` → App 的 `handleUIEvent`；
3. `send({ type: 'ui_event', component_id, value })` 发消息给后端；
4. 后端收到 `ui_event`，找到 component_id 对应的 Python UI 组件，更新其 value，触发注册的 on_change 回调；
5. 回调里可能改了其他变量，后端重算依赖该变量的 cell；
6. 后端逐个推 `cell_result` 给受影响 cell；
7. 前端 `onmessage` 更新 cells，相关 CellView 重渲染，新输出显示。

这条链让滑块拖动能驱动整个 notebook 重算，是 reactive UI 的闭环。关键点：前端只发事件不预测结果，所有重算在后端，前端等消息回写。这保证了 UI 状态和后端计算状态一致——滑块显示的值永远是后端确认的值，不会出现"前端显示 5 但后端按 3 算了"的分歧。

高频拖动时（mousemove 每帧一次），可能连发多条 ui_event。后端可节流：只处理最后一条，或队列合并。教学版不节流，每次都重算，简单但可能卡。生产版加 `useTransition` 把重算结果回写标为低优先级，让滑块拖动手感顺滑。

## 容错：异常不阻塞

一个 cell 报错不应让整个 notebook 卡死。后端执行 cell 抛异常时回 `cell_result` 带 `exception` 和 `exception_type`，前端那个 cell 显示红色 traceback，其他 cell 照常运行：

```tsx
{cell.exception && (
  <pre className="output-error">{cell.exception_type}: {cell.exception}</pre>
)}
```

同时 cell 根 div 加 `cell-error` 类，边框变红，远看就能定位。Run All 遇到错误 cell 跳过下游继续（或停下，教学版可选策略），但 UI 始终响应——用户能改代码重跑。连接断开时，`connected` 变 false，指示器变红，用户知道操作发不出去，不会困惑"怎么点了没反应"。

## 交互设计原则

总原则：**让用户始终知道发生了什么、自己能做什么**。状态指示器说"系统能用"，状态图标说"cell 在干嘛"，defs/refs 标签说"cell 依赖谁产出谁"，Shift-Enter 让"跑一轮"变成一次按键，暗色主题让"长时间用"不痛苦，异常红色边框让"出错了"一眼可见。这些细节单独看都小，合起来决定 notebook 好不好用。交互设计的本质不是堆功能，是让每个状态变化都对用户可见、每个用户意图都有即时反馈。
