# output 与 stdout 提取

cell 执行完，用户想看到的不只是"成功/失败"的状态，还有代码产出的值和打印的文本。传统 notebook 里这两者混在一起：最后一个表达式的值和 `print` 的输出都显示在 cell 下方，用户靠视觉习惯区分"这段是 print 的、那段是返回值"。marimo 的执行引擎需要把两者都捕获并区分开，分别作为 `output` 和 `stdout` 返回，让前端用不同方式渲染。这一章对照 `_execute_cell` 的源码讲清楚提取逻辑，包括 AST 分析、`io.StringIO` 缓冲机制、异常时的状态清理，以及值与文本分离的设计意义。

## output：最后一条 Expr 的值

Python 的 `exec` 默认不返回值，`x = 1` 执行后只是给命名空间赋值，没有"返回值"概念。这是 Python 和交互式语言（如 REPL、Jupyter）的一个差异：REPL 会显示每条语句的值，`exec` 只执行不返回。但 notebook 里 `x + 1` 这种裸表达式，用户期望看到它的值——如果不显示，用户得额外写 `print(x + 1)`，体验退化。marimo 的做法是：编译 cell 代码后，检查 AST 的最后一条语句；若它是 `ast.Expr`（即裸表达式），就把前面的语句和最后一条分开——前面的用 `exec` 执行副作用，最后一条用 `eval` 取值：

```python
tree = ast.parse(cell.code)
if tree.body and isinstance(tree.body[-1], ast.Expr):
    rest = ast.Module(
        body=tree.body[:-1], type_ignores=tree.type_ignores
    )
    last = ast.Expression(body=tree.body[-1].value)
    exec(
        compile(rest, f"<cell:{cell.cell_id}>", "exec"),
        self._global_ns,
    )
    cell.output = eval(
        compile(last, f"<cell:{cell.cell_id}>", "eval"),
        self._global_ns,
    )
else:
    exec(
        compile(tree, f"<cell:{cell.cell_id}>", "exec"),
        self._global_ns,
    )
```

注意这里不是"先 exec 整段再 eval 最后一条"，而是严格分开：`rest` 是去掉最后一条的 `Module`，`last` 是只含最后一条表达式的 `Expression`。这样最后一条表达式只执行一次（通过 `eval`），不会重复执行。这对有副作用的表达式很重要——比如最后一条是 `append_to_list(x)`，若先 `exec` 整段（包含这条）再 `eval` 最后一条（又执行这条），函数会被调两次，列表里会多一个元素；分开执行则只调一次，副作用正确。`ast.Module` 和 `ast.Expression` 的构造是必要的，因为 `compile` 要求特定的 AST 节点类型：`exec` 模式要 `Module`，`eval` 模式要 `Expression`。

举几个例子说明语义：

- `x = 1`：最后一条是 `Assign` 不是 `Expr`，走 else 分支，`output` 保持初始值 `None`。赋值语句没有"值"。
- `x + 1`（假设 `x=1`）：最后一条是 `Expr`，`rest` 为空 Module，`last` 是 `x + 1`。`exec` 空 Module 无副作用，`eval` 算出 2，`output = 2`。
- `print("hi"); 42`：最后一条是 `Expr`（值为 42），`rest` 是 `print("hi")`。`exec` 打印 hi，`eval` 算出 42，`output = 42`，`stdout = "hi\n"`。
- `def f(): pass`：最后一条是 `FunctionDef` 不是 `Expr`，走 else，`output = None`。函数定义没有"值"。
- `x = 1; x + 1`：最后一条是 `Expr`（值为 `x + 1`），`rest` 是 `x = 1`。`exec` 赋值，`eval` 算出 2，`output = 2`。

这个语义和 Jupyter 一致：只有最后一个裸表达式的值被显示，赋值、函数定义等语句的"值"是 None。`ast.Expr` 的判断是关键——它特指"作为语句出现的表达式"，即裸表达式；`x = 1` 里的 `1` 虽然是表达式，但整个语句是 `Assign`，不是 `Expr`，所以不触发 output 提取。这个区分是 Python AST 的标准语义，marimo 只是遵循它，没有自定义规则。

## stdout：redirect_stdout 捕获 print

`print` 写到 `sys.stdout`，默认是终端。要捕获它，用 `contextlib.redirect_stdout` 把 `sys.stdout` 临时换成一个 `StringIO`：

```python
buf = io.StringIO()
with contextlib.redirect_stdout(buf):
    # exec 和 eval 都在这个上下文里
    ...
cell.stdout = buf.getvalue()
```

`io.StringIO` 是一个内存里的文本缓冲区，实现了 `write` 接口，所以能伪装成 `sys.stdout`。`print("hello")` 内部调 `sys.stdout.write("hello\n")`，在 `redirect_stdout` 上下文里 `sys.stdout` 是 `buf`，所以 `"hello\n"` 写进了 `buf` 而非终端。执行期间所有 `print` 都写进 `buf`，执行完 `getvalue()` 取出全部文本。`with` 块退出后 `sys.stdout` 自动恢复（`redirect_stdout` 的 `__exit__` 把原 `sys.stdout` 装回去），不影响后续 cell 或前端通信。这种"上下文管理器临时替换全局、退出自动恢复"的模式，是 Python 捕获标准输出的标准做法，无需 patch `print` 函数或手动保存恢复 `sys.stdout`，代码简洁且异常安全——即使 `exec` 抛异常，`with` 的 `__exit__` 也会执行，`sys.stdout` 不会卡在被替换的状态。

关键是要在同一次执行里同时捕获 stdout 和算 output：`exec`（前面语句）和 `eval`（最后一条）都在 `redirect_stdout` 上下文里执行。这样最后一条表达式若触发 `print`（比如 `eval` 的是 `print_and_return(x)`，函数内部 `print` 了东西），那个 `print` 也会被捕获进 `buf`。完整结构：

```python
buf = io.StringIO()
with contextlib.redirect_stdout(buf):
    if tree.body and isinstance(tree.body[-1], ast.Expr):
        exec(compile(rest, ...), self._global_ns)
        cell.output = eval(compile(last, ...), self._global_ns)
    else:
        exec(compile(tree, ...), self._global_ns)
cell.stdout = buf.getvalue()
```

`buf.getvalue()` 在 `with` 块外调用——此时 `sys.stdout` 已恢复，但 `buf` 这个 StringIO 对象本身还在，里面存着执行期间写入的全部文本，随时可取。为什么在 `with` 外取？因为 `getvalue()` 只是读缓冲区，不依赖 `sys.stdout` 的状态，放外面更清晰：`with` 块只负责"执行期间重定向"，取值是执行后的独立步骤。

## 初始化与异常清理

`_execute_cell` 开头先把运行时状态重置：

```python
cell.status = CellStatus.RUNNING
cell.exception = None
cell.stdout = ""
cell.output = None
```

这确保即使执行失败，`stdout` 和 `output` 也是干净的空值而非上次的残留。若执行抛异常，except 分支不再设置 `stdout`/`output`——它们保持这里的初始值 `""` 和 `None`。这个重置看似简单，实则重要：如果不重置，上次执行成功的 `output=42` 会残留，这次执行失败后前端可能误显示旧的 42，用户以为成功了。重置保证"执行中"和"执行失败"状态下 `output` 都是 None，只有"执行成功"才设真实值。

注意一个细节：若异常发生在 `exec`/`eval` 过程中，`buf` 里可能已经有部分 `print` 输出（异常前打印的），但 `cell.stdout = buf.getvalue()` 这行在 try 块里，异常时不会执行，所以部分输出会丢失。教学版接受这个简化；生产版可能想在 except 里也 `cell.stdout = buf.getvalue()` 保留部分输出，方便用户看到"出错前打印了什么"用于调试——比如 cell 里 `print("开始处理"); result = process(data); print("完成")`，若 `process` 抛异常，"开始处理"已打印但"完成"没有，保留部分 stdout 能让用户知道执行到了哪一步。教学版省略这个细节是为了让 `_execute_cell` 的结构更清晰，突出主流程。

## 两者的区分与展示

`output` 是结构化的值，前端可以用富文本渲染（表格、图表、HTML）；`stdout` 是纯文本，按原样显示在 monospace 块里。区分开能让 DataFrame 显示成表格而非 `__repr__` 字符串，让 matplotlib 图显示成图片而非文本。执行引擎把 `(output, stdout, status, error)` 一起返回，前端按类型分发渲染器。

具体来说，cell 执行完后，`cell.output` 是任意 Python 对象（可能是 int、str、DataFrame、Figure 等），`cell.stdout` 是字符串。前端拿到后：

- `output` 走富文本渲染：若类型是 DataFrame，渲染成 HTML 表格；是 matplotlib Figure，转成 base64 图片；是 dict/list，JSON 美观化；是普通对象，走 `repr` 显示字符串表示。
- `stdout` 走纯文本渲染：`<pre>` 标签里原样显示，保留换行和空格，用等宽字体。

这种"值和文本分离"的设计，是 marimo 输出体验比传统终端式 notebook 更好的底层原因。传统 notebook 里 `print(df)` 和裸 `df` 都显示在同一个输出区，前者是文本后者是富文本，混在一起难以区分，且 `print(df)` 输出的是 `__repr__` 字符串（通常截断的），信息量不如富文本表格；marimo 里 `print(df)` 进 `stdout`（文本区，显示截断的 repr），裸 `df` 进 `output`（富文本区，显示完整交互表格），各走各的渲染路径，视觉上清晰分离，信息量最大化。

同时，执行引擎不需要关心前端怎么渲染——它只负责把 `output` 和 `stdout` 算出来塞进 cell 对象，渲染是前端的事。这种关注点分离让执行引擎保持纯粹：只懂 Python 执行，不懂 HTML/图片，便于测试和复用。前端可以独立升级渲染器（比如新增一个 3D 图表渲染器），不需要动执行引擎；执行引擎也可以独立优化（比如缓存 output 避免重复计算），不影响前端。这种解耦是 marimo 架构的一个优点，而 output/stdout 分离是这个解耦在执行引擎层面的具体体现。


## 与 Jupyter display 协议的对比

Jupyter 用一套更复杂的 display 协议处理输出：对象可以实现 `_repr_html_`、`_repr_png_`、`_repr_json_` 等方法，前端按优先级调用，选第一个能用的渲染。这套协议强大但复杂——库作者要给每个类型实现多个 `_repr_` 方法，前端要维护一个优先级表，还要处理 MIME 类型协商。marimo 教学版不走这条路，而是把"值的类型"作为渲染分发的唯一依据：前端拿到 `output` 后，`isinstance(output, DataFrame)` 就渲染表格，`isinstance(output, Figure)` 就渲染图片。这种按类型分发的做法比 Jupyter 的 `_repr_` 协议简单得多，代价是扩展性弱——新类型要改前端代码，而非库自己实现 `_repr_` 方法。教学版接受这个取舍，因为教学目标是讲清"执行引擎怎么提取 output"，而非"前端怎么渲染各种类型"。

但有一个核心点是共享的：output 必须是结构化的值，而非字符串化的文本。这是 reactive notebook 区别于终端式工具的根本。在终端里，一切输出都是文本，`print(df)` 和裸 `df` 都打印成字符串；在 notebook 里，output 是 Python 对象，前端可以自由选择渲染方式。marimo 的执行引擎通过"eval 最后一条表达式取值"把对象保留下来，而非 `str()` 它，这是富文本渲染的前提。如果执行引擎返回的是 `str(output)`，前端拿到的就是字符串，再也无法区分它是 DataFrame 还是普通字符串，富文本就无从谈起。所以 output 提取的设计——保留对象而非字符串化——是整个富文本输出体系的基石。

## stdout 的边界情况

stdout 捕获有几个值得注意的边界情况。第一，`print` 以外的写入：`sys.stdout.write(...)` 直接调也会被捕获，因为 `redirect_stdout` 替换的是 `sys.stdout` 对象本身，任何通过它写入的都进 `buf`。第二，嵌套 `print`：cell 里调了一个函数，函数内部又 `print`，同样被捕获——因为 `sys.stdout` 在整个 `with` 块里都是 `buf`，不分调用层级。第三，C 扩展的输出：某些 C 扩展直接写文件描述符而非 `sys.stdout`，这种输出绕过 Python 层，`redirect_stdout` 捕获不到。比如 NumPy 的某些警告直接写 stderr，C 库的 `printf` 直接写 fd 1，这些都不会进 `buf`。教学版不处理这个，生产版可能要重定向文件描述符，复杂度高得多。

第四，多 cell 并发的情况：如果未来改成并行执行（见第 21 章），多个 cell 同时 `print` 会写进各自的 `buf` 还是混进一个？当前串行下每个 cell 有独立 `buf`（在 `_execute_cell` 里新建），互不干扰；并行下若共享 `sys.stdout`，多个 `redirect_stdout` 嵌套会出问题。这也是并行执行复杂度陡增的一个具体例子——连捕获 stdout 这种串行下理所当然的事，并行下都要重新设计。


## output 提取的 AST 细节

`ast.Expr` 的判断有几个容易混淆的细节。Python AST 里，`Expr` 节点表示"作为语句出现的表达式"——它包裹一个表达式节点（如 `BinOp`、`Call`、`Name`），表示这个表达式被当作语句执行。裸表达式 `x + 1` 解析成 `Expr(body=BinOp(...))`；赋值 `x = 1` 解析成 `Assign(...)`，不是 `Expr`；函数定义 `def f(): pass` 解析成 `FunctionDef(...)`，也不是 `Expr`。所以 `isinstance(tree.body[-1], ast.Expr)` 精确地选中"最后一条是裸表达式"的情况，不会误判赋值或定义。

另一个细节是 `ast.Expression` 和 `ast.Expr` 的区别——名字相似但角色不同。`ast.Expr` 是语句级节点（在 `Module.body` 里），`ast.Expression` 是表达式级节点（`compile` 的 `eval` 模式要求的顶层节点）。代码里 `last = ast.Expression(body=tree.body[-1].value)` 把 `Expr` 的内部表达式（`tree.body[-1].value`，如 `BinOp`）包进 `Expression`，才能用 `compile(last, ..., "eval")` 编译成可 `eval` 的代码对象。这个"从 `Expr` 提取 `.value` 包进 `Expression`"的转换是标准做法，但容易写错——直接 `compile(tree.body[-1], ..., "eval")` 会报类型错误，因为 `Expr` 不是 `eval` 模式的合法顶层节点。

还有 `type_ignores` 的处理：`rest = ast.Module(body=tree.body[:-1], type_ignores=tree.type_ignores)`。`type_ignores` 是 `# type: ignore` 注释的信息，`Module` 要求这个字段存在。从原 `tree` 拷贝过来保证类型注释语义不变。这种细节在日常代码里很少注意，但 AST 操作里漏了会报 `TypeError: missing required field`，是 AST 编程的常见陷阱。

## 执行状态的完整快照

`_execute_cell` 执行完后，cell 对象的完整状态是：`status`（DONE/ERROR）、`output`（最后表达式的值或 None）、`stdout`（print 捕获的文本）、`exception`（异常对象或 None）、`namespace`（产出的变量映射）、`defs`/`refs`（静态信息，不变）。这六个字段合起来是 cell 的完整运行时快照，前端据此渲染、执行引擎据此做增量决策。`reset_runtime_state` 方法把它们重置到初始值：

```python
def reset_runtime_state(self) -> None:
    self.status = CellStatus.IDLE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}
```

注意 `defs` 和 `refs` 不在重置范围内——它们是 AST 分析的静态结果，不随执行变化。这个区分很重要：`defs`/`refs` 是"代码的属性"，`status`/`output`/`stdout`/`exception`/`namespace` 是"执行的属性"。改代码会改 `defs`/`refs`（通过重新 AST 分析），执行会改运行时属性。两者解耦，让"分析代码"和"执行代码"能独立进行——图构建只看 `defs`/`refs`，执行引擎只读写运行时属性，互不干扰。这种静态/动态分离是 marimo 执行引擎设计的一个原则，让每个模块的职责清晰：`cell.py` 定义数据结构，`graph.py` 基于静态信息建图，`executor.py` 基于图执行并更新动态状态。


## 为什么不直接用 eval 执行整段

有人可能问：既然要取最后一条表达式的值，为什么不直接 `eval(cell.code, _global_ns)` 整段？因为 `eval` 只接受单个表达式，不接受 `x = 1; y = x + 1` 这种含语句的代码。`eval("x = 1")` 会抛 `SyntaxError: invalid syntax`。所以必须用 `exec` 执行语句部分，`eval` 只用于最后一条裸表达式。这是 Python `exec`/`eval` 的固有限制，marimo 的"分开 exec + eval"是对这个限制的标准应对。

另一种方案是"exec 整段后，从 `_global_ns` 里找最后赋值的变量作为 output"。但这不对——最后赋值的变量不一定是用户想看的。比如 `x = 1; y = 2`，最后赋值的是 `y`，但用户可能想看的是 `x`（如果 `x` 是最后一条裸表达式的话，但这里 `x = 1` 是赋值不是裸表达式）。而且"从 `_global_ns` 找最后赋值的变量"需要跟踪执行期间的赋值顺序，`exec` 不提供这个信息——它只往字典写键值对，不记录写入顺序。所以"exec 整段再找最后赋值"既不正确也不可行，"AST 分析 + 分开 exec/eval"是唯一可靠的方案。

这也解释了为什么 Jupyter、IPython 都用类似机制：Python 的交互式显示语义（显示最后一条裸表达式的值）只能靠 AST 分析实现，没有更简单的路径。marimo 沿有发明新方法，只是把这个标准机制放进 reactive 执行引擎里，和命名空间、拓扑序、短路等机制协同。理解了这一点，output 提取就不再神秘——它是 Python 交互式显示语义的标准实现，marimo 只是把它和 cell 执行模型结合。


## stdout 与 output 的执行顺序

在 `_execute_cell` 的实现里，stdout 捕获和 output 计算的顺序是"先 exec 前面语句（可能 print），再 eval 最后表达式（可能也 print），最后取 stdout"。这意味着 stdout 包含执行期间所有 print 的累积输出，不分"前面语句的 print"和"最后表达式的 print"。比如 `print("a"); print("b")` 的 stdout 是 `"a\nb\n"`，output 是 None（最后一条是 `print("b")` 返回 None，但 `print` 调用是 `Expr`，其值是 None）。再比如 `print("a"); 42` 的 stdout 是 `"a\n"`，output 是 42。

注意 `print("b")` 作为最后一条表达式时，`eval` 它得到 `None`（`print` 函数返回 None），所以 output 是 None 而非"b"。这可能反直觉——用户可能期望 output 是"b"，但 Python 语义里 `print` 的返回值是 None，它只是副作用（往 stdout 写），没有返回值。marimo 遵循 Python 语义，output 是 None，"b" 在 stdout 里。这种"print 的内容进 stdout，print 的返回值（None）进 output"的区分，正是 stdout/output 分离的价值——用户看到 stdout 里有 "b"，output 是 None，清楚知道"这是 print 的输出而非返回值"。

如果最后一条是 `x = print("b")`，这是赋值语句不是裸表达式，走 else 分支，output 是 None，stdout 是 `"b\n"`，`x` 被赋值为 None（print 的返回值）。这进一步说明 output 提取的精确性——只有裸表达式的值才进 output，赋值、print 调用等语句的"值"不进。这种精确语义让 output 始终是"用户想看到的那个值"，而非"最后执行的东西的返回值"，符合 notebook 的显示直觉。


## 富文本渲染的类型分发

前端拿到 `cell.output` 后，按类型分发渲染器。教学版的分发逻辑是简单的 `isinstance` 链：若是 `DataFrame` 渲染成 HTML 表格，若是 `matplotlib.figure.Figure` 转成 base64 图片，若是 `dict`/`list` 用 JSON 美观化，若是 `str` 直接显示，其他走 `repr`。这种"按类型分发"比"统一 `str()` 后显示文本"信息量大——DataFrame 表格可排序、可滚动，比截断的 repr 字符串有用得多；图片直接显示，比 matplotlib 的文本表示 `<Figure size 640x480>` 有用得多。

但类型分发有个局限：它只认"已知类型"，新类型要么走默认 `repr`（信息量少），要么改前端代码加新分支。Jupyter 的 `_repr_` 协议解决了这个——库自己实现 `_repr_html_` 等方法，前端自动调用，不需要改前端。marimo 教学版不用 `_repr_` 协议是为了简单，代价是扩展性弱。生产版 marimo 会实现类似 `_repr_` 的协议，让第三方库能自定义渲染，但教学版聚焦"执行引擎怎么提取 output"，渲染协议属于前端范畴，点到为止。

值得强调的是，无论渲染协议复杂还是简单，都依赖执行引擎把 `output` 作为结构化对象保留下来。如果执行引擎返回 `str(output)`，再先进的渲染协议也无用武之地——拿到的已经是字符串，无法还原成 DataFrame 或 Figure。所以 `_execute_cell` 里 `cell.output = eval(...)` 保留对象而非字符串化，是整个富文本输出体系的根基，比前端的渲染协议更根本。这一点容易被忽视——人们关注前端的酷炫渲染，却忘了执行引擎"保留对象"这个看似简单的决定才是让一切成为可能的前提。
