# 并行执行的可能性

到目前为止，执行引擎都是串行的：按拓扑序一个接一个跑。但看一眼 DAG 就会发现，很多 cell 之间根本没有依赖关系——它们既不是对方的祖先也不是后代，理论上可以同时执行。这一章探讨把 marimo 改成并行执行的可能性、收益和限制，并说明教学版为何选择串行。注意当前 `executor.py` 的执行循环是纯串行的 `for cid in order`，本章讨论的是"如果改成并行会怎样"，属于设计层面的前瞻分析，不涉及当前实现的修改。

## 无依赖的 cell 可并行

DAG 的拓扑序不是唯一的，同一"层"里入度同时降为 0 的 cell 互不依赖，可以并发执行。比如：

```
cell A:  x = 1
cell B:  y = 2
cell C:  z = x + y
```

A 和 B 互不依赖，可以同时跑；C 依赖两者，必须等 A、B 都完成。并行执行模型是：维护一个就绪队列，多个 worker 从队列取 cell 执行，执行完通知后继检查入度，入度归零的就入队。这是经典的 DAG 并行调度，理想情况下能把执行时间从"cell 总数"降到"最长依赖链长度"（即 DAG 的深度），对宽而浅的 notebook 收益显著。

用具体数字说明。假设有 100 个 cell，排成 10 层每层 10 个，层间全连接（每层每个 cell 依赖上一层所有 cell）。串行执行要跑 100 个 cell 的时间；并行执行每层 10 个同时跑，只需 10 层的时间，理论上 10 倍加速。更现实的例子：数据预处理 pipeline 里"加载 10 个文件"的 10 个 cell 互不依赖，并行能把加载时间从"10 倍单文件"压到"单文件"（受 IO 带宽限制可能达不到，但 CPU 端的解析确实能并行）。再比如机器学习里"用 4 个不同超参数训练模型"的 4 个 cell 互不依赖，并行能把调参时间从 4 倍压到 1 倍，这对迭代效率的提升是巨大的。

并行调度的伪代码（与当前串行 `for cid in order` 对比）：

```python
# 串行（当前实现）
for cid in order:
    execute(cid)

# 并行（假想）
ready = deque(cid for cid in cells if in_degree[cid] == 0)
while ready:
    batch = list(ready)          # 当前就绪的一批
    ready.clear()
    results = parallel_map(execute, batch)  # 并发执行
    for cid, succs in results:
        for s in succs:
            in_degree[s] -= 1
            if in_degree[s] == 0:
                ready.append(s)
```

关键差异是把"逐个执行"改成"按就绪层批量执行"。串行版每次取一个 cell 执行，并行版每次取所有入度归零的 cell 一起执行，等这批全部完成再更新后继入度，产生下一批就绪 cell。这要求 `execute` 是线程安全的或可隔离的，引出下面的 GIL 问题。注意并行版不再是"按拓扑序逐个"，而是"按就绪层批量"，拓扑序的确定性被打破——同一层里 cell 的执行顺序由调度器决定，可能每次不同。

## Python GIL 限制

Python 的全局解释器锁（GIL）让多线程无法真正并行执行 Python 字节码——同一时刻只有一个线程在跑 Python 代码。GIL 是 CPython 实现的历史包袱，目的是简化引用计数式的内存管理，但代价是多线程在 CPU 密集场景下无法利用多核。对 CPU 密集的 cell（比如纯 Python 写的循环计算），多线程并行几乎拿不到加速，甚至因锁竞争变慢。要真并行有三条路：

1. **多进程**：每个 worker 一个进程，变量靠序列化传递。问题是 `_global_ns` 的共享代价大，cell 间大数据传递要 pickle，开销可能抵消并行收益。比如上游 cell 算出一个 1GB 的 DataFrame，下游四个 cell 都要用，多进程下要 pickle 四次传给四个 worker，内存翻倍且序列化耗时巨大。多进程还破坏了 `_global_ns` 作为单一命名空间的简洁性——每个 worker 有独立命名空间，合并时需处理变量归属、类型一致性、执行顺序等问题。好处是真正绕过 GIL，CPU 密集 cell 能跑满多核。
2. **C 扩展释放 GIL**：若 cell 主体是 NumPy、Torch 等 C 扩展计算，它们执行时会释放 GIL，多线程能真并行。这是科学计算 notebook 并行的现实路径。比如 `cell_a: x = np.linalg.inv(big_matrix)` 和 `cell_b: y = np.fft.fft(big_signal)` 互不依赖，多线程下两个 NumPy 调用各自释放 GIL，真正并行跑在多核上。但纯 Python 的 cell（循环、字典操作）仍受 GIL 限制，混用时加速不均匀——NumPy cell 加速了，纯 Python cell 没加速，整体加速比取决于两者比例。
3. **异步 IO**：对 IO 密集 cell（网络请求、文件读写），用 `asyncio` 并发等待，单线程即可并发，无需多进程。比如 `cell_a: data = await fetch(url_a)` 和 `cell_b: data2 = await fetch(url_b)` 两个网络请求，`asyncio.gather` 能让它们并发等待，总耗时约等于较慢的那个而非两者之和。这要求 cell 代码是 `async` 的，与当前 `exec` 同步执行模型不兼容，需要把 `_execute_cell` 改成协程，`exec` 换成 `async` 执行，改动较大。

三种方案各有适用场景，没有银弹。实际 notebook 往往三种 cell 混合：数据加载（IO）、数值计算（C 扩展）、控制逻辑（纯 Python），理想的并行执行器要按 cell 类型分发到不同后端，复杂度远超当前教学版。这也是为什么主流 notebook（Jupyter、Colab）都默认串行，并行作为可选功能（如 Colab 的 `%parallel` 魔法命令）留给有经验的用户。

## 教学版串行

教学版 marimo 选择串行，原因有三。第一，**确定性**：串行 + `sorted` 拓扑序让每次执行结果完全可复现，并行引入调度随机性，调试更难。比如两个 cell 都 `print` 到同一个 stdout buffer，并行下输出交错顺序不确定，测试无法断言；串行下按固定拓扑序输出，可精确比对。当前 `_execute_cell` 用 `contextlib.redirect_stdout` 捕获 stdout，依赖执行顺序确定——并行下多个 cell 同时写 buffer 会乱序，`buf.getvalue()` 拿到的是交错文本，前端显示混乱。再比如两个 cell 都往同一个列表 append，并行下 append 的顺序不确定，列表内容每次不同，测试和复现都成问题。

第二，**命名空间简单**：串行下 `_global_ns` 是单线程读写，无需锁。看 `_execute_cell` 里这段：

```python
exec(
    compile(rest, f"<cell:{cell.cell_id}>", "exec"),
    self._global_ns,
)
```

`exec` 直接读写 `_global_ns`，没有任何同步原语。并行下要么加锁（每个 cell 执行时锁住整个命名空间，退化成串行，白加锁），要么每个 worker 维护独立命名空间再合并（合并时处理变量归属、冲突、一致性，复杂度陡增）。`_cell_defs_cache` 也面临同样问题——多个 worker 同时更新缓存需要锁，或事后合并各 worker 的局部缓存。命名空间是 marimo 执行模型的核心，一旦它变复杂，整个实现的可读性就崩了，违背教学项目的初衷。

第三，**教学目标**：这一系列文档旨在讲清"依赖图 + 拓扑序 + 命名空间"的核心机制，并行是工程优化，不属于核心概念，留作进阶练习。串行实现把这三个概念讲透后，读者能理解 reactive notebook 的本质；并行引入的线程安全、调度、合并等问题会分散注意力，且没有教学上的新概念增量——它讲的是"如何让执行更快"，而非"reactive 执行是什么"。教学版的价值在于用最少代码讲清最多本质，串行恰好满足这个目标。

## 进阶方向

若要做成生产级并行，最小改动是：识别"纯计算、无副作用、C 扩展为主"的 cell，把它们标记为可并行；其余（写文件、改全局状态、有 `print`）仍串行。调度器按标记分发，纯计算 cell 丢给线程池，副作用 cell 在主线程串行跑。这样既拿到 NumPy 类计算的并行收益，又避免副作用 cell 间的竞态。识别可并行 cell 可以靠静态分析：若 cell 的 `defs` 和 `refs` 都是数值类型、且代码里没有 `open`/`print`/`import` 等副作用调用，就标记为可并行。这种"按 cell 特性分发"的混合策略，比"全部并行或全部串行"更实用，也是 Dagster、Airflow 等任务编排系统的做法。

更激进的做法是把每个 cell 编译成独立函数，参数显式传入，彻底告别共享命名空间。比如 `cell_c: z = x + y` 编译成 `def cell_c(x, y): return x + y`，调度器负责把上游 cell 的返回值作为参数传给下游。这已经接近 Dagster/Airflow 那种"任务图"架构——每个任务是纯函数，输入输出显式声明，调度器管理数据传递。好处是天然并行安全（无共享状态，每个函数有独立栈帧）、可分布式执行（函数和参数都能 pickle 传到远端 worker）、可缓存（相同输入的函数结果可复用）。代价是失去 `_global_ns` 的简洁性，每个 cell 的依赖必须显式声明为函数参数，用户写 cell 的心智负担增加——不能再"直接引用上游变量"，要显式声明"我需要 x 和 y"。

marimo 的设计取舍是优先保持"像写普通 Python 一样"的体验，所以选了共享命名空间 + 串行，把并行留作未来可选层。这个取舍是有道理的：notebook 的核心用户是数据科学家和研究员，他们关心的是"代码对不对、结果准不准"，而非"执行快不快"；当 notebook 大到需要并行时，通常已经该迁移到专门的 task pipeline（Dagster、Prefect）了，notebook 不适合承载生产级并行调度。教学版把这个取舍讲清楚，读者能理解"为什么 marimo 不并行"不是技术不足而是设计选择，这对理解 reactive notebook 的定位很重要。


## 并行执行的正确性条件

要让并行执行结果和串行一致，需要满足几个条件。第一，**无依赖的 cell 间无共享可变状态**。两个互不依赖的 cell 如果都往同一个全局变量写，并行下写入顺序不确定，结果可能不同。marimo 的图构建禁止重复定义（同一变量只能一个 cell 定义），所以"都往同一变量写"在建图阶段就被拦住。但隐式的共享状态仍可能存在：两个 cell 都 `open("log.txt", "a").write(...)`，并行下日志顺序不确定。这种隐式副作用无法靠依赖图捕获，是并行执行正确性的固有风险。

第二，**cell 是其输入的纯函数**。这个条件在第 18 章讨论增量执行时也出现过——它同时是增量执行和并行执行的正确性基础。若 cell 有随机数、读文件、调 API 等外部依赖，相同输入可能产出不同输出，并行下多个 cell 同时执行这些副作用，结果更不可预测。严格来说，有副作用的 cell 应该串行执行，只有纯计算 cell 才并行。这呼应了前面"按 cell 特性分发"的混合策略。

第三，**output 和 stdout 的捕获要隔离**。串行下每个 cell 有独立 `buf`，并行下若多个 cell 同时 `print`，各自的 `redirect_stdout` 会互相覆盖（`sys.stdout` 是全局变量，后设的覆盖先设的）。解决方案是每个 worker 用独立的 `sys.stdout` 替换——但 `sys.stdout` 是进程级的，线程间共享，无法隔离。多进程下每个进程有独立 `sys.stdout`，可以隔离，但回到多进程的开销问题。这个具体困难说明了"并行执行连捕获 stdout 都要重新设计"，不是简单加个线程池就行。

## 主流项目的并行尝试

看几个真实项目的并行尝试，能校准对"notebook 并行"的期望。Jupyter 始终是串行的，它的内核模型是单进程单线程，并行靠用户自己写多线程/multiprocessing 代码，框架不参与调度。Colab 提供了 `%parallel` 魔法命令，但它是"在多个 cell 上并行执行同一段代码"（数据并行），而非"按依赖图并行调度不同 cell"（任务并行），语义不同。Dagster、Airflow、Prefect 这些任务编排系统支持并行调度，但它们把每个任务当纯函数，输入输出显式传递，没有共享命名空间——这避开了 GIL 和共享状态问题，但牺牲了 notebook 的"像写普通 Python"体验。

这些尝试说明一个事实：notebook 的并行执行至今没有好的通用方案。根本矛盾是"共享命名空间的简洁性"和"并行的无共享要求"冲突——共享命名空间让 notebook 好写好读，但让并行不安全；无共享让并行安全，但让 notebook 变成任务图，失去交互式体验。marimo 教学版选择站在"简洁性"这边，串行执行，把矛盾留给未来。这个选择不是技术不足，而是对 notebook 定位的判断：notebook 是探索性编程工具，交互体验比执行效率重要；需要并行时，用户应该迁移到专门的 pipeline 工具，而非在 notebook 里硬扛。理解这个判断，就理解了为什么教学版不并行——不是不会，而是不该，至少在 notebook 这个形态下不该。


## 教学版串行的隐性收益

除了前面说的确定性、命名空间简单、教学目标三个原因，串行还有一个隐性收益：**执行日志可读**。串行下 cell 按拓扑序逐个执行，日志是线性的——"执行 cell_a → 成功 → 执行 cell_b → 成功 → ..."，用户能一步步看到发生了什么。并行下多个 cell 同时执行，日志交错——"开始 cell_a → 开始 cell_b → cell_b 完成 → cell_a 完成"，时序混乱，出问题时难以定位"哪个 cell 先出错"。对教学场景，可读的执行日志很重要，学生能通过日志理解执行流程；并行日志的交错反而增加理解负担。

另一个隐性收益是**错误归因简单**。串行下一次执行最多一个 cell 出错（短路机制保证），错误归因明确——就是这个 cell 的问题。并行下多个 cell 可能同时出错，错误归因复杂——是它们各自独立出错，还是因竞态导致一个 cell 的错误引发另一个？串行排除了竞态可能，错误一定是 cell 自身代码或输入的问题，调试方向清晰。这对教学尤其重要——学生遇到错误时，串行让"哪里错了、为什么错"容易回答，不会因并行竞态把简单问题复杂化。

## 从串行到并行的演进路径

如果未来要把 marimo 改成并行，合理的演进路径是分三步，每步都可独立验证、不破坏现有功能。第一步，**IO 并发**：识别 `await` 开头的 cell，用 `asyncio` 并发执行，其他仍串行。这改动最小（只改 `_execute_cell` 支持 async），收益明确（网络请求并发），且不影响纯计算 cell 的确定性。第二步，**C 扩展并行**：识别"主体是 NumPy/Torch 调用"的 cell，丢进线程池，利用它们释放 GIL 的特性真并行。这需要把 `_global_ns` 在线程间加锁或用 copy-on-write，复杂度上升，但收益大（数值计算并行）。第三步，**多进程分布式**：把无依赖的纯计算 cell 分发到多进程或远端 worker，彻底绕过 GIL。这需要解决变量序列化、命名空间合并、错误传播等问题，接近 Dagster 的架构，改动最大。

每一步都建立在前一步的基础上，且可以回退（如果并行引入问题，禁用并行退回串行，执行仍正确）。这种渐进式演进比"一步到位全并行"风险低，也是工程实践里常见的策略——先拿低风险的收益（IO 并发），再逐步攻高难度的（多进程）。教学版停在"串行"这个起点，把这些演进步骤留作进阶练习，读者理解了串行的机制和并行的难点后，能自己评估每步的收益和代价，而非盲目追求"并行一定更快"。这种"理解后再优化"的思路，是教学版想传递的工程态度。


## 串行执行的哲学

串行执行不只是技术选择，也反映了一种工程哲学：**先正确，再快速**。marimo 的核心价值是 reactive 语义——改一个 cell 自动更新依赖它的一切，且结果和全量重跑一致。这个语义的正确性依赖"按拓扑序执行 + 命名空间共享 + 短路传播"，串行下这三者都简单直接。并行引入的竞态、锁、合并等问题会复杂化每个机制，增加出 bug 的可能，而 reactive 语义的正确性是 marimo 的立身之本，不能为性能冒险。

这种哲学也体现在"教学版"的定位上。教学版的目标是让读者理解 reactive notebook 的核心机制，而非生产可用。串行实现把核心机制讲透——依赖图怎么建、拓扑序怎么排、命名空间怎么管、短路怎么传播——读者理解后能自己评估"改成并行要改哪些、风险在哪"。如果教学版一上来就并行，读者要同时理解 reactive 语义和并发编程，认知负担过重，反而学不到核心。先串行讲透核心，再以进阶形式讨论并行，是教学路径的合理设计。

这个哲学对读者也有启发：面对"要不要优化"的决策时，先问"正确性是否已稳固"。如果核心语义还有 bug 或边界没处理，优化只是让错误更快发生。先把串行执行的正确性做到无懈可击（通过测试、边界分析、不变式证明），再考虑并行优化，是更稳妥的工程路径。教学版停在"串行且正确"，把这个路径走完，留给读者的是"已经正确，可以安全优化"的起点，而非"还没正确就优化，bug 和性能问题交织"的泥潭。
