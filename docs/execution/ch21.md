# 并行执行的可能性

到目前为止，执行引擎都是串行的：按拓扑序一个接一个跑。但看一眼 DAG 就会发现，很多 cell 之间根本没有依赖关系——它们既不是对方的祖先也不是后代，理论上可以同时执行。这一章探讨把 marimo 改成并行执行的可能性、收益和限制，并说明教学版为何选择串行。

## 无依赖的 cell 可并行

DAG 的拓扑序不是唯一的，同一"层"里入度同时降为 0 的 cell 互不依赖，可以并发执行。比如：

```
cell A:  x = 1
cell B:  y = 2
cell C:  z = x + y
```

A 和 B 互不依赖，可以同时跑；C 依赖两者，必须等 A、B 都完成。并行执行模型是：维护一个就绪队列，多个 worker 从队列取 cell 执行，执行完通知后继检查入度，入度归零的就入队。这是经典的 DAG 并行调度，理想情况下能把执行时间从"cell 总数"降到"最长依赖链长度"，对宽而浅的 notebook 收益显著。

## Python GIL 限制

Python 的全局解释器锁（GIL）让多线程无法真正并行执行 Python 字节码——同一时刻只有一个线程在跑 Python 代码。对 CPU 密集的 cell，多线程并行几乎拿不到加速，甚至因锁竞争变慢。要真并行有三条路：

1. **多进程**：每个 worker 一个进程，变量靠序列化传递。问题是 `_global_ns` 的共享代价大，cell 间大数据传递要 pickle，开销可能抵消并行收益。
2. **C 扩展释放 GIL**：若 cell 主体是 NumPy、Torch 等 C 扩展计算，它们执行时会释放 GIL，多线程能真并行。这是科学计算 notebook 并行的现实路径。
3. **异步 IO**：对 IO 密集 cell（网络请求、文件读写），用 `asyncio` 并发等待，单线程即可并发，无需多进程。

三种方案各有适用场景，没有银弹。

## 教学版串行

教学版 marimo 选择串行，原因有三。第一，**确定性**：串行 + `sorted` 拓扑序让每次执行结果完全可复现，并行引入调度随机性，调试更难。第二，**命名空间简单**：串行下 `_global_ns` 是单线程读写，无需锁；并行下要么加锁，要么每个 worker 维护独立命名空间再合并，复杂度陡增。第三，**教学目标**：这一系列文档旨在讲清"依赖图 + 拓扑序 + 命名空间"的核心机制，并行是工程优化，不属于核心概念，留作进阶练习。

## 进阶方向

若要做成生产级并行，最小改动是：识别"纯计算、无副作用、C 扩展为主"的 cell，把它们标记为可并行；其余（写文件、改全局状态）仍串行。调度器按标记分发，纯计算 cell 丢给线程池，副作用 cell 在主线程串行跑。这样既拿到 NumPy 类计算的并行收益，又避免副作用 cell 间的竞态。更激进的做法是把每个 cell 编译成独立函数，参数显式传入，彻底告别共享命名空间——这已经接近 Dagster/Airflow 那种"任务图"架构了。
