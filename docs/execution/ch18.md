# 增量执行：脏节点传播

全量执行每次都跑所有 cell，对大 notebook 既慢又没必要。用户改了一个 cell，真正受影响的只是它自己和它的后代；其他 cell 的输入没变，结果也不会变，重跑是浪费。想象一个有 200 个 cell 的数据分析 notebook：用户只是调整了最后画图的标题字号，如果为此把前面 199 个 cell（含加载几 GB 数据、训练模型）全部重跑一遍，体验会非常糟糕。`run_cell` 实现的就是这种增量执行，核心思想是"脏节点传播"：被改的 cell 标脏，脏沿着依赖边向下游传播，只重跑脏的 cell。这一章我们把 `run_cell` 的每一步拆开，并用一个完整例子展示脏节点如何传播，最后讨论增量执行正确性依赖的隐含假设。

## 只执行 cell + descendants

`run_cell(cell_id)` 的第一步是算出需要执行的集合，再按子图拓扑序排好：

```python
def run_cell(self, cell_id: str) -> list[str]:
    order = self._graph.execution_order_from(cell_id)
    for cid in order:
        self._cleanup_cell_vars(cid)

    executed: list[str] = []
    short_circuited = False
    for cid in order:
        cell = self._graph.get_cell(cid)
        if short_circuited or self._has_failed_upstream(cid):
            cell.mark_stale()
            continue
        self._execute_cell(cell)
        executed.append(cid)
        if cell.has_error:
            short_circuited = True
    return executed
```

`execution_order_from(cell_id)` 内部做的是 `descendants(cell_id) | {cell_id}` 再排子图拓扑序。`descendants` 用 BFS 沿下游边遍历，给出所有传递依赖的下游 cell：

```python
def descendants(self, cell_id: str) -> set[str]:
    return self._bfs(cell_id, self._downstream)

def _bfs(self, start: str, adj: dict[str, set[str]]) -> set[str]:
    visited: set[str] = set()
    queue: deque[str] = deque(adj.get(start, set()))
    while queue:
        node = queue.popleft()
        if node in visited:
            continue
        visited.add(node)
        queue.extend(adj.get(node, set()))
    return visited
```

BFS 从 `cell_id` 的直接下游出发，逐层向外扩展，把所有能沿下游边到达的 cell 都收进 `visited`。用 `deque` 做队列保证 $O(V+E)$ 的复杂度，`visited` 集合防止重复访问。注意 `order` 里包含 `cell_id` 本身，因为改动的源头也要重跑——它自己的代码变了，输出可能变。不在 `order` 里的 cell 一律不动，它们之前的结果留在 `_global_ns` 里，对重跑的 cell 仍然可见——这正是增量执行省时的关键：上游不必重跑，下游只重跑必要的部分。

为什么只重跑"自己加后代"就够了？因为 reactive notebook 的语义是：一个 cell 的输出完全由它的代码和它的输入（即上游 cell 的输出）决定。如果某个 cell 的代码没变、输入也没变，它的输出就不可能变，重跑只会得到相同结果。用户改了 `cell_b`，`cell_b` 的代码变了，它自己要重跑；它的输出可能变，所以引用它输出的后代也要重跑；后代的输出可能变，所以后代的后代也要重跑——这就是"脏沿下游传播"。而 `cell_b` 的上游代码没变、`cell_b` 也没改它们的输出，所以上游的输出不变，不需要重跑。这个推理链条就是增量执行正确性的直觉基础。

## 完整传播示例

假设 notebook 有六个 cell，依赖关系如下：

```
cell_a:  x = 1
cell_b:  y = x + 1      # 依赖 a
cell_c:  z = 2          # 独立
cell_d:  u = y + z      # 依赖 b, c
cell_e:  v = u * 2      # 依赖 d
cell_f:  w = 100        # 独立
```

全量执行后，`_global_ns` 里有 `x=1, y=2, z=2, u=4, v=8, w=100`。现在用户把 `cell_b` 改成 `y = x + 10`，触发 `run_cell('cell_b')`，我们逐步跟踪：

1. **算后代**：`descendants('cell_b')` 沿 `_downstream` 做 BFS。从 `cell_b` 出发，下游是 `{cell_d}`（d 引用 b 定义的 y）；从 `cell_d` 出发，下游是 `{cell_e}`（e 引用 d 定义的 u）；从 `cell_e` 出发，下游为空。BFS 结束，得到 `{cell_d, cell_e}`。
2. **算受影响集合**：`affected = {cell_b} | {cell_d, cell_e} = {cell_b, cell_d, cell_e}`。
3. **排子图拓扑序**：在子集 `{cell_b, cell_d, cell_e}` 上算入度。`cell_b` 的全局上游是 `{cell_a}`，但 `cell_a` 不在子集里，所以子图内入度 0；`cell_d` 的全局上游是 `{cell_b, cell_c}`，与子集的交集是 `{cell_b}`，入度 1；`cell_e` 的全局上游是 `{cell_d}`，入度 1。Kahn 排序得 `order = ['cell_b', 'cell_d', 'cell_e']`。
4. **清理旧变量**：对 `order` 里每个 cell 调 `_cleanup_cell_vars`，把 `cell_b` 上次的 `y`、`cell_d` 上次的 `u`、`cell_e` 上次的 `v` 从 `_global_ns` 删掉。此时 `_global_ns` 里还剩 `x=1, z=2, w=100`（a、c、f 的产出，不在本次重跑范围）。
5. **逐个执行**：`cell_b` 执行 `y = x + 10`，从 `_global_ns` 取到 `x=1`，算出 `y=11` 写回；`cell_d` 执行 `u = y + z`，取到新的 `y=11` 和旧的 `z=2`，算出 `u=13`；`cell_e` 执行 `v = u * 2`，取到 `u=13`，算出 `v=26`。

最终只跑了 3 个 cell，`cell_a`、`cell_c`、`cell_f` 完全没动，它们的输出和状态保持原样。`_global_ns` 更新为 `x=1, y=11, z=2, u=13, v=26, w=100`。这就是脏节点传播：脏从 `cell_b` 出发，沿依赖边传到 `cell_d`、`cell_e`，恰好覆盖所有可能受影响的 cell，不多不少。注意 `cell_c` 虽然是 `cell_d` 的上游，但它没被标脏——因为 `cell_d` 用的是 `cell_c` 的旧输出 `z=2`，而 `cell_c` 的代码和输入都没变，旧输出仍然正确，不需要重跑。

## _cleanup_cell_vars 清理旧变量

重跑一个 cell 之前，必须先把它上次定义的变量从命名空间里清掉，否则会出现"幽灵变量"问题。这个问题的危害比看上去严重。举例：cell A 原来定义 `x = 1`，用户改成 `y = 2`（不再定义 x）。若不清理，`x` 还留在 `_global_ns` 里。现在下游有个 cell C 引用 `x`，它执行时会从 `_global_ns` 取到 `x=1`——但这个 1 是 A 上次的产出，A 现在已经不产出 x 了。C 拿着一个"没有定义者"的幽灵变量，算出来的结果看似正常实则基于过期前提，这种 bug 极难发现，因为不会报错，只是结果错了。

`_cleanup_cell_vars` 用 `_cell_defs_cache` 记录每个 cell 上次定义的变量名，执行前把它们从 `_global_ns` 删掉：

```python
def _cleanup_cell_vars(self, cell_id: str) -> None:
    for var in self._cell_defs_cache.get(cell_id, set()):
        self._global_ns.pop(var, None)
```

`pop(var, None)` 的第二个参数 `None` 是默认值——若变量不在字典里不报错，安静返回。这处理了一种边界情况：cell 上次执行时定义了 `x`，但后来 `x` 被别的机制（如另一个 cell 的清理）删了，这时 `pop` 不会抛 `KeyError`。

`run_cell` 在正式执行前，先对 `order` 里的每个 cell 都调一次清理：

```python
order = self._graph.execution_order_from(cell_id)
for cid in order:
    self._cleanup_cell_vars(cid)
```

注意这一步在执行循环之前完成，先把所有待重跑 cell 的旧定义一次性清掉，再开始逐个执行。为什么要在执行前全部清完，而不是"执行一个清一个"？考虑两个待重跑 cell：`cell_b` 定义 `y`，`cell_d` 定义 `u` 且引用 `y`。若"执行一个清一个"，先清 `cell_b` 的 `y` 再执行 `cell_b`（写回新 `y`），再清 `cell_d` 的 `u` 再执行 `cell_d`——这没问题。但若 `cell_d` 还引用了 `cell_b` 上次定义的某个已不存在的变量，先执行 `cell_b` 可能又写了同名变量，时序就乱了。一次性清完所有旧定义，再按拓扑序逐个执行，保证执行时命名空间里只有"未重跑 cell 的产出"，没有"待重跑 cell 的旧产出"，时序清晰。

执行完再把新的 `defs` 写回缓存（在 `_execute_cell` 里：`self._cell_defs_cache[cell.cell_id] = set(cell.defs)`）。命名空间始终反映"当前已执行 cell 的真实产出"，不会残留旧定义。

## 未受影响的不重跑

增量执行的收益完全来自"不重跑"的部分。假设 notebook 有 1000 个 cell，用户只改了最末端的展示 cell（比如改个图表标题），`descendants` 为空（没有 cell 依赖展示 cell），`order` 只含这一个 cell，其余 999 个全部跳过。这次 `run_cell` 只执行 1 个 cell，省了 999 次。反过来，若改的是最顶端的 `x = ...`，且几乎所有 cell 都依赖 `x`，那 `descendants` 几乎是全图，增量退化为全量——这是合理的，因为确实所有下游都可能变。

增量执行的代价是维护图和缓存，收益是"按需重跑"，两者由 `descendants` 这个集合的大小联系起来：脏节点越少，省得越多。具体省了多少次执行，等于 `总 cell 数 - len(order)`。在上面的六 cell 例子里，省了 3 次；在 1000 cell 改末端的例子里，省了 999 次。最坏情况下 `len(order) == V`，不省也不亏，只多付出了算 `descendants`（BFS，$O(V+E)$）和子图排序（也是 $O(V+E)$）的开销，相对执行 cell 本身的代价（可能含数值计算、IO）通常微不足道。

实际场景里，用户编辑模式往往是"改一个参数看效果"，改的通常是中下游 cell，后代不多，增量收益显著。最坏的全量退化场景（改顶端变量）虽然不省执行，但也不多付出有意义代价，且用户改顶端变量时本就预期全量重跑，体验上可接受。

## 与全量执行的一致性

注意 `run_cell` 用的拓扑序是 `execution_order_from`，它和 `run_all` 用的 `topological_order` 共用同一套 Kahn 算法，只是把顶点集限制在子集上。因此增量执行在"该跑的范围内"和全量执行行为完全一致——执行循环的代码几乎逐字相同，都是"检查上游是否失败 → 执行 → 短路判断"。

用户改一个 cell 看到的结果，和点"全部重跑"看到的结果应当相同，这是增量执行正确性的判据。要保证这一点，关键在于：未被重跑的 cell 在 `_global_ns` 里留下的变量值，必须和"如果重跑它们会得到的值"一致。由于它们的输入（即自己的上游）没变，且 Python `exec` 对相同代码和相同命名空间是确定性的（忽略随机数、IO 等外部副作用），这个条件成立。换句话说，增量执行的正确性依赖一个隐含假设：cell 是其输入的纯函数——相同输入永远产出相同输出。一旦 cell 有外部副作用（读文件、调 API、用随机数、读系统时间），这个假设就可能破坏。比如 `cell_a: t = time.now()`，即使 `cell_a` 代码和输入没变，重跑也会得到不同 `t`，下游引用 `t` 的 cell 在"重跑 a"和"不重跑 a"下结果不同。这也是 reactive notebook 在副作用处理上需要用户配合（如 marimo 的 `@cache` 语义、显式声明 UI 组件为输入源）的根本原因：框架无法自动判断哪些 cell 是纯函数，只能靠用户标注或约定。

`run_descendants` 是 `run_cell` 的一个变体，只跑后代不跑 `cell_id` 本身，用于"上游变了但本 cell 代码没变"的场景。它的实现和 `run_cell` 几乎一样，只是 `order` 来自 `_topological_sort_subset(descendants)` 而非 `execution_order_from`，不包含源头 cell。三者（`run_all`、`run_cell`、`run_descendants`）共享同一套执行循环骨架，差异仅在"算哪些 cell 要跑"和"是否清理整个命名空间"，体现了执行引擎设计的内聚性。这种共享骨架的设计也降低了维护成本：修一个执行循环的 bug，三个入口同时修好，不会出现"全量执行修好了但增量执行还有 bug"的不一致。


## 边界情况与退化

增量执行有几个值得注意的边界情况。第一，**改动的 cell 没有后代**：比如改的是最末端的展示 cell（画图标题），`descendants` 为空，`order = [cell_id]`，只重跑这一个。这是增量执行收益最大的场景，省了几乎所有 cell。

第二，**改动的 cell 是所有 cell 的祖先**：比如改的是最顶端定义基础常数的 cell，几乎所有 cell 都依赖它，`descendants` 几乎是全图。增量退化为全量，`run_cell` 和 `run_all` 执行的 cell 集合几乎相同。这种情况下增量执行不省时，但也不额外耗时（算 `descendants` 的 $O(V+E)$ 相对全量执行可忽略），且行为正确——确实所有下游都可能变，全量重跑是对的。

第三，**循环依赖被图构建拦住**：`descendants` 用 BFS 沿下游边遍历，若图里有环，BFS 会无限循环。但 marimo 在图构建阶段（`_rebuild`）就用 `topological_order` 检测了环，有环直接抛 `CyclicDependencyError`，不会建出含环的图。所以 `descendants` 的 BFS 假设图无环，这是由上游不变式保证的。如果绕过图构建直接调 `descendants`，可能出问题——但教学版不暴露这个入口，所有图操作都经过 `add_cell`/`remove_cell`，保证 `_rebuild` 已执行。

第四，**cell 代码改了但 defs/refs 没变**：比如把 `x = 1` 改成 `x = 2`，defs 仍是 `{x}`，refs 仍是空。图结构不变，`descendants` 不变，`order` 不变，但 `cell_id` 自己要重跑（代码变了）。`run_cell` 正确处理了这个情况——`order` 包含 `cell_id` 本身，不管图结构变没变。如果代码改了但运行时行为没变（比如 `x = 1` 改成 `x = 1 + 0`），增量执行仍会重跑，因为引擎不做"代码语义等价"判断，只看代码字符串变没变。这是安全的过度执行——结果正确，只是没省到最优。做语义等价判断成本太高，不值得。

## 与传统 notebook 的执行对比

传统 notebook（Jupyter）的执行模型是"用户手动逐个运行 cell"，没有依赖图，没有增量。用户改了 `cell_a` 后，要自己知道哪些 cell 依赖它，手动逐个重跑。漏了某个下游 cell，它就保持旧值，结果不一致且不报错——这是传统 notebook 最常见的"隐式状态不一致"问题。用户为了规避，养成"改了就全部重跑"的习惯，但这又抵消了 notebook 的交互优势。

marimo 的增量执行把"该重跑哪些"的判断自动化了：改了 `cell_a`，引擎自动算出 `descendants(cell_a)`，自动按拓扑序重跑它们，用户不需要记依赖关系。这不仅是省时（只跑必要的），更是正确性保证——不会漏掉某个下游 cell 导致不一致。从这个角度看，增量执行的价值有两层：表层是"省时间"，深层是"保证一致性"。即使 notebook 小到全量重跑也很快，增量执行的"不漏下游"价值依然存在——它消除了"我忘了重跑某个 cell"这个人为错误源。这是 reactive notebook 相对传统 notebook 的本质优势，而 `run_cell` + `descendants` 是这个优势的运行时实现。


## descendants 的 BFS 实现细节

`descendants` 用 BFS 而非 DFS 遍历下游，这个选择有性能和正确性两方面的考量。性能上，BFS 用 `deque` 做队列，`popleft` 是 $O(1)$，整体 $O(V+E)$；DFS 用栈（或递归），复杂度相同，但 BFS 的"层序"特性在调试时更直观——先看直接后代，再看二层后代，符合"依赖距离"的直觉。正确性上，BFS 的 `visited` 集合防止重复访问，即使图里有"菱形依赖"（A→B, A→C, B→D, C→D，D 从两条路径可达）也不会把 D 重复加入 `descendants`。DFS 同样能处理菱形依赖，但 BFS 的"先到先记录"更自然地避免重复——D 第一次被 B 的后继入队时就进了 `visited`，C 的后继再遇到 D 时直接跳过。

`_bfs` 的实现有个细节：初始队列是 `deque(adj.get(start, set()))`，不含 `start` 自己。所以 `descendants(cell_id)` 返回的是严格后代，不含 `cell_id` 本身。`execution_order_from` 里要 `| {cell_id}` 补上自己，`run_descendants` 则不补（它只跑后代）。这个"不含自己"的约定让 `descendants` 的语义清晰——"后代"就是"下游"，不含自己，和数学定义一致。如果 `descendants` 含自己，`run_descendants` 就要额外排除，反而更乱。API 设计里"集合是否含自身"是个常见约定选择，marimo 选了"不含"，和 `ancestors` 对称（也不含自己），用法一致。

## 增量执行的触发时机

`run_cell` 什么时候被触发？在 marimo 的交互模型里，用户编辑 cell 代码并提交（比如按 Shift+Enter 或失焦自动提交）时，前端通过 WebSocket 发"执行这个 cell"的请求，后端调 `run_cell(cell_id)`。注意触发的是"被改的 cell"，不是"被改的 cell 及其后代"——`run_cell` 内部自己算后代，前端不需要知道依赖图。这种"前端只说改了哪个，后端自己算影响范围"的分工，让前端逻辑简单，依赖图只存在后端，前端不需要维护副本。

另一个触发场景是"全量重跑"按钮，调 `run_all`。用户通常在"不确定增量执行是否正确"或"改了太多东西想从头来"时点这个按钮。`run_all` 重置命名空间从头跑，结果应该和"逐个改每个 cell 触发 `run_cell`"的最终状态一致——这是增量执行正确性的最终判据，也是测试里的关键断言。教学版的测试会跑"全量执行后改一个 cell 增量执行，再全量执行，比较两次结果"，验证增量执行没引入不一致。这种"增量 → 全量 → 比较"的测试模式，是验证增量执行正确性的标准做法。


## 增量执行的代价与收益平衡

增量执行的代价有两部分：一是维护依赖图和缓存的开销，二是每次 `run_cell` 算 `descendants` 和子图排序的开销。依赖图维护在 `add_cell`/`remove_cell` 时触发 `_rebuild`，是 $O(V + E)$，但只在编辑时触发，不在每次执行的热路径上。`descendants` 的 BFS 和子图排序是每次 `run_cell` 都要做的，各 $O(V + E)$，但相对 cell 执行本身（可能含数据加载、模型训练，秒级以上）通常微秒到毫秒级，可忽略。

收益是"不重跑未受影响的 cell"，省的执行次数等于 `V - len(order)`。对大 notebook（几百 cell）改小范围（几个 cell）的场景，收益巨大——从几百秒降到几秒。对小 notebook 或改大范围（改顶端变量）的场景，收益小甚至为零，但代价也不增（只多了 $O(V+E)$ 的图操作），不亏。所以增量执行是"正期望"优化——任何场景下都不比全量差，多数场景下显著更好。这种"非负收益"特性让它值得默认开启，不需要用户判断"要不要增量"。

但有一个隐性代价：**增量执行的正确性依赖 cell 是纯函数**。如果 cell 有副作用（读文件、随机数），增量执行可能给出和全量不同的结果——未重跑的 cell 保留了上次副作用的结果，重跑的 cell 产生新副作用，两者混合可能不一致。这个代价不是性能上的，而是正确性上的，且无法靠引擎自动解决——引擎不知道哪些 cell 有副作用。marimo 通过文档和约定提示用户"副作用 cell 要小心"，生产版可能提供 `@pure` 装饰器让用户显式标注纯函数 cell，引擎据此做更激进的增量优化。教学版不处理这个，但值得知道它是增量执行的固有局限。
