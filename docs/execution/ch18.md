# 增量执行：脏节点传播

全量执行每次都跑所有 cell，对大 notebook 既慢又没必要。用户改了一个 cell，真正受影响的只是它自己和它的后代；其他 cell 的输入没变，结果也不会变，重跑是浪费。`run_cell` 实现的就是这种增量执行，核心思想是"脏节点传播"：被改的 cell 标脏，脏沿着依赖边向下游传播，只重跑脏的 cell。

## 只执行 cell + descendants

`run_cell(cell_id)` 的第一步是算出需要执行的集合：

```python
targets = {cell_id} | graph.descendants(cell_id)
order = graph.execution_order_from(cell_id)
```

`descendants` 给出所有可能受影响的下游 cell，`execution_order_from` 把它们排成拓扑序。注意这里包含 `cell_id` 本身，因为改动的源头也要重跑。不在 `targets` 里的 cell 一律不动，它们之前的结果留在 `_global_ns` 里，对重跑的 cell 仍然可见——这正是增量执行省时的关键：上游不必重跑，下游只重跑必要的部分。

## _cleanup_cell_vars 清理旧变量

重跑一个 cell 之前，必须先把它上次定义的变量从命名空间里清掉，否则会出现"幽灵变量"问题。举例：cell A 原来定义 `x = 1`，用户改成 `y = 2`，若不清理，`x` 还留在 `_global_ns` 里，下游某个引用 `x` 的 cell 会误以为 A 还提供 `x`，拿到过期的 1。`_cleanup_cell_vars` 用 `_cell_defs_cache` 记录每个 cell 上次定义的变量名，执行前把它们从 `_global_ns` 删掉：

```python
for var in self._cell_defs_cache.get(cell_id, set()):
    self._global_ns.pop(var, None)
```

执行完再把新的 `defs` 写回缓存。这样命名空间始终反映"当前已执行 cell 的真实产出"，不会残留旧定义。

## 未受影响的不重跑

增量执行的收益完全来自"不重跑"的部分。假设 notebook 有 1000 个 cell，用户只改了最末端的展示 cell，`descendants` 为空，`targets` 只含这一个 cell，其余 999 个全部跳过。反过来，若改的是最顶端的 `x = ...`，且几乎所有 cell 都依赖 `x`，那 `descendants` 几乎是全图，增量退化为全量——这是合理的，因为确实所有下游都可能变。增量执行的代价是维护图和缓存，收益是"按需重跑"，两者由 `descendants` 这个集合的大小联系起来：脏节点越少，省得越多。

## 与全量执行的一致性

注意 `run_cell` 用的拓扑序是 `execution_order_from`，它和 `run_all` 用的 `topological_order` 共用同一套 Kahn 算法，只是筛了子集。因此增量执行在"该跑的范围内"和全量执行行为完全一致，用户改一个 cell 看到的结果，和点"全部重跑"看到的结果应当相同——这是增量执行正确性的判据。
