# 命名空间管理

Python 天然用一个字典作为执行命名空间：`exec(code, globals)` 把代码里定义的变量塞进 `globals`，引用的变量也从 `globals` 取。marimo 的执行引擎利用这一点，用一个全局字典 `_global_ns` 把所有 cell 的变量汇在一起，按拓扑序逐个 `exec`，变量就自然地在 cell 间流动。这一章讲清楚这个机制及其维护细节。

## _global_ns 共享

`Executor` 持有一个 `_global_ns: dict[str, Any]`，所有 cell 共享。执行一个 cell 就是：

```python
exec(compile(cell.code, "<cell>", "exec"), self._global_ns)
```

cell 里 `x = 1` 执行后，`_global_ns["x"] == 1`；下游 cell 里 `y = x + 1` 执行时，从同一个字典里取到 `x`，算出 `y` 又写回字典。因为 cell 按拓扑序执行，定义者总在引用者之前，所以引用者取到的 `x` 一定是定义者最新写入的值。这就是 marimo 不需要像传统 notebook 那样"隐式共享内核状态"又同时能保证一致性的关键：状态共享是显式的（一个字典），顺序是确定的（拓扑序），两者结合让结果可预测。

## 按拓扑序执行变量自然可见

传统 notebook（如 Jupyter）按用户手动运行顺序执行，cell 之间变量可见性取决于运行顺序而非代码顺序，容易出"重跑顺序不同结果不同"的问题。marimo 按 DAG 拓扑序执行，定义者必先于引用者，引用者执行时变量一定已在 `_global_ns` 里。即便用户在编辑器里把 cell 上下挪动，只要依赖关系没变，拓扑序就稳定，结果就稳定。命名空间的内容完全由"已执行 cell 的 defs"决定，与 UI 上的排列无关。

## _cell_defs_cache 跟踪

光有 `_global_ns` 还不够，还需要知道"某个变量是哪个 cell 定义的"，否则增量清理和重复定义检查都做不了。`_cell_defs_cache: dict[CellId, set[str]]` 记录每个 cell 上次执行后实际定义的变量名。它有三个用途：

1. **清理旧变量**：重跑 cell 前用 `_cleanup_cell_vars` 把它上次的定义从 `_global_ns` 删掉，防止幽灵变量（见第 18 章）。
2. **重复定义溯源**：若两个 cell 都定义了 `x`，靠这个缓存能快速定位冲突方。
3. **状态展示**：前端可以问"这个 cell 当前产出了哪些变量"，直接查缓存即可，不必扫 `_global_ns`。

每次 cell 执行完，缓存就更新为该 cell 本次的 `defs`。注意是"实际定义"而非"代码里写了的定义"——若 cell 执行到一半报错，后面没定义的变量不应进缓存，否则清理时会误删别的 cell 的同名变量。教学版简化处理，生产版会精确区分"执行成功才更新缓存"。

## inject：注入模块

有些对象不是任何 cell 定义的，但所有 cell 都需要，比如 `marimo_ui` 模块。`Executor.inject(name, obj)` 直接把 `obj` 塞进 `_global_ns[name]`，跳过执行过程。这样 cell 里 `ui.slider(...)` 就能直接用，无需每个 cell 都 `import`。注入的对象不归任何 cell 所有，不进 `_cell_defs_cache`，清理时也不会被删，相当于"全局常量"，为 UI 组件等基础设施提供访问点。
