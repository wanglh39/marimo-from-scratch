# 命名空间管理

Python 天然用一个字典作为执行命名空间：`exec(code, globals)` 把代码里定义的变量塞进 `globals`，引用的变量也从 `globals` 取。这是 Python 执行模型的一个底层特性——模块的 `__dict__`、`exec` 的 `globals` 参数、`eval` 的 `globals` 参数，本质上都是同一个机制：一个字典充当变量名到值的映射，执行引擎往里读写，代码从里取变量。marimo 的执行引擎利用这一点，用一个全局字典 `_global_ns` 把所有 cell 的变量汇在一起，按拓扑序逐个 `exec`，变量就自然地在 cell 间流动。这一章讲清楚这个机制及其维护细节，包括命名空间的初始化、更新、清理和注入的完整生命周期，并对比传统 notebook 的隐式内核状态。

## _global_ns 共享

`Executor` 持有一个 `_global_ns: dict[str, Any]`，所有 cell 共享。执行一个 cell 就是把编译后的代码在这个字典里 `exec`：

```python
exec(
    compile(tree, f"<cell:{cell.cell_id}>", "exec"),
    self._global_ns,
)
```

`exec` 的第二个参数是 `globals` 字典，代码里所有赋值（`x = 1`）会往这个字典写键值对，所有变量引用（`y = x + 1` 里的 `x`）会从这个字典取值。cell 里 `x = 1` 执行后，`_global_ns["x"] == 1`；下游 cell 里 `y = x + 1` 执行时，从同一个字典里取到 `x`，算出 `y` 又写回字典。因为 cell 按拓扑序执行，定义者总在引用者之前，所以引用者取到的 `x` 一定是定义者最新写入的值。这就是 marimo 不需要像传统 notebook 那样"隐式共享内核状态"又同时能保证一致性的关键：状态共享是显式的（一个字典），顺序是确定的（拓扑序），两者结合让结果可预测。

`_global_ns` 在 `__init__` 里初始化为空字典，`run_all` 会把它重置为 `_base_ns` 的副本：

```python
def __init__(self, graph: CellGraph) -> None:
    self._graph = graph
    self._base_ns: dict[str, Any] = {}
    self._global_ns: dict[str, Any] = {}
    self._cell_defs_cache: dict[str, set[str]] = {}

def run_all(self) -> list[str]:
    self._global_ns = dict(self._base_ns)
    self._cell_defs_cache = {}
    ...
```

`_base_ns` 存的是通过 `inject` 注入的全局对象（见后文）。`run_all` 用 `dict(self._base_ns)` 而非直接 `self._base_ns`，是为了避免后续 `exec` 把 cell 定义的变量写回 `_base_ns`，污染注入源。这是一个细节但重要的选择：如果用 `self._global_ns = self._base_ns`，那执行 cell 后 `_base_ns` 里会混入 cell 定义的变量，下次 `run_all` 重置时这些变量又出现，造成"上次执行的变量泄漏到本次"的 bug。`dict(...)` 做浅拷贝，`_base_ns` 保持干净，只存注入的原始对象。

`run_cell` 则不重置 `_global_ns`——这正是增量执行的前提：保留已有变量，只更新受影响的部分。如果 `run_cell` 也重置命名空间，那所有未重跑 cell 的变量就丢了，下游引用它们会 `NameError`，增量执行就退化成"全量执行但只跑一部分"，既不省时又出错。

## 按拓扑序执行变量自然可见

传统 notebook（如 Jupyter）按用户手动运行顺序执行，cell 之间变量可见性取决于运行顺序而非代码顺序，容易出"重跑顺序不同结果不同"的问题。比如三个 cell：`cell_a: x = 1`、`cell_b: x = 2`、`cell_c: y = x + 1`。在 Jupyter 里，先跑 a 再跑 c，`y` 是 2；先跑 b 再跑 c，`y` 是 3——同一个 `cell_c` 代码，结果取决于运行顺序，而非代码本身。用户必须记住"上次最后跑的是哪个"，心智负担重，且重跑顺序错了结果就错，难以排查。

marimo 按 DAG 拓扑序执行，定义者必先于引用者，引用者执行时变量一定已在 `_global_ns` 里。更根本的是，marimo 在图构建阶段就禁止重复定义：若 `cell_a` 和 `cell_b` 都定义 `x`，`_rebuild` 会抛 `DuplicateDefinitionError`，直接拦住。每个变量有且只有一个定义 cell，拓扑序唯一确定，`y` 的值永远可预测。即便用户在编辑器里把 cell 上下挪动，只要依赖关系没变，拓扑序就稳定，结果就稳定。命名空间的内容完全由"已执行 cell 的 defs"决定，与 UI 上的排列无关。

这种"变量唯一归属"是 reactive notebook 一致性的基石，而 `_global_ns` 这个共享字典是它的运行时载体。传统 notebook 的内核状态是一个隐式的、随运行顺序变化的全局字典，用户看不见摸不着，只能靠记忆和经验推断；marimo 的 `_global_ns` 虽然也是一个全局字典，但它的内容由依赖图和拓扑序完全决定，是可推断、可复现的。用户改了哪个 cell，引擎能精确算出哪些变量会变、哪些不变，这种可推断性是 reactive 体验的底层支撑。

## _cell_defs_cache 跟踪

光有 `_global_ns` 还不够，还需要知道"某个变量是哪个 cell 定义的"，否则增量清理和重复定义检查都做不了。`_cell_defs_cache: dict[CellId, set[str]]` 记录每个 cell 上次执行后实际定义的变量名。它有三个用途：

1. **清理旧变量**：重跑 cell 前用 `_cleanup_cell_vars` 把它上次的定义从 `_global_ns` 删掉，防止幽灵变量（见第 18 章）。这是增量执行正确性的关键一环。
2. **重复定义溯源**：若两个 cell 都定义了 `x`，靠这个缓存能快速定位冲突方。虽然图构建阶段已经禁止重复定义，但缓存作为运行时账本，能回答"这个变量现在归谁"。
3. **状态展示**：前端可以问"这个 cell 当前产出了哪些变量"，直接查缓存即可，不必扫 `_global_ns`（扫 `_global_ns` 分不清变量归谁，因为所有 cell 的产出混在一起）。

每次 cell 执行完，缓存就更新为该 cell 本次的 `defs`：

```python
cell.namespace = {
    var: self._global_ns[var]
    for var in cell.defs
    if var in self._global_ns
}
self._cell_defs_cache[cell.cell_id] = set(cell.defs)
cell.status = CellStatus.DONE
```

注意 `cell.defs` 是 AST 分析器在图构建阶段算出的"代码里写了哪些定义"，而 `_cell_defs_cache` 存的是"上次执行后实际生效的定义"。两者在执行成功时一致，在出错时不一致——`_execute_cell` 的 except 分支把缓存清空：

```python
except Exception as e:
    cell.exception = e
    cell.namespace = {}
    self._cell_defs_cache[cell.cell_id] = set()
    cell.status = CellStatus.ERROR
```

这是为了防止"执行到一半报错，后面没定义的变量被误记为已定义"。若不清空，下次清理时会试图从 `_global_ns` 删一个根本没写入的变量，虽然 `pop(var, None)` 不会报错，但更糟的情况是：出错 cell 代码里写了 `x = 1; y = f()` 且 `f()` 抛异常，`x` 已写入 `_global_ns` 但 `y` 没有；若缓存记成 `{x, y}`，下次清理会把 `y` 删掉，而 `y` 可能是别的 cell 定义的，造成误删。清空缓存是安全侧的选择：出错 cell 不提供任何变量，下游自然短路，下次重跑时重新写入正确缓存。

## inject：注入模块

有些对象不是任何 cell 定义的，但所有 cell 都需要，比如 `marimo_ui` 模块（提供 `ui.slider`、`ui.button` 等组件）。这些对象没有"定义 cell"，不属于依赖图，但又必须在命名空间里对每个 cell 可见。`Executor.inject(name, obj)` 直接把 `obj` 塞进 `_global_ns[name]`，跳过执行过程：

```python
def inject(self, name: str, value: Any) -> None:
    self._base_ns[name] = value
    self._global_ns[name] = value
```

注意它同时写入 `_base_ns` 和 `_global_ns`。写 `_global_ns` 让当前执行立即可见，cell 里 `ui.slider(...)` 能直接取到 `ui`；写 `_base_ns` 让 `run_all` 重置时（`self._global_ns = dict(self._base_ns)`）注入的对象不会丢。这样注入一次，全量重跑、增量重跑都保持可见，不需要每次重跑前重新注入。注入的对象不归任何 cell 所有，不进 `_cell_defs_cache`，清理时也不会被删，相当于"全局常量"，为 UI 组件等基础设施提供访问点。

注入的典型场景是启动时注入 UI 框架：

```python
executor = Executor(graph)
executor.inject("ui", marimo_ui_module)
```

之后所有 cell 都能直接 `ui.slider(0, 10)`。若用户在 cell 里重新定义同名变量 `ui = ...`，会覆盖注入值——这是 Python 字典的自然行为，也是 marimo 允许的（虽然不鼓励）。`run_all` 重置时会恢复注入的 `ui`，因为 `_base_ns` 里有原始值，而 cell 的覆盖只在当次执行生效。这种"注入优先级低于 cell 定义，但重跑后恢复"的语义，让注入对象既能被临时覆盖（用户想测试某个自定义 UI 模块时方便），又不会因一次覆盖而永久丢失（重跑后恢复框架提供的标准 `ui`），符合用户对"全局常量"的直觉。

## 生命周期的整体视角

把三个数据结构放在一起看，命名空间的完整生命周期是：

- **`_base_ns`**：注入层，只增不删（除非显式重新注入），是 `_global_ns` 的"底座"。它存的是框架注入的基础设施对象，对用户不可见，用户不直接操作它。
- **`_global_ns`**：运行层，`run_all` 时从 `_base_ns` 重建，`run_cell` 时增量更新。所有 `exec` 都在这里读写。它是 cell 代码执行时实际看到的命名空间，也是变量在 cell 间流动的载体。
- **`_cell_defs_cache`**：账本层，记录每个 cell 在 `_global_ns` 里拥有哪些变量，用于清理和溯源。它是 `_global_ns` 的"索引"，回答"这个变量归谁"的问题，没有它就无法做增量清理。

三者协作保证：全量执行从干净底座重建，增量执行在现有状态上局部更新，出错 cell 不污染下游，注入对象跨重跑持久存在。这套设计没有用任何锁或复杂同步——因为执行是串行的（见第 21 章），单线程下字典操作天然安全。命名空间管理因此可以做得极简：三个字典，几行赋值和删除，就撑起了 reactive notebook 的全部状态语义。这种简洁性是教学版的核心价值——用最少的代码讲清最本质的机制，让读者看到 reactive notebook 不需要复杂的运行时，一个共享字典加拓扑序就够了，复杂的是围绕它的工程化（UI、序列化、网络通信），而非执行模型本身。


## 与 Python 模块系统的对比

Python 的模块系统也用字典做命名空间——每个模块有一个 `__dict__`，模块里的顶层定义都存其中，`import` 把模块对象挂进当前命名空间。marimo 的 `_global_ns` 和模块 `__dict__` 在机制上几乎相同：都是一个字典，`exec` 往里写定义，引用从里取值。差异在于粒度和生命周期：模块是文件级的，`__dict__` 在模块首次 import 时创建，之后常驻；marimo 的 cell 是代码块级的，`_global_ns` 在 `run_all` 时重建，`run_cell` 时增量更新，生命周期跟随用户交互。

这种对比揭示了一个设计洞察：marimo 的整个 notebook 可以看作一个"动态模块"——cell 是模块里的顶层语句，`_global_ns` 是这个模块的 `__dict__`，`run_all` 相当于重新 import 这个模块，`run_cell` 相当于重新执行模块的某几行。这个视角让 marimo 的执行模型很容易理解：它没有发明新概念，只是把 Python 的模块执行机制应用到代码块级别，加上依赖图保证执行顺序正确。这也解释了为什么 `_global_ns` 用一个普通字典就够了——Python 模块系统也是用一个普通字典，没有特殊数据结构，简单即正确。

差异在于 marimo 需要增量更新（模块系统不支持"只重执行某几行"），所以多了 `_cell_defs_cache` 来跟踪每个 cell 的定义，支持清理和重跑。这是 marimo 在模块系统基础上的增量：不是新执行模型，而是"模块执行 + 增量重跑 + 依赖图保证顺序"的组合。理解了这个组合，就理解了 reactive notebook 的执行引擎本质。

## 命名空间的内存考量

`_global_ns` 存着所有 cell 的产出，对大 notebook 可能占大量内存。比如某个 cell 加载了 1GB 的 DataFrame，它就常驻在 `_global_ns` 里，即使用户已经不再引用它。传统 notebook 也有这个问题（内核状态常驻），marimo 没有本质区别。教学版不处理内存管理，生产版可能需要：

- **变量级清理**：当某个变量的所有引用者都改了不再用它，可以把它从 `_global_ns` 删掉。这需要引用计数（哪些 cell 的 refs 包含这个变量），比 `_cell_defs_cache` 更细粒度。
- **显式释放**：提供 `del x` 语义，让用户手动释放大对象。但 `del` 在 cell 里执行只删 `_global_ns` 里的键，不影响 `_cell_defs_cache`，下次重跑该 cell 又会写回——需要特殊处理。
- **弱引用**：对大对象用 `weakref`，让 Python 的垃圾回收器在内存紧张时自动回收。但这破坏了"变量始终可见"的语义，下游 cell 可能拿到 `None` 而非报 `NameError`，行为更难预测。

这些优化都不在教学版的范围内，但值得知道它们的存在，因为它们是"教学版能跑通，生产版能跑久"的差异点。教学版用最简单的"字典常驻"策略，把内存管理交给 Python 的引用计数和用户自己注意，这对教学场景（notebook 不大，交互时间不长）足够；生产场景（长时间运行、大数据）则需要更精细的策略，这也是 marimo 生产版与教学版的差距之一。


## 重复定义的运行时防护

图构建阶段（`_rebuild`）会检测重复定义并抛 `DuplicateDefinitionError`，但运行时还有一道隐式防护：`_cell_defs_cache`。假设绕过图构建直接调 `run_cell`（教学版不暴露这个入口，但假设），两个 cell 都定义 `x`，执行时后执行的会覆盖先执行的值，`_global_ns["x"]` 是最后写入的。`_cell_defs_cache` 会记录两个 cell 都"拥有" `x`，清理时第一个 cell 的清理会把 `x` 删掉，即使第二个 cell 的值还有效——这会导致第二个 cell 的下游拿到 `NameError`。这种异常行为是"绕过图构建"的后果，正常路径下图构建已经拦住重复定义，不会走到这里。

但这个分析揭示了一点：`_cell_defs_cache` 的"每个变量一个 owner"假设依赖图构建的不变式。如果不变式被破坏（重复定义），缓存逻辑会出错。这是"不变式驱动设计"的一个例子——`_cell_defs_cache` 的正确性依赖"每个变量只有一个定义 cell"这个不变式，不变式由 `_rebuild` 保证，运行时代码基于不变式编写，不做防御性检查。这种风格让代码简洁（不到处检查重复定义），但要求不变式维护代码（`_rebuild`）绝对可靠。教学版通过"所有图修改都经过 `add_cell`/`remove_cell` → 触发 `_rebuild`"保证不变式，是典型的"集中式不变式维护"。

## 命名空间与前端展示

`_global_ns` 和 `_cell_defs_cache` 除了驱动执行，还服务于前端展示。用户在 notebook 里能看到每个 cell"定义了哪些变量、值是什么"，这些信息来自 `cell.namespace`（在 `_execute_cell` 里设置）：

```python
cell.namespace = {
    var: self._global_ns[var]
    for var in cell.defs
    if var in self._global_ns
}
```

`cell.namespace` 是 cell 产出的变量名到值的映射，只含 `cell.defs` 里声明定义的变量，且只在执行成功时设置（出错时清空）。前端拿到 `cell.namespace` 能显示"x = 1, y = 2"之类的产出摘要，让用户不用执行下游 cell 就知道这个 cell 提供了什么。注意它做的是浅拷贝（字典推导式创建新字典），但值是引用——如果值是大 DataFrame，`cell.namespace` 里的引用和 `_global_ns` 里的指向同一对象，不会复制数据。这是有意的：复制大数据代价高，而前端只读不改，共享引用安全。

`global_namespace` 属性返回 `_global_ns` 的浅拷贝，供外部（如调试器、测试）检查整个命名空间状态：

```python
@property
def global_namespace(self) -> dict[str, Any]:
    return dict(self._global_ns)
```

返回拷贝而非原字典，防止外部修改影响执行引擎内部状态。这是"封装边界"的一个细节——外部能看不能改，修改只能通过 `run_all`/`run_cell`/`inject` 等正式接口，保证状态变更可追踪。这种"只读快照"模式在需要暴露内部状态又不想被外部破坏的场景很常见，是 API 设计的常用手法。


## inject 的实际用途与扩展

教学版里 `inject` 主要用于注入 UI 组件模块，让 cell 里能直接 `ui.slider(...)` 而非 `import marimo_ui as ui`。但 inject 的机制更通用——任何"不归任何 cell 所有但所有 cell 可见"的对象都适合注入。比如注入一个共享的数据库连接，所有 cell 直接用 `db.query(...)` 而非每个 cell 自己建连接；注入一个配置对象，所有 cell 读 `config.timeout` 而非硬编码。这些场景下 inject 把"基础设施"和"cell 逻辑"分离，cell 代码只关心业务，不关心基础设施怎么来的。

inject 的一个潜在问题是"注入对象的可变性"。如果注入的是一个可变对象（如 list、dict），cell 里修改它会影响所有其他 cell——这是全局可变状态的典型问题。比如 `inject("shared", [])`，cell_a 做 `shared.append(1)`，cell_b 做 `shared.append(2)`，`shared` 的最终内容取决于执行顺序，破坏了 reactive 的确定性。所以 inject 适合注入"不可变对象"或"无状态工具"（如模块、函数、连接池），不适合注入"可变共享状态"。教学版不强制这个约定，但文档应提示用户注意，生产版可能只允许注入特定类型的对象或做只读包装。

inject 的另一个设计点是"注入时机"。教学版在 Executor 创建后立即 inject，之后不再变。但动态 inject 也是合理的——比如运行时根据 cell 代码动态加载插件并注入。这要求 inject 能在执行过程中安全调用，当前实现里 inject 只写两个字典，不涉及执行状态，确实可以在任何时候调。但动态 inject 会让"哪些对象可用"随时间变化，增加理解难度，教学版选择静态注入保持简单。
