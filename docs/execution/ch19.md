# 短路机制

notebook 执行时，某个 cell 报错是常态：除以零、文件不存在、键不存在、类型不对……如果不管错误继续往下跑，下游 cell 会拿到缺失或过期的变量，产生两种糟糕后果。第一种是连锁报错：上游定义的 `x` 不存在了，下游 `y = x + 1` 会抛 `NameError`，再下游 `z = y * 2` 又抛 `NameError`，一次执行刷出一屏错误，用户被淹没在连锁异常里，反而看不出真正的病因。第二种更糟：静默用过期值算出错误结果。上游 `x = 1/0` 报错，但 `_global_ns` 里可能还残留着上次执行留下的旧 `x`，下游 `y = x + 1` 拿到旧 `x` 算出 `y`，不报错但结果基于过期前提，用户以为成功了实则全错。marimo 用"短路"机制处理这两个问题：出错的 cell 标记失败，它的所有后代不再执行，直接标记为 STALE（过期），等用户修复源头后自动恢复。这一章对照源码讲清楚短路的触发、传播和恢复。

## cell 出错后 short_circuited=True

`run_cell`（以及 `run_all`、`run_descendants`）的执行循环里，每个 cell 用 try/except 包裹在 `_execute_cell` 内。一旦抛异常，`_execute_cell` 把该 cell 的状态置为 `CellStatus.ERROR`，并把 `exception` 记下来；外层循环检测到 `cell.has_error` 为真，就设置 `short_circuited = True`：

```python
short_circuited = False
for cid in order:
    cell = self._graph.get_cell(cid)
    if short_circuited or self._has_failed_upstream(cid):
        cell.mark_stale()
        continue
    self._execute_cell(cell)
    executed.append(cid)
    if cell.has_error:
        short_circuited = True
return executed
```

注意这里没有 `break`——循环继续，但后续每个 cell 进入循环时，`if short_circuited` 为真，直接走 `cell.mark_stale()` 分支后 `continue`，不再执行。为什么不用 `break` 而用标志位加 `continue`？因为循环还需要遍历完 `order` 里所有剩余 cell，把它们都标 STALE。如果 `break` 直接跳出，剩余 cell 的状态会停留在上次执行的结果上（可能是 DONE），前端就不知道它们其实已经过期了。用 `short_circuited` 标志位让循环继续跑完，每个剩余 cell 都被 `mark_stale`，状态正确反映"因上游出错而过期"。

这样一次执行最多只有一个 cell 报错（第一个碰到的），后续 cell 全部标 STALE，避免连锁异常刷屏。用户看到的是一个红色的出错 cell 加一串灰色的过期 cell，清楚地知道"这里坏了，后面都受影响"，而不是一屏红色错误分不清因果。

`_execute_cell` 里出错时的处理：

```python
except Exception as e:
    cell.exception = e
    cell.namespace = {}
    self._cell_defs_cache[cell.cell_id] = set()
    cell.status = CellStatus.ERROR
```

出错 cell 的 `namespace` 清空，`_cell_defs_cache` 也清空（表示它没产出任何可用变量），状态置为 `ERROR`，`exception` 存着异常对象供前端显示 traceback。这三步合起来确保出错 cell 不会向下游提供任何"看似有效"的值——`namespace` 空了，下游即使想取也取不到；`_cell_defs_cache` 空了，下次清理时不会误删别的 cell 的同名变量。这是短路能正确阻止"静默用过期值"的关键：出错 cell 的产出被彻底清空，不像传统 notebook 那样残留旧值误导下游。

## 后代标记 STALE

短路之后，出错 cell 的后代都标为 STALE。`mark_stale` 的实现：

```python
def mark_stale(self) -> None:
    self.status = CellStatus.STALE
    self.output = None
    self.stdout = ""
    self.exception = None
    self.namespace = {}
```

STALE 表示"这个 cell 的输入可能已经不一致，结果不可信，需要重跑才能恢复"。`mark_stale` 把 `output`、`stdout`、`namespace` 全部清空，`exception` 也清掉（它不是出错，只是过期），状态置为 `STALE`。前端据此给这些 cell 加上视觉标记（比如灰色或黄色边框），告诉用户"这里的输出是旧的，别当真"。标记 STALE 不执行代码，所以不会产生新的错误，只是状态更新。

关键在于 STALE 会沿下游传播：出错 cell 的直接后继被标 STALE（因 `short_circuited` 为真），后继的后继也被标 STALE，一直到 `order` 末尾。因为 `order` 是 `cell_id` 及其后代的拓扑序，所以出错 cell 之后的所有 cell 恰好是它的所有后代，全部被标 STALE。这就是"短路 = 出错 cell 的后代全部 STALE"的实现原理——不是单独写一个遍历后代的逻辑，而是利用执行循环本身，让 `short_circuited` 标志位把剩余 cell 自然过滤掉。这种"复用执行循环做状态传播"的设计很简洁：没有额外的遍历代码，状态传播和执行跳过在同一次循环里完成。

STALE 和 ERROR 的区别很重要：ERROR 表示"这个 cell 自己执行失败了"，有 `exception`，前端显示红色和 traceback；STALE 表示"这个 cell 没执行，因为上游坏了"，没有 `exception`，前端显示灰色提示"过期"。用户看到 ERROR 知道要修这个 cell，看到 STALE 知道要修上游，两种状态引导不同的修复动作。

## _has_failed_upstream 检查

`short_circuited` 只能挡住"本次执行里出错 cell 之后的 cell"。但还有一种情况：增量执行时，出错 cell 不在本次 `order` 里，但它的后代在。比如用户改了下游某个 cell，触发 `run_cell`，执行集合里不含出错的源头 cell（源头没改），但含它的后代（后代在改动 cell 的下游里）。这时靠 `_has_failed_upstream` 把后代挡住：

```python
def _has_failed_upstream(self, cell_id: str) -> bool:
    for up_id in self._graph.predecessors(cell_id):
        up_cell = self._graph.get_cell(up_id)
        if up_cell.status in (CellStatus.ERROR, CellStatus.STALE):
            return True
    return False
```

注意它检查的是 `predecessors`（直接上游），不是 `ancestors`（所有祖先）。这看似不够——万一祖先链上有 ERRORED 但直接上游是 DONE 呢？实际上不会发生：短路机制保证出错 cell 的所有后代都被标 STALE，所以如果祖先链上有 ERRORED，那么从出错 cell 到当前 cell 路径上的所有中间节点都是 STALE，当前 cell 的直接上游必然是 STALE 或 ERRORED。换句话说，STALE 状态沿下游"传染"，使得只检查直接上游就足够捕获整条链路上的任何失败。这是一个巧妙的不变式：`_has_failed_upstream` 的正确性依赖短路机制已经把祖先的失败传播到了直接上游。两者协同工作——短路负责"本次执行内的传播"，`_has_failed_upstream` 负责"跨执行的传播检查"，合起来覆盖所有情况。

执行循环里 `short_circuited or self._has_failed_upstream(cid)` 这个条件把两种情况统一了：`short_circuited` 处理"本次执行内已短路"，`_has_failed_upstream` 处理"本次执行外有失败上游"。两者任一为真，当前 cell 就标 STALE 跳过。这个统一条件是执行循环能同时处理全量和增量的关键——不管 `order` 是全图还是子图，同一个条件都能正确判断"该不该执行这个 cell"。

## 修复后自动恢复

短路不是终态。用户修好出错的 cell（比如把除数改成非零），再次触发执行时，源头 cell 重新执行成功，状态变回 `CellStatus.DONE`；它的后代在本次 `order` 里，`_has_failed_upstream` 返回 False（上游已是 DONE），于是正常执行，STALE 状态被覆盖为 DONE。整条链路自动恢复，无需用户手动"重跑全部"。

用一个完整例子说明恢复过程。假设 `cell_a: x = 1 / 0` 出错，`cell_b: y = x + 1` 被标 STALE。用户把 `cell_a` 改成 `x = 1 / 1`，触发 `run_cell('cell_a')`：

1. **算后代和排序**：`descendants('cell_a') = {cell_b}`，`order = ['cell_a', 'cell_b']`。
2. **清理旧变量**：清掉 `cell_a` 上次的 `x`（虽然上次执行失败，`_cell_defs_cache` 已被清空，所以实际没清什么）和 `cell_b` 上次的 `y`。
3. **执行 cell_a**：`_has_failed_upstream('cell_a')` 检查 `cell_a` 的上游（假设没有上游），返回 False；`short_circuited` 也是 False。于是执行 `x = 1 / 1`，成功，`x = 1.0`，状态从 ERROR 变为 DONE。
4. **执行 cell_b**：`_has_failed_upstream('cell_b')` 检查 `cell_a` 的状态，是 DONE，返回 False；`short_circuited` 也是 False。于是执行 `y = x + 1`，取到 `x=1.0`，算出 `y=2.0`，状态从 STALE 变为 DONE。

整条链路在一次 `run_cell` 调用里自动恢复。这种"出错即短路，修复即恢复"的行为，让 notebook 在频繁试错时保持清爽：错误不会向下游蔓延，修复后下游自动跟上。用户不需要记住"哪些 cell 受影响了要手动重跑"，执行引擎靠依赖图自动算出恢复范围，这正是 reactive notebook 相对传统 notebook 的核心体验优势——传统 notebook 里，修复上游后下游不会自动重跑，用户得手动逐个重跑，容易漏掉某个下游 cell 导致结果不一致，而漏掉的 cell 不会报错，只是用着旧值，问题更隐蔽。


## 状态机全貌

把短路机制放进 CellStatus 的完整状态机里看，能更清楚它的定位。cell 有六种状态：`IDLE`（初始，未执行过）、`PENDING`（等待执行）、`RUNNING`（执行中）、`DONE`（执行成功）、`ERROR`（执行失败）、`STALE`（过期）。状态转移如下：

- `IDLE/PENDING/STALE → RUNNING`：开始执行时由 `_execute_cell` 设置。
- `RUNNING → DONE`：执行成功，`_execute_cell` 的 try 块正常结束。
- `RUNNING → ERROR`：执行抛异常，except 块设置。
- `DONE/ERROR → STALE`：因上游出错或短路，由 `mark_stale` 设置。
- `STALE → RUNNING → DONE`：修复上游后重跑，自动恢复。

短路机制在这个状态机里的作用是"截断 RUNNING → ERROR 的下游影响"：出错 cell 进 ERROR，后代不进 RUNNING 而直接进 STALE，避免后代在 ERROR 上游下执行产生连锁错误或静默过期值。STALE 是一个"安全等待"状态——它表示"我知道自己过期了，不会假装有效，等上游修好我就重跑"。没有 STALE 的话，后代要么保持 DONE（假装有效，误导用户），要么进 ERROR（但自己没出错，报错信息误导），都不如 STALE 准确。

`is_runnable` 属性定义了哪些状态可以触发执行：

```python
@property
def is_runnable(self) -> bool:
    return self.status in (CellStatus.IDLE, CellStatus.PENDING, CellStatus.STALE)
```

IDLE、PENDING、STALE 都可执行，DONE 和 ERROR 不可直接执行（DONE 是已完成无需重跑，ERROR 需要用户改代码后才重跑）。这个分类让前端能正确显示"运行"按钮——只有 runnable 的 cell 才显示运行按钮，DONE 的 cell 显示"已成功"，ERROR 的 cell 显示"出错需修复"。

## 与传统异常处理的对比

传统 Python 程序里，异常要么被 catch 往下继续，要么向上传播终止程序。notebook 里这两种都不合适：catch 了下游用过期值，不 catch 连锁报错刷屏。marimo 的短路是第三种选择——"出错即停止下游，但不终止整个 notebook"。这类似数据库事务的"失败隔离"：出错的事务回滚，不影响其他事务，但本事务内的后续操作不执行。cell 的"事务"就是它和它的后代：出错 cell 回滚（output 清空），后代不执行（标 STALE），其他 cell 不受影响（保持原状）。

这种类比揭示了一个设计原则：reactive notebook 把每个 cell 视作一个"微型事务"，以依赖子图为边界。事务内要么全成功，要么出错点之前成功、出错点及之后回滚/跳过。这种语义比传统 notebook 的"逐 cell 手动运行，出错就停在那"更清晰——传统 notebook 里出错后下游仍是上次的结果，用户不知道哪些是新的哪些是旧的；marimo 里出错后下游明确标 STALE，用户知道"这些都是过期的，修好上游就恢复"。


## 短路与重试的交互

短路机制和"用户重试"之间有个微妙交互。假设 `cell_a` 出错短路，`cell_b` 标 STALE。用户没改 `cell_a` 代码，只是点了"重跑 cell_b"按钮（触发 `run_cell('cell_b')`）。这时 `order = ['cell_b']`（`cell_b` 没有后代），执行 `cell_b` 前检查 `_has_failed_upstream('cell_b')`：`cell_a` 是 ERROR，返回 True，`cell_b` 被标 STALE 跳过。结果：`cell_b` 仍是 STALE，用户的重试被挡住了。这是对的——`cell_a` 还坏着，重跑 `cell_b` 只会再次失败或用过期值，不如保持 STALE 提示用户"先修上游"。

但如果用户改了 `cell_a` 并触发 `run_cell('cell_a')`，`order = ['cell_a', 'cell_b']`，`cell_a` 执行成功变 DONE，`cell_b` 的上游检查通过，正常执行，STALE 变 DONE。这是"修复即恢复"的完整路径：改源头 → 源头重跑成功 → 后代自动重跑恢复。用户不需要单独重跑后代，一次 `run_cell` 全搞定。

这个交互说明短路机制的设计哲学：**不让用户在坏的状态下做无意义的重试**。`cell_a` 坏着时，重跑 `cell_b` 被挡住，避免用户反复点重试却总是失败或得到错误结果。只有修好源头，后代才允许重跑，且自动重跑。这把"修复上游"和"恢复下游"绑成一个原子操作，用户心智简单——"修好坏的，其他自动好"，不需要想"哪些要手动重跑"。

## 短路的粒度选择

marimo 的短路粒度是"出错 cell 的所有后代"，这是较粗的粒度——所有后代无一例外标 STALE，即使某些后代其实不依赖出错 cell 的产出。这种情况存在吗？在 marimo 的依赖图里，"后代"定义为"沿下游边可达"，下游边是"引用了上游定义的变量"。如果 `cell_a` 定义 `x` 并出错，`cell_b` 引用 `x`，`cell_c` 引用 `cell_b` 的 `y` 但不直接引用 `x`——`cell_c` 仍是 `cell_a` 的后代（通过 `cell_b`），被标 STALE。但 `cell_c` 真的受影响吗？如果 `cell_b` 因 `cell_a` 出错而没产出 `y`，`cell_c` 执行时拿不到 `y`，确实会失败，所以标 STALE 是对的。

更微妙的情况：`cell_b` 引用 `x` 但只是 `if x > 0: y = 1`，`x` 出错时 `cell_b` 没执行，但若 `cell_b` 代码改成 `y = 1; if x > 0: y = 2`，`x` 出错不影响 `y = 1` 的执行。静态依赖图无法区分"运行时是否真的用到 x"，所以保守地把所有后代标 STALE。这是"过近似"——可能标了一些其实不受影响的 cell，但不会"漏标"真正受影响的。过近似的代价是多重跑一些 cell，收益是正确性保证。静态分析要精确判断"运行时是否用到某变量"需要数据流分析甚至符号执行，复杂度远超教学版的范围，保守过近似是合理的工程取舍。


## 短路与前端交互的细节

短路机制在前端的体现是状态驱动的视觉反馈。后端执行完后，每个 cell 有明确状态：DONE（绿色）、ERROR（红色带 traceback）、STALE（灰色带"过期"提示）。前端根据状态渲染，用户一眼看出"哪里坏了、哪里过期了"。这种状态驱动的交互比传统 notebook 的"最后输出的 cell 是当前状态"更清晰——传统 notebook 里，出错 cell 显示红色，但下游 cell 仍显示上次成功的绿色输出，用户不知道哪些是新的哪些是旧的，容易误信过期结果。

短路还影响前端的"运行"按钮状态。出错的 cell 显示"修复后重跑"按钮，STALE 的 cell 不显示单独重跑按钮（因为单独重跑会被 `_has_failed_upstream` 挡住，没有意义），而是显示"上游有错误，修复上游后自动恢复"的提示。这种"按状态显示不同操作"的设计，引导用户做正确的动作——修源头而非徒劳地重跑下游。教学版前端简化处理，但生产版会精确区分这些状态对应的操作选项，让交互更顺滑。

一个体验细节：短路后 STALE cell 的旧输出要不要显示？marimo 选择"显示但加灰色遮罩和过期标记"。保留旧输出有好处——用户能对比"修复前后的差异"，比如"之前图表长这样，修复后变了"。但遮罩明确提示"这是旧的别当真"，避免误信。这种"保留历史 + 明确标记"比"直接清空"更友好，用户不会因修复一瞬间输出消失而困惑。这个设计选择不在执行引擎层面（引擎只管标 STALE），而在前端层面，但值得提及，因为它体现了 reactive notebook 对用户体验的细致考量。


## 短路在 run_all 中的表现

`run_all` 也有短路逻辑，和 `run_cell` 共用同一套循环骨架。全量执行时，若中间某个 cell 出错，`short_circuited` 置 True，后续 cell 全部标 STALE。这和增量执行的短路行为一致——"出错即停止下游"，只是 `run_all` 的 `order` 是全图拓扑序，所以"下游"是出错 cell 的所有后代，和 `run_cell` 里的一致。

`run_all` 开头会重置命名空间：`self._global_ns = dict(self._base_ns); self._cell_defs_cache = {}`。这意味着全量执行从干净状态开始，之前的错误状态、STALE 标记都被清掉。如果上次执行有 cell 出错，这次 `run_all` 会重新尝试所有 cell——出错 cell 若代码没改仍会出错，但它的后代不会再因"上次 STALE"而被 `_has_failed_upstream` 挡住（因为 `_cell_defs_cache` 清了，但 cell.status 没重置——这里有个细节：`run_all` 不重置 cell.status，所以上次 STALE 的 cell 这次执行时，`_has_failed_upstream` 检查上游可能仍是上次的状态）。

实际上 `run_all` 的执行循环里，每个 cell 都会经过 `if short_circuited or self._has_failed_upstream(cid)` 检查。如果上次 `cell_a` 是 ERROR 且这次没改代码，`cell_a` 会再次执行（`run_all` 不跳过任何 cell，除非已短路），再次出错，再次短路。如果用户改了 `cell_a` 代码并 `run_all`，`cell_a` 执行成功变 DONE，后代正常执行。所以 `run_all` 的短路是"当次执行内"的短路，每次 `run_all` 都从头尝试，不因上次状态跳过 cell（除非当次已短路）。这和 `run_cell` 的"增量跳过未受影响 cell"不同——`run_all` 总是尝试所有 cell，短路只在当次执行内生效。


## 短路与增量执行的协作

短路和增量执行是两个正交的机制，但在 `run_cell` 的执行循环里协同工作。增量执行决定"跑哪些 cell"（`order` 的范围），短路决定"跑到哪里停"（`short_circuited` 标志）。两者不冲突：增量执行算出 `order` 后，短路在 `order` 的范围内生效——若 `order` 里某个 cell 出错，短路只影响 `order` 里它之后的 cell，不影响 `order` 外的 cell（它们本来就不跑）。这种"短路在增量范围内生效"的语义，让两个机制可以独立设计、组合使用，不需要特殊处理交互。

一个有趣的组合场景：`cell_a` 出错（ERROR），`cell_b` 是其后代（STALE），`cell_c` 是 `cell_b` 的后代（STALE）。用户改了 `cell_c` 的代码（不是改 `cell_a`），触发 `run_cell('cell_c')`。`order = ['cell_c']`（`cell_c` 没有后代）。执行 `cell_c` 前检查 `_has_failed_upstream('cell_c')`：`cell_b` 是 STALE，返回 True，`cell_c` 被标 STALE 跳过。结果：`cell_c` 仍是 STALE，用户的修改没有被执行。这是对的——`cell_b` 还坏着（因 `cell_a` 坏），`cell_c` 依赖 `cell_b`，执行 `cell_c` 会用过期值，不如保持 STALE。用户必须先修 `cell_a`，才能让 `cell_b`、`cell_c` 恢复。这个例子展示了短路如何跨"增量执行边界"生效——即使 `cell_a`、`cell_b` 不在本次 `order` 里，它们的状态仍通过 `_has_failed_upstream` 影响 `cell_c`。
