# 拓扑排序：Kahn 算法

执行引擎要回答的第一个问题是"按什么顺序跑这些 cell"。这个问题看似简单，实则暗藏玄机。notebook 里 cell 之间有依赖关系：cell B 引用了 cell A 定义的变量，那 A 必须先跑，否则 B 执行时变量还不存在。把所有 cell 看作顶点，依赖关系看作有向边，就得到一张有向图。如果这张图里没有环，它就是一个 DAG（有向无环图），而 DAG 的拓扑序就是合法的执行顺序。`CellGraph.topological_order` 用的正是 Kahn 算法——一种基于入度的经典方法，既能在 $O(V+E)$ 时间内排出序，又能顺带检测环。这一章我们拆开它的实现细节，并用一个具体例子把入度表、队列变化的每一步都走一遍，最后讲清楚为什么 marimo 选择 Kahn 而非其他拓扑排序方法。

## 入度法

入度（in-degree）指指向某个顶点的边数。在 marimo 的依赖图里，边 A → B 表示"cell A 定义了 cell B 引用的变量"，即 B 依赖 A。所以一个 cell 的入度就是"它引用了多少个由其他 cell 定义的变量"。入度为 0 意味着这个 cell 不依赖任何其他 cell，可以最先执行——它引用的变量要么是自己定义的，要么是注入的全局对象，不需要等待任何 cell。Kahn 算法的直觉正是从这里出发：入度为 0 的 cell 不依赖任何 cell，可以最先执行；执行完把它"摘掉"，它指向的后继就少了一条入边，入度随之减一；若某个后继的入度减到 0，它就成了新的"无依赖"cell，可以执行。如此反复，就像剥洋葱一样一层层去掉无依赖的顶点，直到所有顶点都被剥完。

这个直觉可以类比成"排队等前置任务完成"：每个 cell 是一项任务，入度是它还没完成的前置任务数。前置全做完的任务可以立刻开工，开工后它作为别人的前置也完成了，于是别人的待等数减一。等到某个任务的待等数归零，它就能开工。整个算法就是不断把"可以开工的任务"捞出来执行，再把因它完成而新变得可执行的任务捞出来，直到没有可执行的任务为止。

具体步骤如下：

1. 计算每个顶点的初始入度，即该 cell 的上游集合大小。
2. 把所有入度为 0 的顶点放进一个待处理队列。
3. 从队列取出一个顶点 $u$，追加到结果序列 `order`；对 $u$ 的每个后继 $v$，把 $v$ 的入度减一，若减到 0 就把 $v$ 入队。
4. 重复第 3 步直到队列为空。

若最终 `len(order) == V`，排序成功；否则图里有环，剩下的顶点入度永远降不到 0。下面是 `graph.py` 里的真实实现：

```python
def topological_order(self) -> list[str]:
    in_degree = {
        cid: len(self._upstream.get(cid, set())) for cid in self._cells
    }
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set())):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    if len(order) != len(self._cells):
        remaining = set(self._cells) - set(order)
        raise CyclicDependencyError(
            f"检测到循环依赖，涉及 cell: {sorted(remaining)}"
        )
    return order
```

注意几个细节：`in_degree` 直接用 `len(self._upstream.get(cid, set()))` 算出，因为 `_upstream` 存的就是每个 cell 的直接上游集合，其长度恰好是入度；入度为 0 的顶点在入队前先 `sorted`，保证确定性；主循环用 `deque.popleft()` 从左端取，新入队的顶点追加到右端，整体是 FIFO（先进先出）。用 `deque` 而非普通列表，是因为 `deque.popleft()` 是 $O(1)$ 操作，而 `list.pop(0)` 要把所有元素左移，是 $O(V)$，在几百个 cell 的 notebook 里差异不大，但在几千个 cell 时会明显。

## 逐步演示

光看步骤还不够直观，我们用一个具体例子把整个过程走一遍。假设有四个 cell，依赖关系如下：

```
cell_a:  x = 1
cell_b:  y = x + 1      # 依赖 cell_a
cell_c:  z = 2          # 不依赖任何人
cell_d:  w = y + z      # 依赖 cell_b 和 cell_c
```

对应的边是 `a→b`（b 引用 a 定义的 x）、`b→d`（d 引用 b 定义的 y）、`c→d`（d 引用 c 定义的 z），初始入度表为：

| cell | 上游集合 | 入度 | 含义 |
|------|----------|------|------|
| a    | {}       | 0    | 无前置，可立即执行 |
| b    | {a}      | 1    | 等 a 完成 |
| c    | {}       | 0    | 无前置，可立即执行 |
| d    | {b, c}   | 2    | 等 b 和 c 都完成 |

初始时入度为 0 的是 `a` 和 `c`，排序后队列为 `deque(['a', 'c'])`。下面逐步推演，每一步都标出队列和入度表的变化：

1. 取出 `a`，`order = ['a']`。`a` 的后继是 `{b}`，把 `b` 的入度从 1 减到 0，入队。队列变为 `deque(['c', 'b'])`。此时 `b` 的前置已全部完成，可以执行了。
2. 取出 `c`，`order = ['a', 'c']`。`c` 的后继是 `{d}`，把 `d` 的入度从 2 减到 1，不归零，不入队。队列变为 `deque(['b'])`。`d` 还在等 `b`，暂时不能执行。
3. 取出 `b`，`order = ['a', 'c', 'b']`。`b` 的后继是 `{d}`，把 `d` 的入度从 1 减到 0，入队。队列变为 `deque(['d'])`。`d` 的前置全部完成。
4. 取出 `d`，`order = ['a', 'c', 'b', 'd']`。`d` 没有后继，队列空，循环结束。

最终 `order = ['a', 'c', 'b', 'd']`，长度等于 cell 总数 4，排序成功。注意 `c` 排在 `b` 前面——初始入队时入度为 0 的是 `a` 和 `c`，`sorted(['a', 'c'])` 得到 `['a', 'c']`，所以 `c` 在第二步被取出。而 `b` 要等 `a` 执行完入度归零才入队，此时队列里已有 `c`，`b` 追加到右端成为 `['c', 'b']`，于是 `c` 先于 `b` 被取出。这就是确定性来源：同一时刻有多个可选顶点时，永远先取 id 字典序最小的。如果不用 `sorted`，初始队列可能是 `['c', 'a']`，结果就变成 `['c', 'a', 'b', 'd']`，虽然也是合法拓扑序，但每次运行可能不同，测试和调试就难了。

## sorted 保证确定性

一个 DAG 通常有多种拓扑序。比如三个互不依赖的 cell `a, b, c`，任何排列都是合法拓扑序，共 6 种。但 marimo 需要每次得到同一个序列，否则执行结果可能因顺序不同而漂移。考虑一个场景：三个 cell 分别往同一个日志文件 append 一行，顺序不同日志内容就不同，测试断言会失败。再考虑调试：用户报告"第 3 个 cell 报错"，如果"第 3 个"每次指向不同 cell，报告就无意义。为此，Kahn 在把入度为 0 的顶点入队时，先按 cell id 排序：

```python
queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
while queue:
    node = queue.popleft()
    order.append(node)
    for ds in sorted(self._downstream.get(node, set())):
        in_degree[ds] -= 1
        if in_degree[ds] == 0:
            queue.append(ds)
```

注意实现里并没有在每次 `append` 后重新 `sort` 整个队列——它依赖一个更微妙的性质：后继在入队前也经过 `sorted(self._downstream.get(node, set()))` 遍历，且初始队列已排序。由于 cell id 是字符串，字典序稳定，同一输入图永远产出同一 `order`。这种可复现性对调试和测试极其重要：测试可以断言执行顺序等于某个固定列表，而不必处理集合的无序性；用户报告"第 3 个 cell 报错"时，"第 3 个"也指向同一个 cell，开发者能可靠地复现问题。

确定性的另一个好处是增量执行的一致性。`run_cell` 和 `run_all` 共用同一套排序逻辑，子图排序用的也是 `sorted`，所以"改一个 cell 后重跑"和"全部重跑"在各自范围内产出的执行顺序是一致的投影关系，不会因随机顺序导致变量可见性差异。

## 环检测

Kahn 算法天然能检测环：有环时，环上的顶点入度永远降不到 0，最终 `len(order) < V`。实现里在循环结束后做了一次校验：

```python
if len(order) != len(self._cells):
    remaining = set(self._cells) - set(order)
    raise CyclicDependencyError(
        f"检测到循环依赖，涉及 cell: {sorted(remaining)}"
    )
```

`remaining` 就是那些入度永远没归零的顶点，它们必然处于某个环上（或依赖了环上的顶点）。报错信息把它们列出来，方便用户定位。举个例子，若 `cell_a` 引用 `y`、`cell_b` 引用 `x`，而 `cell_a` 定义 `x`、`cell_b` 定义 `y`，就形成 `a→b→a` 的环：`a` 依赖 `b`（因为 `a` 引用 `b` 定义的 `y`），`b` 依赖 `a`（因为 `b` 引用 `a` 定义的 `x`）。两个 cell 的入度都是 1，初始队列为空，`order` 为空，`len(order) = 0 != 2`，直接抛 `CyclicDependencyError`，报错信息是"检测到循环依赖，涉及 cell: ['cell_a', 'cell_b']"。

这种"排序即校验"的设计很优雅：不需要单独写一个环检测算法（比如 DFS 三色标记法），拓扑排序本身就把环暴露出来了。而且报错信息直接给出环上的顶点，用户一眼就知道是哪几个 cell 互相依赖，比 DFS 检测后还要回溯找环更直接。代价是排序失败的图不会有部分结果返回——但这对 marimo 来说是对的，有环的 notebook 根本不能执行，应该在建图阶段就拦住。

## 时间复杂度 O(V+E)

建入度表要遍历所有顶点的上游集合，每条边在上游集合里出现一次，合计 $O(E)$；主循环里每个顶点出队一次，每条边在"减后继入度"时被访问一次，合计 $O(V+E)$。`sorted` 的加入会让单次排序付出 $O(k \log k)$（k 是当前就绪队列长度），最坏情况下（比如所有顶点互不依赖，初始就全部入队）整体退化为 $O(V \log V + E)$，对 notebook 规模（几百到几千个 cell）完全可接受。`deque.popleft()` 是 $O(1)$，不会像 `list.pop(0)` 那样带来 $O(V)$ 的元素搬移开销——这是实现里用 `deque` 而非普通列表的关键原因。

实际 notebook 里，依赖图通常是"窄而长"的：cell 依次依赖前一个，形成链状结构。这种图每层只有一两个顶点入度为 0，`sorted` 排序的代价接近 $O(1)$，整体接近纯 $O(V+E)$。即使是"宽而扁"的图（很多独立 cell），排序代价也只是 $O(V \log V)$，在 1000 个 cell 时约 10000 次比较，毫秒级，相对执行 cell 本身（可能含数值计算、IO）的开销可忽略。

## execution_order_from：子图拓扑序

`execution_order_from` 在全局拓扑序的基础上再做一次过滤，只保留某个 cell 及其后代，用于增量执行。它的实现不是"先排全局再筛子集"，而是直接在子图上重新跑一遍 Kahn：

```python
def execution_order_from(self, cell_id: str) -> list[str]:
    affected = self.descendants(cell_id) | {cell_id}
    return self._topological_sort_subset(affected)

def _topological_sort_subset(self, subset: set[str]) -> list[str]:
    in_degree = {
        cid: len(self._upstream.get(cid, set()) & subset) for cid in subset
    }
    queue = deque(sorted(cid for cid, d in in_degree.items() if d == 0))
    order: list[str] = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for ds in sorted(self._downstream.get(node, set()) & subset):
            in_degree[ds] -= 1
            if in_degree[ds] == 0:
                queue.append(ds)
    return order
```

关键区别在入度的计算：`len(self._upstream.get(cid, set()) & subset)`，只统计"在子集内"的上游。比如 cell `d` 的全局上游是 `{b, c}`，但若子集是 `{b, d}`（只重跑 `b` 及其后代），那 `d` 在子图里的入度就是 `|{b, c} & {b, d}| = |{b}| = 1`，`c` 不算入度，因为它不在本次执行范围里——它的值已经留在命名空间中，对 `d` 来说是已知常量，不需要等它。这样增量执行和全量执行共用同一套 Kahn 逻辑，只是图的顶点集和边集被限制在子集上，行为完全一致。

这也是增量执行正确性的根基：子图拓扑序就是全局拓扑序在子集上的投影，定义者仍先于引用者。假设全局序是 `[a, c, b, d]`，子集 `{b, d}` 的子图序是 `[b, d]`——`b` 在 `d` 前，和全局序里的相对顺序一致。这保证了增量执行里变量可见性和全量执行完全相同：`d` 执行时 `b` 已执行完，`y` 在命名空间里是最新的。


## 与 DFS 拓扑排序的对比

拓扑排序有两种经典实现：Kahn 算法（基于入度）和 DFS 后序逆序（基于深度优先搜索）。DFS 版的思路是：对图做深度优先遍历，每个顶点在"访问完所有后继后"加入结果列表，最后把列表逆序就是拓扑序。两者都能排出合法拓扑序，都能检测环（DFS 用三色标记，Kahn 用入度归零计数），复杂度都是 $O(V+E)$。marimo 选 Kahn 的原因有三：

第一，**就绪队列天然对应执行调度**。Kahn 的"入度为 0 的顶点入队"直接就是"可以执行的 cell"，队列内容就是调度器的待办列表。DFS 的后序逆序没有这个直觉——它是"先访问到底再回溯"，中间状态（哪些 cell 在栈上）不直接对应"可执行"。对执行引擎来说，Kahn 的中间状态更有意义，便于调试和扩展（比如并行执行时，就绪队列就是可并行的 cell 集合）。

第二，**环检测报错更直接**。Kahn 排完后 `len(order) != V` 就知道有环，`remaining` 直接给出环上的顶点。DFS 检测环要靠"回边"（遇到灰色顶点），报错时还要从调用栈回溯找出环路径，代码更复杂。marimo 的 `CyclicDependencyError` 直接列出 `remaining`，用户一眼看到涉及哪些 cell，这是 Kahn 的天然优势。

第三，**确定性更容易保证**。Kahn 只需在入队时 `sorted` 就能得到唯一拓扑序，因为就绪队列是一个显式的集合，排序它即可。DFS 的确定性要靠"按固定顺序遍历后继"，虽然也能做到，但"遍历顺序"比"集合排序"更隐式，容易遗漏某处排序导致不确定性。marimo 的 Kahn 实现里 `sorted` 出现在两处（初始入队和后继遍历），显式且易审查。

## 实际 notebook 的拓扑特征

实际数据科学 notebook 的依赖图通常有几种典型形态。第一种是**链式**：`加载 → 清洗 → 特征 → 训练 → 评估 → 可视化`，每个 cell 依赖前一个，形成长链。链式图的拓扑序唯一（每层只有一个可选 cell），Kahn 的 `sorted` 不起作用，排序退化为 $O(V)$。第二种是**树形**：一个数据加载 cell，下游分叉成多个独立分析（不同指标、不同图表），再汇合到一个汇总 cell。树形图在分叉层有多个可选 cell，`sorted` 决定它们的执行顺序，虽然顺序不影响结果（它们互不依赖），但影响调试时的可读性。第三种是**网状**：多个 cell 互相引用彼此的变量，形成复杂依赖网。网状图的拓扑序可能有很多种，`sorted` 的确定性保证尤其重要——没有它，每次执行顺序不同，测试无法断言，调试无法复现。

了解这些形态有助于理解 Kahn 在实际场景下的表现：链式图几乎无排序开销，树形图排序开销集中在分叉层，网状图排序开销最大但通常 cell 数不多。对几百个 cell 的 notebook，Kahn 的执行时间在毫秒级，相对 cell 本身的执行（可能含数据加载、模型训练，秒到分钟级）完全可忽略。这也是为什么教学版不优化排序性能——它已经够快了，瓶颈在 cell 执行而非排序。


## Kahn 算法的历史与直觉

Kahn 算法由 Arthur Kahn 在 1962 年的论文"Topological Sorting of Large Networks"中提出，最初用于解决大型项目管理里的任务排序问题——给定一堆任务和它们的先后约束，排出一个执行计划。这和 marimo 的场景完全对应：cell 是任务，依赖关系是先后约束，拓扑序是执行计划。Kahn 的贡献在于把"找一个合法顺序"这个看似需要搜索的问题，化简为"不断剥无依赖顶点"的贪心过程，证明了贪心策略对 DAG 总能成功，且复杂度是线性的。这个化简是算法设计里的经典案例：利用问题结构（DAG 的无环性）保证贪心选择的安全性，避免回溯。

理解 Kahn 的直觉有助于理解它为什么能检测环。环的本质是"循环等待"：A 等 B，B 等 A，两者都无法开始。Kahn 的"剥洋葱"过程里，环上的顶点永远有入度（总有前置没完成），永远进不了就绪队列，最终被留在 `remaining` 里。这比 DFS 三色标记的环检测更直观——DFS 靠"遇到回边"检测，要理解"什么是回边"和"为什么回边意味着环"；Kahn 靠"剥不完"检测，"剥不完"直接对应"有循环等待"，因果一目了然。对教学来说，Kahn 的环检测更容易讲清楚，这也是教学版选它的一个隐性原因。

## 子图排序的工程意义

`_topological_sort_subset` 不复用全局排序结果再过滤，而是重新在子图上跑 Kahn，这个选择有工程意义。如果"先排全局再筛子集"，全局排序的 $O(V+E)$ 每次增量执行都要付，即使子集很小。直接在子图上排，复杂度是 $O(V' + E')$（$V', E'$ 是子图的顶点数和边数），通常远小于全图。比如 1000 个 cell 的 notebook，改一个末端 cell，子集只有 1 个顶点，子图排序是 $O(1)$，而"先全局再筛"仍是 $O(1000)$。对频繁的增量执行（用户每改一次就触发一次），这个差异累积起来很可观。

更微妙的是子图入度的计算：`len(self._upstream.get(cid, set()) & subset)`，用集合交集而非遍历计数。`_upstream[cid]` 是全局上游，`& subset` 筛出子集内的上游，`len` 取数量。这是 $O(\min(|upstream|, |subset|))$ 的集合操作，比遍历上游逐个判断是否在子集里更快。Python 的集合交集用哈希表实现，对几百个元素的操作是微秒级。这些细节单独看都不大，但执行引擎是热路径（每次交互都调），累积起来影响响应速度，所以实现里用了 `deque`、集合交集、避免不必要的遍历等优化，和教学清晰性之间做了平衡。


## 确定性排序的测试价值

`sorted` 保证的确定性拓扑序在测试里极其有价值。测试可以断言 `graph.topological_order() == ['cell_a', 'cell_c', 'cell_b', 'cell_d']`，一个固定列表，不需要处理"合法但不唯一"的拓扑序集合。如果排序不确定，测试要么断言"结果在某个合法集合里"（写起来啰嗦），要么固定随机种子后断言（脆弱，依赖实现细节）。确定性排序让测试简洁且鲁棒——只要图结构不变，排序结果永远相同，测试不会因排序实现微调而失败。

这种确定性还支持"快照测试"——把执行顺序、每个 cell 的输出序列化成快照文件，下次运行比对。如果排序不确定，快照每次不同，测试无意义；确定性排序让快照稳定，能检测出"执行顺序变化"这类回归。比如有人改了 `sorted` 的排序键（从 cell_id 改成 cell 创建时间），快照测试会立即失败，提醒"执行顺序变了，可能影响下游"。这种"排序变化即回归"的检测对维护执行引擎的正确性很有用，而它依赖确定性排序作为基础。
