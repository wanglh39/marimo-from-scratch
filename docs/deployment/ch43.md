# FastAPI 服务架构

后端服务的入口在 `backend/server/webapp.py`，核心是 `create_app()` 函数，它构造一个 FastAPI 实例并注册所有必要的路由和中间件。这一章我们逐项拆解这个函数的内部结构，并深入到 `NotebookSession` 的消息分发机制，理解一个 WebSocket 消息从到达后端到返回响应的完整旅程。

后端的整体架构可以用一张图概括：

```
            浏览器（前端 React 应用）
                    │
               WebSocket /ws
                    │
                    ▼
        ┌───────────────────────────┐
        │     FastAPI 应用实例        │
        │  /ws        WebSocket 端点  │
        │  /api/health 健康检查      │
        │  /          StaticFiles    │
        └────────────┬──────────────┘
                     ▼
        ┌───────────────────────────┐
        │    NotebookSession         │
        │    CellGraph + Executor    │
        └───────────────────────────┘
```

## create_app 函数

`create_app()` 是后端的工厂函数，教学版的完整实现如下：

```python
def create_app() -> FastAPI:
    app = FastAPI(title="marimo-from-scratch")

    @app.websocket("/ws")
    async def websocket_endpoint(websocket: WebSocket) -> None:
        await websocket.accept()
        session = NotebookSession()
        try:
            while True:
                msg = await websocket.receive_json()
                responses = session.handle_message(msg)
                for resp in responses:
                    await websocket.send_json(resp)
        except WebSocketDisconnect:
            pass

    @app.get("/api/health")
    async def health() -> dict:
        return {"status": "ok"}

    frontend_dist = (
        Path(__file__).resolve().parent.parent.parent / "frontend" / "dist"
    )
    if frontend_dist.exists():
        app.mount("/", StaticFiles(directory=str(frontend_dist), html=True),
                  name="frontend")
    return app
```

它做四件事：创建 FastAPI 实例、注册 WebSocket 端点、注册健康检查、有条件挂载静态文件。注意它没有显式创建 `Session` 存入 `app.state`——教学版在 WebSocket 端点内为每个连接新建 `NotebookSession`，这是"每连接一会话"的简化模型，避免了多连接共享状态的并发问题，代价是同一用户的多个标签页有独立 notebook 状态。

## WebSocket 端点

`/ws` 是前后端通信的唯一通道。流程：`accept()` 接受连接，进入 `while True` 循环，`receive_json()` 阻塞等待前端消息，`session.handle_message(msg)` 同步处理返回响应列表，`send_json()` 逐条发回前端，`WebSocketDisconnect` 异常打断循环清理连接。

这里有个细节：`handle_message` 是同步函数，但 `websocket_endpoint` 是 `async` 函数。这意味着 `handle_message` 执行时会阻塞事件循环——如果某个 cell 执行耗时 5 秒，这 5 秒内无法处理其他连接的消息。教学版接受这个限制以保持代码简单，生产版 marimo 会把执行放到线程池用 `await run_in_executor(...)` 实现非阻塞。对于单用户教学，阻塞模型完全够用。

选择 WebSocket 而非 HTTP 长轮询，是因为 notebook 交互是双向、高频、需服务端主动推送的。cell 执行可能耗时数秒，期间用户可能继续操作其他 cell，WebSocket 的全双工特性让这些并发交互自然表达。

## NotebookSession 消息分发

WebSocket 端点收到消息后，真正干活的是 `NotebookSession.handle_message`。它是消息分发枢纽，用字典把消息类型映射到处理方法：

```python
def handle_message(self, msg: dict[str, Any]) -> list[dict[str, Any]]:
    msg_type = msg.get("type")
    handler = {
        "get_state": self._handle_get_state,
        "update_cell": self._handle_update_cell,
        "run_cell": self._handle_run_cell,
        "run_all": self._handle_run_all,
        "add_cell": self._handle_add_cell,
        "remove_cell": self._handle_remove_cell,
        "ui_event": self._handle_ui_event,
    }.get(msg_type)
    if handler is None:
        return [make_error_message(f"未知消息类型: {msg_type}")]
    try:
        return handler(msg)
    except Exception as e:
        return [make_error_message(f"{type(e).__name__}: {e}")]
```

构造函数里 `executor.inject("ui", ui_module)` 把 UI 组件模块注入执行器全局命名空间，cell 代码可直接写 `mo.ui.slider(...)` 而无需 import。`try/except` 包裹确保任何处理器的异常都变成 `error_message` 返回前端，而不是让 WebSocket 连接崩溃——这种"消息级容错"让单个 cell 的语法错误不会影响其他 cell 交互。

每种消息类型的语义如下：

| 消息类型 | 触发场景 | 处理逻辑 | 返回消息 |
|---------|---------|---------|---------|
| `get_state` | 前端首次连接 | 更新组件 ID，返回全状态 | `state` |
| `update_cell` | 用户编辑 cell 代码 | 重新 AST 分析，替换 cell | `graph_changed` |
| `run_cell` | 用户手动运行某 cell | 执行该 cell 及其依赖 | `cell_result` 列表 |
| `run_all` | 用户点击"全部运行" | 拓扑序执行所有 cell | `cell_result` 列表 |

| `ui_event` | 用户拖动 UI 组件 | 更新组件值，执行后代 cell | `cell_result` 列表 |

最体现 reactive 特性的是 `ui_event`：`component_id` 格式是 `"cell_id:var_name"`，定位到具体 cell 里的变量；`component.set_value(new_value)` 更新组件值后，`run_descendants(cell_id)` 只重新执行依赖这个 cell 的后代 cell，而非全量重跑。最后 `_collect_results()` 按拓扑序收集所有 cell 的最新结果返回前端。这就是用户拖动 slider 后图表立即更新的完整链路。

## 静态文件挂载

`app.mount("/", StaticFiles(...), name="frontend")` 把前端构建产物挂载到根路径。`html=True` 让 FastAPI 请求目录路径时自动寻找 `index.html`。挂载顺序很重要：WebSocket 端点在挂载之前注册，`/ws` 路径优先匹配，不会被静态文件处理器拦截。`if frontend_dist.exists()` 守卫让开发模式和生产模式共用同一份 `webapp.py`——开发时后端只跑 WebSocket，前端由 Vite dev server 提供；生产时挂载后整个应用只需一个端口。

## 健康检查与生产就绪

`/api/health` 端点返回 `{"status": "ok"}`，供 Kubernetes 或负载均衡器做存活探测。这个端点的存在本身就是生产部署的标志——它告诉运维系统"这个 HTTP 服务是可被编排的"。配合 `uvicorn --workers` 可启动多进程，但 WebSocket 的 session 状态在多进程间不共享，教学版建议单进程运行。生产部署推荐 `uv run uvicorn backend.server.webapp:app --host 0.0.0.0 --port 8000`，需要 TLS 时前置 Nginx 或 Caddy 做反向代理。

整个 FastAPI 架构的精妙在于它的"薄"——`webapp.py` 55 行，`session.py` 128 行，却完整实现了 reactive notebook 服务端。这种简洁源于职责清晰：`webapp.py` 管协议层，`session.py` 管消息分发，`CellGraph` 和 `Executor` 管执行模型，每层都可独立测试和替换。
