# FastAPI 服务架构

后端服务的入口在 `backend/server/webapp.py`，核心是 `create_app()` 函数，它构造一个 FastAPI 实例并注册所有必要的路由和中间件。这一章我们逐项拆解这个函数的内部结构。

## create_app 函数

`create_app()` 的大致骨架如下：

```python
def create_app():
    app = FastAPI()
    session = Session()
    app.state.session = session

    @app.websocket("/ws")
    async def websocket_endpoint(ws: WebSocket):
        await ws.accept()
        await handle_connection(ws, session)

    app.mount("/", StaticFiles(directory="frontend/dist", html=True))

    @app.get("/health")
    def health():
        return {"status": "ok"}

    return app
```

它做了四件事：创建 FastAPI 实例、创建 Session 并存入应用状态、注册 WebSocket 端点、挂载静态文件。还附加了一个健康检查端点。下面分别看每一部分。

## WebSocket 端点

`/ws` 是前后端通信的唯一通道。WebSocket 连接建立后，`handle_connection` 进入一个循环：从前端读取 JSON 消息，根据消息类型分发到不同处理器。消息类型包括 `run_cell`（执行 cell）、`ui_event`（组件交互）、`get_state`（请求当前状态）等。处理器的返回结果通过同一个 WebSocket 发送回前端，消息类型包括 `cell_output`（cell 执行结果）、`cell_error`（执行错误）、`state_update`（全状态同步）等。

选择 WebSocket 而非 HTTP 长轮询，是因为 notebook 的交互是双向、高频、需要服务端主动推送的。cell 执行可能耗时数秒，期间用户可能继续操作其他 cell，WebSocket 的全双工特性让这些并发交互自然表达。教学版的 `handle_connection` 是单连接单 session 的简化模型，生产版 marimo 支持多 session 复用同一连接，但那需要更复杂的路由逻辑。

## 静态文件挂载

`app.mount("/", StaticFiles(directory="frontend/dist", html=True))` 把前端构建产物挂载到根路径。`html=True` 参数让 FastAPI 在请求目录路径时自动寻找 `index.html`，这是单页应用的标准行为。挂载顺序很重要：WebSocket 端点在挂载之前注册，因此 `/ws` 路径优先匹配，不会被静态文件处理器拦截。

开发模式下这行挂载通常不存在，因为前端由 Vite dev server 独立提供，后端只负责 WebSocket。生产模式下前端已构建为静态文件，挂载后整个应用只需一个端口。这种"开发时双进程、生产时单进程"的模型既保留了开发时的热重载便利，又实现了生产时的部署简洁。

## 健康检查与生产就绪

`/health` 端点返回 `{"status": "ok"}`，供 Kubernetes 或负载均衡器做存活探测。教学版没有实现更复杂的就绪检查（如检查 session 是否初始化完成、依赖服务是否可达），但这个端点的存在本身就是生产部署的标志——它告诉运维系统"这个 HTTP 服务是可被编排的"。配合 `uvicorn` 的 `--workers` 参数可以启动多进程，但要注意 WebSocket 的 session 状态在多进程间不共享，教学版建议单进程运行。
