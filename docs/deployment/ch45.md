# CI/CD 自动部署

文档站的更新是全自动的：每当 `main` 分支有新的提交，GitHub Actions 会自动构建文档并部署到 GitHub Pages，无需任何手动操作。这一章我们看这个 workflow 的完整定义，理解每一步在做什么，以及为什么这样配置。

CI/CD 对教学项目的价值常常被低估——教学项目不像业务项目那样需要自动化测试保障回归，但文档的及时更新同样关键。想象一下：你改了某章的 markdown，push 到仓库，然后要手动跑 `vitepress build`、手动把 dist 上传到服务器、手动刷新 CDN 缓存——这种手动流程做几次就会让人懒得更新文档，文档和代码开始漂移。自动化部署把这个摩擦消除掉，push 即上线，文档与代码始终同步。

## workflow 文件

GitHub Actions 的 workflow 定义在 `.github/workflows/deploy-docs.yml`。教学版的完整实现如下：

```yaml
name: Deploy Docs to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: docs/package.json

      - name: Install dependencies
        run: npm install
        working-directory: docs

      - name: Build VitePress
        run: npm run build
        working-directory: docs

      - name: Setup Pages
        uses: actions/configure-pages@v4

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: docs/.vitepress/dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

这个 workflow 分成 `build` 和 `deploy` 两个 job，`deploy` 用 `needs: build` 声明依赖——只有 build 成功才会触发 deploy。这种两段式结构是 GitHub Pages 部署的最佳实践：GitHub 要求部署必须在一个绑定了 `environment: github-pages` 的 job 里执行，而构建步骤不需要这个绑定，分开后职责更清晰，也方便日后在 build job 里加测试步骤。

## 触发条件与权限

`on.push.branches: [main]` 表示只在 push 到 `main` 分支时触发。教学版没有加 `paths` 过滤——任何 push 到 main 都会重新构建文档，哪怕只改了后端 Python 代码。这种"全量触发"代价是偶尔做无用功，但配置简单且不会漏更新。如果文档量大、构建慢，可以加 `paths: ['docs/**', '.vitepress/**']` 过滤。

`workflow_dispatch` 允许在 GitHub Actions 页面手动触发 workflow，方便调试或强制重新部署。点击仓库的 Actions 标签页 → 选 workflow → 点 "Run workflow" 即可。触发后 workflow 在 GitHub 托管的 Ubuntu runner 上执行，无需自建 CI 服务器。GitHub 对公开仓库免费提供 2000 分钟/月的 Actions 额度，这个 workflow 每次跑约 1-2 分钟，完全在免费额度内。

`permissions` 字段授予 workflow 最小必要权限：`contents: read` 让 checkout 能拉取代码，`pages: write` 让 deploy 能写入 Pages，`id-token: write` 让 workflow 能签发 OIDC token 用于认证。这是新版 Pages 部署机制的要求——不再需要配置 SSH key 或 personal access token，OIDC 认证自动完成，token 是短期签发的，比长期 PAT 安全得多。

`concurrency` 控制同一组的 workflow 并发行为。`group: pages` 把所有部署归到一组，`cancel-in-progress: false` 表示不取消正在进行的部署——快速连续 push 两次，两次部署会排队依次执行，而不是后一次取消前一次。这适合文档部署：每次部署都是完整构建，取消进行中的部署可能让 Pages 处于半更新状态。

## 构建步骤详解

`build` job 的步骤依次执行：`checkout@v4` 拉取仓库代码到 runner；`setup-node@v4` 安装 Node.js 20，`cache: npm` 启用 npm 依赖缓存——首次 run 会把 `~/.npm` 缓存起来，后续 run 命中缓存可省去重新下载依赖的时间，`cache-dependency-path: docs/package.json` 用这个文件的 hash 作为缓存 key，能把 `npm install` 从 30 秒降到 5 秒左右。

```yaml
- name: Install dependencies
  run: npm install
  working-directory: docs
```

`working-directory: docs` 让这一步在 `docs/` 子目录执行，因为 `package.json` 在那里。教学版用 `npm install` 而非 `npm ci`——`npm ci` 更严格（要求 lock 文件与 package.json 完全一致），适合生产 CI；`npm install` 更宽容，适合教学项目避免 lock 文件漂移的麻烦。接着 `npm run build` 执行 `vitepress build docs`，产物落到 `docs/.vitepress/dist/`。

`configure-pages@v4` 配置 Pages 部署的元数据（如 base path）。`upload-pages-artifact@v3` 把 dist 目录打包成一个名为 `github-pages` 的 artifact，这是 GitHub Pages 部署的输入格式。artifact 会暂存在 GitHub 的 artifact 存储里，供下一个 job 下载部署。

## 部署到 Pages

`deploy` job 只有一步：`deploy-pages@v4` 拿到 build job 上传的 artifact，通过 GitHub Pages API 发布，几秒后站点就更新了。`environment: github-pages` 是关键——这个 environment 绑定让 GitHub 知道这个 job 是部署到 Pages，会自动注入部署所需的 token 和上下文。`url: ${{ steps.deployment.outputs.page_url }}` 让 Actions 页面显示部署后的站点 URL，点进去就能看到文档。

注意 `deploy` job 不需要 `checkout`——它不碰源码，只处理 artifact。这种"构建产物与部署解耦"的设计让部署 job 极简，也方便日后把构建产物换成别的来源。

## 整个流程的时效

从 push 到文档上线，整个流程通常耗时 1-2 分钟，时间分布大致如下：

| 步骤 | 耗时 | 说明 |
|------|------|------|
| checkout | 2-3 秒 | 拉取仓库代码 |
| setup-node | 3-5 秒 | 安装 Node.js（命中缓存更快） |
| npm install | 5-30 秒 | 安装依赖（命中缓存 5 秒，首次 30 秒） |
| vitepress build | 15-25 秒 | 编译 46 章 markdown |
| upload-artifact | 3-5 秒 | 打包上传 dist |
| deploy-pages | 5-10 秒 | 发布到 Pages |

作者推送代码后，在仓库的 Actions 标签页可以看到实时进度，绿色对勾出现后刷新文档站即可看到新内容。如果某步失败，Actions 页面会显示红色叉号，点进去能看到完整日志——最常见的问题是 markdown 语法错误导致 vitepress build 失败，日志会指出具体哪个文件哪一行出错。

这种全自动部署让文档与代码始终同步——不存在"代码改了但文档忘了更新"的漂移问题，因为文档本身就是仓库内容的一部分，和代码一起被提交、一起被构建。教学项目选择 GitHub Pages 而非 Vercel 或 Netlify，是因为它零配置、零成本、且与代码仓库同构，最符合教学项目的极简定位。Vercel 当然更强大（预览部署、边缘缓存），但对一个文档站来说那些能力都是过度设计，GitHub Pages 的"push 即上线"已经足够。
