# CI/CD 自动部署

文档站的更新是全自动的：每当 `main` 分支有新的提交，GitHub Actions 会自动构建文档并部署到 GitHub Pages，无需任何手动操作。这一章我们看这个 workflow 的完整定义。

## workflow 文件

GitHub Actions 的 workflow 定义在 `.github/workflows/docs.yml`。一个典型的文档部署 workflow 如下：

```yaml
name: Deploy Docs
on:
  push:
    branches: [main]
    paths: ["docs/**", ".vitepress/**"]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build-deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deploy.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: docs/.vitepress/dist
      - id: deploy
        uses: actions/deploy-pages@v4
```

## 触发条件

`on.push` 配置只在 `main` 分支且 `docs/` 或 `.vitepress/` 目录有变更时触发。这个 `paths` 过滤很重要——如果只改了后端 Python 代码，没必要重新构建文档。触发后 workflow 在 GitHub 托管的 Ubuntu runner 上执行，无需自建 CI 服务器。

## 构建步骤

构建步骤依次执行：`checkout` 拉取代码，`setup-node` 安装 Node.js 20，`npm ci` 根据 `package-lock.json` 安装依赖（`ci` 比 `install` 更严格，保证可复现构建），`npm run build` 执行 VitePress 构建。构建产物在 `docs/.vitepress/dist/`，是一个纯静态文件目录。

## 部署到 Pages

部署用两个官方 action 完成。`upload-pages-artifact` 把 dist 目录打包成一个名为 `github-pages` 的 artifact，这是 GitHub Pages 部署的输入格式。`deploy-pages` 把这个 artifact 发布到 GitHub Pages，输出一个 `page_url` 供 environment URL 使用。`permissions` 字段授予 workflow 写入 Pages 和签发 id token 的权限，这是新版 Pages 部署机制的要求——不再需要配置 SSH key 或 personal access token，OIDC 认证自动完成。

## 整个流程的时效

从 push 到文档上线，整个流程通常耗时 1-2 分钟，其中 `npm ci` 约 30 秒，`vitepress build` 约 20 秒，部署约 10 秒。作者推送代码后，在仓库的 Actions 标签页可以看到实时进度，绿色对勾出现后刷新文档站即可看到新内容。这种全自动部署让文档与代码始终同步——不存在"代码改了但文档忘了更新"的漂移问题，因为文档本身就是仓库内容的一部分，和代码一起被提交、一起被构建。教学项目选择 GitHub Pages 而非 Vercel 或 Netlify，是因为它零配置、零成本、且与代码仓库同构，最符合教学项目的极简定位。
