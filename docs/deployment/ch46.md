# 源码导读与对比

最后一章我们把视角拉高：看真实 marimo 的源码结构，把它与 Streamlit、Dash、Jupyter 对比，并诚实地列出教学版为保持简洁而未实现的挑战。这一章既是全书的总结，也是读者后续深入真实 marimo 源码的导航图。

## 教学版源码结构

先看教学版本身的完整目录结构，这是读者最熟悉的代码：

```
marimo-from-scratch/
├── backend/
│   ├── app.py                    # App 类，notebook 即 app
│   ├── core/
│   │   ├── cell.py               # Cell 数据结构
│   │   ├── ast_analyzer.py       # AST 分析，提取 defs/refs
│   │   ├── graph.py              # CellGraph，DAG 构建与查询
│   │   └── executor.py           # Executor，增量执行
│   ├── storage/
│   │   ├── parser.py             # .py 文件解析为 cell 列表
│   │   └── serializer.py         # cell 列表序列化为 .py
│   ├── server/
│   │   ├── webapp.py             # FastAPI 应用，WebSocket + 静态文件
│   │   ├── session.py            # NotebookSession，消息分发
│   │   └── protocol.py           # 消息构造函数
│   └── components/
│       └── ui.py                 # UI 组件（Slider/Button/Checkbox）
├── frontend/                     # React 19 + CodeMirror 6
├── docs/                         # VitePress 文档站
├── tests/                        # pytest 测试
└── .github/workflows/deploy-docs.yml
```

这个结构遵循"按职责分层"的原则：`core/` 是纯算法层（不依赖 HTTP），`server/` 是协议层（依赖 core），`storage/` 是持久化层（依赖 core），`components/` 是 UI 组件层（依赖 core）。`app.py` 是顶层编排，把 core 和 components 串起来让 notebook 可直接运行。这种分层让每一层都可以独立测试——`core/` 的测试不需要启动 HTTP 服务，`storage/` 的测试不需要 WebSocket。

## marimo 源码结构

真实 marimo 的源码大致分为以下几块。`marimo/` 核心包包含 `_ast/`（AST 分析，提取 cell 间的依赖关系）、`_runtime/`（执行器、session、数据流）、`_server/`（FastAPI 服务、WebSocket、API 模型）、`_output/`（富文本输出格式化）、`_plugins/`（UI 组件系统，称为 plugin）。前端 `frontend/` 是一个 Islands 架构的 React 应用，包含 `editor/`、`components/`、`core/` 等模块。

真实 marimo 的核心目录大致如下：

```
marimo/
├── _ast/
│   ├── codegen.py          # 代码生成与重写
│   ├── compiler.py         # cell 编译
│   └── visitor.py          # AST 访问者，提取依赖
├── _runtime/
│   ├── runtime.py          # 执行运行时
│   ├── dataflow.py         # 数据流分析
│   └── cache.py            # 内容寻址缓存
├── _server/
│   ├── api/                # REST API
│   ├── sessions.py         # 多 session 管理
│   └── models/             # Pydantic 模型
├── _output/                # 富文本输出（md/mpl/...）
└── _plugins/               # UI 组件系统
```

与教学版相比，真实版最显著的扩展在 AST 分析——它能静态分析 cell 代码的引用关系，无需执行即可构建依赖图，这使得 cell 重跑的依赖追踪精确到变量级别，而非教学版的 cell 级别。教学版的 `ast_analyzer.py` 对应真实版的 `_ast/visitor.py`，`executor.py` 对应 `_runtime/runtime.py`（但真实版有缓存、虚拟文件等扩展），`webapp.py` 对应 `_server/`（但真实版支持多 session、REST API 与 WebSocket 并存）。

## 与 Jupyter 对比

Jupyter 的执行模型是"cell 按顺序手动执行"：用户按 Shift+Enter 执行 cell，多个 cell 之间共享一个全局命名空间，但 Jupyter 不追踪 cell 间的依赖关系——如果你改了上面的 cell，下面的 cell 不会自动重跑，常常导致"隐式状态"bug：notebook 看起来是对的（因为之前执行过），但从头重跑就会挂。

marimo 的执行模型是"reactive 自动传播"：改了 cell A，所有依赖 A 的 cell 自动重跑，状态始终一致。代价是 marimo 需要静态分析 cell 代码提取依赖，这限制了 cell 的写法（不能用 `exec` 或 `globals()` 动态访问变量，否则依赖分析失效）。这是经典的"约束换保证"权衡——marimo 用语法约束换取了状态一致性保证。

文件格式上，Jupyter 用 `.ipynb`（JSON 包含代码、输出、元数据），marimo 用 `.py`（纯 Python 代码）。`.ipynb` 的优点是自带输出，缺点是 JSON 难以 diff、merge、code review。`.py` 的优点是 Git 友好、IDE 友好，缺点是打开时没有输出。marimo 认为前者更重要，因为代码协作场景远多于"离线查看 notebook"场景。

## 与 Streamlit 对比

Streamlit 的模型是"自顶向下脚本重跑"：每次用户交互，整个脚本从头到尾重新执行一遍，通过 `@st.cache` 装饰器缓存昂贵计算。优点是心智模型简单，缺点是脚本变长后重跑开销巨大，且缓存装饰器要手动加、容易漏。

```python
# Streamlit：每次拖动 slider 重跑整个脚本
x = st.slider("x", 1, 100)
@st.cache
def expensive(x): return ...
result = expensive(x)
```

```python
# marimo：只在 x 变化时重跑依赖 cell
@app.cell
def _(mo):
    x = mo.ui.slider(1, 100)       # 组件是持久化对象
    return (x,)
@app.cell
def _(x):
    result = expensive(x.value)    # 只在 x 变化时重跑
    return (result,)
```

marimo 的模型是"细粒度 reactive"：只有依赖变化的 cell 重跑，无需手动加缓存装饰器。Streamlit 的 UI 组件是函数调用（`st.slider()` 返回值），marimo 的组件是持久化对象，这使得 marimo 的组件状态在 cell 重跑间自然保持，而 Streamlit 每次重跑都重建组件。

## 与 Dash 对比

Dash 的模型是"显式回调注册"：用户定义 `@app.callback` 把输入组件的值映射到输出组件的属性。这给了最大的灵活性，但代价是每个交互都要手写回调函数，代码量大且容易遗漏边界情况。marimo 的 reactive binding 是隐式的——cell 代码直接引用组件变量，依赖关系自动推导，无需注册回调。Dash 的优势在于它天然支持多页面应用和复杂的布局嵌套，marimo 教学版只支持单页面纵向布局。

三者可以放在一个谱系上理解：**Jupyter 是手动执行无依赖追踪，Streamlit 是全量重跑加手动缓存，Dash 是显式回调，marimo 是隐式 reactive**。从 Jupyter 到 marimo，自动化程度递增，对用户的心智负担递减，但对实现者的复杂度递增。marimo 选择把复杂度交给实现者（一次性成本），换取用户的长期便利。

## 教学版未实现的挑战

为保持代码可读，教学版省略了真实 marimo 的多个重要特性。诚实地列出这些省略，既是给读者设定期望，也是给想深入真实源码的读者指明方向。

**缓存**：真实版有基于内容寻址的缓存系统，避免重复计算相同输入的 cell；教学版每次都全量重跑。**多文件 notebook**：真实版支持 import 其他 notebook 作为模块；教学版只支持单文件。**SQL cell**：真实版有专门的 SQL cell 类型，连接数据库执行查询；教学版只有 Python cell。**富文本输出**：真实版支持 matplotlib 图表、pandas DataFrame 表格、自定义 MIME 类型输出；教学版只支持文本和 UI 组件。**文件持久化**：真实版 notebook 可保存为 `.py` 文件并恢复；教学版 session 结束即丢失。**多用户并发**：真实版支持多 session 隔离；教学版单 session 单连接。**前端编辑器**：真实版有完整的 CodeMirror 6 编辑器集成，支持语法高亮、自动补全；教学版前端是简化版。

这些省略每一项都对应真实源码中数千行代码，但它们的核心思路都建立在本教学版已实现的骨架之上——理解了这 46 章的内容，就具备了阅读真实 marimo 源码的地图。建议读者按以下路径深入：先读真实版的 `_ast/visitor.py`（对比教学版的 `ast_analyzer.py`，看变量级依赖分析的细节），再读 `_runtime/runtime.py`（对比 `executor.py`，看缓存如何融入执行），最后读 `_server/sessions.py`（对比 `session.py`，看多 session 管理的架构）。每一步都能对应到教学版的简化版本，差异处就是真实版为生产场景做的扩展，理解这些扩展的动机，就理解了从教学原型到生产系统的工程跃迁。
