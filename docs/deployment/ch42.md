# 从 notebook 到 web app

marimo 最迷人的特性之一是：**同一份 `.py` 文件既是交互式 notebook，又是一个可部署的 web 应用**。这不是通过打包转换实现的，而是因为 notebook 的运行时本身就是 FastAPI 服务。开发时你在浏览器里编辑 cell，部署时用户在同一个浏览器界面里使用那些 cell 的结果——只是没有了编辑入口。这一章我们看这种"双面应用"是如何做到的。

这种设计哲学可以浓缩成一句话：**notebook 的运行时就是应用的运行时**。传统 notebook 工具把"探索"和"交付"割裂成两种产物——`.ipynb` 用于探索，Dash 应用用于交付，转换过程常常丢失交互能力和组件状态。marimo 把这两个阶段统一成同一个运行时：开发时多一组编辑器 UI，生产时少一组编辑器 UI，仅此而已。

## 同一份代码的两种角色

一个 marimo notebook 文件 `app.py` 的顶层结构是一系列 cell 定义。在开发模式下，你运行 `marimo edit app.py`，服务启动后浏览器打开编辑器，你可以增删改 cell、拖动 slider、查看实时输出。在生产模式下，你运行 `python app.py`，服务同样启动，但前端不再渲染编辑器工具栏，cell 代码不可修改，用户只能与 UI 组件交互。两种模式的区别仅在于前端是否加载编辑器模块，后端代码完全相同。

这种设计消除了"开发原型"和"生产应用"之间的部署鸿沟。传统 notebook 工具如 Jupyter 需要把 `.ipynb` 转成脚本或 Dash 应用才能部署，转换过程常常丢失交互能力。marimo 的 cell 定义本身就是合法的 Python 代码，部署时无需任何转换。

我们可以把这种"双面"关系画成流程图：

```
        ┌───────────────────────────────────┐
        │      同一份 notebook.py 文件       │
        │  ┌───────┐ ┌───────┐ ┌──────┐    │
        │  │cell_0 │ │cell_1 │ │cell_2│    │
        │  └───────┘ └───────┘ └──────┘    │
        └──────────────┬────────────────────┘
                       │
          ┌────────────┴────────────┐
          │                         │
   marimo edit notebook.py    python notebook.py
   （开发模式）                （生产模式）
          │                         │
          ▼                         ▼
  ┌───────────────┐         ┌───────────────┐
  │ 前端加载编辑器  │         │ 前端不加载编辑器│
  │ 可增删改 cell   │         │ cell 只读      │
  │ 可拖动 UI 组件  │         │ 可拖动 UI 组件  │
  └───────────────┘         └───────────────┘
          │                         │
          └────────────┬────────────┘
                       ▼
              同一个 FastAPI 后端 + WebSocket
```

关键洞察是：**后端从不区分开发与生产**。`create_app()` 构造的 FastAPI 实例对两种模式一视同仁，WebSocket 消息协议完全一致。区分只发生在前端 bundle 里——开发 bundle 包含编辑器，生产 bundle 把这些剔除。开发时验证过的 cell 执行逻辑、依赖传播、UI 交互，部署后一字不改地复用，不存在"开发能跑生产跑挂"的迁移风险。

## App 类：直接运行 notebook

教学版提供了一个 `App` 类，让 notebook 文件可以直接 `python notebook.py` 运行：

```python
app = App()

@app.cell
def _(mo):
    slider = mo.ui.slider(1, 100, value=20)
    return (slider,)

@app.cell
def _(slider):
    import matplotlib.pyplot as plt
    plt.plot([i for i in range(slider.value)])
    return

if __name__ == "__main__":
    app.run()
```

`@app.cell` 装饰器收集所有 cell 函数，每个函数的参数声明表达了它引用了哪些变量，`return` 表达式表达了它定义了哪些变量。`app.run()` 内部调用 `_build_graph()` 构造依赖图，再用 `Executor` 执行，最后 `_print_results()` 把每个 cell 的状态、stdout、output 打印到终端。

`App` 类的核心实现：

```python
class App:
    def __init__(self) -> None:
        self._funcs: list = []

    def cell(self, func):
        self._funcs.append(func)
        return func

    def run(self) -> None:
        graph = self._build_graph()
        executor = Executor(graph)
        from .components import ui as ui_module
        executor.inject("ui", ui_module)
        executor.run_all()
        self._print_results(graph)
```

`cell` 装饰器把函数追加到 `_funcs` 列表。`run()` 的流程：构建图 → 注入 `ui` 模块 → 全量执行 → 打印结果。`_build_graph()` 对每个被装饰的函数：用 `inspect.getsource` 拿到源码，`ast.parse` 解析成 AST；从函数参数提取 `refs`，从 `return` 语句提取 `defs`，从函数体提取 `code`。这种"函数签名编码依赖"的设计让 notebook 文件本身就是合法的 Python，可以直接被 IDE 的语法检查、formatter 处理——这是 marimo 拒绝 `.ipynb` JSON 格式的根本理由。

`if __name__ == "__main__"` 的写法是 Python 的标准入口模式，文件既可以被 `import` 当作模块使用（拿到 `app` 对象），也可以直接执行启动服务。这种双用途在测试场景特别有用——测试代码可以 `import app` 检查 cell 图的拓扑结构，而不需要启动 HTTP 服务。

## 部署模式

生产部署的关键步骤是前端构建。开发时前端由 Vite dev server 在 `:5173` 提供服务，WebSocket 通过 proxy 转发到 `:8000` 的后端。生产时运行 `vite build`，把前端打包成静态文件到 `frontend/dist/`。后端的 `create_app()` 通过 FastAPI 的 `StaticFiles` 挂载这个目录：

```python
frontend_dist = (
    Path(__file__).resolve().parent.parent.parent / "frontend" / "dist"
)
if frontend_dist.exists():
    app.mount("/", StaticFiles(directory=str(frontend_dist), html=True),
              name="frontend")
```

`if frontend_dist.exists()` 这个守卫让同一份 `webapp.py` 既能用于开发（dist 目录不存在，只跑 WebSocket），也能用于生产（dist 目录存在，挂载静态文件）。开发者不需要切换配置文件或设置环境变量，构建产物存在与否自然决定了运行模式。

开发模式的 Vite proxy 配置很简洁：

```typescript
server: {
  port: 5173,
  proxy: {
    '/ws': { target: 'ws://localhost:8000', ws: true },
  },
}
```

浏览器访问 `http://localhost:5173/`，前端资源由 Vite 提供；前端 JS 建立 WebSocket 连接到 `/ws`，Vite 代理到 `ws://localhost:8000`，后端处理消息。这种双进程模型保留了开发时的热重载便利——改前端 Vite 即时刷新，改后端 uvicorn `--reload` 即时重启，互不干扰。

生产模式下浏览器访问 `http://server:8000/` 时，FastAPI 直接返回 `dist/index.html`，前端 JS bundle 加载后建立 WebSocket 连接到 `/ws` 端点，整个应用就跑起来了。部署只需要一个 Python 进程和一个静态文件目录，无需 Node.js 运行时，无需 Nginx 反向代理（大型部署仍建议加 Nginx 做负载均衡和 TLS 终止）。

完整的部署流程：① 前端构建 `npm run build`，产物落到 `frontend/dist/`；② 后端启动 `uvicorn backend.server.webapp:app`；③ 用户访问浏览器，JS bundle 加载，WebSocket 连接到 `/ws`；④ 用户拖动 slider，前端发 `ui_event`，后端执行依赖 cell，返回 `cell_output`，前端更新视图。

整个过程没有"转换 notebook 为应用"的步骤——notebook 本来就是应用。对比传统方案：Jupyter notebook 部署成 Dash 应用需要重写交互逻辑，Streamlit 部署需要专门的 server 进程，而 marimo 部署只需要一个普通的 Python HTTP server。这种简洁靠的是架构的一致性——notebook 的运行时本来就是 HTTP server，部署只是把这个事实暴露给最终用户。
