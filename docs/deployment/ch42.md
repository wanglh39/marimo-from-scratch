# 从 notebook 到 web app

marimo 最迷人的特性之一是：**同一份 `.py` 文件既是交互式 notebook，又是一个可部署的 web 应用**。这不是通过打包转换实现的，而是因为 notebook 的运行时本身就是 FastAPI 服务。开发时你在浏览器里编辑 cell，部署时用户在同一个浏览器界面里使用那些 cell 的结果——只是没有了编辑入口。这一章我们看这种"双面应用"是如何做到的。

## 同一份代码的两种角色

一个 marimo notebook 文件 `app.py` 的顶层结构是一系列 cell 定义。在开发模式下，你运行 `marimo edit app.py`，服务启动后浏览器打开编辑器，你可以增删改 cell、拖动 slider、查看实时输出。在生产模式下，你运行 `python app.py`（或 `marimo run app.py`），服务同样启动，但前端不再渲染编辑器工具栏，cell 代码不可修改，用户只能与 UI 组件交互。两种模式的区别仅在于前端是否加载编辑器模块，后端代码完全相同。

这种设计消除了"开发原型"和"生产应用"之间的部署鸿沟。传统 notebook 工具如 Jupyter 需要把 `.ipynb` 转成 `.py` 脚本或 Dash 应用才能部署，转换过程常常丢失交互能力。marimo 的 cell 定义本身就是合法的 Python 代码，部署时无需任何转换。

## App 类：直接运行 notebook

教学版提供了一个 `App` 类，让 notebook 文件可以直接 `python notebook.py` 运行。文件末尾通常有：

```python
app = App()
app.add_cell(cell_1)
app.add_cell(cell_2)
# ...

if __name__ == "__main__":
    app.run()
```

`app.run()` 内部调用 `create_app()` 构造 FastAPI 实例，注册 WebSocket 端点，挂载前端静态文件，然后用 `uvicorn.run()` 启动服务。这种 `if __name__ == "__main__"` 的写法是 Python 的标准入口模式，意味着这个文件既可以被 `import` 当作模块使用（拿到 `app` 对象），也可以直接执行启动服务。

## 部署模式

生产部署的关键步骤是前端构建。开发时前端由 Vite dev server 在 `:5173` 提供服务，WebSocket 通过 proxy 转发到 `:8000` 的后端。生产时运行 `vite build`，把前端打包成静态文件到 `frontend/dist/` 目录。后端的 `create_app()` 通过 FastAPI 的 `StaticFiles` 挂载这个目录：

```python
app.mount("/", StaticFiles(directory="frontend/dist", html=True))
```

这样浏览器访问 `http://server:8000/` 时，FastAPI 直接返回 `dist/index.html`，前端 JS bundle 加载后建立 WebSocket 连接到 `/ws` 端点，整个应用就跑起来了。部署只需要一个 Python 进程和一个静态文件目录，无需 Node.js 运行时，无需 Nginx 反向代理（当然大型部署仍建议加 Nginx 做负载均衡）。这种极简部署模型是 marimo 对"notebook 即应用"理念的最直接兑现。
