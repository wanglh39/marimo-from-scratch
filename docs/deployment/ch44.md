# GitHub Pages 文档站

这套教学项目的文档本身也是一个可部署的网站，由 VitePress 构建，托管在 GitHub Pages 上。这一章我们看文档站的配置结构、46 章是如何组织的，以及从 markdown 到上线静态站点的完整构建链路。

文档站的存在有一个经常被低估的价值：**教学项目的可读性不亚于代码本身**。一个 46 章的教学项目如果只有源码没有文档，读者要靠 grep 和断点去理解设计意图，学习曲线会陡峭得多。VitePress 把 markdown 编译成带侧边栏、搜索、导航的静态站点，让读者能在浏览器里流畅地按章节阅读。而 GitHub Pages 提供零成本的托管——不需要买服务器、不需要配 CDN、不需要管 TLS 证书，push 一下文档就上线了。

## VitePress 配置

VitePress 是 Vue 官方的静态站点生成器，专为技术文档优化。项目根目录的 `docs/` 目录就是 VitePress 的源目录，配置文件在 `docs/.vitepress/config.ts`。教学版的核心配置如下：

```typescript
import { defineConfig } from 'vitepress'

export default defineConfig({
  title: 'marimo-from-scratch',
  description: '从零实现 marimo：理解 reactive notebook 的底层原理与设计哲学',
  lang: 'zh-CN',
  themeConfig: {
    nav: [
      { text: '首页', link: '/' },
      { text: 'GitHub', link: 'https://github.com/wanglh39/marimo-from-scratch' },
    ],
    sidebar: [ /* 九篇 46 章，见下文 */ ],
    socialLinks: [
      { icon: 'github', link: 'https://github.com/wanglh39/marimo-from-scratch' },
    ],
  },
})
```

逐项看每个配置的作用：`title` 是站点标题，显示在浏览器标签页和页面左上角；`description` 是 SEO meta 描述，搜索引擎抓取时会用到；`lang: 'zh-CN'` 声明文档语言，让浏览器和屏幕阅读器正确处理中文排版和语音；`themeConfig.nav` 是顶部导航栏；`themeConfig.sidebar` 是左侧侧边栏；`themeConfig.socialLinks` 是右上角的社交链接图标。

注意这里**没有 `base` 配置**。VitePress 的 `base` 选项用于站点部署在子路径时给所有资源 URL 加前缀，比如部署在 `https://user.github.io/marimo-from-scratch/` 时需要 `base: '/marimo-from-scratch/'`。如果你的项目要部署到项目站点（而非 user 站点），需要加上 `base: '/marimo-from-scratch/'`，VitePress 会自动给所有内部链接、静态资源路径加上这个前缀，无需手动改 markdown 里的链接。

## 侧边栏结构

侧边栏按"篇"组织，共九篇 46 章。配置是一个嵌套数组，每篇有 `text`（篇名）、`collapsed`（是否默认折叠）、`items`（章节列表）：

```typescript
sidebar: [
  {
    text: '第一篇：背景与动机',
    collapsed: false,
    items: [
      { text: 'ch01 - 什么是 marimo', link: '/overview/ch01' },
      { text: 'ch02 - Jupyter 的痛点', link: '/overview/ch02' },
      // ... ch03-05
    ],
  },
  // ... 第二篇到第八篇
  {
    text: '第九篇：部署与延伸',
    collapsed: false,
    items: [
      { text: 'ch42 - 从 notebook 到 web app', link: '/deployment/ch42' },
      { text: 'ch43 - FastAPI 服务架构', link: '/deployment/ch43' },
      { text: 'ch44 - GitHub Pages 文档站', link: '/deployment/ch44' },
      { text: 'ch45 - CI/CD 自动部署', link: '/deployment/ch45' },
      { text: 'ch46 - 源码导读与对比', link: '/deployment/ch46' },
    ],
  },
]
```

`link` 字段的路径对应 `docs/` 下的 markdown 文件——`/overview/ch01` 对应 `docs/overview/ch01.md`。这种"目录即篇、文件即章"的结构让作者维护时只需在对应目录增删 `.md` 文件并更新侧边栏数组，VitePress 自动处理路由和构建。`collapsed: false` 让所有篇默认展开，方便读者通览全貌。

九篇的划分对应着从设计到实现的递进逻辑：

| 篇 | 章节 | 子目录 | 主题 |
|----|------|--------|------|
| 第一篇 | ch01-05 | `overview/` | 背景与动机 |
| 第二篇 | ch06-11 | `cell-ast/` | Cell 与 AST 分析 |
| 第三篇 | ch12-16 | `dag/` | DAG 构建 |
| 第四篇 | ch17-22 | `execution/` | 执行引擎 |
| 第五篇 | ch23-27 | `file-format/` | 文件格式 |
| 第六篇 | ch28-31 | `protocol/` | 通信协议 |
| 第七篇 | ch32-37 | `frontend/` | 前端实现 |
| 第八篇 | ch38-41 | `ui-components/` | UI 组件系统 |
| 第九篇 | ch42-46 | `deployment/` | 部署与延伸 |

## 46 章的组织逻辑

46 章按照从宏观到微观、从设计到实现的顺序排列。第一篇概览介绍项目目标和范围；第二篇搭建 cell 数据结构和 AST 分析的基础设施，这是 reactive 的前提——没有依赖分析就没有增量执行；第三到五篇实现核心的 cell 模型、DAG、执行引擎和文件格式；第六到七篇实现通信协议和前端编辑器；第八篇（第 38-41 章）实现 UI 组件系统；第九篇（第 42-46 章）覆盖部署与延伸。

读者可以按顺序通读，建立从零到一的完整心智模型；也可以根据兴趣跳转到特定篇——比如只想理解 AST 分析的读者可以直接看第二篇，只想理解 reactive 执行的可以看第四篇。每章控制在 500-800 字（原始设计目标，部分章节如本篇已扩充以深入讲解），保证单次阅读 3-5 分钟即可完成，适合碎片化学习。这种"小章 + 篇分组"的组织方式借鉴了 SICP 的风格——每个概念独立成章，但章与章之间有严格的依赖序，串起来就是一个完整的体系。

## 构建命令与产物

文档站的构建命令是 `cd docs && npm install && npm run build`。`npm run build` 实际执行 `vitepress build docs`，把 `docs/` 下所有 markdown 编译成静态 HTML，输出到 `docs/.vitepress/dist/`。构建过程做了几件事：解析所有 markdown 文件，提取 frontmatter 和标题；把 Vue 组件渲染成 HTML；生成侧边栏和导航的 JSON 数据；预渲染每个页面的 Vue 布局，输出带样式的静态 HTML。

本地预览用 `npm run docs:dev`，启动 VitePress dev server，支持热重载，写作时修改 markdown 即时看到效果。修改 `config.ts` 的侧边栏配置也会热重载，方便调试导航结构。

构建产出的 HTML 已经预渲染了 Vue 组件，因此首屏加载无需客户端 JS 即可阅读，这对文档站的 SEO 和可访问性都很重要——搜索引擎爬虫拿到的是完整 HTML 而非空 `<div id="app">`，屏幕阅读器也能立即读出内容。客户端 JS 加载后会给页面"激活"（hydration），加上交互能力（如侧边栏折叠、搜索框），但内容本身不依赖 JS。这种"渐进增强"是 VitePress 相比纯 SPA 文档方案的优势。

构建完成后 `docs/.vitepress/dist/` 的结构大致如下：每个 markdown 文件对应一个 `.html` 文件（如 `docs/overview/ch01.md` → `dist/overview/ch01.html`），`assets/` 目录是打包后的 JS/CSS（文件名带内容 hash，方便长期缓存）。把这个 `dist/` 目录整体上传到 GitHub Pages，文档站就上线了。下一章我们会看 CI/CD 如何把这个过程完全自动化。
